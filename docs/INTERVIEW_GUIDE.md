# CharaMate 面试介绍与深挖问答

整理日期：2026-10-05。代码基线：`31d8328`。本文依据当前目录、核心实现、测试和 Decision 记录整理；历史验收以 2026-09-18 的 STATUS 为准，不代表本次重新运行了实验。

建议先练熟开场、两条核心链路和三个问题案例，再按岗位选择问答。个人分工请按真实贡献表述；下面的项目能力不能自动等同于个人独立完成的工作。

## 1. 可以直接口述的开场

> CharaMate 是一个常驻桌面的 AI 陪伴应用，也能通过 Agent 操作文件、浏览器和应用。技术上采用 Electron、React、严格 TypeScript 和 SQLite，文本、语音、自动化与角色自主行为共享 Run/Item、工具、审批和持久化合同。
>
> 项目重点是长期连续性：一方面，把对话和真实执行结果形成有主体、时间、来源和修订历史的记忆，再通过语义、词法和实体时间检索，选择能回答当前问题的证据；另一方面，用持续认知状态管理当前情境、未完成意图和信息缺口，决定继续、澄清、行动还是保持安静。
>
> 难点主要是用户改口后的历史一致性、高频事件下的信息筛选，以及异步模型结果过期后的执行控制。实现上使用版本校验、持久工作队列、精确来源引用和 Worker 隔离。验证则分开检查工程正确性、真实模型语义和容量性能，避免只凭检索命中或测试通过，就宣称记忆有效。

面试最值得突出的是：**有证据的长期记忆、持续情境与注意控制、异步执行一致性、分层评测与成本取舍。** UI、桌宠和领地用于说明完整产品闭环，不必一开始罗列全部功能。

当前完整桌面运行与打包目标是 **macOS Apple Silicon**。本地保存数据、计算 embedding，文本理解、形成、选证及语音等使用配置的 Provider；不能把它介绍成完全离线模型产品或已经支持所有桌面平台。

## 2. 项目结构与职责

这是一个 npm package，不是微服务或 monorepo。Main 拥有业务真源，Renderer 维护交互和展示投影，Preload 提供窄的类型化调用边界。

主要数据流可以简化为：

```text
用户文字 ───────────────────────────────→ Agent Run
桌面观察 → Activity → Cognition → 决策 ─→ 同一 Run/Item、Tool、Approval 合同
                              ↕                    ↓
                        Memory 证据检索      真实回应 / 执行回执
                              ↑                    ↓
                        有来源形成 ←───────────────┘

语音：原生 Realtime 模型驱动，共享产品合同、上下文、工具执行与持久化
```

“统一运行时”要讲准确：文本 `AgentRuntime` 与 Voice Realtime 的模型循环不同；统一的是产品状态和能力边界，不能说所有入口都使用同一个文本推理循环。

## 3. 重点一：记忆系统到底怎么做

### 3.1 先区分三种状态

| 层次 | 存什么 | 解决什么问题 |
| --- | --- | --- |
| Chat / Run / 原始观察 | 用户原话、助手回复、真实工具结果、局部可见内容 | 可追溯的原始来源 |
| Cognition 当前状态 | 当前情境、断言、未完成意图、支持和反证 | 此刻在做什么、还缺什么 |
| Memory 长期记录 | 稳定 Memory 身份、Revision、主体、时间、限定条件、精确来源 | 跨会话回忆、改口、纠错和长期理解 |

FTS、向量和巩固内容有各自身份与来源，但不会替代原始事实。对话摘要服务于上下文容量，也不等于长期记忆。

### 3.2 写入：真实来源 → 提炼 → 旧记忆比较 → 原子提交

1. **接收真实材料。** 来源包括已保存的消息、可用的执行结果和 Activity 原始观察。`memory.record({})` 不接受模型随意编出的事实清单，由宿主读取当前真实材料。
2. **可靠交接。** Cognition 提交状态时留下持久 handoff；Memory 入队与 handoff ack 在同一个 SQLite 事务内完成，提交后才启动异步模型工作。
3. **按预算分段。** 保存来源身份、原始范围、primary/context 区别和处理游标。辅助前文可以消歧，但不能被算成一次新的用户确认。
4. **形成提案并比较。** 提炼内容、主体、时间和引文；按提案问题检索旧记录。当比较材料实际改变时，再让形成模型作完整比较，决定 `create`、`revise` 或 `support`。
5. **宿主验证。** 检查真实 source ID、逐字引文及区间、实体映射、主体范围、旧 Revision 和历史处置。模型选择提案，宿主决定这份提案是否能合法落盘。
6. **事务内落盘。** 再查目标版本；一次提交相关事实、来源、语义、关系、FTS 和该段进度。模型请求留在事务外，避免长时间持锁。
7. **派生索引异步跟进。** 向量工作独立持久化；形成成功不等待全库索引排空。尚未索引的事实仍可经词法/实体通道找到，并返回索引缺口说明。

一个关键细节：**需要比较的旧原件必须完整供应，不能在请求仍有空间时被固定的小额度裁掉。** 同一来源已形成的 current、实际引用目标、前段产出等是必要材料；其他相关记忆才是可选候选。必要集合装不下就保留未提交进度并明确失败。

### 3.3 修订：变化与纠错是两回事

`Memory` 是稳定身份，`Revision` 保存版本和前驱。语义维度包括 episode、claim、commitment、experience、reflection；与展示用类型分开。还记录 user/character 归属、Persona 范围，以及明确陈述、直接观察、推断等依据。

`owner` 表示适用范围，不等于说话人或语法主语。例如用户说“你陪我时不要讲冷笑话”，可能只适用于当前角色，应保留角色范围；不能仅因用户说出，就推广成跨角色通用偏好。语法主体另外用实体表达。

| 概念 | 例子与意义 |
| --- | --- |
| 记录时间 `recordedAt` / 查询 `knownAt` | 系统什么时候知道；能回答“截至当时知道什么” |
| 发生时间 `occurredFrom/To` | 事情什么时候发生；未来约定可能现在已经被知道 |
| 有效时间 `validFrom/To` / 查询 `validAt` | 偏好或约定在哪段时间适用 |
| `retained_history` | “以前喝咖啡，后来改喝茶”：旧偏好曾经成立 |
| `corrected` | “刚才记错了，礼物是给表弟的”：旧内容只能作为错误记录回忆 |
| `unresolved` | 尚不能确定旧说法是否成立，不能把它作为已证实事实 |

**示例用于解释机制，不是新增评测结果：** 周五约定改为周六，保留同一 Memory 身份并新增 Revision；“原本以为给姐姐，其实给表弟”则需要标记旧版本错误，而不是描述成“曾经送给姐姐”。只保留最新文本无法回答历史问题；只保留全部文本又会让错误反复混入答案。

### 3.4 读取：先提出问题，再选最小充分证据

入口是 `recall(RecallPlan) → EvidencePack`。`RecallPlan` 包含用途、问题列表、可选实体/时间/主体范围、精确引用、排除版本和预算。

检索顺序：

1. **精确引用单独读取。** 已知 Memory/Revision 配对按身份及 current/history 资格验证，不被普通相关搜索的过滤条件误伤，也不偷偷换成另一个版本。
2. **每个问题多路召回。** SQLite FTS5/BM25 处理专名与精确用语；本地 embedding 处理不同表述；实体/事件时间提供结构化候选。有效时间和获知时间主要决定资格，不自动制造相关性。
3. **交替融合去重。** 各问题、各通道按原排名轮流贡献候选；当前生产没有使用 RRF 加权公式。
4. **模型选证。** Selector 判断哪些候选真正回答各问题，返回 `supported / partial / missing / conflicting`，不是只取相似度最高的几条。
5. **必要时一次关系扩展。** 候选确有缺口时补入相关版本/来源关系，再选证；进一步搜索由同一个 Run 围绕明确缺口继续提出。
6. **分配最终材料。** 优先保留完整事实和各问题的首要证据，再给引用细节分配余量；明确节选、未形成、未索引和缺失。
7. **异步后重验。** 模型选择、输入计量后，再查删除、版本及时间资格；用户期间改口，旧选择不能冒充当前事实。

候选池、最终证据包、完整 Provider 请求是三个预算。当前候选默认为 `min(32000, finalBudget × 4)`，它是内部成本边界，没有被证明为全局最优；最终 Tool 结果还会按真实消费请求的剩余空间分配。

### 3.5 本地向量与巩固

唯一编码路径是 **Qwen3-Embedding-4B Q4_K_M + llama.cpp，LAST pooling，取 MRL 前 512 维并重新 L2 归一化**。模型原输出 2560 维。降低维度减少索引和扫描成本，不减少 4B 主干的前向计算。

文档通过实际 tokenizer 分段，不能截掉尾部假装已经索引。模型 hash、引擎 commit、维度、指令与关键编码参数共同组成索引 namespace，防止混用不同向量空间。

SQLite 中按 chunk 存向量；一个常驻只读 Worker 做精确余弦扫描，同一 Revision 取最好 chunk，用有界堆保留候选。当前没有 ANN 或独立向量数据库。Worker 保持 Main 可响应，但扫描、编码、Selector 和多问题等待仍有真实成本。

后台巩固从已有原始记忆生成有限的情节总结或模式，保存为 `inference`，保留精确父 Revision 和引文。同一实际形成批次共享 Recall，但不强行合并不同主题。父事实被纠正、删除或失去资格后，旧派生理解必须失效；原事实继续保留。

**当前“遗忘”主要体现为选择性使用和来源回收：** 不按日历年龄机械删除重要事实，不把检索曝光当作用户强化；纠错、归档、时效、相关性和预算控制当下使用。只有无消费者需要的完整原文才可回收，仍合法的身份、引文和回执保留。没有上线艾宾浩斯公式、独立互动时钟或未来需求预测排序。

## 4. 重点二：注意力机制到底是什么

这里主要指**应用层的注意控制**：在持续变化的来源中，选择当前要理解的信息、保持目标、决定是否行动。项目没有训练新的 Transformer Attention 层，也没有用一个未经验证的“显著性分数”替代这些逻辑。

### 4.1 持续维护哪些对象

| 对象 | 作用 |
| --- | --- |
| Evidence | 来源类型、对象、actor、发生/接收时间、序列、可见范围与真实内容 |
| Situation / Episode | 跨窗口情境和经历片段；切 App 不等于切任务 |
| Claim | observed/reported/inferred，支持、反证与可修正状态 |
| Intent | 用户或角色目标、成功条件、阻碍、恢复条件、真实效果与下次考虑时间 |
| Attention | 当前情境、承诺意图、焦点版本、用户接管代次及消费进度 |
| DecisionAttempt | 本次读到的版本、缺失信息、候选行为、选中依据、dispatchKey 和实际 Run |

**物理焦点与任务焦点分开。** 用户从编辑器切到浏览器查资料，前台对象变了，写稿的承诺仍可继续；角色自己的目标也不能覆盖用户当前请求。

### 4.2 从高频事件到有界输入

- 原生侧聚合键鼠类别和次数，区分 user、agent、system、unknown；计数不证明兴趣、理解程度或情绪。
- 连续同内容可以合并，但切走再返回属于新观察；保留宿主来源时钟，防止迟到旧事件覆盖当前焦点。
- 纯计数段可以本地汇总并推进必要处理进度，不逐键请求模型；真正内容变化不能当空计数吞掉。
- 当前生产把连续版本组织为**来源目录**：保留对象、代次、首末版本和短暂变化片段，模型按具体信息需要提出 `sourceReadPlan`，宿主读取真实版本或明确节选。
- 当前用户原话、同一 Run 的已完成回复、执行反馈、承诺及必要依据优先直接供给。目录只是查找线索，未打开的正文不能用来作事实断言。

读取先在数据库侧约束，不先 `.all()` 全库再截提示词。当前分析原文分配为 128 KiB，完整模型请求另算；行动所需的目标、关键条件和反证不能受普通补充背景的小额度静默截断。

### 4.3 决策与过期控制

模型 driver 只提出状态变更、信息需求和候选行为，不直接发消息或执行工具。候选包含保持安静、回应、澄清、继续共同活动、主动开场和角色日常。

宿主分别检查：

1. **分析提交：** 读取的实体版本、引用和用户代次是否仍有效。
2. **行动分发：** 选中目标、当前断言、来源及当下可执行条件是否仍成立。
3. **Run 绑定与发布：** 唯一 dispatchKey、实际 Run 身份和展示前的资格是否一致。

用户接管、取消或切角色使相关旧结果失效。后台分析读取的全部资料是提交校验集；真正行动只绑定它实际依赖的那部分资料，避免无关窗口变化让所有工作都失效。

必须区分**收到、目录审阅、正文供给、状态提交、Memory 接管、形成、最终采用**。收到事件不代表模型看见；看见不代表理解；理解也不代表最终回答正确使用。

## 5. 如何证明有效：评测口径与可引用数字

### 5.1 分层定位，不能只看最终回答

```text
原始资料 → 正确形成 → 进入候选 → 正确选证 → 真正进入请求 → 最终正确使用
```

每一层分别保留数据，才能知道该修 formation、query、过滤、encoder、Selector、预算还是 Agent。适用的指标包括：

| 层次 | 关键检查 |
| --- | --- |
| 形成 | 主体、否定、时间、条件、纠正与引文是否完整；是否错误重复创建 |
| 候选召回 | 必要证据覆盖、排名、实体/版本过滤是否误杀；MRR 等只是中间指标 |
| 选证与供给 | 每问题覆盖、无关证据、冲突、预算遗漏、真实下一次请求里的内容 |
| 最终使用 | 是否自然搜索、是否正确采用、是否错用旧值、是否合理承认未知 |
| 注意与行为 | 关键瞬态信息遗漏、重复回应、错误打扰、过期行动、接管与恢复 |
| 资源 | 完整调用及 Token、预付和查询总成本、事件积压、Main 延迟、RSS 和存储 |

“必要证据完整覆盖率”可按“全部必要证据均保留的问题数 / 问题总数”统计；它不同于“命中任意相关文档”。一条事实被多次曝光不能增加独立证据分母。

### 5.2 现有验证怎么组织

**工程层：** fake clock、注入 Provider、真实 SQLite 与固定 fixture 验证事务、引用、取消、重启、IPC 重放和预算；Vitest/Testing Library 做单元与集成，Playwright Electron 验证完整界面旅程。

**语义层：** 冻结故事、预期事实、模型、源码和输入，做同源配对；真实运行形成、Recall、Selector 和普通 Agent。开发诊断、独立故事及后验修复分开记账。开放回答结合盲化身份的独立复核和逐事实审阅，不只让生成模型给自己打分。

**冷检索：** 经正常情境收束、新 Chat 或重启后检查首个完整请求，确认待考事实没有预先进入上下文，再观察自然 `memory.search`、实际候选/Pack、下一请求和最终答案。新 Chat 本身不能证明冷，因为 Cognition 仍可能携带答案。

**长期与容量：** 可控时钟模拟跨日、跨月、长期停用和重新提起；真实模型验证语义，实际进程测资源。模拟长期功能、合成容量、真实桌面采集各自报告，不冒充真人数月使用效果。

## 6. 深挖问答：架构与运行时

**Q1：这个项目和普通聊天套壳的区别是什么？**

答：核心工作在模型之外：持续情境、带修订和证据的记忆、可恢复的行动生命周期，以及它们之间的一致性。模型提供理解与决策提案，产品负责真实来源、状态、执行、取消和验证。

追问“创新点是什么”：可以讲具体工程机制与取舍，不宣称提出了新基础模型或原创注意力算法。

**Q2：为什么选择 Electron + SQLite？**

答：项目是单用户桌面应用，需要托盘、多窗口、浏览器和原生能力，又希望共用 TypeScript/UI 生态。SQLite 适合本机事务和来源关系，减少服务部署；代价是同步访问和大计算会阻塞 Main，因此要从读取和执行位置控制。

**Q3：Main、Preload、Renderer 为什么这样划分？**

答：Main 拥有业务真源、凭据和领域服务；Preload 只暴露 typed 方法；Renderer 消费投影并处理交互。这样重载页面不等于丢掉 Run，也不需要前端再维护另一套执行状态机。

**Q4：TypeScript 已经有类型，为什么还用 TypeBox/Ajv？**

答：TypeScript 不验证运行时输入。IPC、模型输出、MCP 和持久化读取都可能带来不符合类型的值；Schema 同时提供运行时验证和静态类型来源，减少合同漂移。

**Q5：为什么自建 Harness，没有直接用 LangGraph？**

答：Run/Item、审批、用户追加、语音和恢复是产品的核心合同。当前选择让这些状态由 CharaMate 直接拥有，Provider SDK 只做适配，避免外部编排框架和产品状态产生双重所有权。代价是必须自行承担完整测试与生命周期维护。

**Q6：一个文本 Run 如何执行和停止？**

答：编译上下文 → 模型流式输出 → 处理 Tool Search/Function Call → 审批与执行 → 回注 ToolResult → 下一轮。正常完成、等待输入、取消、错误有显式状态；没有用统一“最多 N 步”终止所有任务。另有语义重复工具周期检测及受限恢复，属于已选启发式。

**Q7：流式 UI 如何在断线或重载后恢复？**

答：Run 事件有 streamId 和连续 sequence，先持久化状态与事件，再发布；重复追加不重复发布。Renderer 使用已有游标重放，校验流身份和顺序，发现缺口后恢复投影，而不是依赖内存里的 delta。

**Q8：系统是否实现了严格 exactly-once？**

答：本地事务和唯一身份可以约束入队、绑定与状态提交；它们不能自动保证外部系统副作用 exactly-once。完成结果不重放，未决操作按幂等性与已知执行状态恢复；没有可靠回执时不能猜测成功或盲目重做。

## 7. 深挖问答：记忆系统

**Q9：长期记忆和 RAG 有什么区别？**

答：这里包含 RAG 式检索，但还要管理事实如何形成、归谁、何时有效、如何纠正和删除。知识库常把文档作为既定输入；陪伴系统必须处理用户改口、角色经历、错误历史和持续变化的来源。

**Q10：为什么不把全部历史塞进长上下文？**

答：完整历史会增加请求成本和无关信息，也不会自动解决版本冲突。当前保留用户可见历史，模型侧只带当前工作集、必要摘要和按问题选择的证据；“存得完整”与“每次全部读入”分开。

**Q11：为什么 Memory 和 Revision 分开？**

答：稳定身份让一次约定的改期仍是同一件事；Revision 保留当时内容、来源与前驱，支持当前查询和历史解释。直接覆盖会丢历史，每次新增又会产生多个互相矛盾的“当前事实”。

**Q12：用户改主意和系统记错了，处理有什么不同？**

答：改主意可以保留“当时成立”的历史；记错需要标记 corrected，不能再作为真实过去使用。新的 Revision 还应保留未被否定的原报告细节及精确引文，不能因纠正一处而把整段经历改写。

**Q13：为什么记录时间、发生时间、有效时间都要有？**

答：今天知道下周的约定，三者明显不同。把 `occurredTo=now` 当作普通历史过滤，会把已经知道的未来约定排除；缺少时区的“周五”也不能伪造一个精确 UTC 时刻。

**Q14：怎样避免把小说、别人说的话或角色行为记成用户事实？**

答：来源保留 speaker、actor、类型和可见范围，语义保存主体、owner、Persona 与 basis。形成模型必须引用真实原文，宿主校验来源资格；屏幕观察只证明看到某内容，助手复述也不等于用户再次确认。语义归属仍需真实模型场景验证。

**Q15：三种形成操作为什么有必要？**

答：`create` 建立新事实；`revise` 改变已有事实的内容或适用范围；`support` 只为不变的事实增加真实支持。support 不让模型重写旧正文和语义，减少“补证据时顺手改变事实”。

**Q16：模型生成了合法 JSON，为什么不能直接写数据库？**

答：Schema 只验证形状。引文可能不存在、主体可能错、target 已被改版，或者计划被说成完成；还需要精确 span、当前版本、归属、来源语义和事务校验。最后的自然语言正确性不能全靠机械验证。

**Q17：怎么防止同一来源重复形成多条记忆？**

答：来源集合、版本和处理身份进入持久工作记录，已提交分段保存游标；比较阶段读取该来源已有的 current 记录，判断不变时补充或不写。不同入口再次接管同一原文，不增加独立用户支持。

**Q18：为什么不是一次模型抽取就完成？**

答：不查旧记录，模型无法可靠判断“新增”还是“改口”。实现先形成提案，再按具体事实检索比较；比较输入变化才做后续形成判断，避免无信息变化仍固定多一次调用。这是自适应流程，不保证每次恰好两次请求。

**Q19：形成中应用退出，或者模型配置变了怎么办？**

答：已提交前缀与工作游标持久化，恢复从未完成部分继续。模型请求绑定实际 Provider/模型/处理器快照，异步后重验；取消、可恢复服务故障和语义拒绝分别处理，不以后台无限重试覆盖失败。

**Q20：中文 FTS 怎么做？为什么还需要向量？**

答：代码用 `Intl.Segmenter` 分词、NFKC/小写规范化，并对连续汉字段补相邻双字词，进入 FTS5/BM25。词法适合专名和精确措辞，向量补不同表达；两者都有误召回，所以后面还要问题级选证。

**Q21：为什么当前融合没有用常见的 RRF？**

答：真实比较里，主比较必要材料两者都是 29/30，交替融合在较小预算下保留了更多部分单通道细节，而且省去 RRF 常数，因此选简单路径。不能说交替融合普遍优于 RRF。详见[融合 Decision](benchmarks/MEMORY-RANK-FUSION.md)。

**Q22：最终选证是不是 reranker？**

答：它承担语义筛选和排序，但合同更细：把证据映射到具体问题，显式报告支持、部分、缺失或冲突。相似度高只表示候选相关，不能证明已经回答了问题；当前没有另放一个交叉编码器 reranker。

**Q23：为什么选 4B、512 维？是不是降维损失很大？**

答：开发比较中 4B/512 与 8B/1024 最终选证同为 27/28，4B 的原生资源更低。512 维使用模型支持的 MRL 前缀并重新归一化；是否足够看完整候选预算和最终回答，不能只看原维度 top1。

追问“节省多少”：100k 个 Float32 向量的净荷是 `100000 × 512 × 4 = 204.8 MB`，不包括 SQLite 表、页、索引和模型权重，也不代表实际只有一段/Revision。

**Q24：为什么不用 ANN？精确扫描复杂度是多少？**

答：当前证据支持单机精确路径，还没有证明 ANN 的额外索引、维护与召回损失值得。若扫描 C 个 chunk、维度 D、保留 K 个候选，主要计算约 `O(CD + C log K)`，堆保留 `O(K)` 状态；读取和缓存另计。规模继续增长时应重新测，不宣称精确扫描无限可扩展。

**Q25：Worker 如何取消同步扫描？**

答：仅发 cancel 消息不能打断忙于同步循环的 Worker。当前使用 `SharedArrayBuffer` 中的原子标记，Main 写取消，Worker 在逐行扫描时检查；查询向量用可转移副本传入。退出等待任务收口并关闭连接，没有 Main 同步扫描备用路径。

**Q26：异步索引是否会让刚记住的东西搜不到？**

答：会暂时缺少语义通道，但事实与 FTS/实体信息先提交，所以其他通道仍可用。EvidencePack 明确区分“经历未形成”和“语义索引未完成”；不能把这时的空结果解释为用户从未说过。

**Q27：巩固与摘要的区别是什么？如何避免越总结越偏？**

答：巩固是有父版本和精确引文的派生理解，保留限定条件并标注 inference；原始记忆不会被替换。新增或修订派生内容要重验父版本和来源，父事实失效后旧结论也失去资格。跨午夜、同会话重复和助手复述不构成稳定模式证据。

**Q28：记忆会像人一样遗忘吗？**

答：当前没有实现人脑式遗忘模型。采用曝光中性、按问题选择、纠错和有效性控制，保留低频旧事可达；物理回收只针对无消费者需要的完整原文。年龄淡化曾损害旧事召回，因此没有进入当前生产。

追问“什么叫曝光中性”：系统自己搜到并读了一条记忆，不会因为这次读取就自动把它变得更重要。

**Q29：删除记忆后，摘要或其他领域还会继续用它吗？**

答：读取和真正采用时检查原记录、精确 Revision 与派生依赖；删除、归档或纠正会影响资格。Territory 引用 Memory ID 和发布事件，不读取其私有表。合法原文回收与用户删除不是一回事，仍有效引文不会因全文回收被误判不存在。

**Q30：模型为什么有时根本不搜索？怎么修？**

答：这是信息需求判断失败。共享指令要求个性化规划和历史回顾先检查当前上下文是否覆盖所需事实及例外，不足时用具体问题检索；问候和自包含任务不用强制搜索。最终 d01 缺陷就在这一层，换 encoder 无法修复一次未发生的检索。

## 8. 深挖问答：注意力与连续认知

**Q31：和 Transformer 的 Attention 有什么关系？**

答：这里是应用层信息选择与执行控制，处理哪些事件要读、目标如何保持、旧决策还能不能执行。底层模型当然有神经网络结构，但本项目没有修改其 Attention 权重或训练专用注意力网络；PFC 是功能类比。

**Q32：注意力是不是“最近事件优先”或一个加权分数？**

答：都不足以描述当前实现。宿主保留用户输入、必要支持和反证等边界，模型依据持续意图、新信息、缺口与打扰代价选择行为；未完成承诺可以比新窗口更重要，也允许保持安静。

**Q33：桌面每秒都有变化，怎么避免每秒调模型？**

答：来源侧合并、同内容去重、纯计数段本地处理，再通过事件目录按需读原文。模型请求由有意义的新证据、反馈或到期条件触发。当前一秒批次和 128 KiB 分配是工程选择，不是生理常数或“最佳频率”。

**Q34：只看最新页面，会不会漏掉短暂出现后删掉的信息？**

答：会，所以目录保留首末来源和真实变化片段，以及对应原版本的引用。模型可以针对关键变化读取旧版本；保护中的来源不提前回收。不过“可定位”并不保证模型一定选对，因此要专测瞬态约定、错误和撤回。

**Q35：为什么要区分接收水位和消费水位？**

答：事件可能已到达，但正文因积压尚未供给。用消费水位判断“新用户输入”，会把快照之前已经收到的消息反复当成新中断；所以决策固定当次接收边界，正文处理进度单独推进，后来真实到达的用户输入仍能使旧行动失效。

**Q36：优先读最新用户输入，会不会把中间消息跳过去？**

答：最新原话可提前供给，但不据此跳过连续消费水位；最老未处理来源仍保留，中间纠正继续有序处理。提前看到与已经连续完成消费是不同状态。

**Q37：为什么后台会重复回复一个已经回答的问题？**

答：实际遇到过 FIFO 分页把用户问题和同 Run 的已完成助手回复分开，后台据不完整材料误以为尚未回答。修复按 Persona/Run 精确关联共同供给回复和终态，并标明节选；扩大页大小只会偶然掩盖这个合同问题。

**Q38：模型分析期间用户改口，如何避免旧结果执行？**

答：分析提交检查 read-set 的版本；行动另检查所选意图、当前断言、来源、用户代次和接收边界，Run 绑定及发布前继续验证。用户输入优先使相关在途工作取消或过期，不能靠一条 prompt 要求模型自己记住取消。

**Q39：模型只看到局部情境，更新会不会把没看到的部分删除？**

答：局部分配记录明确哪些字段和子项可见；已显示项按 ID 更新，未显示的 canonical 内容保留。严格输出使用 keep/set/clear 表达保持、设置和清除，避免把必须输出的 null 错当成“没改”。

**Q40：为什么要区分分析依赖和行动依赖？**

答：模型可能阅读很多背景，但一次行动只依赖其中几项。分析提交要检查读过的状态；行动绑定最小必要依据，否则无关背景变化也会废掉合法动作。反过来，必要条件和反证也不能为了减少失效而省略。

**Q41：什么情况下一个目标才算完成？**

答：独立完成依据可以是实际效果、有归因的用户完成报告，或确实满足有限文字任务的已完成回复。读取成功不能证明写入，Run 结束不能证明任务效果，助手声称做完也不能替代回执。

**Q42：角色自己的生活需要第二套 Agent 吗？**

答：不需要另建生活目标库和执行器。角色目标就是 character-owned Intent，生活工具修改同一状态，由既有调度器唤醒并进入同一产品执行合同。下次到期表示重新考虑，不能把离线时间包装成已经发生的经历。

## 9. 深挖问答：验证、取舍与工程细节

**Q43：如何证明记忆有效，而不是模型碰巧猜对？**

答：选用无法从常识猜出的特定事实，冻结来源和标签；核首请求没有答案，记录自然搜索、候选、选证、下一请求与答案之间的链路。再测更新、同名主体、未知和无需回忆场景。只有最终答案对，不能定位记忆是否真正起作用。

追问“有没有消融”：仓库有形成分配、融合、encoder、信息依赖指令等局部对照；不能声称已经用同一最终版完成所有有/无记忆、全链路消融。

**Q44：召回率很高，为什么回答仍然错？**

答：必要证据可能进入候选却被 Selector 漏选，被预算挤出，或根本没进入下一请求；Agent 也可能忽略已供给的限定条件。因此要分开看候选覆盖、最终 Pack 覆盖、实际 wire 供给与回答采用，而不是只调 topK。

**Q45：你会怎样设计记忆和注意力测试集？**

答：按故事家族覆盖跨会话组合、改口、错误历史、同名人物、临时例外、长期停用、隐含旧约束和无答案；注意部分加入跨 App 同目标、瞬态内容、迟到事件、重复计数和接管。冻结后保留 holdout，修改所用案例归开发集，不能修完仍称独立通过。

**Q46：怎样解释小样本和失败？**

答：报告分子分母、逐对差异、实际成本及可用区间，不把同一故事多个检查点当独立用户。原失败、取消和缺 usage 保留；后验定向成功只能证明相应故障得到修复。没有独立重复依据时，不制造总体 P95 或显著性结论。

**Q47：为什么 Token 少了，不一定是系统更好？**

答：可能漏掉必要条件，也可能把工作移到更多查询、追问或后续重做。形成分配实验就接受了输入增加 7.59% 来修正实际错误；巩固则同时计算后台预付与消费者成本，不能只比摘要请求。

**Q48：目前最大瓶颈和边界是什么？**

答：持续新内容的语义处理速度、后台形成积压和真实端到端延迟仍是边界。合并容量窗仍有最长约 2.56 秒到达延迟及未排空队列；本地 4B 也有首次加载和数 GB 资源代价。工程通过不代表任意规模、真人长期收益或零错误。

**Q49：完整上下文预算怎么控制？**

答：在 Provider 组装完整请求后，计入指令、工具、Schema、历史、记忆及多模态，取用户 258000 与较低 Provider 限制的交集，并满足输出预留。支持真实计数时用精确结果；本地代理 count 曾返回 404，只能对可估计请求保守放行，不能声称绝对精确保证。

追问“128 KiB 和 258k 什么关系”：前者是原文读取字节分配，后者是完整请求 Token 约束，不能直接换算或互相替代。

**Q50：语音为什么不直接复用文本回答再做 TTS？**

答：真实体验暴露句间等待、文字与朗读偏差以及跨队列打断复杂度，所以当前采用 Azure 原生 speech-to-speech Realtime，应用显式创建 response、管理 Run 和工具续接。WebRTC 承担媒体，文字与语音共享 Tools/审批和产品状态；语音没有伪造文字端的托管 web_search。

**Q51：为什么有些工具常驻，有些按需发现？多 Agent 怎么用？**

答：核心能力按权限直接给 Schema，避免基础文件操作因召回失败变成“没有能力”；长尾通过 Registry 的 BM25 发现后加载。Agent 的协作能力仅限两个声明互斥资源的只读 child，父任务汇总，不能共享可变 Browser/Computer 会话，也不宣称已证明普遍提速。

**Q52：如果继续优化，你会先做什么？**

答：先按阶段测真实瓶颈：形成积压看服务率和必要材料，检索慢区分编码/扫描/选证，答案错先查证据有没有真正供给，Main 卡顿查同步读取和调度。达到真实规模瓶颈再比较 ANN 或多 query 扫描；只有可靠错误落在表示能力上，才考虑 embedding 微调。这些属于下一步，不是已实现成绩。

## 10. 三个最适合讲的难点案例

### 案例 A：已经检索到旧事实，还是重复创建

**现象：** 形成模型的必要旧比较材料被局部预算裁掉，后续检索找回了原记录，最终仍可能提交旧的 create 提案；另一条链甚至保留了错误旧时间。

**定位与处理：** 沿原文 → F1 → Recall → F2 实际输入 → SQL 比较，发现问题在材料完整性和后续比较，不是向量召回。将同源 current、真实引用和已采用目标列为必要集合，完整读取并按整份请求计量；材料变化时重新比较，事务提交前再校验。

**结果：** 四条件形成从 0/4 到 4/4，冷答 2/4 到 4/4，输入增加 7.59%。这个案例体现“为正确性接受合理成本”，不声称普遍提高到 100%。

### 案例 B：高频事件下，少发 Token 也不能丢短暂线索

**现象：** 逐版正文进入模型导致积压；只留最后版本则会丢掉出现后被删掉的约定和错误。

**定位与处理：** 采用来源目录保留身份、变化和原版本，按具体问题展开；当前用户、执行反馈与承诺直接供给，接收和消费分开记录。未读目录不能当事实，行动仍需真实依据。

**结果：** 四家族的已报告输入约降 70%、生成次数降 46%；同时保留路线场景线索未采用、部分前台更慢的反例。说明成本收益明确，但不能只凭压缩率宣布理解无损。

### 案例 C：用户早已得到回答，后台却再次确认

**现象：** 前台完成后，后台又发出类似确认。

**定位与处理：** 检查真实事件序列与模型输入，发现问题和同 Run 回复被 FIFO 拆到不同页。按同 Persona、同 Run 把真实完成回复与终态关联供给，身份优先、内容节选明确；同时区分“回复存在”和“外部动作完成”。

**验证：** 相同材料分别缺/有回复的真实请求呈现再次回应/保持安静，关联回归覆盖分页和消费水位。解释时强调修的是上下文合同，不能只靠调大页或 prompt 要求“别重复”。
