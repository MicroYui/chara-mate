# AGENT-PENDING-INPUT-STEERING：提问与待审批动作中的普通消息接管

日期：2026-09-16。状态：接管修复已随共同 v21 集成 Main；该次 v21 完整离线验证通过；最终同版连续语义与 Electron E2E 仍待完成。集成负责人：当前主任务。

## 产品问题与选定行为

真实陪伴开发场景中，角色通过 `request_user_input` 询问接下来的休息方式，用户随后直接发来一段新内容。原 Chats Store 把 `needs_input` 视为活跃 Run 并调用 `steer`，Runtime 却拒绝这个状态，导致普通聊天被旧问题卡住。实验 runner 也错误地尝试新建 Run；两者都要修正，不能通过让模拟用户必选一项掩盖产品缺口。

选定行为遵循产品设计的“用户可以随时继续输入”和同一 Run 接管：普通消息保持为真实用户消息；旧提问结束，使用现有 `cancelled` resolution，不替用户选择选项、不伪造回答。收到新输入后，旧模型响应中尚未执行的调用必须重新决策；已经完成的动作与结果保留。卡片答复同样属于新输入。新意图不自动授权任何外部操作。

界面将被结束的问题显示为“已结束提问”，未执行的旧调用显示为“工具调用已取消”；不能把取消显示为“已收到补充信息”或“已调用工具”。

同样的语义覆盖待审批动作：新消息到达后，尚未执行的原动作结束审批等待并重新决策；稍后到达的批准不能执行过时动作。若批准已先落盘，保留已经批准的历史事实，但在动作实际执行前到达的新消息仍要求重新判断。这里结束的是旧动作，不能将取消伪装成用户拒绝，更不能将新消息当成新的执行授权。

## 一手来源、边界与建模

- 项目基线：`fc81239304c03648ee3f39ca178f3695ce474ffc` 加本次开始前保留的完整工作区快照。直接核对 `chatStore.ts`、`agentRuntime.ts`、`runRepository.ts`、`runEventWriter.ts` 与既有输入卡片实现（2026-09-16）。这是当前代码行为，不是外部协议规定。
- [OpenAI Function calling：Handling function calls](https://developers.openai.com/api/docs/guides/function-calling#handling-function-calls)，2026-09-16 核对；项目使用官方 `openai@6.49.0`。模型一次可以返回多个调用，返回结果必须对应具体 `call_id`。因此未执行调用也要向模型给出配对的明确结果，不能删除调用的一半或假装成功。
- 产品设计与 UI 设计的当前请求接管语义在实现前补齐。本次没有新增时长、次数、并发量或失败重试阈值；无需算法候选比较。它是已复现的状态机正确性修复。

每个活跃 Run 增加一个仅在内存存在的用户输入版本号。模型步骤记录实际供给本轮请求的版本；工具执行前核对版本。后续[动态材料修复](COGNITION-DYNAMIC-ACTION-BUDGET.md)还会在材料化等待期间出现新输入时重建请求，不把流生成期间才到达的消息误算为已供给。版本已经改变时，记录 `TOOL.USER_INPUT_CHANGED` 的 rejected ToolResult 与 cancelled Item，并保留 `call_id` 配对，让下一步读取新输入重新决定。用拒绝表示“未执行”不会把这类正常交互计为工具故障。

普通用户消息落盘时，Run 仍保持 `needs_input` / `waiting_approval`，不能因为 `item.started` 把等待中的状态提前投影成 running。结束旧问题由既有 Writer 负责。输入版本无须持久化：重启时通过 SQL 游标只恢复 checkpoint 边界之后、已完成且带 steering 标记的用户消息；不会重新加载整个历史 Run，也不会丢失“用户消息已落盘、结束问题尚未落盘”的中间状态。等待输入恢复后消费这个已持久化的消息，不产生第二个用户消息或第二次答复。

审批接管复用现有 `cancelled` 审批状态，并在等待恢复与即将执行两个位置检查新输入。重启依据 checkpoint 的 approval phase 恢复边界，覆盖审批结果已经落盘、Run 已投影为 running、工具尚未继续的中间状态。已批准的审批 Item 保持原结果；其后被新消息替代的未执行 Tool Item 单独记为 cancelled。

本包不改变审批模式，也不把需要确认执行结果的其他 `needs_input` 状态当成问答卡片；不取消已经执行的外部效果。没有新表、数据库迁移、IPC 方法、后台任务、依赖或产品设置。

## 已完成验证与保留的失败

验证在隔离集成快照进行，使用真实 Run Writer、Runtime、SQLite 和界面组件，模型行为通过确定性 Provider 驱动。模拟的是响应时序和故障位置，不是用另一套状态机代替产品实现。

| 验证                                  | 当前结果                | 证明范围                                                                                                                       |
| ------------------------------------- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 完整受影响 Agent Runtime 集成套件     | 67/67，2.26 秒          | 活跃/重启接管、原消息保留、迟到卡片回答、旧批余下动作不执行、之前完成结果保留、调用配对、审批竞争、故障恢复及既有 Runtime 回归 |
| Chats Store 聚焦套件                  | 9/9，114 毫秒           | running / waiting_approval / needs_input 的普通消息均路由到同一 Run                                                            |
| RunProcess 组件套件                   | 11/11，179 毫秒测试时间 | 取消问题/动作的真实界面标签与原有过程展示                                                                                      |
| TypeScript 与受影响 ESLint / Prettier | 通过                    | 当前候选静态契约；不代表 Electron 桌面验收                                                                                     |

第一次聚焦执行保留了 4 个失败、6 个通过的原始结果：新增消息的 Item 投影过早改变 Run 状态，导致结束问题失败，其中恢复用例超时。修复该根因后的相同聚焦集为 10/10，随后完整 Runtime 为 62/62。另一次 lint 发现测试对未知值默认字符串化，已改成明确类型判断。失败记录没有被成功结果覆盖。

v2 增加五种待审批动作接管时序：新消息先到、批准先落盘、重启后接管、审批结束落盘前中断、审批结束落盘后中断。各用例检查旧动作写入次数为零、用户原文恰好一次、配对的调用结果恰好一次、迟到批准无执行效果，以及已批准的历史事实保留。开发中的类型收窄与实例故障注入修订也保留原始输出；其中一次 65/67 是测试获取 mock 原实现的方式错误，修正为实际 fixture Writer 的绑定方法后为 67/67。最终 TypeScript、受影响 ESLint 均通过。

已补充 Electron 旅程：真实 Composer 在问题卡片可见时直接发送新话题，等待同一 Run 完成，检查取消的提问、唯一用户消息和工具调用配对；原卡片选项旅程保留。另一条旅程在真实文件写入审批期间改话题，检查主窗口与角色窗口的审批卡片结束、文件未写入、应用重开后也不恢复旧动作。本包编写时为避免干扰同期真实桌面资源对照，未执行这些 E2E 或构建；当前 v21 的同版桌面验证仍以 STATUS 后续记录为准，不能由离线通过替代。
