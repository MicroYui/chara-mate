# MEMORY-SOURCE-LOOKUP：长期来源定位与未完成工作核对

日期：2026-09-15。状态：来源索引及其真实仓储验证已完成，合入主工作区；最终桌面和打包回归随本轮交付运行。Owner：root（Schema/Main/选型），memory_research（Memory 仓储和回归）。这项决定只改善持久化来源定位，不证明形成、召回或回答质量。

## 问题与选择

开放断言和闭合情节共用 Memory 形成任务，任务保存完整原始来源，便于崩溃后继续处理及 Activity 原始层回收后恢复文字证据。若每次恢复、检索完整性判断或清理都遍历全部 `memory_work.payload_json.sources`，小库看不出问题，长期运行却会阻塞 Electron Main。

采用一张 Memory 所有的可重建来源定位表 `memory_work_sources`：保存 work_id、来源 ordinal、source_type、reference_id、source_id，不复制原文。主键为 `(work_id,ordinal)`，使用 `STRICT, WITHOUT ROWID`；一个 covering index 以 type/reference/source ID 起始。未完成形成任务使用一个限定 kind/status 的 owner/persona 表达式索引。没有新增后台服务、第二份来源真相或运行模式。

形成任务与定位行在同一事务写入；重复入队不改写已有输入，错误回滚二者。删除任务级联清理定位行。文字仍从原任务 payload 的准确 ordinal 读取，规范化六字段后去重并验证；同一引用对应冲突原文时返回不可恢复，不能挑最近一条。Activity 的批量保护/快照检查走同一索引。

失败任务只有在一个同 owner/persona/situation 的完成任务包含其全部原始来源、六字段逐项相等时，才不再表示待处理缺口。先用首个来源的 type/reference/source ID 找候选工作，再验证完整集合；不能把两个完成任务拼成一个覆盖证明。原错误和状态不删除，不自动重试付费调用，处理过也不等于记住了每个事实。

## 当前来源与实验

查阅日均为 2026-09-15，运行环境为 Apple M4 Pro、24 GiB、Node 24.18.0、better-sqlite3 13.0.1、SQLite 3.53.3。

- [SQLite expression indexes](https://www.sqlite.org/expridx.html)：查询表达式需与索引一致，索引不允许子查询。这里只索引同一行的 JSON 标量。
- [SQLite JSON](https://www.sqlite.org/json1.html)：以实际数组序号从不可变 payload 提取来源；JSONB 本身不保证常量复杂度，未为此另换存储格式。
- [SQLite CROSS JOIN](https://www.sqlite.org/optoverview.html#manual_control_of_query_plans_using_cross_join)：可固定查询嵌套顺序。普通 IN 子查询在本实测中仍让优化器先遍历全部 completed 工作；最终只在已证明退化的候选定位处使用来源表在前的 CROSS JOIN。
- [WITHOUT ROWID](https://www.sqlite.org/withoutrowid.html)：小行、复合非整数主键可能节省空间，但不是通用最优默认。本表单独比较后选用，不改变其它表。

基线预先冻结 1k/10k/100k 完成任务，每任务两条合成来源，另有十条被单个完成工作完整覆盖的失败，以及一条可切换的 pending 工作。三个规模原仓储方法均实际执行三次，检查返回结果；记录全部范围，不以三次观察估计总体 p95。原文长度固定、ID 为合成 UUID，不能等同实际多年使用分布。真实编码器与其他模型实验同时存在，不能宣称资源完全隔离。

发现基线成本后，在同一数据库副本上逐项比较 completed 情境表达式索引、来源投影、unfinished 索引及最后物理布局。另增加所有任务同 owner/persona、没有 situationId、同一 chatId 但不同 messageId 的实际退化情形。Chat referenceId 是会话 ID，不能单凭 referenceId 声称候选已经有界。

## 结果

基线范围，单位毫秒；每格 n=3：

| 完成任务数 | 已覆盖失败核对 | 读取完整来源 | 批量接口核对一个快照 |
| --- | ---: | ---: | ---: |
| 1,000 | 4.02–4.03 | 1.50–4.88 | 1.57–1.69 |
| 10,000 | 38.61–40.71 | 15.26–15.31 | 15.55–15.60 |
| 100,000 | 559.39–649.13 | 176.75–183.17 | 172.61–179.72 |

仅 completed 情境索引把普通分布的核对降至约22ms，但所有任务共享同一空情境时仍需851–855ms。增加来源 IN 子查询仍需359–368ms，EXPLAIN 显示先遍历 complete 工作。这两种候选均被删除，生产不保留 completed 情境索引。完整 source ID 索引加来源在前的连接顺序，在同聊天反例中为0.125–0.289ms，计划是三键查来源、work 主键定位，再核对该工作全部来源。

最终实际生产仓储方法在100k库回测，每格 n=3：

| 方法 | 范围 / ms |
| --- | ---: |
| formationIncomplete，原失败均有单任务覆盖 | 0.150–0.411 |
| getFormationSource，含六字段 schema 校验 | 0.165–3.663 |
| 一个来源的快照检查 | 0.200–0.379 |

读取原文的首次3.663ms与随后0.422/0.165ms均保留，不能仅报告已预热的SQL时间。所有结果与预期原文、完整性及保护集合一致；独立回归还验证字段冲突、不同归属、不同情境、分散完成任务、pending/running、事务失败及级联清理。

200,022行、五字段最终定位表的布局比较中，ROWID 表及其索引总占49,758,208 bytes，WITHOUT ROWID 为39,075,840 bytes，少10,682,368 bytes。两种布局复制相同内容并单独 VACUUM 后计量；并非新生产清理策略。事务内追加2,000个定位行分别为3.31–3.65ms和3.12–3.27ms（各n=3，无fsync承诺）。定位索引确实增加空间与写入，收益来自避免反复读取整部历史，不是免费存储。更早四字段原型的总库数值不可混作最终五字段开销。

## v6 归属与覆盖合同修正

上述测量保留原 v5 环境与分母。v6 不再为整个 Episode 指定 owner：personaId 绑定当前参与角色，每个形成单元独立决定用户或角色归属。未完成任务表达式索引因而只使用 personaId；包含用户记忆的检索必须检查所有角色尚未完成的形成工作，因为其中可能形成全局用户事实。

失败工作被一个完成工作覆盖时，除相同 persona/situation、全部来源六字段一致外，还要求每个旧来源作为 primary 或 context 的用途一致。不能用只看过消歧材料的完成任务证明主材料已处理。当前修改已通过 v6 完整离线验证，但新覆盖谓词尚未重新测量十万任务延迟，不能把上表数字当作 v6 实测。

本表只索引定位，不消除不同形成工作 payload 中的原文重复。连续输入下的 pending 工作合并、逐条读取及单份来源存储正在单独比较；不以年龄 TTL、删除历史或增加线程掩盖队列与容量问题。
