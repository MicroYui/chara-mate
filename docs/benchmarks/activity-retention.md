# ACTIVITY-RETENTION：原始活动与资产的有界保留

## 问题与边界

本 Decision 在蒸馏层级固定后选择一种 Activity 保留策略，使截图、原始事件、Episode 与 Digest 的磁盘斜率有界，同时不删除尚未蒸馏的证据，也不让长期 Memory/Territory evidence 随原始资产过期。Settings 最终只提供暂停、占用与立即清理，不暴露 TTL/容量档位。

引用完整与不删除未蒸馏数据是正确性红线。其余时间窗、容量和批量仅为实验探针；定案综合 Activity 回看、长期问答代理指标、回收量、耗时、数据库增长和实现复杂度，不靠自定单项门槛机械淘汰。

## 来源、环境与冻结负载

- 执行日、基线、硬件与 `ACTIVITY-DISTILLATION` 相同；数据库使用 `MEMORY-STORAGE` 已选的 SQLite WAL/FULL。
- 使用同一 `activity-set-v1.json`（SHA-256 `b0ea066ba95acabdcfecf1a992e54269c5a33f31b556a4da55c17e7d860e1f7f`）循环形成 1、7、30、180 天负载。每个新 Episode 至多一个截图 metadata；测试资产大小按冻结分布而非写死为同一文件。
- 模拟最近两天蒸馏未完成、清理中断后重试、已生成 Digest/Memory 只保留稳定 evidence label 而不保存即将删除的绝对路径。

## 预注册 Arms

| Arm | 原始层 | Episode/Digest | 容量 | 角色 |
| --- | --- | --- | --- | --- |
| `K0-KEEP` | 不删 | 全保留 | 无 | 污染/空间压力基线，不可进入产品 |
| `K1-UNIFORM` | 统一 30 天 | 全保留 | 无 | 简单 TTL |
| `K2-TIERED` | 截图 7 天、event 30 天 | Episode 90 天、Digest 保留 | asset 512 MiB | 分层但不看蒸馏状态 |
| `K3-GATED` | 与 K2 相同 | 与 K2 相同 | 截图资产层 512 MiB；event metadata 另受 TTL 约束 | 只回收 `distilled_at` 已提交数据，并做 orphan/索引清理 |

时间窗与容量先作为一组完整产品策略比较，不运行大网格。只有 K2/K3 在 7 天回看或 180 天磁盘上出现实际问题，才在开发负载补测截图 `3/14` 天或 `256/1024 MiB`，避免为数字形式完整制造笛卡尔积。

## 指标与定案规则

- 1/7/30/180 天主库、asset、峰值临时和每日增长斜率；
- 删除文件、缩略图/OCR metadata、event、Episode 引用与检索项的完整率；
- 未蒸馏证据误删数、dangling reference、orphan asset；
- 清理前后稳定 topic/Digest/Memory 覆盖和最近 7 天 Activity 回看；
- 幂等重试、批次耗时、WAL 增量与交互阻塞代理；
- 状态、后台作业和维护复杂度。

K0 只用于展示无界增长。若 K3 相对 K2 唯一收益是保护未完成蒸馏且没有显著成本，它作为正确、可恢复的最小策略；不增加多级优先队列、可调保留档位或额外安全状态机。

## 结果

所有策略保留 100% Digest/稳定 topic，最近 7 天截图回看覆盖均为 100%；K1–K3 的原始 event 普通 Memory 检索可见数为 0。清理实现同时删除 row、asset、派生引用，四个 horizon 的 dangling reference 与 orphan asset 均为 0。

| Arm | 30 天总占用 | 180 天总占用 | 180 天保留 asset / event / Episode | 未蒸馏证据误删 | 说明 |
| --- | ---: | ---: | --- | ---: | --- |
| `K0-KEEP` | 184.0 MB | 1,136.3 MB | 714 / 930 / 846 | 0 | 六个月仍近线性增长，且 930 个原始 event 可进入检索压力基线 |
| `K1-UNIFORM` | 184.0 MB | 191.6 MB | 119 / 155 / 846 | 35 | 空间有界，但统一 TTL 不保护失败/积压的蒸馏 |
| `K2-TIERED` | 43.8 MB | 42.7 MB | 27 / 155 / 423 | 35 | 空间最小，但按年龄删除了尚未蒸馏的截图/event |
| `K3-GATED` | 49.9 MB | 90.0 MB | 57 / 193 / 444 | 0 | 保留全部未完成证据；已蒸馏截图资产远低于 512 MiB 上限，其余 metadata 由 TTL 约束 |

K3 相对 K2 在 180 天多占约 47.3 MB，来自冻结负载故意注入的长期未完成蒸馏日；它不是重复或孤儿。这个成本换取 35 个未完成证据不被错误删除，且总量仍处于已选容量边界内。K0 的无界斜率和原始检索污染使其不能进入产品；K1/K2 的更小状态不足以补偿真实数据丢失。

原始结果 `activity-retention-raw.json` 的 SHA-256 为 `434055ceba5c1a42766e6f991676cf39b347055877e9614d3d703a60357233b9`，保存 1/7/30/180 天每个 Arm 的行数、asset bytes、回收数、覆盖与引用检查。

## 综合定案

选择 **`K3-GATED`**：截图在完成必要蒸馏后保留 7 天、raw event 30 天、Episode 90 天，Digest/已接受 Memory 使用自己的生命周期；原始截图资产层上限 512 MiB，event metadata 通过 30 天 TTL 保持有界。到期和容量回收都只选择 `distilled_at` 已提交记录，单个事务先删数据库引用，提交后删除文件；失败重试按稳定 ID 幂等完成 orphan sweep。

立即清理复用同一 eligibility，不越过未蒸馏红线。若积压使截图资产层临时超过上限，产品显示真实截图占用并继续重试蒸馏，不静默删除，也不引入多档保留设置或复杂优先级系统。这里不把 SQLite 中其他表的文件字节误报成截图占用；数据库增长由各层 TTL 与独立行数回归验证。

应用重启时，上一进程遗留的开放 Activity event 以自身开始时刻保守闭合，避免把离线时长伪记为用户活动；遗留的 `running` 蒸馏/保留记录标为中断失败。随后沿相同幂等路径重新蒸馏和清理，不增加恢复队列或第二套状态机。

## 限制

- asset 大小来自冻结的 0.8–2.4 MB 分布，不能预测所有 Retina 多屏截图；容量上限因此与时间窗共同生效。
- 本实验验证逻辑引用与磁盘斜率；真实文件删除中断、WAL 和 orphan sweep 仍需生产 integration test。
- Digest 长期保留不等于永久保存原始屏幕内容；删除后来源 UI 必须显示稳定的“原始活动已按策略清理”。

候选 runner 在 hash 核验后删除；生产只保留 K3。
