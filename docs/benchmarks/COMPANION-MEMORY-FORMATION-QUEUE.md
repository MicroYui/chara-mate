## 产品规则与实现范围

Q2 已把 canonical 原文保存一份，但每次情境扩展仍有完整有序引用集。连续 n 次、每次多一个来源的未消费输入，可保留 n(n+1)/2 条排队引用。本方案仅在新工作包含旧工作的全部来源时，取消尚未开始的旧后台输入：

- 旧工作必须为 `pending/attempt=0/result=NULL`。running、failed、complete、已尝试、已有 partial/progress 的工作全部保留。
- persona、situation、processor 必须相同；每个 canonical source 的 primary/context 用途相同，旧来源相对顺序相同，新输入来源数严格更多。
- 原文注册、新工作引用和旧排队项删除在同一同步 SQLite 事务里；上游 outbox ack 失败会整体回滚。删除排队项不删除 canonical 原文。

只有一条来源的新工作不可能是合法非空旧工作的严格超集，因此直接省略替换查询。这是合同推导，不是经验 topK 或时间阈值。

没有 alias 表、新状态、额外队列、定时重试或用户设置。实际 Maintenance/Cognition 入队后不长期保留未启动句柄；同步 Tool 及后台逐项处理在第一次 await 前 startWork。取消的旧任务不借用超集回执，后来重入旧材料会创建自己的 exact 工作。complete 回执、当前 Revision 过滤和 Q3B 处理器接续保持原语义，不把“来源已处理”说成“每条事实都记住”。如果将来产品新增长期持有未启动 workId 的调用者，必须重新定义这个边界。

## 输入预算、资源和能力边界

用户要求每次完整输入不超过258,000。两批真实最大usage分别5,123和4,873，最大完整wire保守估算21,887和21,347，unknownKinds为空，远离边界。可选input_tokens端点每Provider首次404后缓存不支持；成功请求有实际usage。估算不是精确tokenizer保证，模型后的usage也不证明任意未来大附件能预先精确计数。形成工作集16,384、Recall8,192是同臂一致的host预算，不是将磁盘历史塞满请求。

v8与v9真实模型阶段在此前本地模型退出后分别执行，各臂encoder依次关闭；未与已知重型资源实验重叠，普通系统及网络波动仍在。Node RSS不含encoder子进程，不能当全App上限。小型真实故事DB固定结构占主导，不能代替资源阶段容量数据。

本方案不消除未被严格覆盖的积压、不缩减already-started工作、不自动预测未来记忆价值、不按日历删除记忆，也没有解决canonical原文的长期回收。上述形成/Recall测量没有经过真实Cognition划分或Agent决定何时memory.search并最终采用；作者提出的RecallPlan不是Agent使用验收。长周期用户陪伴质量和冷话题跨Chat检索需单独验收。
