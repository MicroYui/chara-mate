# 05 检索与向量：索引怎么建，方案怎么选，结果说明了什么

一面追问“最初为什么用 FTS5，后来为什么改成三路”的演进与证据边界见[第 17 章第 5–7 节](17-memory-control-and-retrieval-evolution.md)。它把没存、没查、没召回和没选中分开诊断，特别说明28问没有证明结构化通道的增益。

本章回答一条完整链路：一条已经形成的记忆，怎样变成可搜索的数据；用户换一种说法提问时，怎样找出材料；材料已经找到了，为什么回答仍然可能出错。对应 R05、R09，学习后完成 A05、A09。

先记住当前实现：**SQLite 保存记忆正文、版本、全文索引和向量；本地 Qwen3-Embedding-4B 生成 512 维向量；独立 Worker 做精确余弦扫描；词法、语义和结构化查询合并出候选，再由语言模型挑选回答各个问题需要的证据。** 这里没有独立向量数据库，也没有采用 HNSW。

下面的性能与质量数字来自仓库已保存的实验记录，设备主要是 Apple M4 Pro、24 GiB 内存。它们不是本次文档修订重新运行的结果。

## 1. 从一个问题开始：为什么已经记住，还是回答错了

假设已经保存三条记录：

- 用户平时喜欢冰咖啡。
- 用户今天胃不舒服，想喝热饮。
- 用户的朋友喜欢拿铁。

用户问：“你觉得我今天应该点什么？”

单纯按相似度排序，三条都可能很靠前。真正需要回答的是：哪条属于用户，哪条只在今天成立，哪条描述朋友，以及当前建议应如何兼顾长期偏好和临时条件。检索系统要把这些区别完整带给回答模型，不能只返回一堆看起来相关的句子。

可以按下面的顺序排查漏答：

| 阶段 | 应检查什么 | 常见故障 |
| --- | --- | --- |
| 形成 | 原话是否变成正确的记忆，主体与条件是否保留 | 把朋友的偏好写到用户名下 |
| 建索引 | 当前版本有没有全文索引和所需模型的向量 | 新记忆已提交，向量任务仍在排队 |
| 触发 | 回答模型是否真的调用了搜索 | 只读当前聊天就回答“不记得” |
| 查询 | 问题有没有包含“今天”“用户本人”等必要条件 | 把有情境的问题改写成宽泛主题 |
| 召回 | 正确材料是否进入候选列表 | 同义改写没被词法匹配找到 |
| 选择 | 候选中已有正确材料，模型是否选了它 | 选了日常偏好，漏掉今天的例外 |
| 供给 | 所选材料是否进入最终生成请求 | 被上下文预算裁掉 |
| 使用 | 最终回答是否正确处理证据 | 读到“朋友喜欢”，仍说“你喜欢” |

项目中的 d01 失败发生在“触发”一层：记忆和 26 条索引仍然存在，模型却没搜索。后继修正中自然触发搜索，25 个候选里选出 13 项，才正确处理条件偏好；完整轨迹用了 7 次生成、71.066 秒、126618 个输入 token。这个结果说明问题被定位到调用链，但成本也明显存在，不能把它描述成一次毫秒级向量检索的成功。原记录见[本地验收](../../progress/LOCAL_MATURITY_ACCEPTANCE.md)。

## 2. “索引”在这个项目里具体指什么

很多面试回答会说“把记忆存到向量库”，接着就跳到检索。这会漏掉索引的数据身份、更新方式和恢复过程。

实际有三类访问路径：

| 路径 | 保存或组织的内容 | 适合回答的问题 |
| --- | --- | --- |
| 关系型表及普通索引 | 记忆归属、角色、实体、有效时间、版本关系 | “只查这个角色知道的、关于这个玩家的当前事实” |
| FTS5 全文索引 | 从记忆正文生成的词项及其对应版本 | “松柏咖啡馆”“订单编号”等明确名称 |
| 语义向量 | 每个正文分块对应的 Float32 数组 | “以前说的碰面地点”与“约在松柏咖啡馆”这样的改写 |

数据的权威仍是记忆正文和版本表。全文索引、分块和向量是根据正文重建出来的搜索数据。向量丢失可以重建；原始事实、来源和版本关系丢失，不能靠向量还原。

当前主要表如下，完整定义见 [cognitiveMemory.ts](../../../src/main/db/schema/cognitiveMemory.ts) 和 [current.ts](../../../src/main/db/schema/current.ts)。

| 表 | 关键内容 | 为什么需要 |
| --- | --- | --- |
| `memories` | 稳定记忆 ID、当前版本、生命周期 | 指明现在以哪一版为准 |
| `memory_revisions` | 不可变正文、前一版本及旧内容处置 | 固定模型当时实际读到的内容 |
| `memory_fts` | 词项、Memory ID、Revision ID | 搜索结果回到具体版本 |
| `memory_revision_semantics` | 主体、归属、时间、依据类型 | 查询资格和语义条件 |
| `memory_search_chunks` | 版本 ID、分块序号、正文、正文哈希 | 长文本分段及向量定位 |
| `memory_chunk_embeddings` | 分块 ID、模型标识、维度、向量字节 | 防止不同编码空间混用 |
| `memory_work` | 任务种类、目标、来源版本、处理器版本、状态 | 后台索引的排队、恢复与错误记录 |

向量表的主键是分块 ID 与模型标识，数据库还检查 `length(vector) = dimensions * 4`。512 维 Float32 向量恰好占 2048 字节。这只能证明字节长度符合结构要求，数值是否有限、范数是否为零还要由代码检查。

## 3. 新记忆提交之后，索引是怎样建立的

### 3.1 全文索引同步写入，向量任务先登记

在 [MemoryRepository.#indexRevision](../../../src/main/memory/memoryRepository.ts) 中，每次写入新版本会处理两件事：

1. 对这版正文运行 `memorySearchDocument`，写入对应的 FTS5 行。
2. 调用 `enqueueRevision`，把“这版内容需要编码”的任务写入 `memory_work`。

这些操作位于创建或修订记忆的事务内。事务提交后，正文、版本指针、全文索引和索引任务处于一致状态；不会出现用户看见记忆已保存，却没有任何持久化任务负责生成向量的情况。

这时不调用编码器。模型装载、分词和编码可能耗时，若放进 SQLite 写事务，会阻塞其他写入，也会让取消与故障恢复变得困难。

最初任务使用 `pending-model` 占位，绑定 Revision ID 和正文哈希。这样记忆领域不必在写正文时知道当前打包的模型已经装载到什么程度。

### 3.2 调度器把占位任务绑定到当前编码配置

[MemoryRecallRepository.scheduleIndex](../../../src/main/memory/memoryRecallRepository.ts) 根据当前 `modelKey` 找出缺少分块或对应向量的版本，创建具体编码任务，再删除该版本自己的占位任务。

任务身份包括目标版本、正文哈希和处理器版本。同一输入重复调度，不应产生任意多份相同工作。已有 pending、running 或 failed 任务时，调度器也不会擅自把它当成新任务重复加入；失败任务有明确的重试入口。

调度按 Revision 主键推进游标，每项用短事务登记，随后让出事件循环。若让出期间新版本的 ID 排在游标前面，它自己的占位仍然存在，下一轮可以发现它。这里不能在最后用一次“删除所有占位”来清理，否则会把尚未处理的新工作一起抹掉。

### 3.3 后台执行一次编码任务

[MemoryRecallPipeline.indexPending](../../../src/main/memory/memoryRecallPipeline.ts) 的执行顺序是：

```text
安排待索引版本
  → 以 pending → running 的条件更新领取任务
  → 按真实 tokenizer 分块
  → 调用本地编码器
  → 校验向量并提交分块、向量及完成状态
```

同一个流水线实例用正在执行的 Promise 合并重复唤醒。任务状态也必须条件更新成功才开始处理，不能只靠一个内存布尔值防重复。

取消时，将尚在执行的任务恢复为待处理；普通编码异常记为 failed，并保存错误类型。应用重启时，原来留在 running 的编码任务可以恢复为 pending。这里保证的是可恢复处理，不保证每个 GPU 计算只执行一次；即使重算了一次，只要最终写入按任务和版本身份提交，也不应生成重复知识。

### 3.4 编码结果返回时，再检查一次目标

`finishIndex` 在短事务内读取目标版本，确认它仍存在、所属记忆未删除、正文哈希仍与任务相符。确认后才写入：

- 每块的正文、顺序和哈希；
- 对应模型标识的向量；
- 任务完成状态。

如果新的分词方式改变了同一分块序号对应的文字，先清理该分块原有向量；如果新分块数减少，删除多余旧块。否则可能出现“第 2 块已经换成新文字，向量却还是旧文字”的隐蔽错误。

**旧版本不是一律拒绝。** 用户在编码期间创建了 r2，r1 本身仍是合法历史记录时，r1 的向量可以完成。是否可以拿 r1 回答当前问题，由查询时的版本资格决定。索引任务完成得晚，不会让它变成当前事实。

## 4. 全文索引怎样处理中文，BM25 在这里有什么限制

[memorySearchText.ts](../../../src/main/memory/memorySearchText.ts) 先做 NFKC 规范化、转小写，再用 `Intl.Segmenter` 按中英文词边界切分。纯汉字词还补相邻双字。例如分词器若把“松柏咖啡馆”作为一个词，会额外加入“松柏”“柏咖”“咖啡”“啡馆”。实际分词结果受运行时影响，不能把这个解释例子当成固定快照。

补双字的动机是降低中文边界不同造成的漏召回：查询只写“咖啡馆”，也可能与较长名称共享词项。代价是“柏咖”这类片段未必有独立语义，召回变宽之后需要后续选择处理噪声。

还有一个容易漏讲的实现细节：词项用 `Set` 去重，再连接成 FTS 文档。因此正文中同一个词出现十次，不会原样保留十次词频。这是当前实现，不应照着教科书声称 BM25 完整利用了原始正文词频。

查询也按同样方式规范化，把每个词项安全地组成引号项，再用 OR 连接。OR 有利于找到只匹配部分表达的候选；它不会自动理解“不能”“不是我”和时间关系。主体、有效时间、删除状态等条件由 SQL 资格过滤和后续证据选择处理。

概念上，BM25 会考虑词项稀有程度、出现频率和文档长度；在 SQLite FTS5 中，更相关的 `bm25()` 值更小，所以源码使用升序。数值不能直接与余弦相似度相加，因为两者尺度和方向不同。实现细节可核对 [FTS5 官方文档](https://sqlite.org/fts5.html)，本轮查阅日期为 2026-10-20。

## 5. 编码器究竟做什么：模型、量化、维度、分块分别影响哪里

这四件事经常被混成“模型大小”。

**模型参数量**决定编码器主干规模。0.6B、4B、8B 是约 6 亿、40 亿、80 亿参数；它们影响权重体积、推理资源和语义表征能力。

**权重量化**改变部署权重的表示。当前采用 Q4_K_M 格式的 4B 模型。它降低权重和推理资源成本，但当前写入 SQLite 的输出向量仍是 Float32，不能说“4 位向量”。

**输出维度**决定每个向量存多少个数。4B 原始输出为 2560 维，当前取前 512 维后重新做 L2 归一化。Qwen3 Embedding 支持 Matryoshka Representation Learning，简称 MRL：训练时使向量前缀也能承担表征任务。因此可以评估不同前缀长度；普通模型未经这种训练，不能随意截断后假定效果保持。[Qwen 官方模型卡](https://huggingface.co/Qwen/Qwen3-Embedding-4B)

**分块**决定一段长正文编码成几条向量。分块太大，局部事件可能被整体主题稀释；太小，代词和条件可能失去上下文，索引数也增加。当前实现首先受真实本地 tokenizer 和已分配上下文限制，再尽量靠近句子边界切开，保持原文顺序，不做固定字符截断。

L2 归一化可以写成：

```text
u = 原始向量的前 512 个分量
v = u / sqrt(sum(u[i] * u[i]))
cosine(q, v) = dot(q, v) / (norm(q) * norm(v))
```

取短前缀后必须重新求范数。只截前缀却继续假设范数为 1，内积排序可能改变。源码仍按完整余弦公式计算，并检查非有限值、零范数和维度不一致；这些检查属于数据正确性，不代表每个语义匹配都正确。

## 6. 本地编码器的输入与部署细节

[LocalEmbedding](../../../src/main/providers/localEmbedding.ts) 对查询加一条任务说明：需要找到能回答个人记忆问题的材料；文档直接编码正文。查询和文档职责不同，不能为了“保持一致”把查询说明也拼到每条记忆里。

长文切分使用真实 tokenizer。由于 BPE 长度对字符前缀并非严格单调，代码寻找的是一个满足限制的前缀，不保证数学上最长；每个实际编码的块仍重新检查。当前切块没有人为重叠，切完应能按顺序拼回原文。若以后增加重叠，必须比较条件丢失、重复候选和索引成本，不能说固定重叠 20% 就是最佳方案。

实际部署还遇到过特殊标记问题：用户正文中的字面文本 `<|im_start|>`，走字符串接口时可能被解释为控制标记，导致 token 和向量变化。实验中同一段文字两条路径的相似度明显偏离。因此现在先以 `parse_special=false` 分词，再把准确 Token ID 交给 embedding 接口。这确保编码的是用户写的文字，而不是另一段经过特殊解析的序列。

[localEmbeddingResources.ts](../../../src/main/providers/localEmbeddingResources.ts) 生成的 `modelKey` 包含权重哈希、引擎版本、维度、查询说明、上下文分配、pooling、归一化和特殊标记处理方式。改了这些语义配置，应进入新的索引空间；即使新旧向量长度都是 512，也不能混在一起比较。线程数和批处理调度参数则不属于语义身份。

当前资源清单支持的是 darwin/arm64。历史证明的是 Apple Metal 打包、装载和退出，不意味着这份 Windows 工作区已经有可运行的相同本地模型发布物。

## 7. 选型经历了哪些阶段，为什么早期结论和当前实现不同

项目并非一开始就决定“必须混合检索”。

2026 年 8 月的实验比较了全文检索、0.6B 语义检索和两者融合。中文确认集上语义方案有收益，但在 LoCoMo 上融合反而退化；最终回答小样本只多答对一题，新增模型和资源成本却很明确。因此当时选择纯全文检索。

| 8 月确认集 | 全文检索：前 8 项至少命中一条所需证据 | 混合检索：同一指标 |
| --- | ---: | ---: |
| LongMemEval，60 题 | 56/60 | 57/60 |
| LoCoMo，1125 题 | 664/1125 | 618/1125 |
| 中文产品集，39 题 | 32/39 | 38/39 |

随后同一回答模型读取相同证据预算，22 道题中全文方案答对 16 题，混合方案答对 17 题；全文方案的 22 份回答全部有证据支持，混合方案有 1 份被判依据不足。22 题不足以证明整体优劣，但足以说明“召回提高多少”与“回答实际好多少”必须分别测量。[8 月检索决定](../../benchmarks/memory-retrieval.md)

到了 9 月，产品对条件偏好、人物归属、历史修订和连续经历的要求更明确，重新建设了问题驱动的混合候选、证据选择及本地编码路径。这是后继设计和新实验形成的选择。介绍当前系统时必须讲 9 月的实现，复盘早期研究时保留 8 月结果；不能把两批不同任务和不同实现拼成一个“统一提升百分比”。

这段经历适合回答：“你为什么不用最初选好的方案？”需求和代表性数据发生变化，应重新比较；保留旧实验是为了知道改变的理由，而不是让旧结论永久限制后续设计。

## 8. 4B 与 8B 到底怎样比较

### 8.1 先确定比较对象与数据

9 月实验冻结了 60 篇文档、28 个问题，来自 20 个故事或人物关系组。包含人物混淆、时间变化、纠正、计划与结果、同一应用中的不同任务等对照。材料来自开发场景，未读取独立留出测试集的标签。

首先测试原始维度，再用同一批真实向量比较不同 MRL 前缀。这里的 top1 表示第一条是否命中，top5 表示前五条是否命中；“前二十项覆盖全部证据”要求一个问题需要的多条材料都在其中，不是只命中一条即可。

| 配置 | 第一条命中的问题数 | 前五条命中的问题数 | 前二十条包含全部必要材料的问题数 | MRR |
| --- | ---: | ---: | ---: | ---: |
| 4B，512 维 | 20/28 | 28/28 | 28/28 | 0.838 |
| 4B，1024 维 | 21/28 | 27/28 | 28/28 | 0.852 |
| 4B，2560 维 | 22/28 | 27/28 | 28/28 | 0.870 |
| 8B，512 维 | 22/28 | 27/28 | 28/28 | 0.866 |
| 8B，1024 维 | 23/28 | 28/28 | 28/28 | 0.905 |
| 8B，4096 维 | 22/28 | 28/28 | 28/28 | 0.876 |

MRR 是“第一条正确结果排名的倒数”的平均值：第一名贡献 1，第二名贡献 1/2，没有命中贡献 0。它看排序是否靠前，但无法单独衡量多条证据有没有找齐。上表来自开发集，不能据此宣称 512 维普遍优于更高维；小样本波动、任务分布和多个比较都可能影响次序。

### 8.2 再通过实际候选流水线比较

真正回答问题时，不是只拿前五条。实验让两套配置通过同一份 SQLite 数据、资格过滤、当时的融合方法、来源装配与预算裁剪。最终证据预算为约 8000 token，候选阅读预算约 32000 token；每题实际送入选择模型的是 45–46 项，并非把全部 60 项无条件发送。

最终选取两套部署配置：4B 配 512 维，8B 配 1024 维。每个问题分别调用一次相同的 gpt-6-astra 证据选择模型，共 56 次；按题交替执行先后顺序，避免所有小模型结果总是先跑。

“证据选择模型”在源码里叫 selector。它的工作是从候选中挑出回答需要的材料，并说明每个问题的证据是否充足。这一步还没有生成面向用户的完整答案。

| 最终比较 | 4B，512 维 | 8B，1024 维 |
| --- | ---: | ---: |
| 候选列表已包含全部必要材料 | 28/28 题 | 28/28 题 |
| 按实验开始前的标注，最终选齐必要材料 | 27/28 题 | 27/28 题 |
| 调用或输出协议失败 | 0/28 | 0/28 |
| 证据选择耗时中位数 | 4.575 秒 | 4.435 秒 |
| 证据选择耗时第 95 百分位 | 7.216 秒 | 7.250 秒 |
| 28 次选择的实际输入 token 合计 | 302459 | 302622 |

**27/28 的正常说法是：28 道题中，两套配置各有 27 道题选齐了预先标注的必要证据。** 这不是“模型回答准确率 96.4%”，因为本实验主要检查最终证据集合，没有据此证明全部自然语言回答正确。

### 8.3 两套方案共同漏掉的那道题是什么

原问题只问“本人喜欢的放松活动”，标注要求找到摄影偏好被纠正的记录。但库里另有一句明确自述：“喜欢船，在海上最放松。”两套方案都选择了后者，它也能回答表面问题。

实验记录仍保留 27/28。随后只给问题补上“替表妹挑摄影课曾被误认成自己的爱好”这一情境，保持原候选不变，两套方案都选到纠正记录。这说明缺少情境会影响选择；不能为了得到漂亮数字，事后把原问题改掉并将正式成绩写成 28/28。

这一反例也解释了为什么当时没有继续做 embedding 微调：目标材料已经进入候选，改编码器无法自动补回提问中缺失的约束。

### 8.4 为什么最后选 4B、512 维

资源差异不是抽象的“更省”。

| 实测或固定资源 | 4B | 8B |
| --- | ---: | ---: |
| Q4_K_M 权重文件 | 约 2.50 GB | 约 4.68 GB |
| 短文两条一批的预热后编码中位数 | 142.1 ms | 211.7 ms |
| 同条件第 95 百分位 | 180.1 ms | 284.4 ms |
| 短文测试采样的模型进程最高 RSS | 约 3.13 GB | 约 5.32 GB |
| 独立 2048-token 长文、相同较小批处理分配 | 3.237 秒 | 5.643 秒 |

选择理由是：**在这批任务及实际候选预算下，两套方案的必要证据覆盖相同，而 4B 的部署和推理成本更低；512 维进一步减少向量存储及扫描工作。**

边界也要主动说明：样本只有 28 题，且来自 20 个相关来源组；最终比较同时改变模型和维度；0.6B 没有完成同条件的最终证据选择实验。因此可以说“本轮证据支持采用 4B/512”，不能说“已证明这是所有模型中最小、最优的组合”。完整记录见 [LOCAL-MEMORY-ENCODER](../../benchmarks/LOCAL-MEMORY-ENCODER.md)。

## 9. 一次查询怎样把三路结果合起来

[MemoryRecallPipeline.recall](../../../src/main/memory/memoryRecallPipeline.ts) 先验证查询计划，再执行检索。

例如“为本周见面安排地点和饮品”，应该至少拆成两个信息问题：当前日期、时间和地点；本人饮品偏好及本次例外。问题 ID 用于之后检查有没有漏答，并不意味着每个问题都启动一个独立 Agent。

执行顺序可以概括为：

1. 检查角色、记忆归属、明确实体、时间范围及已知精确引用。
2. 为每个信息问题分别取得词法与语义候选，必要时加入结构化候选。
3. 按各列表的排名轮流取结果，按 Revision ID 去重。
4. 优先安排明确引用和各通道的重要起始候选，再按实际序列化预算装入正文与来源。
5. 由语言模型选择证据，逐题返回充分、部分支持或缺少材料。
6. 有缺口时，可沿既有修订关系或共同来源扩展一次；有新材料才重新选择。
7. 对最终所选版本重新读取、测量消费者实际请求大小，再次核对版本资格。

显式实体过滤与作为线索的实体候选是两回事。“只查询玩家 A”应限制范围；从当前界面猜到的某个实体，只能帮助找材料，不能自动把其他必要证据全部排除。

预算也分两层：候选阶段可以读得比最终答案需要更多；最终供给必须适合真正消费者。默认候选预算为 `min(32000, 最终证据预算 × 4)`，调用方还可以提供明确分配。这个数来自当前工程成本边界，现有实验没有证明“四倍”普遍最优。

另一次真实形成库比较固定最终预算 8192，只将候选预算从 8192 增到 32000：小池送入 7 项、选 3 项，大池送入 11 项、选 5 项；输入分别 3283 与 5133 token。两组都足以回顾主要任务，大池补充了一些失败和状态背景，也不是小池的纯超集。这个单问题结果说明多花 1850 token 能多看到什么，不能证明全局扩大或缩小预算必然更好。[融合与额度记录](../../benchmarks/MEMORY-RANK-FUSION.md)

## 10. 为什么把 RRF 换成按列表轮流取候选

RRF 把一个候选在多个列表中的排名转换成分数再相加，常见形式为 `sum(1 / (k + rank))`。它不要求不同通道的原始分数处在同一尺度，是合理基线。

但在本项目里，一些宽泛背景同时出现在词法和语义列表，会积累两次分数；一条仅被语义通道找到、却直接回答问题的记录，可能因此被挤到很后面。当前轮流取候选的方法，让每个列表按自己的次序贡献下一项，共同命中的记录只占一个位置，不额外加权。

这并非纯理论猜测。历史诊断中，一条当天原话在语义列表排第 3、没有词法命中；RRF 合并后排第 31，交替取候选时排第 5。另一条搬城记录从第 45 变成第 8，在较小候选预算下能够进入模型可见范围。

主比较的 28 道题，两套融合都选齐 27 题的预标注材料，没有总体领先。另有三个问题在不同较小预算下形成五组诊断条件：RRF 最终保留 2/7 个预标注材料实例，交替融合保留 7/7。这里的七个是重复预算条件下的材料实例，不是七名玩家；五组条件也不是五次独立最终问答获胜。

因此选择交替融合的依据是：主比较没有显示必要材料退化，部分预算压力下保住单通道的重要材料，并且删除了分数累加和 RRF 常数。它也有代价：不再奖励多通道一致性，低质量通道仍可能占位置。后续若问题分解或语料改变，应重新测量。来源见 [MEMORY-RANK-FUSION](../../benchmarks/MEMORY-RANK-FUSION.md)。

还要限定这份证据的适用范围：本批 28 个查询计划各只有一个信息问题，没有实体/时间结构候选和跨记忆关系，也没有显式引用输入。当前实现支持多问题轮转，但这次真实模型比较主要验证通道覆盖，不能据此宣称多问题预算分配已经全面验证。长正文、大库和更复杂关系需要另外比较。

## 11. 为什么当前做精确扫描，Worker 又解决了什么

`searchMemoryVectors` 逐块计算查询向量与文档向量的余弦相似度。一个 Revision 有多个块时取最高分，防止同一条长记忆占据多个返回位置；用容量受限的堆保留最好的 K 个版本，同分以 ID 稳定排序。[扫描实现](../../../src/main/memory/memoryVectorSearch.ts)

若实际扫描 N 个块、每块 d 维，主要计算约为 `O(Nd + N log K)`，堆与位置表约 `O(K)`。这只描述算法保留的候选状态，不包括数据库页缓存、模型权重和 Electron 内存。

取最高块分数有明确取舍：一句局部约定埋在长文里时容易找到，但一个偶然相似片段也可能让整条记忆靠前。因此最终选择阶段仍读正文与条件，不能把最高相似度直接当事实置信度。

同步 SQLite 和 JavaScript 扫描放在 Electron Main，会让 UI、IPC 和取消响应一起等待。当前使用单个常驻 Worker、独立只读 SQLite 连接，读取时先应用范围与版本资格，再流式扫描。模型编码进程和向量扫描 Worker 是不同资源：前者生成向量，后者读库比较已经存在的向量。

| 512 维合成负载 | Main 直接扫描 | Worker 扫描 |
| --- | ---: | ---: |
| 10000 条，一问 | 90–101 ms | 91–157 ms |
| 100000 条，一问 | 852–877 ms | 903–958 ms |
| 100000 条，三问 | 2.45–2.65 秒 | 2.41–2.81 秒 |

每格只有三次测量。Worker 的价值主要是把扫描期间 Main 的事件循环延迟压到毫秒范围，并非让一秒计算变成零成本。三问顺序扫描仍约 2.4–2.8 秒，之后还要付查询编码和证据选择的时间。

十万条、512 维向量的纯数组为 204.8 MB；这一批实验数据库约 524.7 MB。另一批带多个历史版本、原文和来源结构的容量实验最终数据库约 850.80 MB。两者负载不同，不能拿一个充当另一个的存储增长曲线。[编码器记录](../../benchmarks/LOCAL-MEMORY-ENCODER.md)、[Worker 记录](../../benchmarks/MEMORY-VECTOR-EXECUTION.md)

Worker 内查询看到的是读取时的数据库快照。查询期间新记忆提交，不要求正在扫描的快照半途变更；下一次查询应看到新提交，最终证据输出还要做版本资格重读。测试因此同时检查“本次快照保持一致”和“下次可以看到新版本”。

## 12. 十万条索引准备卡死：一个完整的性能故障

这次失败发生在编码器启动之前。旧调度查询由 memories 的索引驱动，再按 memory_id 取 Revision，每次寻找下一项还需要临时排序；整个调度循环又位于 Main 的同步处理过程中。结果是长时间没有事件循环回调，取消信号也无法及时被处理。把责任归给 4B 模型会修错地方。

定位方法是保留原数据库和进度，检查 SQLite 查询计划。旧查询的前三次读取分别约 26.5、27.3、27.8 ms；由于旧全量没有正常完成，不能据此外推“新方案快了多少倍”。

修复改成按 Revision 主键范围推进，关联条件用 EXISTS，单条任务短事务提交后让出事件循环。相同十万条合成数据的完整调度约 13.130 秒，生成十万条待办，正文哈希一致。已有完整索引后新增一版，调度约 144.92 ms，其中首次资格检查仍占约 138.82 ms：这是真实剩余成本，不应写成“彻底无阻塞”。

后续在原负载中实际调用 4B，十万条 Revision 的编码与索引准备耗时 10003.784 秒，正常结束。它证明这批索引实际完成，不证明十万条内容的语义检索质量，也不证明普通用户每次启动都需要重建全部向量。[故障与调度修复](../../benchmarks/memory-storage.md)、[后续真实索引完成记录](../../progress/LOCAL_MATURITY_ACCEPTANCE.md)

面试被问“你做过什么性能优化”时，这个案例比“加了 Worker”更完整：先区分等待模型和本地 SQL，检查查询计划，再改访问顺序和事务长度，最后报告完成时间与仍有的同步成本。

## 13. 什么时候才考虑 HNSW、向量数据库或训练检索器

这些是后续方案，当前没有实施。

HNSW 用分层近邻图逐步接近相似结果，通常用更多内存与维护成本换取较少距离计算；搜索范围参数影响速度与召回的取舍。它是近似搜索，不能承诺与精确扫描永远一样。[HNSW 原论文](https://arxiv.org/abs/1603.09320)

应先保存同一批查询的精确扫描结果作对照，再比较近似搜索的必要证据覆盖、最终答案、插入和删除成本、内存、构建时间与尾延迟。玩家范围、角色知识、时间和当前版本的过滤也必须参与实验：全库先取 K 条再过滤，可能剩下零条，尽管范围内实际有好结果。

独立向量数据库适合需要独立扩缩容、多用户隔离和较高查询吞吐的部署，但它还增加数据库之间的一致性、删除传播、运维与失败恢复问题。桌面单机当前没有这些收益证据，不为名称更“专业”而引入。

训练编码器之前，要确认正确事实已经形成、查询情境充分、范围过滤正确，必要材料仍经常落在实际候选预算外。训练样本应是问题、正例及困难负例；同一个人不同时间、不同人同一偏好、被纠正旧事实都是有价值的对照。能够共同回答问题的材料不能随意标为负例。

如果微调改变编码空间，需要新模型标识和重新编码。发布用的 Q4 GGUF 不能直接当成常规梯度训练底座；应在独立训练环境处理原始权重及适配，再转换部署。当前没有已经完成的训练收益可引用。

## 14. 面试中的连续回答与练习

“为什么用 4B？”先说明实际候选覆盖和证据选择结果，再讲权重、内存、长文编码成本；最后说明样本范围及 0.6B 未参加最终比较的限制。

“512 维为什么够？”回答这是针对支持 MRL 的模型进行过比较后的部署取舍，并非通用维度；补充存储与扫描减少、主干前向计算不因此减少。

“向量还没生成怎么办？”说明全文索引随版本同步提交，精确引用也可读；当前用户输入仍可支持本轮回答，但自然语言改写的语义召回可能不完整，应如实报告缺口。

“怎么证明换融合有用？”区分主比较无总体差异与较小预算诊断中材料位置变化，说明只改融合函数、其它环节保持一致，不能把证据覆盖直接叫答案成功。

“百万条怎么办？”先估算按玩家与时间过滤后实际扫描的块数、查询到达率、排队和多问题成本，再比较缓存、一次遍历计算多个查询、分片或 ANN。百万个全库版本与一次查询要扫描百万块不是同一件事。

完成本章应交付三样东西：一张从 Revision 提交到向量入库的时序图；一张能解释每个分母的选型表；一份能定位形成、召回、选择、供给、回答任一层故障的诊断记录。仅记住“混合检索加 RAG”不算掌握。
