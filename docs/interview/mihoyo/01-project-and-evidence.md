# 01 项目定位与事实口径

对应 R02、R09、R10；验收 A01、A14。基线与证据标签见 [README](README.md)。

## 1. 面试中这个项目最值得讲什么

CharaMate 是本地桌面 AI 陪伴应用。它的工程价值是把对话、工具执行、连续认知与长期记忆放进可追踪的生命周期：角色依据什么行动，用户纠正后哪些依据过时，已经完成的外部动作如何保留，后台记忆怎样在后续会话中重新发挥作用。这些问题能够迁移到游戏 NPC；导航、游戏服权威状态、多人会话与剧情调度则需要新增设计。

建议的 90 秒表述，个人职责按真实经历替换：

> 我做的是一个桌面 AI 陪伴项目，核心问题是让角色在多轮交互与环境变化中保持连续性。文字、语音和自主行动共享 Run/Item 执行合同，文字与原生语音使用不同模型驱动，执行过程包含工具、审批、中断与恢复。认知层维护带证据的 Claims、Intent 和 Choice，长期记忆则有形成、修订、检索和失效机制。
>
> 我参加过相关学术交流，之后对 NPC 如何注意环境、维持目标和更新记忆产生了兴趣。这是研究动机。工程上我没有直接把脑区映射成一组 Agent，而是研究哪些功能值得显式建模。例如，分析提交检查本轮已读实体的版本，实际行动只绑定必要的事实和目标，避免无关变化反复取消行动。
>
> 我最愿意展开的是用户纠正旧约定后，当前对话、异步记忆形成、索引、召回和自主行动如何处理版本变化。项目有本地测试和实验记录，也有召回未触发、长上下文成本高等失败。大规模线上数据飞轮、多人游戏服务端与长期玩家实验是下一阶段方案，我会说明怎么建设和验证。

不要把“我知道这个团队的内部架构”当作开场。用户提供的团队背景可以作为沟通背景，公开材料能证明什么就在第 10 章限定到什么。

## 2. 系统地图与岗位对应

| 岗位关键词 | 当前工程对应 | 可以展示的能力 | 边界 |
| --- | --- | --- | --- |
| Planning / Tool Use / Action | Agent Runtime、Plan Item、Tool Registry、Approval | 多轮工具闭环、Steering、真实效果和恢复 | 没有强制每次先启动独立 Planner |
| State Tracking / 自主决策 | Cognition 的观察、断言、意图、注意状态和行动依据 | 过时分析拒绝、当前观察与历史回忆区分 | 不代表实现人脑或通用自主智能 |
| Persona | 角色快照及上下文编译 | 表达风格、动机、知识边界 | Persona 不能覆盖事实和执行约束 |
| Memory / RAG | Formation、Revision、EvidencePack、混合候选与选择器 | 条件化事实、历史处置、可溯源召回 | 存储成功不等于形成成功，索引成功不等于回答正确 |
| Reflection | 运行反馈、认知更新、Experience Review | 从证据提出记忆或 Skill 候选 | 不是在线更新基础模型权重 |
| 游戏 NPC | 当前能力的迁移设计 | 事件驱动、选择性注意、行为前置条件 | 咖啡馆方案尚未实现为游戏服 |
| 数据闭环 / Eval | 本地测试、Decision、验收、局部经验复盘 | 可复现、分层归因、保留失败 | 没有可宣称的大规模线上玩家数据飞轮 |

阅读代码按实际因果路径走：

1. [AgentRuntime](../../../src/main/agent/agentRuntime.ts)：一个 Run 怎样开始、等待、接收纠正、调用工具和结束。
2. [CognitionService](../../../src/main/cognition/cognitionService.ts) 与 [CognitionRepository](../../../src/main/cognition/cognitionRepository.ts)：观察如何转为带依赖的分析。
3. [MemoryFormationService](../../../src/main/memory/memoryFormationService.ts) 与 [MemoryRecallPipeline](../../../src/main/memory/memoryRecallPipeline.ts)：长期知识如何形成并被使用。
4. [CognitionRuntime](../../../src/main/app/cognitionRuntime.ts)：认知决策怎样回到唯一 Agent Runtime，怎样在发布前复查。
5. [本地成熟度验收](../../progress/LOCAL_MATURITY_ACCEPTANCE.md)：哪些真实链路跑过，哪些失败还不能外推。

### 2.1 用一次真实需求把目录串起来

假设用户说：“帮我整理周五的安排，之后提醒我。”不要先背所有模块。按以下路线解释每个模块为什么出现：

1. 输入进入对话与执行系统，建立任务身份和过程记录。模型可以回答，也可以提出工具调用；两种输出都属于同一用户任务的可见过程。
2. 当前对话获取已提交的角色和认知上下文。认知层可以保留当前目标和有依据的状态，但普通输入不必先经过一个额外的心理分类模型。
3. 若任务需要过去的安排，系统调用记忆检索，带着具体问题读取合法证据；不能因为记忆数据库存在，就假定所有任务自动知道全部历史。
4. 需要执行的操作经过工具与审批边界，真实结果进入后续模型步骤。模型说“完成了”不能代替工具回执。
5. 交互中出现值得保留的经历，通过明确接入路径进入记忆形成；原始来源、修订和后台进度各有生命周期。
6. 如果之后用户说“改到周六，不用再提醒”，当前输入立即影响旧任务与行动资格，长期记忆异步更新不能成为及时响应的前置条件。
7. 下一次会话检索时使用新事实；若询问过去如何安排，可以在历史规则允许的范围内解释旧版本。

每一步都能继续追问“读了什么、写了什么、等待什么、谁能中断”。这比介绍十个目录名更接近真实研发能力。

### 2.2 数据不是都放进一个大上下文

| 数据 | 主要用途 | 变化方式 | 容易犯的设计错误 |
| --- | --- | --- | --- |
| 当前输入与运行状态 | 决定正在做什么、是否继续 | 随新输入和执行事件更新 | 等后台记忆写完才响应纠正 |
| 认知工作状态 | 保留跨事件的目标、判断与注意 | 有依据地分析和提交 | 把推断直接当用户事实 |
| 长期记忆 | 跨会话保留经历和知识 | 有来源地形成、修订和检索 | 只有一段随时覆盖的摘要 |
| 角色设定 | 表达、动机和背景边界 | 由明确配置或接受流程修改 | 用人设覆盖真实效果或当前拒绝 |
| 工具效果 | 说明世界实际上发生什么 | 由执行端确认并记录 | 把计划文本当完成证据 |
| 经验候选 | 提出下一次可以怎样改进 | 草稿、复核、接受与版本检查 | 模型自评通过就直接改产品 |

这些对象会一起影响回答，但不是同一种状态。共同进入提示词并不意味着它们可以共用一套修改规则。

### 2.3 单机架构为什么既有优势，也有边界

本地 SQLite 使某些跨模块交接可以在一个事务中完成，例如记忆工作入队与交接确认；它还便于保存精确修订和恢复进度。代价是同步数据库操作仍可能阻塞主线程，大模型与向量扫描也需要考虑设备资源。

迁移到游戏后，单机事务优势不会自动延伸到模型服务、房间服务器和记忆服务之间。先决定谁拥有当前世界状态，再设计持久化投递、去重与提交检查；不要把“加消息队列”当作原子性已经解决。第 09 章专门处理这个变化。

## 3. 必须分清的四类证据

**源码证据**证明某条路径存在，不能单独证明所有条件下都可靠。**确定性测试**证明给定模型替身和时序下的不变量，不证明真实模型一定选择正确工具。**真实模型实验**受任务集、模型、设备和版本约束。**真实用户长期实验**才更接近体验与留存；当前不能用前三类冒充第四类。

同理，产品设计是意图，旧研究文件是候选，较新的已接受 Decision 和当前源码决定实际采用什么。项目的历史文档可能同时出现 RRF、不同编码器、不同注意力结构；这不代表产品保留多个运行模式。

### 3.1 遇到矛盾文档怎样判断

比如早期研究介绍一种排名融合方式，后来的实验决定使用按问题轮转，当前源码也已经改变。正确做法是把早期方案放在历史比较中，按照较新的已接受决定和代码讲当前行为，而不是说“我们支持两种模式”。

如果设计写应当发生，源码没有对应路径，测试也没有覆盖，只能把它称为设计目标。如果测试覆盖的是假模型条件，就说明它验证了宿主合同；真实模型是否按预期使用工具，还要看真实调用记录。把这些证据层级分清，面试官就能判断你知道结论在哪些条件下成立。

### 3.2 每个重要结论准备一条证据链

可以用四行笔记：

```text
主张：用户纠正后，旧自主行动不能继续发布。
代码：谁记录接收顺序，谁在提交/发布时检查实际依赖。
测试：在哪个异步等待位置插入纠正，断言哪个结果被拒绝。
限制：已经曝光的片段和已完成的外部效果不能倒退。
```

再做一张实验笔记：

```text
问题：更大的编码模型是否改善真实证据选择。
比较：相同语料和问题，模型/维度配置与固定后续选择流程。
结果：候选覆盖、最终选择、资源代价分别报告。
限制：小开发集、标签歧义、未测最终答案，不宣称一般最优。
```

一条源码路径回答“如何实现”，一份实验回答“为什么这样选”。两者不能互相代替。

## 5. 三个可以讲成“研究故事”的案例

**案例一：记忆存在，却没有被使用。** 从“回答错”追到模型没调用 `memory.search`，而不是候选质量差。修复目标是调用时机和问题覆盖，再衡量新增 token 与延迟。展示你会定位因果链，不是只会更换模型。

**案例二：更像认知理论的结构未必更好。** [COGNITION-APPRAISAL-MODELING](../../benchmarks/COGNITION-APPRAISAL-MODELING.md) 增加 Appraisal，局部改善未转化为端到端改善，输入输出成本上升且实现增加 15 个候选文件。保留简单结构的依据是现有任务证据与复杂度，不是宣称理论错误。

**案例三：降低过时行动，又不把角色变成永远无法行动。** 全依赖检查适合分析提交；行动阶段只依赖选定目标、事实、对象和回忆。无关背景更新不必撤销行动，但用户纠正、目标替代和当前对象变化必须阻断。测试既要覆盖“该取消”，也要覆盖“不该取消”。

讲故事使用：具体失败 → 排除的假设 → 改动位置 → 公平比较 → 残余问题。不要使用“世界领先”“SOTA”“生产验证完美”替代证据。

### 5.1 把第一件事讲成可追查的失败复盘

现象是用户问长期偏好，回答没有使用已有记忆。第一种直觉可能是向量模型不够强，但记录显示原始记忆和 26 条索引仍在，失败发生在没有调用记忆搜索。

排查顺序是先确认来源与存储，再看是否触发检索，然后才看候选。后续覆盖修正场景中，系统自然发起搜索，得到 25 个候选并选择 13 个，能使用带条件的偏好。这个结果支持“补上了这条使用链路”，没有证明检索本身已经全面解决。

代价也要同时说：该完整轨迹耗时 71.066 秒，包含 7 次生成和 126618 个输入 token。不能用改善后的回答掩盖较高成本，更不能将总时间当作向量查询时间。下一步应分解调用、重复上下文和选择开销，再做保持质量的比较。原始证据见[本地成熟度验收](../../progress/LOCAL_MATURITY_ACCEPTANCE.md)。

### 5.2 复杂认知方案为什么被放弃

研究问题不是“情绪重要吗”，而是“额外显式建模某种评估结构，是否让当前角色行为更好”。比较使用相同连续故事输入，观察局部决策和完整执行链。

复杂方案在 16 个检查点上多通过 1 个，但完整流程没有改善；输入和输出用量分别增加约 10.29% 和 10.92%，候选实现还增加 15 个文件。这个时候保留更简单的方案，是对当前任务收益不足的判断。

如果未来发现某类角色误解反复出现，可以提出新的结构和实验。拒绝一次候选不等于永久禁止相关理论；研究能力体现在能说明新证据是什么，而不是一开始偏好复杂架构，后来一直为它找理由。

### 5.3 正确性优化也要测试“不该取消”

旧行动应该被用户纠正阻断，但不能因任意后台更新都失效。例如角色已经决定提醒即将开始的会议，后台记录了一次无关窗口变化；如果动作绑定整个全局状态版本，就可能永远没有执行窗口。

因此要区分两次提交：认知分析修改一组状态，需要核对本轮已读情境和意图的版本，防止覆盖它们的新状态；一个已选行动只使用部分事实和目标，应该检查这些实际依赖。依赖还包含相关支撑与反证，不能只比较最终句子。

测试至少有成对场景：会议取消必须拒绝；无关窗口变化应保留。只测前者会推动系统越来越保守，看似“更安全”，实际上失去正常响应。这是稳定性与可用性需要一起定义的例子，详见第 03、06 章。

## 6. 面试官质疑与回答

**这只是拼 API 吗？** 模型生成只是一个依赖。工程难点在于跨多次模型调用、数据库提交、外部效果、当前用户输入和后台工作的约束：哪些可重试，哪些不可重放，依据变更后如何拒绝，如何区分模型说成功与真实成功。用第 06 章的具体竞态回答，避免泛谈“有架构”。

**你个人到底做了什么？** 按真实情况明确需求、方案、代码、实验、工具辅助和自己能够解释的部分。准备一处自己能现场改写的核心函数或伪代码、一份自己读得懂的失败轨迹。仓库总测试数不等于个人贡献。

**如果今天重新做，你先砍什么？** 先保留唯一 Runtime、证据和版本边界、可回放评测；按目标体验决定是否需要自主生活、复杂感知和技能复盘。没有相应收益证据时，不加多脑区 Agent、关系分数或通用图数据库。

完成本章后，能够在 90 秒内介绍项目，在另 90 秒内主动说明一个失败和一个未建设能力。下一章沿一次真实 Run 展开。
