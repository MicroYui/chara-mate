# 07 工具、语音与反思：从模型提议到真实效果，再到可复用经验

一面语音深挖见[第 18 章](18-voice-duplex-interruption-and-asr.md)：当前原生音频与转写的关系、完整连接／回合／工具流程、打断和播放身份、全双工边界、真实故障及“一起／仪器”错误如何处理。

这一章讨论三个连续问题：模型怎样找到并正确调用工具；语音交互为什么需要额外的轮次与播放状态；任务结束后，哪些经验值得保存，怎样避免把一次偶然成功变成错误规则。对应 R01、R02、R06、R07，验收 A02、A07、A12。

## 1. 一次工具调用应拆成六个检查点

用户说“打开昨天整理的文件”，模型需要先知道文件能力存在，再拿到准确参数格式，确认当前入口允许调用，绑定实际文件目标，等待工具返回，最后根据结果继续回答。

| 检查点 | 失败示例 | 应修复的层 |
| --- | --- | --- |
| 能力可见 | 有文件工具，模型却说无法访问文件 | 工具发现和上下文 |
| 参数合同 | 把文件名放进目录字段 | Schema 与调用表达 |
| 使用范围 | Chat 入口调用写文件 | 执行模式过滤 |
| 当前条件 | 用户刚撤销操作，旧调用继续开始 | 输入版本与审批绑定 |
| 执行效果 | 请求被接受，但文件未写完 | 执行器和结果合同 |
| 结果理解 | 工具已报失败，模型仍说成功 | 下一轮上下文与模型评测 |

把所有失败归为“幻觉”，就无法知道应改模型、发现算法还是宿主代码。

[ToolRegistry](../../../src/main/tools/toolRegistry.ts) 统一工具描述和调用边界。内置能力、MCP、Skill 和应用适配可以遵循不同外部协议，但最终进入同一 Run/Item 与执行合同。工具效果和幂等性由能力定义，不能让模型在参数里自称“这是只读”。

## 2. 为什么常用工具直接给，长尾工具先搜索

把几百个完整工具 Schema 放进每次请求，输入成本高，也可能增加选择干扰。全部工具都先搜索，则会让简单动作也依赖发现质量。

当前折中是：`file.list/read/search/write/patch/trash` 和 `command.run` 这七个核心原语，按执行模式过滤后直接提供完整合同；其他长尾工具先提供元数据，命中搜索后才加载详细参数。发现阶段使用元数据 BM25，当前最多返回八项。八项是本项目选择，不是 MCP 的协议上限，也不是长期记忆的候选数量。

这个边界来自实际失败：要求列出当前目录时，中文搜索没找到 `file.list`，模型错误声称没有文件访问能力。工具本身存在，权限也未拒绝，失败发生在它根本没拿到 Schema。修复是让稳定核心能力直接可见。[发现决定](../../benchmarks/tool-discovery.md)

后来还修正了明确名称与范围顺序：用户明确提某个工具时，不能让“描述里提到它”的别的工具挤掉真正目标；先按当前可用范围过滤，再做最终数量截取，避免前八项全被过滤后返回空结果。[身份与范围修正](../../benchmarks/TOOL-DISCOVERY-IDENTITY-SCOPE.md)

## 3. 工具发现怎样比较，而不是只看少用了多少 token

历史比较同时看业务是否完成、具体工具是否选对、参数是否准确、错误调用、总输入与时延。只看最终任务完成，模型多次试错后碰巧成功也可能被掩盖。

在一个 256 工具、600 任务的阶段，全量 Schema 与客户端搜索分别完成 599/600、600/600；精确工具选择为 589/600、586/600，错误调用数为 20、50，而搜索方案输入 token 约为全量的 13.5%。这个阶段省输入明显，但错误调用仍有代价，原机械判定没有直接宣布搜索获胜。

后续使用更接近产品的多步流程，在 256 与 512 工具两个规模分别比较。512 工具层，两者都完成 300/300；客户端搜索的串行端到端第 95 百分位约为全量的 0.5805，首段响应约为 0.2447。256 层点估计没有变慢，但时延比值的单侧置信上界 1.1190 略高于预设 1.10。

最终记录保留原机械结论，再结合两种规模的质量、输入、时延和复杂度接受客户端搜索。这个过程说明数值门槛是如何使用的：正确性红线必须守住，自定性能阈值则需要结合完整证据说明取舍，不能事后偷偷改成通过。

这不证明任何工具数量都应该搜索。当前核心工具直接可见，就是后续使用中对适用范围作出的修正。

## 4. 发现工具、允许调用、执行批准不是同一件事

“搜索到了”只说明能力存在；“当前入口可用”由模式和范围决定；“这次具体操作是否需要批准”由效果和审批模式决定。

[approvalPolicy.ts](../../../src/main/agent/approvalPolicy.ts) 区分 Chat 与 Agent。Chat 通常只允许幂等读取，另有产品明确允许的记忆、陪伴和生活等内部操作；因此不能把 Chat 简化成“数据库永远不写”。Agent 有请求批准、自动批准和完全访问三档；自动批准仍会对 critical 效果询问，完全访问跳过的是这套执行批准，不代表获得所有操作系统权限。

批准应绑定具体调用及参数。用户批准“另存摘要”，不等于批准后来参数变成“覆盖原稿”。等待批准时输入改变，需要回到当前状态重新核对，不能把旧批准当作永久许可。

本项目对安全的产品范围有限：凭据存储与脱敏、明确执行审批及平台所需权限。面试可以解释能力边界，但不应把现有产品说成已经实现通用企业安全平台。

## 5. 游戏动作合同应该怎样设计

以教学动作“给玩家端上一杯饮品”为例，模型可以提出 playerId、orderId 和动作类型，但不能凭自然语言直接修改背包或扣库存。

可以设计以下结构：

```text
提议：actionId、NPC、订单、预期订单版本、目标玩家、依据
接受：服务器确认有资格开始，返回 operationId
过程：移动中、等待动画、服务被中断
结果：实际完成 / 明确失败 / 已取消 / 效果暂时未知
证据：订单版本、完成事件、实际接收者
```

这是游戏方案，不是当前项目已有的接口。ID 格式正确只证明结构合法，服务器还需检查玩家在场、订单仍有效、库存足够及 NPC 有权操作。

如果服务器已扣库存但响应丢失，客户端不能直接用新 actionId 再做一次。应按原身份查询或重试，由服务器返回相同效果回执。幂等设计的目标是重复消息不重复副作用，不是保证网络只发送一次。

## 6. 感知与执行之间的时间差怎样处理

桌面读取 DOM 或截图之后，模型可能思考几秒，页面已变；游戏里 NPC 判断玩家空闲之后，玩家可能开始讲话。感知版本要与动作用途绑定。

历史用途允许保留旧材料，例如回答“刚才你画的是什么”；当前操作用途要求目标仍可用，例如点击按钮、对正在店内的玩家说话。仅检查页面内容还不够，用户也可能撤销原目标。

因此当前项目的行动依据与输入版本提供宿主层检查，游戏版本还需在服务器真正提交动作时校验权威状态。若 Memory 与世界状态分服务，先查询后提交之间仍有变化窗口，不能用“都带 version”掩盖没有原子比较的位置。第 09 章会给出房间所有者的设计。

## 7. 语音为什么选择原生 Realtime 驱动

当前文字走 AgentRuntime，语音由 Realtime 模型直接理解音频、发起函数调用并生成音频与转写；两者共享会话、Run/Item、工具执行、审批与持久化。

项目曾试图让文字 Agent 先生成完整或分句文本，再交给语音模型朗读，以追求同一个模型循环。实际体验暴露了额外等待、朗读与文字不完全一致，以及打断时需要跨文字 Run、句子队列和音频响应收口的问题。

最终选择原生语音驱动，但由应用显式创建 response。这样应用能先建立输入与执行身份，再让模型回答，保留工具续接和恢复边界。[VOICE-ARCHITECTURE](../../benchmarks/voice-architecture.md)

原始小样本比较只改变语音端点检测后由谁创建 response，各三轮。服务自动创建时，停止说话到首音频约 673–727 ms；应用显式创建时约 836–942 ms。后者多了控制往返，但更容易绑定应用的执行身份。三轮证明路径可用和当时观察到的代价，不能当作稳定 p95 或所有部署的延迟结论。

## 8. 一个语音工具回合怎样闭合

当前采用最小串行工具续接：一次语音回合处理一个 Function Call，完整参数校验后进入同一执行器，结果按原 call identity 回注，然后继续原来的生成过程。[VOICE-TOOL-JOIN](../../benchmarks/voice-tool-join.md)

至少要跟踪四类身份：当前会话连接、输入回合、输出生成、具体工具调用。只检查“这条事件来自同一个 socket”不够，旧生成的结果可能晚到同一连接。

用户说“别改文件了”时，应停止客户端播放、通知远端停止生成、取消尚未完成的任务，并拒绝旧生成的迟到事件。工具已经完成的效果仍保留。输出转写完整，不等于声音已播完；音频已生成，也不等于客户端成功播放。

Voice 与文字工具可见范围要一致，但 Provider 能力可以不同。例如当前语音路径没有文字接口的托管网页搜索，不能暗中伪造另一套回答路径。可用的客户端浏览器能力仍沿共同工具合同执行。

## 9. 语音应该测哪些延迟和错误

把延迟拆开才能优化：用户停顿判断、输入识别或语音理解、模型首音频、网络传输、播放缓冲、工具等待和工具后续答。只报首音频，会漏掉工具完成后长时间沉默；只报最终文本，会漏掉声音实际没有播出。

故障用例至少包含：

- “周五改周六”被识别错，是否能由后续纠正恢复；
- 旧 call 的结果晚到，是否错误推进新回合；
- 用户打断后，缓冲区旧音频是否还继续播放；
- 工具已成功但生成取消，是否仍保存真实效果；
- 连接中断后，UI 是否区分思考、等待、已结束和失败。

[voiceService.ts](../../../src/main/voice/voiceService.ts) 与 [工具调用身份记录](../../benchmarks/VOICE-TOOL-CALL-IDENTITY.md) 是代码与故障定位入口。迁移到 NPC 还需要记录实际曝光给哪些玩家，不能只记服务器生成完成。

## 10. Reflection 实际有三种时间尺度

当前 Run 根据工具错误修改下一步，是即时反馈；Cognition 根据实际结果调整判断和目标，是工作状态更新；任务结束后的 Experience Review 才是较慢的经验复盘。

最后一种过程会生成 Memory、Persona 偏好、用户 Skill 修改或新 Skill 的草稿。它不训练基础模型权重，也不能修改源码、Provider 凭据、审批规则和数据库 Schema。

触发依据包括用户明确纠正或教学、具有客观证据的成功以及可证实的重复流程。[evolutionTrigger.ts](../../../src/main/evolution/evolutionTrigger.ts) 目前包含文本启发式，可能漏掉隐含学习信号，不应称为完整心理理解。

## 11. 为什么选择触发式复盘，实验结果怎样解释

[SELF-EVOLUTION](../../benchmarks/self-evolution.md) 比较过不复盘、每个 Run 都复盘、是否用户确认、是否追加 Skill 评估，以及只有出现信号才复盘。

30 个合成场景中，16 个有学习信号、14 个没有。对照“不复盘”和“触发式复盘”，正例后续任务从 12/16 到 16/16；全体从 26/30 到 30/30。每 Run 复盘与触发式复盘在这组数据上结果相同，但 Review 调用从 30 次降到 16 次，相关 token 从 13890 降到 8655。

因此选择先筛选学习信号，再执行异步 Review。这个结论的前提是这 14 个无信号场景本来就不会产生有用候选；真实含蓄表达可能被筛选漏掉，后续要测触发召回，而不是只看省了多少调用。

0/30 的新增错误迁移也不能说成风险为零。原记录的区间上界仍很宽，项目保留用户确认、来源和版本恢复，没有把小样本成功当成无人监督自修改的依据。

## 12. Skill 评估为什么不能吹成真实环境测试

当前 [evolutionReviewer.ts](../../../src/main/evolution/evolutionReviewer.ts) 中的 replay，是把候选和情境用例交给无工具模型，得到逐项结果，再检查 case ID 完整与通过情况。它没有真的在浏览器或游戏世界执行所有动作。

主实验十一项 Skill 评估全通过，但这些候选本来都正确，不能证明评估器能识别坏规则。随后另加十个故意扩大适用范围的错误修改，评估只拦住五个。这是很有价值的负面结果：模型评估提供信号，却不足以独自把关。

还存在共同来源偏差：候选生成器写出的预期结果，不能自然成为独立标准答案。下一阶段应由人类或确定性环境定义验收，再对新任务和不相关任务回放，尤其检查“学会某件事之后是否破坏别的行为”。这属于第 08 章的数据闭环方案。

## 13. 接受草稿到激活 Skill，还要检查哪些版本

[EvolutionService](../../../src/main/evolution/evolutionService.ts) 要求用户接受候选；Skill 还需经过评估，激活时重新核对目标 ID、Revision 和正文哈希。

例如草稿基于 Skill r4，用户后来手动编辑为 r5。即使草稿的评估通过，也不能覆盖 r5，因为评估的是旧基线加修改后的内容。应保留冲突和可编辑结果，由当前状态重新处理。

被固定、归档或不属于可修改目录的 Skill 不能被后台草稿偷偷改写。回滚也应产生新的当前版本并保留历史，而不是删除修改发生过的事实。

## 14. 游戏中的反思应该学什么，不应该学什么

适合学习的是可复用但有范围的经验：“玩家正在直接交谈时，服务提醒应等待合法话轮”“这种任务线索需要先检查柜台物品”。不适合直接学成永久规则的是“某次玩家离开，所以所有玩家都讨厌问候”。

NPC 的正式角色设定、任务奖励和世界规则仍由设计师及权威系统控制。经验可以改变在合法动作中的选择与表达，不能自行放开未解锁剧情，或把别人玩家的私人反馈作为全局规则。

安全评测也应具体：跨玩家记忆误用、角色不知道的剧情泄露、未授权世界动作、不当内容以及合理请求被误拒绝。每项都应有可观察输入和结果，不能用一个笼统的“安全分”覆盖所有问题。

## 15. 连续追问练习

先解释“有工具却没调用”的完整诊断，再解释“工具已经执行但模型说失败”的恢复，最后解释“任务成功是否值得变成 Skill”。

必须能说出三个实验故事：工具发现减少输入却曾增加错误调用；原生语音接受一次控制往返换取身份与持久化；触发式复盘减少无信号成本，而模型评估只拦住一半故意过宽的修改。

每个故事都要说清比较对象、数据范围、实际结果、最终选择和限制。这样才是在解释工程判断，而不是罗列 Function Calling、Realtime 和 Reflection 三个名词。
