# 17 一面复盘：记忆由谁控制，为什么从词法检索走到三路

本章回答一面后的第 1、5 问。源码基线为 `8e50d50f47fd961fbed9174d76f145a5e22b58d1`，核对日为 2026-10-27。当前行为、历史比较、外部研究与下一步方案分别说明；本次没有重新调用模型或重跑检索实验。字段级写库过程接[第 04 章](04-memory-lifecycle.md)，索引与编码细节接[第 05 章](05-retrieval-and-context.md)。

## 1. 先回答：不是所有记忆操作都由聊天 Agent 决定

普通聊天里“这次是否调用 `memory.record` 或 `memory.search`”，主要仍由回答模型遵循共用指令判断。但原文落盘、来源提取、数据库事务、版本过滤、索引排队和取消检查由宿主控制；Cognition 还有独立的后台记忆交接。因此，准确说法是：**语义选择仍大量依赖模型，数据正确性不能只依赖模型。**

把五种不同动作放在一起说“Agent 自己记忆”会掩盖问题：

| 动作 | 当前主要决定者 | 实际约束 | 没解决的事情 |
| --- | --- | --- | --- |
| 保存已接受的聊天输入、Tool 回执 | Chat／Run 等领域 | 来源身份、顺序、持久化及事件发布 | 保存原始输入不等于已经形成长期记忆 |
| 普通聊天发起记忆形成 | 回答模型调用 `memory.record({})` | 宿主从实际 Run 提取来源，模型不能传自己编的事实清单 | 模型可能漏调用、不必要调用，或调用太晚 |
| 后台认知交接长期材料 | Cognition 的状态变化及持久 handoff | 原始来源冻结、同事务入队和确认、失败保留 | 哪些来源被认知选中仍可能漏判 |
| 回答前提出历史信息问题 | 回答模型调用 `memory.search`；认知分析也可要求回忆 | 限定用户／角色／时间／修订，证据与覆盖状态一起返回 | 有数据不保证模型意识到需要搜索 |
| 候选筛选、形成／更新语义 | 领域流水线中的模型与宿主共同完成 | Schema、来源、引用、当前版本及预算校验 | 结构合法不代表语义判断正确 |

源码依据：[共用指令](../../../src/main/agent/agentInstructions.ts)、[Memory 工具](../../../src/main/memory/memoryTool.ts)、[交接桥](../../../src/main/app/cognitionMemoryBridge.ts)、[原始来源解析](../../../src/main/app/cognitionMemoryIntake.ts)、[认知交接仓储](../../../src/main/cognition/cognitionMemoryHandoff.ts)。

### 1.1 普通聊天到底怎么写

用户说“下周六三点和小林去松柏工作室做陶艺”。

1. 真实用户消息先成为 Chat／Run 输入；它不是 `memory.record` 的参数。
2. 共用指令要求模型识别持久事实、重要经历、偏好、进行中的事情、纠正与承诺。问候、凭空推测和虚构扮演不应写入。
3. 模型调用无参数的 `memory.record`。宿主通过 `resolveEpisode(runId,itemId)` 取当前交流及合格 Tool 结果，建立形成任务。
4. `enqueueEpisode` 后执行 `formEpisode`。形成模型提出有来源的记忆变化，领域层比较已有证据并提交修订。
5. 工具回执区分“来源与修订已提交”“没有新修订”“旧处理结果已变化”等；异步索引尚未完成也要如实表达。
6. 模型等到真实结果后才能说“记下了”。一个合法的零新增结果也可能代表内容已经记录过，不能每次硬造新 Memory。

当前文本指令允许在只剩内部记忆保存时先给一句贴合用户意思的简短回应，再完成保存和最终回应。它缓解等待，不代表允许在保存前宣称成功，也不是后台写入已经覆盖了所有交流。

### 1.2 Cognition 后台又怎么写

认知状态提交时，可以创建持久 `cognition_memory_handoffs`。它保存明确的原始证据集合和上下文边界，不能把认知模型写的概述冒充用户原话。

交接桥逐项读取待办，在同一个 SQLite 事务中完成：

```text
解析冻结来源 → Memory.enqueueEpisode → acknowledgeMemoryHandoff
事务提交后 → wakeMemory → 异步形成
```

入队失败则确认不能单独成功；事务回滚后不应启动付费形成。进程在提交后退出，Memory 已有工作可恢复。通知丢失也不等于数据丢失：pending work 才是恢复依据。去重键来自来源集合，不是“每隔几分钟全部重记一次”。

这条路径降低对普通聊天工具调用的单点依赖，但仍不能宣称“所有值得记的内容必然存了”。来源选择、事实抽取、冲突识别都需要分别评测。

## 2. 为什么完全交给 Agent 并不够，全部自动写又不对

完全交给 Agent 的优点是灵活：它知道当前要做什么，能够临时改变检索问题，避免每句问候都查库。缺点是漏调用会发生在检索器之前；换更好的 embedding 对这种失败没有帮助。

全量自动抽取也不是无条件更好。“我在写小说，主角讨厌咖啡”可能被记成用户偏好；“也许搬去苏州”可能被固化为已经搬家；一段转写错误会被加工成语气很确定的事实。每条都运行抽取还会增加费用、重复修订和等待积压。

更合理的分工是：

- 宿主保证真实输入进入可恢复的处理范围，并保存处理进度；原始来源是否保留多久遵循产品已有生命周期。
- 模型负责辨别含义、重要性、人物归属与同一事实是否发生变化。
- 宿主保证写入必须有来源、一次效果不重复、旧结果不能覆盖新事实。
- 对显式记忆、纠正、删除和关键业务事实提供产品流程上的保障；普通闲聊允许选择性处理。
- 宿主供给少量必要的当前状态；模型继续按问题查历史。不能把长期库全文当常驻上下文。

“规则还是模型”应按层回答。消息类型、来源 ID、修订是否当前、是否已有处理回执适合确定性代码；“这里的‘算了’取消哪件事”需要语义判断；“是否能承诺已经取消成功”最终仍取决于领域事务结果。

## 3. 行业路线：读完后能借鉴什么

### 3.1 Anthropic：Agent 管理笔记，应用管理存储

Anthropic 的 [Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool) 是客户端执行的工具接口。模型提出查看、创建、修改等操作，应用实现处理器，实际数据可以存在文件或数据库。它没有替应用决定“每轮一定写什么”，也不自动提供人物消歧、修订语义和漏记保障。核对版本为文档中的 `memory_20250818`，访问日 2026-10-27。

借鉴到本项目：允许 Agent 管理信息有官方实践基础，但不能由此推导“全部可靠性都交给模型”。CharaMate 的无参数 record 比任意文本笔记写入更强调真实来源，这是自己的产品取舍。

### 3.2 Anthropic：预装少量背景，再按需取资料

[Context engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)（2025-09-29）讨论按需读取、渐进展开，以及预先提供部分背景与 Agent 搜索相结合。其结构化笔记用于跨上下文保持进度，不等同于无限保存的用户画像。

借鉴是“双层供给”：角色身份、当前明确约束和正在执行的事情应容易取得；久远细节由具体问题触发。这里的“两层”是职责分配，不是让产品维护两套 Memory 或检索模式。

### 3.3 Mem0：把形成拆成抽取和更新

[Mem0 v1](https://arxiv.org/html/2504.19413v1)（2025-04-28）的方法先从新交流结合历史摘要／近期消息提取候选事实，再找相近已有记忆，决定新增、更新、删除或保持。摘要刷新可以异步进行。论文在 LoCoMo 等条件下比较自己的系统；其结果不能替代本项目的中文纠错、历史版本及人物归属测试。

启发不是“把 Mem0 装进来就好了”，而是让**候选生成和正式写入分开**。本项目应继续保留来源和 revision；用户改期通常是保留旧历史、改变当前有效事实，不能机械复制论文中的删除操作而丢掉历史。

### 3.4 Letta／Berkeley：把可复用整理移到查询之前

[Sleep-time Compute v1](https://arxiv.org/html/2504.13171v1)（2025-04-17）在还没有具体问题时先处理已有上下文，生成之后可能有用的表示；相关问题可以复用处理成本。实验包含改造后的数学任务和软件任务案例，并分析问题可预测性。它不是“人睡觉所以数据库也必须每天凌晨整理”的证据。

对 CharaMate 的启发：经历分段、实体候选、时间归一化和索引可以在后台准备。用户刚说“周五取消，改周六”则不能等夜间批处理才生效。预计算负责提速，当前事实检查负责纠错；要分别量后台花费和前台延迟，不能只报后者变快。

### 3.5 OpenAI Dot：持续笔记与当前对话分开

[Dot tasks and memory](https://learn.chatgpt.com/docs/dots/tasks-and-memory) 的公开说明是：它维护偏好、决定和持续工作的笔记，跨自己的对话使用；这些笔记不等于全部聊天逐字记录。公开页面没有给出内部数据库、抽取阈值或召回算法。访问日 2026-10-27。

可借鉴的是把“持续事项及其变化”作为长期连续性的中心。不能在面试里说 Dot 已证实采用了 CharaMate 这种三路检索或 cognition。

上述路线并非同一评测下的排行榜：一个提供工具协议，一个给上下文工程经验，两个提出研究方法，一个描述产品行为。合适方案来自职责与约束的组合，而非选择名气最大的项目。

## 4. 建议的下一步：补齐处理保障，保留语义自主性

以下是拟建方案，没有修改当前生产代码。优先复用 Memory 的形成队列、Cognition 的交接和既有版本机制，不新增一个永久“记忆 Agent”循环。

### 4.1 写入入口如何补

给已经接受的真实交流建立可恢复的处理进度，按既有来源身份去重；任务边界可从一段结束的交流或持续事项的真实变化产生。选择处理单位必须实验，不预设“每三句”“每五分钟”最佳。

| 建议记录的控制信息 | 谁填写 | 作用 |
| --- | --- | --- |
| 来源 ID、作用域、来源版本、发生／接收时间 | 宿主 | 精确追溯与乱序处理 |
| 触发原因：用户要求、纠正、经历结束、普通交流待审 | 宿主可确认的事件＋语义提议 | 区分优先级和结果承诺 |
| 已处理来源边界、处理器版本、任务状态 | 形成服务 | 恢复、重试和覆盖统计 |
| 候选事实、人物、时间、支持／反对来源 | 形成模型提议 | 语义抽取与冲突判断 |
| 接受／不形成／需澄清／失败及依据 | 领域校验与模型结果 | 不把“队列空”误认为全都处理正确 |

这是控制信息清单，不是要求新增同名表。原文不该复制进多份状态；背景任务只引用已有可读取来源。对内容分类不确定时，“暂不形成但保留待处理依据”优于悄悄编造事实。

显式“记住”“忘掉”的语义仍可能有歧义，例如用户引用电影台词中的“记住”。因此入口可由模型生成结构化请求，但是否持久化成功由宿主核验；针对真实显式请求，最终答复之前要有结果或清楚说明未完成。

### 4.2 读取入口如何补

在现有准备上下文位置补一个轻量的历史依赖检查，比较的重点是漏查收益是否覆盖代价：

1. 当前请求是否自足？翻译一句话通常自足，不必查生日和口味。
2. 这次决定依赖什么？“继续上次那份计划”依赖计划和当前状态；“推荐我们今晚做什么”可能依赖未完成约定及边界。
3. 依赖是否已在当前可信上下文中？已覆盖就复用，避免重复检索。
4. 未覆盖则提出具体问题，进入现有召回流水线；普通回答模型仍可继续有目的地补查。
5. 证据不全时明确保留缺口，不把没有搜到解释成用户从没说过。

起步不必每轮额外调用一个大模型。可先利用显式继续、指代、历史枚举等可识别入口，在已有模型步骤中输出依赖；再实验独立预检是否值得。不要凭空给“需要记忆”的自报置信度设 `0.8` 门槛。应使用独立标注的“这次回答是否确实需要历史”样本校准，连同漏查、无谓查库和延迟一起比较。

### 4.3 一条完整纠错流程

以下为方案推演，时间和 ID 仅为教学标签：

| 顺序 | 输入与处理 | 必须保持的事实 |
| --- | --- | --- |
| t0 | 用户说“周五三点去松柏工作室”，来源 U1 已落盘 | U1 是用户表达，不代表外部预约已经成功 |
| t1 | 形成任务 W1 提交 Memory M 的 R1；索引 J1 排队 | record 可以确认保存，不能确认预约 |
| t2 | 用户说“周五不行，改周六三点”，U2 已接受 | 当前回答和行动不能继续按周五 |
| t3 | 纠正进入优先处理；旧依赖标为失效或待核实 | 含义未解析完成时也不应继续执行冲突旧动作 |
| t4 | W2 读取 U1、U2 及 M 当前版本，提议 R2 | 原话、旧历史和新有效事实分别保存 |
| t5 | 事务提交 R2 及索引工作，重复回执不再建 R3 | 改期保存成功与新向量可用是两个时间点 |
| t6 | J1 迟到，只能完成 R1 的索引任务或被判过时 | 不能把 M.currentRevisionId 改回 R1 |
| t7 | 用户新开 Chat 问“我们什么时候去” | 历史依赖检查发起具体召回 |
| t8 | 向量可能仍命中 R1；读取按当前／历史请求验证 | 旧候选不能直接成为当前答案 |
| t9 | R2 已有词法／明确实体读取，或本轮纠正已在可信上下文 | 不必等所有向量更新才知道最新事实；覆盖不足要说明 |
| t10 | 最终回答“周六三点”；动作执行前再检查 revision | 不是因为模型“记性好”，而是答案依赖可核验 |

“写后马上读到”不意味着全部索引必须同步重建。可以等待必要的事实事务、保留本轮已提交引用，并在读取时检查是否当前。后台索引继续异步，前台不会假装索引完整。

## 5. 先诊断错在哪，再决定是否改检索器

记忆问题至少要沿下面顺序检查：

```text
原话是否被接受
→ 是否产生形成工作
→ 是否抽对事实／人物／时间
→ 修订是否提交
→ 索引是否可用且属于正确模型
→ 本轮是否真的发起搜索
→ 正确事实是否进入候选
→ 选证与上下文分配是否保留
→ 最终回答是否正确使用
```

具体反例：

- 原话在 Chat，却没有形成任务：修入口覆盖，不是加 reranker。
- Memory 正确且向量已建，但 Agent 未搜索：修历史依赖决策。
- 搜索给错人物硬过滤：修查询计划，扩大向量模型也找不到被 SQL 排除的记录。
- 正确事实进入候选，随后被同主题重复内容挤出：修融合、候选预算或选择。
- 旧版本进入最终答案：修当前性过滤、最终复读和使用规则。
- 候选全对但回答编造已完成行动：修回答／执行证据，不是记忆库吞吐。

[结构化范围记录](../../benchmarks/MEMORY-RECALL-STRUCTURED-SCOPE.md) 及其追加冷延续记录里就有“库里已经存在材料，但普通 Agent 没发起所需搜索”的诊断。该例不能包装为向量召回失败，更不能把修复后的一次成功称为稳定质量。

## 6. FTS5 到三路：历史应该怎样讲

### 6.1 早期为什么选 FTS5＋BM25

FTS5 是 SQLite 的全文检索模块，BM25 是它提供的相关性排序函数；它们不是两条独立召回通道。早期中文文本经过归一化、分词和汉字 bigram，再进入全文索引。早期也实际比较过向量与混合检索，结论不是“没听说过 RAG”。

[早期 MEMORY-RETRIEVAL](../../benchmarks/memory-retrieval.md) 的确认数据如下。Hit@8 表示前八条候选至少命中一项所需证据，不是最终回答正确率：

| 确认集合 | 纯词法 | 纯向量 | 混合检索 | 当时能说明什么 |
| --- | ---: | ---: | ---: | --- |
| LongMemEval 子集，60 问 | 56/60 | 50/60 | 57/60 | 混合小幅增加命中 |
| LoCoMo 确认部分，1125 问 | 664/1125 | 383/1125 | 618/1125 | 混合并没有普遍胜过词法 |
| 中文产品确认部分，39 问 | 32/39 | 38/39 | 38/39 | 中文语义表达确有值得继续研究的空间 |

同一 reader 的公平配对只有 22 题：词法答对 16 题，混合 17 题；所有回答主张都有来源支持的分别是 22/22 与 21/22。结合本地编码成本、资源和维护复杂度，当时保留简单词法路径有依据。不能只拿中文 38/39 隐去其他集合和额外的不受支持主张。

### 6.2 后来的契机不是一条万能原因

后续产品开始强调持续事项、跨表达回忆、人物和时间约束、修订纠错，以及不能只因旧事很久没提就永远不取用。这让“关键词能找到一些相关文本”不再等于满足产品需求。

以下是解释机制的教学例子，不是伪造原始失败集：

| 用户问法 | 已存材料 | 单靠词面的问题 | 对应能力 |
| --- | --- | --- | --- |
| “今天按我们以前说的，别安排庆祝了” | “每年这个日子我想安静纪念外婆” | 几乎没有相同关键词 | 语义召回 |
| “小林上次借的相机还了没” | 借出、还回、同名人物的几条经历 | 相机都相关，但主体和当前状态不同 | 实体约束、事件时间、修订 |
| “松柏工作室几点” | 具体名称与时间原话 | 稀有名称不应被只求语义近似削弱 | 词法召回 |
| “之前说周五，现在呢” | R1 周五、R2 周六 | 相似度无法决定哪版当前有效 | 版本资格检查 |

仓库当前 Git 把较多认知、记忆工作合并在一笔集成提交中；历史研究文档还保留“先维持 R0”的起点。所以不能从现有记录编造“某一天线上召回率跌到某值，于是一次完整实验选出三路”。可确认的是需求扩大、后续局部失败与分项比较共同促成新实现；完整的整体因果证据仍有缺口。

### 6.3 当前三路分别是什么

1. **词法通道**：FTS5＋BM25，保留名称、术语和明确字面线索。
2. **语义通道**：本地 Qwen3-Embedding-4B Q4_K_M，512 维表示，寻找措辞不同但意义相关的事实。
3. **实体／事件时间通道**：有明确实体或事件发生区间时，用结构化关系和时间条件取证据。

第三路不是“图数据库”，也不是 reranker。一次有预算的关系扩展属于另一个阶段。三路共享资格条件，再经交替去重、候选预算、模型选证、最终读取和供给；不是把三个分数直接相加。

`validAt`、`knownAt` 和“包含被替代版本”回答的是**能不能使用**，不自动证明**与问题相关**。当前只有明确实体或 `occurredFrom/occurredTo` 才开启结构化正向补充。[实际修复](../../benchmarks/MEMORY-RECALL-STRUCTURED-SCOPE.md) 的起因是无范围的时间资格把整库近期材料带进来，挤掉了本来词法和向量都能找到的相机归还记录。

### 6.4 为什么选这个编码器和融合方式

[本地编码器记录](../../benchmarks/LOCAL-MEMORY-ENCODER.md) 的 60 份材料、28 个问题、20 个故事或关系组，比较 4B／512 与 8B／1024 后，**两套方案各有 27 个问题选齐了预先标注的必要材料**。这是正常中文表达，也清楚给出分母。共同未取齐的一题存在多个合理答案，补充摄影情境后都能取对；没有理由先训练 embedding。

选较小方案的依据还包括权重和向量存储：权重约 2.50 GB 对 4.68 GB（十进制字节换算），512 维 Float32 的纯向量净荷为 2048 字节，1024 维为 4096 字节。不包含数据库页、文本、索引、内存中间值或运行时。0.6B 没参加最后这组完整选证比较，因此不能说“已经证明 4B 是所有候选中的最小充分模型”。

[融合比较](../../benchmarks/MEMORY-RANK-FUSION.md) 固定其他条件，对比 RRF 和按通道排名交替取项。主比较两者都是 27/28 个问题覆盖齐必要材料。小预算诊断里，有事实在语义通道排第 3，却因没有词法命中，在 RRF 总列表落到第 31；交替后排第 5，更有机会进入选择阶段。另一个例子是第 45 对第 8。这是具体机制，不能扩写成所有问题上 RRF 都不好。

诊断五种条件来自三个问题，必要材料覆盖为 2/7 对 7/7，不是五个独立真实用户，也不是五次最终回答全胜。最重要的边界是：**这组 28 个检索计划都只有一个问题，结构化通道和跨记忆关系没有实际内容。它选择的是融合，不证明三路整体胜过单路。**

## 7. 下一轮怎样把证据补完整

分开做三项选择，不把多个改动混成一次“新版更好”。

| 研究问题 | 固定条件与唯一改动 | 必须记录 | 防止自欺的检查 |
| --- | --- | --- | --- |
| 漏记能否减少 | 同输入、同形成器；只比较是否有宿主处理进度及自动待审入口 | 应记材料覆盖、误存虚构／临时信息、重复写、费用、形成积压 | 不以新增记忆条数越多越好 |
| 漏查能否减少 | 同记忆库、检索器、回答模型；只比较历史依赖预检 | 该查未查、不该查却查、证据覆盖、最终回答、额外等待 | 保留已存但不查、当前自足两类反例 |
| 三路贡献是否成立 | 同形成库、版本过滤、预算和 reader；一次去掉一种通道 | 各类问题的必要证据覆盖、最终回答、冲突旧事实使用、延迟／资源 | 语义改写、稀有词、人物／时间问题都要真实出现 |

先在开发集调策略；按人物／连续故事／模板分组，隔离保留集，避免同一事实换一句话泄漏。对随机模型做配对并报告重复次数；相关故事按组分析不假装每次调用独立。形成和查询时间必须模拟真实先后，不能把未来纠正提前写进历史库。

标注至少包括：是否需要历史、哪些原话值得形成、允许的事实与时间范围、支持／反对材料、允许回答及必须保留的不确定性。自动检查负责 ID、版本、去重和效果；语义是否完整、是否唐突仍需人工抽检。模型裁判先与人工锚点比较，不把它当真值。

晋级要同时看收益、误写、漏查、最终质量、前后台成本与复杂度。数值门槛通过开发数据和产品代价选择，不把论文或其他项目的 topK 直接写成产品默认值。

## 8. 面试怎么讲，怎样证明掌握

可以这样组织两分钟回答，个人贡献按实际经历替换：

> 我的记忆不是一句“全交给 Agent”。聊天模型决定是否发起读写，但 record 只能触发从真实来源形成记忆，事务、修订和索引由宿主保证；认知后台也有独立交接。进一步做可靠产品，我会补齐输入处理覆盖和历史依赖检查，因为有些失败不是搜不到，而是没存、没查或用错旧版本。
>
> 早期 FTS5 是比较后保留的简单方案。后来持续陪伴要求跨措辞、人物和时间约束，才扩展到词法、语义、结构化三路。编码器与融合有局部实验依据，但 28 题并没有证明三路整体优势。我能说明已确认的收益，也会补同一数据和回答模型下的通道消融。

闭卷验收需交四份材料：
