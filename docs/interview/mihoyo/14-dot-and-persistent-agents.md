## 2. 为什么它与 CharaMate 相似：连续的是责任，不只是聊天

普通对话的一次响应，可以在输出文本后结束。持续型 Agent 面对的问题不同：已经答应的事可能还在等待数据、外部结果或时间条件；用户随时能回来修改要求；等待期间还可能发生相关新事件。

Dot 官方说明区分当前对话可用的材料、相关 ChatGPT 记忆及 Dot 自己保存的笔记。检索历史对话不等于每个任务自带完整历史；新的分派任务也不会自动继承用户的所有对话。它还支持定时和受支持的事件触发，以及等待后继续工作。[任务与记忆](https://learn.chatgpt.com/docs/dots/tasks-and-memory)

从这些行为可以推导出一个工程问题：系统必须回答“接下来有什么未完成的事”，不能仅回答“以前说过什么”。下面这张表是我们用于设计的分类，不是 Dot 的内部数据表。

| 信息 | 自拟例子 | 需要的处理 |
| --- | --- | --- |
| 一次经历 | 玩家昨天来过咖啡馆 | 保留来源、时间、参与者 |
| 相对稳定的知识 | 玩家明确说不喝含乳糖饮品 | 可检索、可纠正，保留条件 |
| 当前责任 | 等玩家结束谈话后交付蛋糕 | 状态、完成条件、取消和恢复 |
| 唤醒条件 | 谈话结束事件；约定时间到达 | 可持久恢复、去重、重新检查 |
| 一次执行 | 本次尝试交付蛋糕 | 对象身份、当前依据、效果回执 |
| 已发生结果 | 玩家实际收到了蛋糕 | 独立事实，不能用计划文本代替 |

因此，不应该把“下午提醒我”只存进向量库。没有可靠的调度，系统可能永远没有机会查询这条记忆；只把它写进计划，执行时又可能不知道玩家已取消。记忆与调度相互配合，但不能由两个模块各自拥有一套“当前任务真相”。

## 3. 从一项持续责任开始设计

假设玩家对店员说：“等我和朋友聊完，帮我取预订蛋糕；如果今天没到货，只告诉我结果，不要替我改订单。”

先拆出条件和责任：

- 目标：把这张订单的蛋糕交给当前玩家。
- 前提：谈话已经结束、玩家仍在可交付位置、订单有效、货物已到。
- 可独立做的事：读取订单与到货状态，形成下一步建议。
- 需要玩家决定的事：换品、改订单或选择另一天。
- 完成证据：权威订单与交付结果，而非一句“已经安排好了”。

这些含义可以由现有 Intent、Automation 和 Run 的合同承接。只有现有对象确实无法拥有的需求，才考虑新增状态。本章不建议先创建一个包办认知、记忆、调度和执行的“DotService”。

### 3.1 一个可复核的逻辑记录

下面是教学数据形状，不是仓库当前 Schema，也不要求拆成四张新表：

```ts
type OngoingResponsibility = {
  id: string;
  ownerNpcId: string;
  playerId: string;
  revision: number;
  goal: string;
  status: "active" | "waiting" | "needs_player" | "completed" | "cancelled";
  orderId: string;
  sourceRefs: string[];
  waitFor?: "conversation_finished" | "delivery_arrived";
  nextCheckAt?: string;
  completionReceiptId?: string;
};
```

`revision` 表示这项责任的当前约定，不能代替订单版本、玩家在场身份或发言权版本。一次行动需要保存自己实际用了哪些依据，例如订单第 6 版和谈话第 12 个话轮。改变无关背景音乐，不应该因此取消行动；改变订单则必须重新检查。

`sourceRefs` 回答为什么承担这件事；`completionReceiptId` 回答为什么说已经完成。前者可能来自用户指令，后者应该来自实际效果，不能互相替代。

### 3.2 “持续运行”如何做到不持续空转

一种可实现的路径是：保存责任与等待条件 → 注册可恢复的到期或事件触发 → 当前执行释放资源 → 条件变化后重新读取 → 仍需行动才创建或续接 Run。

等待不需要让一个模型请求保持几个小时，也不必让一个 JavaScript Promise 永远挂着。内存定时器只是唤醒手段；责任状态与触发进度要能在重启后恢复。触发事件也不直接等于动作命令，它只是让系统重新判断的输入。

为什么还可能保留 `nextCheckAt`？外部事件源可能不提供完成通知，或需要在约定时间重新确认。但这个时间由任务语义和实验决定，不能任意设定“每 30 秒全量思考”并称为先进架构。

## 4. 用九个事件走完一次纠错与恢复

以下时序是我们的咖啡馆设计推演。Dot 公开文档没有披露它是否使用这些事务或版本字段。

| 时刻 | 发生什么 | 系统必须做的事 |
| --- | --- | --- |
| t0 | 玩家提出取蛋糕要求 | 保存责任及来源，明确订单与等待条件 |
| t1 | 读取到货信息的后台任务开始 | 记录责任版本 r1 和所需对象；读取不等于交付 |
| t2 | 玩家说“今天不拿了，改明天” | 提交 r2，更新等待与完成条件，通知旧执行失效 |
| t3 | t1 的旧任务返回“蛋糕已到” | 到货事实可按来源保存；旧 r1 的交付计划不能继续 |
| t4 | 旧定时触发也到达 | 按触发身份去重，再读当前 r2，不创建 r1 的行动 |
| t5 | 进程在保存新待办后、通知调度器前崩溃 | 重启从持久待办恢复，不能丢掉已确认的责任 |
| t6 | 次日玩家重新进入店铺 | 使用新的在场身份，确认订单、责任与当前请求 |
| t7 | 提交交付，服务器已生效但响应丢失 | 按动作身份查询效果；未知时不重复扣库存或交付 |
| t8 | 查询确认已交付 | 保存完成回执，结束责任；根据当前场景给出确认 |

这条链里最容易遗漏的是 t3：旧后台结果不一定全无价值。“蛋糕已经到货”可能仍是有效事实，而“现在立刻交付”已经无效。不要简单把整段模型输出全部当成当前命令，也不要为了消除旧任务，把合法世界事实一起丢掉。

另一个易错点是 t7：责任版本只能判断“现在还应不应该做”，动作身份才能帮助确认“刚才是不是已经做了”。把这两个字段合并，会在修改目标和重试网络请求时混淆语义。

### 4.1 事务放在哪里

可借用项目已有的模式：在同一短事务内更新责任、持久待办和交接确认，提交后再唤醒调度。模型推理、网络请求和引擎动作在事务外。等待结束后，在提交或效果发起前重新检查相关版本。

如果权威世界在远端服务，本地事务不能包住服务器副作用。需要远端接收唯一动作身份并提供查询，或提供业务上等效的去重协议。这里追求的是重复投递下效果可识别，不能把网络消息说成天然“恰好执行一次”。

### 4.2 结果怎样进入最终回答

用户仍在谈话时，交付状态更新不意味着应立即插话。可以先更新可见的订单状态，等待合适机会；若玩家明确问“好了没”，再按最新结果回答。对已取消的事，不发送旧任务的庆祝消息。对效果未知，解释正在确认，不能凭模型确信宣布完成。

这同时连接了第 06 章的一致性、第 09 章的发言权和第 08 章的评测：真实效果、最终回答、玩家实际看到或听到的内容，需要分别记录。

## 5. 主动发现、等待与行动，为什么要分开

Dot 的公开控制说明把主动研究与后续行动区分：主动研究所用工具不负责发送消息、修改应用或控制计算机；发现可以返回建议，真正的后续动作再遵循相应权限。[控制说明](https://learn.chatgpt.com/docs/dots/controls)

我们可以从中提出一个适合 NPC 的设计，但不要照抄一整套账户权限产品：

1. **观察阶段**：接收可见环境与允许感知的对话。
2. **理解阶段**：判断是否与目标或角色有关，必要时检索记忆。
3. **提议阶段**：形成“可以提供帮助”“应继续等”等候选。
4. **行动阶段**：检查当前用户控制、世界前提和发言权，才产生真实效果。

例如 NPC 听到玩家讨论某份配方，可以在内部发现线索；但这不意味着要立刻插话，也不意味着允许透露另一名玩家私下告诉它的秘密。游戏里的边界应围绕角色所知、受众、玩法动作和用户控制，保持必要且具体。

### “主动”如何避免变成“打扰”

至少需要区分三个量：

- 有用机会：当前确实存在值得提供的帮助。
- 合适时机：玩家此刻愿意接收，并有合法发言机会。
- 新信息：这次贡献是否与刚才已经说过的内容不同。

一段高质量建议，在错误时机重复播放，仍是坏行为。评测应包含没有发言的正确样本。不能只拿“主动发言里有多少条好消息”当成功率，因为系统可能靠完全不说话回避错误，也可能靠大量刷消息碰巧命中。

可以先做确定性基线：点名或明确请求优先，其他候选等待公共话轮空闲；再研究语义触发。要比较的是有效帮助覆盖、无效打扰、重复曝光、等待和资源成本。打扰评分由策划或玩家按明确规则判定，模型评分只能辅助。

## 6. 记忆连续性与共享范围：知道，不代表任何地方都能说

Dot 官方说明：不同沟通渠道联系的是同一个 Dot，但可见会话不会自动互相复制；可以使用信息与可以向另一受众披露信息，是不同问题。已保存的自有笔记，也不等同于 ChatGPT 记忆设置中的内容。[任务与记忆](https://learn.chatgpt.com/docs/dots/tasks-and-memory)

这给游戏迁移一个直接问题：同一个 NPC 在单人互动、公共咖啡馆和多人任务里，可能拥有连续记忆，却不应拥有无条件公开所有记忆的权利。

我们可以在方案中分别记录：

| 检查 | 自拟场景 | 处理重点 |
| --- | --- | --- |
| 事实来源 | A 私下说自己准备离职 | 是 A 的陈述，未必是已发生世界事实 |
| 角色可知 | B 没在场，NPC 在场 | NPC 可以记住，B 不自动获得 |
| 当前用途 | NPC 帮 A 调整见面时间 | 可以利用必要背景进行推理 |
| 输出受众 | NPC 准备在公共场所解释原因 | 不能因为检索到了就直接透露私人细节 |
| 后续纠正 | A 说计划已取消 | 更新当前资格，派生安排也要重查 |

这些是咖啡馆方案的知识与输出合同，不要求给当前桌面产品新增企业级访问控制体系。已有记忆的来源与精确修订可以复用；多人世界中的受众规则需要单独定义。

删除也要讲清具体对象：断开信息源，通常首先停止未来获取；旧记录、派生摘要和已有任务是否保留，是另一项产品约定。不能仅删除一个向量，就保证原经历、概括和正在执行的任务都已失效。CharaMate 的删除与保留以自身合同为准，不因为 Dot 的某个设置行为就自动修改。

## 7. 多任务协调：主对话保持可用，任务结果仍需检查

Dot 可以分派后台工作和可见任务；新任务拿到的是与该工作相关的上下文。暂停主任务与停止已分派任务、取消未来计划，是不同操作。[任务说明](https://learn.chatgpt.com/docs/dots/tasks-and-memory)、[停止工作的范围](https://learn.chatgpt.com/docs/dots/controls)

由此推导我们的协调合同：

- 分派时传递任务目标、必要材料、允许动作、版本依据和返回格式。
- 子任务报告观察、产物、错误与完成证据，不仅返回“我做完了”。
- 主任务收到结果时检查相关目标是否仍有效。
- 用户中途修改目标，主任务保存新状态；向子任务发送取消只是减少浪费，返回时的检查仍不可省。
- 独立任务可以继续，依赖旧目标的任务应停止或改派；不能只按父子关系一刀切。

例如一个任务查蛋糕到货，另一个任务准备生日祝福。玩家改为明天取货时，到货查询仍可能有价值，今天的祝福曝光应取消。这需要明确任务依赖，不能由“后台线程仍在运行”推断它仍被授权完成原动作。

### 环境也是任务的一部分

Dot 的云端电脑与个人电脑有不同的在线条件；更改选中的电脑不会自动搬走已有任务。浏览器登录与文件也属于相应环境。[计算机与应用](https://learn.chatgpt.com/docs/dots/computers-and-apps)

游戏中对应的问题是场景与世界分区：NPC 离开咖啡馆，正在执行的桌边动作不能悄悄迁到另一场景。主任务仍然可以记得“要交付蛋糕”，执行尝试却应绑定具体世界、对象和在场身份。持续目标可以跨环境保留，具体效果不能脱离环境身份。

这是设计推论，不代表 Dot 的任务环境与游戏分区使用同一实现。

### 8.2 顺着一次调用读，而不是看目录猜架构

在固定版本的 [thread.ts](https://github.com/openai/codex/blob/014489466a1739c2c563cdfe57880c2c7c8680e3/sdk/typescript/src/thread.ts) 中：

1. `Thread` 保存会话 ID 与调用配置，一个会话可以经历多轮。
2. `runStreamedInternal` 组织输入与输出 Schema，调用执行器并消费事件。
3. 收到 `thread.started` 后记录 ID，后续继续可复用这个身份。
4. `run` 将事件汇总为条目、最终文本与用量；遇到 `turn.failed` 会记录错误并抛出。
5. Schema 临时资源在 `finally` 中清理，而不是只在成功分支清理。

在 [exec.ts](https://github.com/openai/codex/blob/014489466a1739c2c563cdfe57880c2c7c8680e3/sdk/typescript/src/exec.ts) 中，执行器启动 Codex 子进程；有 thread ID 时加入继续该会话的参数。它把输入写到 stdin，从 stdout 按行读取 JSON 事件，并处理进程退出与取消信号。

在 [events.ts](https://github.com/openai/codex/blob/014489466a1739c2c563cdfe57880c2c7c8680e3/sdk/typescript/src/events.ts) 中，条目开始、更新、结束与整轮完成、失败是不同事件；条目结束本身可能代表成功，也可能代表失败。

从这些代码可以看出：**持续会话身份不等于同一个进程永不退出。**本次调用的资源有明确生命周期，后续调用通过身份继续。类似地，NPC 的责任不能绑定到一次模型连接或一次语音通话是否还活着。

### 8.3 三个具体工程启发

**第一，界面事件不能代替领域成功。**收到一个条目结束，可以更新对应 UI；是否完成订单，还要检查条目内容与世界回执。收到整轮完成，也不能自动认为全部业务目标达成。SDK 提供过程边界，产品承担验收条件。

**第二，取消信号与效果判定分开。**`AbortSignal` 传入子进程启动边界，有助于停止执行。但已经发送到外部系统的请求是否生效，不由进程退出状态决定。CharaMate 对 Tool 与 Run 的处理也要保存效果已完成、已拒绝或未知的区别。

**第三，资源清理属于正常路径的一部分。**流式消费者提前退出、JSON 解析失败、子进程错误，都可能跳过普通成功收尾。源码中的 `finally` 清理体现的是这一问题。咖啡馆里对应的不只是关闭连接，还包括释放未用发言权、取消未播放音频和保留已经产生的效果记录。

本段总结源于已读文件；它不覆盖整个 SDK 的全部错误传播和恢复保证。尤其不能看到几个事件类型，就说生产崩溃恢复已被完整验证。

### 8.4 一个与项目版本检查很像的公开合同

固定版本的 [app-server README](https://github.com/openai/codex/blob/014489466a1739c2c563cdfe57880c2c7c8680e3/codex-rs/app-server/README.md) 说明了线程已读状态更新：客户端携带它实际看到的 `expectedRevision`；版本冲突时返回当前状态，不应盲目重试清空未读。

用一个自拟界面例子解释：窗口看到了结果 A，准备标已读；后台此时又产生结果 B。如果只发送“全部已读”，B 可能被误清。携带 A 时看到的版本，才能发现这次操作落后于新结果。

这个合同与 CharaMate 的分析提交有共同思想：异步工作只能对它真正观察过的版本作承诺。但已读版本保护的是界面状态；行动依赖保护的是执行依据，两者不能机械合并成一个全局计数器。这里引用的是公开协议说明，没有声称本次逐行审计其服务端 CAS 实现。

## 9. CharaMate 已有基础与真正的差距

| 问题 | 当前项目可核实的基础 | 仍需建设或单独证明 |
| --- | --- | --- |
| 多入口执行 | 文本、工具、自动化和语音使用共同 Run/Item 合同；模型驱动有差异 | 不能据此宣称所有模型循环只有一份函数 |
| 自主性与等待 | Cognition 维护意图、注意和下次考虑时机 | 多人场景里何时主动最合适，仍需玩法评测 |
| 唤醒恢复 | Scheduler 使用持久 runner，启动/恢复时检查到期任务 | 本地进程关闭后不会自行获得云端算力 |
| 长期知识 | 来源、修订、异步形成与检索 | 持续数月真实玩家表现，不由小样本历史实验证明 |
| 动态纠正 | 分析提交检查与行动依据检查 | 游戏服务端的原子动作提交、分区与音频曝光 |
| 任务结果 | Run/Tool 事件与执行记录 | 跨环境完成证据、未知效果查询及多人世界协议 |
| 持续改进 | 经验候选、技能复核及历史比较 | 完整线上数据飞轮、长期收益和持续发布评测 |

本表不是根据文件名推断。调度部分已读[AutomationScheduler](../../../src/main/automations/automationScheduler.ts)：启动与系统恢复会刷新，串行检查各 runner，选择最近到期时间设置下一次计时；停止会清计时并等待当前检查结束。认知部分可见[服务](../../../src/main/cognition/cognitionService.ts)中的 `earliestNextRunAt`、`runDue` 和行动分配，以及[运行时接口](../../../src/main/cognition/cognitionTypes.ts)中对分配事务的要求。

这支持“本地持续状态可以恢复”的工程说明，却不等于 Dot 的云端常驻能力。若面试问用户关机以后怎么办，当前答案是：本地执行受设备在线条件限制；需要云端执行时，要新增经过需求确认的部署与同步方案，不能把现有 timer 说成已经实现 24 小时后台服务。

## 10. 如果继续做，先做哪四个实验

### D1：唤醒是否既省成本又不漏事

先冻结同一批事件轨迹，覆盖静默等待、明确点名、到货、取消、离店重返与重复通知。只改变唤醒策略：固定间隔检查作为简单基线，对比语义事件与持久到期结合。模型、可用信息、动作集合和任务必须相同。

记录关键事件覆盖、无效检查次数、过期行动、事件到可见回应的延迟，以及模型输入与调用成本。重启和重复投递用确定性故障注入测试正确性；真实推理延迟单独测，不混入离线回归。若事件驱动漏掉没有通知的外部变化，应补正确的重新检查合同，再比较，不能删除失败例。

### D2：任务该继续还是新建

Dot 的 10 月更新明确提到改进继续旧任务与新建任务的判断。[更新说明](https://learn.chatgpt.com/docs/whats-new/dots-october-9-2026) 这提示一个值得单独评测的问题，但未公开内部算法或成绩。

我们的数据应同时包含修改当前订单、另开一张订单、仅询问旧结果、换一个玩家提出新要求。独立标签标明目标、对象和责任是否相同；先建立显式 ID 与用户指代规则基线，再比较增加语义判断。测错误合并、错误拆分、上下文遗漏和重复动作，不能只测任务列表看起来整齐。

### D3：保存事实与保存未完责任，差别有多大

比较只有对话摘要与事实检索，和额外明确保存现有 Intent/任务状态的方案。相同轨迹中加入隔天返回、目标取消、部分完成、执行环境离线、旧子任务迟到。所有组获得相同来源，避免把“提供更多信息”误当结构本身的收益。

主要看未完任务恢复、已取消任务误恢复、重复执行和错误宣告完成；同时记录状态维护与上下文成本。若显式状态没有增益，分析是任务太简单、标签不足，还是重复实现已有状态，不能预设复杂方案一定赢。

### D4：什么时候通知玩家

固定同一批已确认结果，分别测试每次阶段变化都通知，与按新信息、用户期待和场景机会组织通知。这里不改变推理质量，避免同时变更内容与时机。

分母要包括应该通知但没有通知的机会、实际曝光的通知和重复曝光。记录漏报、错误打扰、重复、等待与主观接受度。不能用用户回复次数代替效用，也不能用完全沉默取得“零打扰”。版本修改或取消后还发旧通知，应作为独立失败类。

这四项都没有本项目实测结果。本章交付的是实验方案；目标阈值与资源预算需要正式 Decision 预注册，不能用教学数字直接定生产参数。

## 11. 分阶段实施：先补责任闭环，再考虑云端常驻

**第一阶段：在现有本地系统里证明状态闭环。**复用 Intent、Automation、Run；选一个持续责任，走通创建、修改、等待、恢复、取消、完成，补对应的确定性故障案例。退出条件是断开 UI、进程重启、旧任务迟到后仍能解释当前状态。

**第二阶段：证明它确实改善交互。**完成 D1、D3、D4 的比较，记录漏事、打扰、正确性与成本。只保留被证据支持的路径，不把每种策略做成用户设置。

**第三阶段：迁移到权威游戏环境。**增加有限感知、订单与任务服务、动作回执、受众和发言仲裁。使用第 09 章的合同，测双 NPC 竞争、玩家离店重返、音频中断和效果未知。

**第四阶段：只有真实需求要求时再做跨设备持续执行。**明确谁拥有责任状态、环境离线怎么等待、任务何时能迁移、旧执行如何失效，以及需要怎样的成本与运行维护。云端常驻是部署和生命周期工作，不是多加一句 system prompt。

文档方案不改变当前单一 Harness、单 npm 包和领域归属。任何生产实施仍需独立工作包与对应验证。

## 12. 面试中可以怎样讲 Dot

可以这样概括自己的理解：

> 我调研了 OpenAI 的 Dot。它最贴近我场景的地方，是同一个 Agent 能跨对话承担责任，并决定什么时候继续工作、什么时候把结果带给用户。公开资料可以确认这些行为，但没有公开它的具体记忆索引和完整调度实现，所以我没有把推测当成源码。工程上，我实际读了固定版本的 Codex SDK，看到会话身份、单轮执行、条目事件和取消分别有边界。CharaMate 已有认知意图、记忆修订、到期唤醒和统一运行合同；迁移到咖啡馆还需要权威世界动作、发言时机和多人结果确认。我会用漏响应、过期动作、错误打扰和真实效果来判断借鉴是否有效。
