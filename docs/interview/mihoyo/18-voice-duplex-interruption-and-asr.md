## 1. 当前采用什么架构

当前产品是 **Azure Realtime GA＋WebRTC 的原生语音对话**。模型直接接收音频并产生音频；输入转写用于界面、聊天记录和宿主流程，不是先让文字 Agent 完成答案再交给 TTS。Text 与 Voice 共用 Persona、工具、审批、Memory、Chat／Run／Item，但各有自己的模型驱动。

历史上曾尝试“识别 → 文字 Agent → 按句朗读”，出现分句空档、口述与文字不同步、打断跨多个队列后卡在思考等问题，后来按产品体验要求改回原生语音编排。这个变更记在[语音架构决定](../../benchmarks/voice-architecture.md)，不是一次充分控制变量的端到端优胜实验。

### 1.1 先分清四条通道

```text
麦克风 → Renderer 的 WebRTC 音轨 → Azure Realtime
Azure Realtime → 下行音轨 → Renderer 播放

Realtime DataChannel 事件 ↔ WebRtcVoiceDriver ↔ typed IPC ↔ VoiceService

VoiceService → Chat / Run / Item、Cognition、工具注册 / 审批 / 执行
            → Tool 结果回到同一 Realtime 会话 → 后续语音
```

媒体与控制事件不是同一条有序字节流。因此不能假设“先收到 response.done 就一定已经听完”，也不能用单个布尔值代表回答、播音和工具执行的所有状态。

关键文件：[会话签发](../../../src/main/voice/azureWebRtcSession.ts)、[浏览器驱动](../../../src/renderer/features/voice/WebRtcVoiceDriver.ts)、[Main 编排](../../../src/main/voice/voiceService.ts)、[本地指标](../../../src/main/voice/voiceMetrics.ts)。

### 1.2 当前真实配置代表什么

| 配置／行为 | 当前值 | 工程含义 |
| --- | --- | --- |
| 输入转写模型 | `whisper-1` | 当前 Azure 路径的已选配置，不代表它是今天所有端点的最佳模型 |
| 转写 prompt | 简体中文、English 和 CharaMate 等领域词 | 给名称及语言表达提示，没有固定单一 language |
| 断句 | `server_vad` | 用语音活动及静音判断边界 |
| 自动开始回复 | `create_response:false` | Provider 检测一句话结束后，不能越过宿主自行开答 |
| 自动中断 | `interrupt_response:true` | 检测新讲话时，中断已有响应 |
| 输出 | `output_modalities:["audio"]` | 回答音频及相应输出转写来自同一原生响应 |
| 并行工具 | `parallel_tool_calls:false` | 当前选定串行调用，避免无证据地扩展复杂度 |

OpenAI 的 [VAD 文档](https://developers.openai.com/api/docs/guides/realtime-vad) 区分基于静音的 server VAD 和判断一句话是否说完的 semantic VAD；后者不是“判断用户是否在对 NPC 说话”的分类器。文档支持的字段还取决于具体模型与会话类型，不能直接认为 Azure 当前 deployment 全部支持。

### 1.3 VAD 是谁实现的，两个自动开关分别做什么

`server_vad` 和 `semantic_vad` 都是 Realtime 服务端提供的模式，当前项目没有训练或实现这两个检测器。[Azure Realtime 官方说明](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/realtime-audio?view=foundry-classic)也列出了两种模式；某个目标 deployment 的协议、字段和实际效果仍需单独验证，不能把文档列出能力等同于本地已接通。

| 机制 | 判断或控制的事情 | 不负责的事情 |
| --- | --- | --- |
| `server_vad` | 根据语音活动与静音间隔划分输入 | 不理解每一次停顿是不是思考，也不识别说话对象 |
| `semantic_vad` | 根据表达是否像已经结束，调整结束输入的时机 | 不自动解决旁人讲话、附和和真正插话的区分 |
| `create_response` | VAD 判定输入结束后，是否自动生成回答 | 不决定工具是否获准执行 |
| `interrupt_response` | VAD 检测新讲话时，是否自动取消默认会话中正在进行的响应 | 不取消宿主进程里的工具、审批和 Run |

当前 `create_response:false`、`interrupt_response:true` 的含义是：“开始回答要等宿主发命令，检测到新讲话则允许服务端自动打断。”关闭自动开答并没有同时关闭自动打断。官方允许两个开关都设为 false，并继续发送 VAD 事件；宿主此时要自行决定何时取消、何时创建响应。见 [Realtime 会话配置](https://developers.openai.com/api/reference/resources/realtime/subresources/client_secrets/methods/create)。

例如用户说“改到周五……不，周六”，首先要判断整句话是否结束；Agent 讲解时用户说“嗯嗯”，则要判断是否想接过话轮。这是两个问题。只切换到 semantic VAD，却保留“所有 speech_started 都中断”的客户端处理，不能解决后一个问题。

## 2. 从点击语音到一句回答，逐步发生什么

### 2.1 建立连接

1. Main 确定绑定的 Chat、Persona 快照、执行模式、Provider／Realtime model／voice；准备共用指令、上下文和当前可用工具。
2. Main 用平台秘密存储中的长期凭据调用 `/openai/v1/realtime/client_secrets`，得到短期凭据；它不是把长期 key 暴露给 Renderer。
3. Renderer 调用 `getUserMedia`。当前请求 AEC 回声消除、噪声抑制、自动增益；是否有效还依赖设备和驱动，设置为 true 不等于声学验收通过。
4. 建立 RTCPeerConnection，上行 microphone track、下行 audio track 和 DataChannel；用短期凭据向 `/calls` 交换 SDP。
5. 连接、初始化和历史恢复成功后进入可交谈状态。复用已暂停会话前会刷新指令和工具；绑定条件变化时重建，不能把旧响应当作新会话响应。

语音绑定 Chat 不跟随用户浏览别的 Chat 自动迁移。暂停会停采集／播放并中断当前回合；结束会释放媒体、连接和相关工作。复用与冷启动是同一生命周期的条件分支，不是保留另一套语音架构。

### 2.2 用户说一句话

假设用户说“帮我看看我们周六几点去做陶艺”。

| 顺序 | 协议／应用事件 | 实际处理 |
| --- | --- | --- |
| 1 | `input_audio_buffer.speech_started` | 驱动立即抑制旧音频；Main 中断旧回合，创建新的 VoiceTurn／generation |
| 2 | 上行音频持续送入 | Realtime 模型听到声音；转写服务也处理输入 |
| 3 | `speech_stopped` | 记录语音结束时刻，尚不能当作文本识别成功 |
| 4 | 非空 `input_audio_transcription.completed` | 按 input item ID 找到对应回合；重复、过时输入不能开启另一份回答 |
| 5 | `prepareTranscript` | 准备 Cognition 背景和完整请求预算，等待后检查会话、代际、暂停和取消状态 |
| 6 | Chat 串行提交段 | 建立 source=voice 的 Run，保存真实转写用户消息及 user_message Item |
| 7 | 再次检查回合仍有效 | 发出宿主管理的 `response.create`，携带本回合身份和指令 |
| 8 | `response.created`／输出事件 | 绑定 responseId；输出转写更新同一回答，音轨播放相应音频 |
| 9 | 工具或回答完成 | 工具进入共用执行链；无工具时逐步完成回答／Run |
| 10 | 服务端输出缓冲停止事件 | 更新播放状态；服务端报告缓冲排空不等于人耳实际听完，也不与生成完成等同 |

当前因此有一个明确取舍：**模型听的是原生音频，但宿主仍等待非空最终转写，才能建 Run 并显式启动回复。** 转写慢会增加首答延迟，转写失败会走失败处理。不能说“原生语音因此完全不受 ASR 影响”。

当前驱动对空白 completed 文本不报告有效转写。噪声、极短输入或转写为空时，仍需专项检查 UI 是否能可靠回到可重试状态；“忽略空白”本身不证明无卡住风险。本章没有通过真实设备复现这种边界，不能把它写成已经修好的缺陷。

### 2.3 查询记忆或操作工具

模型产生函数调用后，VoiceService 验证工具名、参数、call 身份及回合当前性，进入同一工具注册／执行边界。需要审批则创建 approval Item；批准后再执行，拒绝也返回真实结果。结果用原 `call_id` 作为 `function_call_output` 回给 Realtime，再创建后续响应。

例如：R-A 说“我查一下”并调用 `memory.search`；搜索结束后 R-B 说“改成周六下午三点了”。R-A、R-B 是两个 responseId，但属于同一 VoiceTurn／Run／generation。协议响应不是产品任务身份。

如果查询失败，结果应表达失败；不能播“我查到了”再去填一个空结果。若工具可能改变外部世界，批准也不代表之后所有前置条件都永久有效。

### 2.4 页面文字为什么能和声音一起出现

当前不是先生成完整文字再交给 TTS，而是同一原生响应分别输出音频和转写。两条通道各自推进：

```text
响应 R-A 的音频 → WebRTC 下行音轨 → 浏览器播放
响应 R-A 的转写 → DataChannel delta → typed IPC → VoiceService
                → 更新同一消息、VoiceTurn 和界面快照
```

驱动收到 `response.output_audio_transcript.delta` 后，上报 responseId、generation、protocol itemId、outputIndex 和文字片段。Main 的 `#appendAssistantTranscript` 找到所属回合，把片段追加到对应输出；`#syncAssistantOutput` 更新 Chat 消息、数据库中的 assistantTranscript 和 Voice 快照。`done` 事件可以用服务端最终转写修正同一部分的文本。同一回合存在多个响应或输出项时，按响应顺序和 outputIndex 组织文本，不把网络到达先后直接当表达顺序。

对应实现是[驱动](../../../src/renderer/features/voice/WebRtcVoiceDriver.ts)的两个 `response.output_audio_transcript` 分支、[服务](../../../src/main/voice/voiceService.ts)的上述三个方法，以及 [VoiceDock](../../../src/renderer/features/voice/VoiceDock.tsx)对快照文本的展示。

这里的“同时出现”是两条流并行，不是逐字卡点。文字可能已经显示“我们先去咖啡馆，再去看展”，声音却只说到“我们先去……”。当前没有把每个字绑定到音轨播放时间，也不能用 delta 的到达时间推断该字已经播放。打断后的保存规则必须另行处理，见 3.5、3.6。

## 3. 用户打断时，必须同时处理哪些对象

假设 Agent 正说“周五三点……”，用户插话：“不是，改到周六了。”

### 3.1 当前应用侧执行顺序

下面描述当前代码处理，不表示媒体、服务端取消与本地事件存在同一个全局时序。服务端可能在客户端收到 speech_started 之前就已取消响应。

1. **Renderer 抑制旧声音。** 收到 speech_started 就禁用旧输出、设置抑制状态，记录输入 item 与估计的播放时长。当前没有在这一步先区分附和和真正插话。
2. **服务端自动打断，应用还会主动取消。** 当前 WebRTC 使用服务端管理音频，VAD 自动中断会清理相关输出；应用取消命令另外发送 `response.cancel` 与 `output_audio_buffer.clear`。两者存在重叠，不应都说成协议要求，详见 3.4。
3. **Main 中断仍在进行的旧逻辑。** abort 当前回合及 pending tool，取消尚待审批的旧请求，关闭尚未终态的 Run／Item，流式消息标成 interrupted，保留已经发生的内容和效果。当前函数对已完成回合提前返回；“生成完了但没播完”的缺口见 3.5。
4. **开始新回合。** 新 input item 对应新 generation；最终转写到来后再建新 Run 和回复。
5. **丢弃迟到旧结果。** 旧模型、旧工具和旧上下文准备即使回来了，也不能继续新回合或恢复旧播音。
6. **新回答根据纠正处理。** 新话改变事实时，进入相同 Memory 修订流程；旧语音已经被听到的部分无法收回，只能在后续说明更正。

OpenAI [Realtime interruption 文档](https://developers.openai.com/api/docs/guides/realtime-conversations) 指出，WebRTC／SIP 由服务端管理输出缓冲并截断未播放内容；WebSocket 客户端需要自行跟踪播放进度并发送 truncate。当前驱动接收 `conversation.item.truncated` 回执，没有在 speech_started 分支自行发送 `conversation.item.truncate`。不要把早期手工截断的故障修复讲成当前仍在估算并发送截断命令。

服务端截断也不能提供逐字对齐的“用户确实听到哪一个字”。界面最终转写、音频已播放区间与用户实际听觉仍有差异；审计或记忆不能把中断后未播出的句子视为已经交流完成。

### 3.2 为什么需要这么多 ID

| 身份 | 区分什么 | 缺少它会发生什么 |
| --- | --- | --- |
| sessionId | 哪条连接及绑定上下文 | 重连后旧事件污染新连接 |
| input itemId | 用户哪段音频 | 两段转写乱序，被接到错误回合 |
| turnId／generation | 当前用户回合 | 旧模型或工具结束后继续抢答 |
| runId／itemId | 产品执行与持久结果 | 界面、工具、恢复各讲一套状态 |
| responseId | 同回合中的各次协议响应 | 前一段停止事件把后一段静音 |
| function callId | 哪次工具请求及其返回 | 重复执行或把 A 结果交给 B |

**generation 相同不代表音频片段相同。** 这是项目曾出过问题、最适合讲细节的一点。

### 3.3 打断不能做到什么

| 打断时刻 | 正确行为 |
| --- | --- |
| 旧回答仍在生成 | 停生成／播音，保留中断状态 |
| 只读工具正在执行 | 尽力取消；迟到结果不允许继续旧回答 |
| 审批尚未决定 | 取消旧 pending approval，避免之后批准过时动作 |
| 外部服务已经接受操作 | 不能凭 abort 声称回滚；保留实际效果并核查最终状态 |
| Memory 事务已经提交 | 不应删除真实发生的交流；之后以新来源修订 |
| 下行媒体仍有缓冲 | 自动打断由服务端处理输出清理；主动停止需要相应媒体控制，不能只结束 Run |
| 用户只发“嗯”或咳嗽 | 当前 server VAD 可能照样触发打断；自然附和区分还没有被证明 |

取消是向工作发出停止要求；不保证远端立刻停，更不保证已经提交的动作消失。最终能否继续必须由当前身份和状态检查决定。

### 3.4 Realtime 已经自动截断，为什么应用还要处理

**在当前 WebRTC＋VAD＋`interrupt_response:true` 的自动打断路径里，不需要客户端再次计算截止毫秒数并发送 `conversation.item.truncate`。** 服务端管理输出缓冲，负责中断、清理未播放音频及调整自己的会话上下文。WebSocket 的播放队列由客户端管理，才需要客户端报告截断位置。不能把 WebSocket 的职责照搬到当前 WebRTC 路径。

| 需要完成的事 | 当前职责归属 |
| --- | --- |
| VAD 自动打断正在生成的响应 | Realtime 服务端 |
| 清理服务端剩余音频、截断服务端会话 | WebRTC Realtime 服务端 |
| 取消本地工具、待审批动作和旧回合 | CharaMate |
| 防止旧工具回来后重新创建回答 | CharaMate 的身份、代际和状态检查 |
| 更新页面、SQLite 和之后重建的历史 | CharaMate；服务端不会直接改本地数据 |

举一个完整例子：用户让 Agent 查周六安排，R-A 说“我查一下”并调用 `memory.search`。搜索还在宿主执行，用户改口“先别查，帮我看论文”。Realtime 可以停掉 R-A，却不会替 CharaMate 取消数据库工作。如果宿主仍接受旧结果并发送工具输出和下一次 `response.create`，Agent 就可能重新讲起日程。因此本地仍要使旧任务失效、尽力取消工具，并拒绝它的迟到接续。这里需要的是任务取消，不是再做一次音频截断。

当前代码确实在自动打断后又发了一次 `response.cancel` 和 `output_audio_buffer.clear`。这是当前统一取消流程的行为，不能把它解释为服务端漏做了必要步骤。[服务端事件文档](https://developers.openai.com/api/reference/resources/realtime/server-events#output_audio_buffer.cleared)明确说明，输出缓冲清理事件既可由 VAD 自动中断产生，也可由客户端主动 clear 产生。重复 cancel 可能得到没有活跃响应的错误；驱动目前忽略 `response_cancel_not_active`。

更清楚的候选改进是区分中断来源，而不是给每种来源都无条件发送相同命令：

| 中断来源 | 服务端已做什么 | 宿主还要做什么 |
| --- | --- | --- |
| VAD 已自动打断 | 按自动打断协议取消及处理输出 | 处理本地状态、关联回执；通常不再重复 cancel／clear |
| 用户点击停止回答 | 没有讲话事件替应用表达停止 | 主动取消仍在生成的响应，清理未播完输出，关闭本地工作 |
| 自动打断关闭，宿主确认用户确实插话 | 等宿主决定 | 确认后主动取消、清输出和使旧任务失效 |
| 暂停、结束或应用主动终止任务 | 取决于是否还保留连接 | 按生命周期停止媒体与工作，不依赖用户再说一句话 |

主动停止且连接仍保留时，取消生成和清输出有不同意义：模型可能已经生成结束，但音频还在播放。[客户端事件文档](https://developers.openai.com/api/reference/resources/realtime/client-events#output_audio_buffer.clear)给出手动 cancel／clear 的用法。这不意味着自动打断路径也必须额外重发一遍。`output_audio_buffer.clear` 本身不带目标 responseId；如果以后做延迟重试，也不能让旧任务的清理命令误清新回答。

当前客户端只接收 `conversation.item.truncated`，没有在这条路径发送 `conversation.item.truncate`。它上报的 audioEndMs 是本地观察值，不是已发给服务端的截断指令。本地抑制旧输出可以控制播放器出口，但不能把这个措施描述为服务端无法停止播放的证明，也不能声称它准确测量了用户实际听到的位置。

### 3.5 打断后，字幕和本地历史实际保留到哪里

假设原回答是“周六下午三点，我们先去咖啡馆，再去看展”。页面已收到完整转写，声音只播放到“周六下午三点”，用户就说“等等，我下午没空”。

| 观察对象 | 此刻可能的内容 | 不能据此推断什么 |
| --- | --- | --- |
| 模型生成 | 完整句子 | 不能推断音频播完 |
| 页面文字 | 完整句子 | 不能推断用户读过或听过后半句 |
| 音频播放 | 只到第一分句 | 不能按文字字符比例精确求截止字 |
| 服务端会话 | 按服务端打断协议处理 | 不代表本地消息被同步裁剪 |

当前 Main 的 `#appendAssistantTranscript` 和 `#completeAssistantTranscript` 会拒绝已经标成 interrupted 的回合继续追加文字，但不会把之前存下来的文字裁短。`item.truncated` 分支只记录指标，并在符合条件时写 audioEndMs，没有产生“已播放文字前缀”。官方也说明截断不会提供一份精确对齐的截断后文字；不能假定回执会把缺少的对齐信息补给客户端。

接着要分两条源码路径看，而不能笼统说“下一次只保存到这里”：

1. **生成中被打断。** `#closeRun` 把仍在 streaming 的消息改为 interrupted，已保存文本留在消息中。[ChatRepository](../../../src/main/chat/chatRepository.ts)的 `listContextMessages` 只选 completed 消息；Voice 的 `history()` 也筛选 completed。因此这段回答在重建历史时可能整条被排除，不是保留一个准确的已播放前缀。用户已经落盘的请求与其他已完成消息另按各自状态处理。
2. **生成已完成，音频尚未播完。** `#responseDone` 调用 `#completeTurn`，把消息和回合标为 completed，界面仍可保持 speaking。随后 `#interruptTurn` 对 completed 回合提前返回。因此存在完整转写仍按已完成消息被后续历史选中的风险。服务端即使已截断，重连时再从 SQLite 注入全文，也可能把未播完的内容重新带回模型。

以上是对[当前服务代码](../../../src/main/voice/voiceService.ts)的静态路径核对，不是本次已经复现或修复的线上故障。需要补的事件回放是：`transcript.done → response.done → 音频仍在播放 → speech_started → truncated → 重建同一 Chat 历史`，同时检查消息、VoiceTurn 和注入服务端的内容。

此外，截断事件应根据其协议 itemId 找到原输出所属回合，不能仅假定到达时“当前回合”还是被打断的那个。当前截断分支查询的是当前回合；新回合已经开始后，旧回执能否正确归属，也是需要回放确认的边界。它同样不能靠多发一次 truncate 解决。

### 3.6 如果希望“只留下已经播出的内容”，还缺什么

先明确产品语义：已经展示过的文字与已经播放过的音频是两个事实。把页面文字事后删掉，也无法撤回用户已经读到的信息。以下是待决策的呈现方案，不是当前同时存在的产品模式：

- 保留已生成的文字，标明语音被打断、未完整播出。后续上下文和 Memory 不得把全文当成已经口头传达完成。
- 让字幕跟随播放，并在打断时只保留已播放部分。这需要文本片段与音频时间的可靠对应，以及对应输出的播放游标。

如果选择后者，完整流程应是：立即停播和停止旧工作；固定旧响应的截止位置；保留截止前已完整播放的文字片段；把截止处尚未完整播放的片段视为不确定；更新界面和本地历史投影；处理同一服务端会话与重连恢复；拒绝旧响应迟到片段重新补回文字。没有时间对齐时，不能用“音频播了三分之一，所以保留前三分之一字符”代替。

至少要分别表达“生成是否完成”和“播放是否完成或中断”。即便 Run 的生成已经完成，也需要能记录后来的播放中断，而不是直接返回。具体持久字段应由 Voice 的正式契约决定，不能为面试说明先加一套平行状态库。

在无法获得可靠前缀时，可以给后续上下文保留用户请求和“上次回答中断、未确认完整传达”的事实；对无法确认的尾部避免宣称“我已经告诉过你”。已经完成的工具效果则必须保留。例如保存文件已经成功，只是“保存好了”没播完，不能因此抹掉保存结果。Memory 同样要区分工具确实完成、Agent 生成过一句话、用户实际作出承诺这几类来源。

## 4. “全双工”应拆成三层回答

**第一层，媒体双向并行。** 麦克风采集和输出音轨可以同时存在，不必“播放时整段关麦”。当前具备这层基础。

**第二层，应用能及时让话。** 新 speech_started 可以停播、取消旧回合，并接续新输入。当前有相关身份和取消机制，但麦克风／扬声器／噪声条件下的成功率需要实测。

**第三层，自然重叠交流。** 能区分咳嗽、附和、插话、改口、说给别人听，必要时一边听一边继续说。这不由“WebRTC 支持双向音频”自动获得。当前 server VAD 分段编排不能证明已完成这一层。

还有一个真实限制：**当前等待工具审批时调用 `#setCapture(active,false)`，审批结束再恢复。** 更准确地说，Renderer 把已有麦克风音轨的 `enabled` 设为 false，并不是调用 `stop()` 释放设备。用户的讲话因此不能沿当前路径正常进入识别，所以不能宣传始终全双工。这样简化了审批期间输入和执行状态，但也让用户难以用语音说“算了”；改善方式见 4.4。

### 4.1 建议怎么改善，哪些需要实验

| 层次 | 建议方案 | 验证重点 |
| --- | --- | --- |
| 音频采集 | 检查实际设备处理能力、音量和回声；保留可见静音状态 | 外放／耳机、蓝牙、噪声下的误打断和漏听 |
| 结束说话判断 | 在目标 Azure deployment 比较当前 server VAD 与确实支持的语义断句 | 是否截断“周五……不，周六”、响应等待是否过长 |
| 审批期间 | 持续接收输入；明确取消或修改才使对应审批失效，解释请求可以保持等待 | 不能把任何人声都当取消，也不能用“嗯”冒充授权；旧批准不能放行新参数 |
| 工具等待期间 | 继续接受用户纠正，维持回合和 effect 身份 | 已提交效果与可取消工作明确分开 |
| 附和与真正打断 | 在带重叠讲话的数据上验证交互策略 | 不能只按文本“嗯”一刀切；语调、时机和当前话轮也重要 |
| 多人 NPC | 游戏权威提供发话者、距离、朝向、目标对象和会话成员 | 不能把旁人的谈话都当对 NPC 的指令 |

这些是待比较方案，不在本轮偷偷加另一套语音管线。尤其 semantic VAD 主要解决结束说话时机，不能单独解决误唤醒、说话人或授权语义。

### 4.2 Moshi 论文给了什么启发

[Moshi v1](https://arxiv.org/html/2410.00037v1)（2024-09）将输入、输出音频作为并行流建模，并结合文本表示；模型可在对方讲话时输出声音或静音，训练包含重叠与打断。它说明真正自然的双工涉及模型与训练数据，而不只是通信协议。

迁移启发是把“持续听”和“是否开口”分开评价。不能因为开源模型会全双工，就断言它能等价替换当前中文角色、Memory 和 Tool 能力。若另做实验，应同时看中文与混说、任务成功、工具正确性、打断、资源和角色一致性，不只比较演示视频里的抢话速度。当前没有接入 Moshi。

### 4.3 没说完、旁人讲话、嗯啊附和，分别怎样处理

#### 4.3.1 先把问题分开

| 例子 | 真正需要判断什么 | 只改 VAD 阈值为什么不够 |
| --- | --- | --- |
| “帮我约到……呃……周六” | 用户是否结束这一轮表达 | 停顿可能只是思考；把静音等待统一拉长又会拖慢所有回答 |
| 用户对室友说“等一下” | 当前声音是否属于对 Agent 的输入 | 这是清晰人声，声音更大不代表更相关 |
| Agent 讲解时用户说“嗯嗯” | 用户是在附和，还是想取得发言权 | 附和也是真实语音，不是简单的背景噪声 |
| Agent 问“继续吗”，用户说“嗯” | 用户是否给出了有效短回答 | 把“嗯”加入忽略词表会漏掉正确回答 |
| Agent 将执行时用户说“嗯？别动” | 用户是否要求立即停下 | 不能等到整句最终转写才开始考虑取消 |

当前是优先快速让话的简单方案，代价是误打断。若目标是自然陪伴，需要分别评估结束输入、发话对象和插话意图，不能把 semantic VAD 当成三个问题的统一答案。

#### 4.3.2 结束输入和发话对象

结束输入可以先比较当前 server VAD 与目标部署支持的 semantic VAD。测试要包含句中犹豫、拖尾、改口和明确结束。例如“改到周五……不，周六”应尽量作为完整意图处理；“就定周六，没别的了”应及时开答。前者少抢答，后者少等待，是需要共同观察的两面。`eagerness` 或静音等待的取值通过代表性录音和真人使用选择，不把某个服务示例值当本项目最佳配置。

发话对象则优先使用已有的明确信息。桌面先验证 AEC 是否挡住 Agent 自己的外放，再检查麦克风距离、方向和旁人声音。游戏若有独立玩家音轨、会话成员和目标 NPC，应直接使用这些信息，避免先把多人声音混在一起再猜是谁。说话人分离能区分不同声音，并不自动知道谁是账号用户，更不证明一句话说给谁听。同一个用户也可能正在对室友讲话。

无法确定对象时，不要把背景句子转成用户承诺或工具授权。唤醒词、明确呼叫和按住说话可以作为交互候选，但不能未经体验比较就要求每句话都重复叫名字。当前没有证明已经具备完整的多人语音隔离或发话对象分类器。

#### 4.3.3 插话判断用什么特征，怎样选择阈值

候选方案是在检测到语音后，用低延迟判断器结合声学和当前话轮状态，决定继续讲话、让话或等待更多证据。可比较的特征包括连续语音长度、语调和重音、是否继续展开、Agent 是否刚问了问题、当前是否等待审批，以及在可用时取得的中间转写。

“停”“不是”“先别执行”等内容有价值，但不能依赖当前 whisper-1 的非空最终转写来承诺几百毫秒内做完语义判断。当前没有证明可获得及时稳定的逐词中间结果。若需要更快判断，要验证音频分类器或支持流式结果的识别路径，测量它们的额外延迟；不能每个音频帧都启动完整对话模型。

训练或评估标签至少区分真实插话、附和、无关讲话和模糊样本，标注时提供当前 Agent 话语及必要音频，而不只给文字“嗯”。真实纠正和停止请求要覆盖短句，不能用统一最短时长或最少字数把它们过滤掉。阈值在开发集上选择，再在未参与选择的说话人和场景上报告：附和误打断、真实插话漏检、停止延迟、短回答丢失。模型自报的分数不是天然校准的概率，当前也没有一条已验证的阈值可直接照搬。

#### 4.3.4 接到当前系统时，流程要怎么变

以下是待验证的宿主管理方案，不是当前实现：

```text
持续接收输入音频
→ VAD 提供人声线索，先不直接销毁旧 Run
→ 判断是否面向 Agent，以及是否需要接过话轮
   → 附和：允许旧回答继续，不建立一条无意义的新任务
   → 真正插话：停止旧输出，使旧工作失效，接收完整新输入
   → 暂不确定：积累必要证据；不能无限期压住明确的停止请求
→ 确认用户表达结束后，宿主创建对应回答
```

要让这条判断有效，不能保留“服务端已经无条件打断，再慢慢问是不是附和”的配置。支持的 Realtime 路径可以关闭自动取消与自动开答，例如下面的 OpenAI GA 配置片段；实际 Azure 端点仍需核对。`low` 是比较候选，不是生产选定值：

```json
{
  "type": "session.update",
  "session": {
    "type": "realtime",
    "audio": {
      "input": {
        "turn_detection": {
          "type": "semantic_vad",
          "eagerness": "low",
          "create_response": false,
          "interrupt_response": false
        }
      }
    }
  }
}
```

仅改配置仍不够：当前 Renderer 在 speech_started 直接静音，Main 直接取消旧回合，这两处也要改为消费经过确认的决定。反过来，输入如果已经由服务端提交为会话 Item，宿主决定忽略它时，只是不创建 Run 并不能阻止它进入未来上下文；还要按协议管理该 Item。尚未提交的缓冲与已提交的会话 Item 不是同一对象，不能混用 clear 和删除。

“先静音，误判后恢复”也有条件。对当前远端 WebRTC 音轨，静音不等于把服务端播放游标暂停；静音期间音频可能继续前进。只有拥有可暂停、可恢复的缓冲及准确游标，才能声称从原位置续播。若已取消生成并清掉音频，就只能依据上下文重新接着讲，不能称为无损恢复原响应。

#### 4.3.5 工业参考应该学什么

2026-11-01 阅读的 [LiveKit adaptive interruption 官方文档](https://docs.livekit.io/agents/logic/turns/adaptive-interruption-handling/)把附和识别放在 VAD 之后，用音频判断是否应让出话轮。它说明可以把这个能力做成独立的低延迟环节，而不是依靠对话大模型在回答中自我克制。

它的 Realtime 接法要求关闭服务端 turn detection，由宿主控制输入提交；不等于上面的“保留服务端断句、关闭两个自动行为”示例。在整段输入作为一个单元的接法中，丢弃附和可能丢弃整段，所以“嗯，等一下我改主意了”这类混合输入必须测试。当前没有接入 LiveKit，也没有因此决定引入其框架、服务或另一条生产语音路径；这里借鉴职责划分与测试方法，不把官方演示效果当成本项目中文指标。

### 4.4 审批期间持续收音：从“算了”到“改成周日”

当前链路是：工具需要审批 → 保存 pendingTool 与 approval → `#setCapture(active,false)` → 等待审批决定 → `#setCapture(active,true)` → 继续或拒绝工具。调用最终落到音轨 `enabled`；显式静音、暂停和会话关闭等状态仍由原有条件控制。

建议把“能否接收用户声音”和“某个工具能否执行”分开。最小改进可以是：审批期间继续听，允许用户取消、修改和询问；批准仍走现有审批卡。这样先解决不能口头叫停的问题，不必同时承诺已经实现完整语音批准。

不能只删除关麦那一行。否则当前 speech_started 会取消旧回合及审批，连轻声“嗯”都会变成取消。因此要与 4.3 的输入判断一起处理：

| 审批期间输入 | 建议行为 | 原审批是否仍有效 |
| --- | --- | --- |
| “算了，不要执行” | 取消待执行动作，给原调用真实取消结果 | 否 |
| “日期改成周日” | 旧参数失效，提出新参数并重新审批 | 否 |
| “这个操作会改哪些内容？” | 解释待审批动作，继续等待决定 | 可以保持，前提是参数未变化 |
| 附和或含糊的“嗯” | 不执行，也不机械地取消 | 保持等待 |
| “批准刚才这个操作” | 仅在产品正式支持语音批准后，绑定具体动作核验 | 只能批准对应参数版本 |
| “先做另一件事” | 明确处理原动作的暂停或取消，再接新任务 | 不可暗中放行 |

以修改日历为例，A1 对应调用 C1 和参数 v1“周六 15:00”，状态为 pending。用户说“改成周日”后，流程应是：确认这句话在修改当前动作 → A1 失效 → 重新构建参数 v2 → 新调用／审批 A2 → 等待对 A2 的决定。用户之后点击旧卡 A1 的批准，不能把批准移到 A2。这里的 v1、v2 是说明所需身份关系的示例，不是声称当前数据库已有该字段。

若进一步支持语音批准，必须能确定用户批准的是哪一个 approvalId、callId 和冻结的参数版本。不能把一次泛泛的“可以”授权给后来已经改变的动作；也不能让模型自行生成一个“用户已批准”标记绕过宿主检查。询问操作影响可以形成对话，但不能仅因多了一段语音就销毁仍有效的审批；动作身份与解释回合的关系要在同一个运行时中明确管理。

批准点击与语音取消并发时，进入同一串行状态转换：检查仍为 pending、动作与参数未变、尚未执行；先取消则后批准无效，先批准并提交外部操作则后取消不能伪称回滚。网络请求不应放在长数据库事务里等待。已提交的外部动作根据其回执、幂等标识或查询能力核实结果，保留实际效果。

如果连接仍继续使用，先前函数调用必须获得对应 call_id 的真实终态结果，不能只删页面审批卡，留下悬空调用。旧结果也不能不经当前性检查就重新触发旧语音。上述改变需要 Voice／Approval／Run 的集成验收，本次仅记录方案，没有修改审批模式或执行规则。

## 5. 项目遇到过什么问题，怎样解释修复

| 真实记录中的问题 | 为什么会发生 | 采取的处理及证据边界 |
| --- | --- | --- |
| “只听到半句”，后半段仍有生成 | 同 generation 的前一 response 停止事件，误关闭了后一个正在播放的 response | 以 responseId 管理开始／停止／释放；驱动只让当前播放 response 的 stopped 关闭声音 |
| Memory 工具使会话创建失败 | Azure 目标路径不接受某些根级 JSON Schema 组合 | 在 Realtime 适配边界用 arguments 包装，执行时严格解包并验证原 schema；没有改领域工具意义 |
| 早期 truncate 越界报错 | 客户端估算的 audio_end_ms 大于服务端音频长度 | 保留当时相关错误和处理；当前 WebRTC 截断路径见第 3 节，不能继续用旧实现描述 |
| 音频测试永远等不到一句结束 | 测试输入 WAV 播完就停止供给，没有尾部静音供 VAD 判断 | 修外部测试驱动继续提供静音，不在产品随意 sleep |
| 模型说网页仍在加载，却没有可用页面 | 空白 about:blank 曾被当作成功结果 | 返回真实工具错误，使后续语音依据实际状态 |
| 转写把专名或课程说错 | 词汇／发音／采集及识别存在误差 | 有领域词提示的小样本改善，但没有彻底消灭近音误识别 |

详见[架构](../../benchmarks/voice-architecture.md)、[传输](../../benchmarks/voice-transport.md)、[工具接续](../../benchmarks/voice-tool-join.md)。这些都是历史记录，不是本次新跑的结果。

历史转写提示比较只有中文、英文、混说三段：两种提示都保留主语言3/3，中文相关输出用简体的观察为0/2对2/2；关键词提示改善了CharaMate拼写，但Haidian被听成Haitian的问题两边都存在。后续真实两段WAV又出现“淘逸客／陶艺课”等偏差，虽该案例没有把错误课程固化进记忆，也不能证明形成器普遍能纠正ASR。每个分母都很小，不能宣称中文识别准确率已经达到某个百分比。

早期受控比较各只有 3 次相同合成音频：一种配置从说话结束到首音频约 673／705／727 ms，宿主显式编排的一种配置约 836／840／942 ms。它说明编排会增加等待，不能称线上 p95，不能替代当前整个版本的性能，更不能代表人耳在真实设备上实际听到的时刻。

## 6. “一起”识别成“仪器”：先找是哪一层错

“一起”和“仪器”是近音且声调不同，结合上下文通常容易区分，但弱声调、噪声或短句会增加混淆。要拆成四个观测：

1. 麦克风实际采到了什么：有没有开头被裁掉、爆音、回声或别人的声音？
2. 转写给了什么：屏幕上是否真是“仪器”？
3. 原生语音模型理解和回答了什么：它可能仍听懂“一起”，也可能没听懂。
4. 后续哪一层使用了转写：Run、Cognition、Memory 形成或 Tool 参数是否被错误文本影响？

Realtime 的原生音频理解与输入转写不是同一个结果。官方 [Realtime client events](https://developers.openai.com/api/reference/resources/realtime/client-events) 将输入转写说明为异步辅助信息，而非模型听到内容的精确等价物。即使原生回答正确，项目仍会把最终转写保存为用户消息，所以记忆可能受到污染。反过来，字幕看起来正确也不保证模型行为正确。

### 6.1 一个错误如何扩散

用户说“下次我们一起去看展”，转写为“下次我们仪器去看展”。

- 界面展示只是第一处影响；不是改一个显示字符串就结束。
- Cognition 读到转写，可能误以为讨论仪器或工作安排。
- 形成模型可能“合理化”成“用户打算带仪器去看展”，把不存在的对象变成长期事实。
- 之后 search 正确找到这条错误记忆，最终回答仍然错。此时更好的召回反而更稳定地传播错误。

因此要保留“这是语音转写来源”与用户后续明确纠正的关系；不允许无证据的文本润色升格为用户确认。本项目目前未证明已经具有完整的 ASR 可信度／歧义处理策略，不能仅凭有 provenance 就声称解决了误识别。

## 7. 减少识别错误的分层方案

### 7.1 先修采集和边界

检查静音、实际麦克风、音量、采样与设备切换；测试 AEC 是否能去掉 Agent 自己的外放，避免把自己的回答识别成用户。追踪 speech_started／stopped、音轨状态及设备变化。音频有问题时，文本后处理不能恢复缺失的声音。

断句太早可能把“周五……不，周六”拆成两个互相冲突的指令。比较断句要用实际改口和犹豫语料，兼顾等待时间；不能只增大静音阈值，导致所有用户都等更久。

口癖要分成两种影响。用户习惯“那个……我想一下”，首先影响什么时候算说完，需要话轮策略容忍思考；转写完成后才删除“那个”不能挽救已经发生的抢答。展示文本可以适当整理重复和填充词，但原始识别与语义理解应可区分。“周五，不，周六”中的否定和改口不能当口癖删掉，也不能把两个日期各记成一个当前约定。

### 7.2 给真实相关的词汇，不强迫听见某词

当前 [realtimeSessionRequest](../../../src/main/voice/azureWebRtcSession.ts)使用固定 prompt：

```text
简体中文, English, CharaMate, Chat, Agent, Settings,
Voice, Model, Provider, Realtime, Azure OpenAI
```

没有按用户、任务或最近纠正动态构建词表。历史 3 段音频比较里，关键词方式改善了简体输出和 CharaMate 拼写，但一个地名仍被识别错，说明提示不是保证。

#### 7.2.1 提示到底发给谁

| 位置 | 接收方及作用 | 容易产生的误解 |
| --- | --- | --- |
| `audio.input.transcription.prompt` | 辅助转写服务，提供相关词汇或模型支持的背景 | 以为给 Realtime 写过 Persona，就等于 ASR 也拿到了全部背景 |
| Realtime `instructions` | 原生语音模型，指导角色、理解、回答与工具行为 | 以为一句“仔细听清楚”就训练好了识别器 |
| 转写后的语义解释 | 宿主准备、Cognition 或其他消费者 | 以为润色后的文字就是声学模型的原始结果 |

例如 Cognition 知道用户在写论文，不表示独立 ASR 自动知道当前软件叫 Overleaf。需要明确把相关词汇传到转写接口，而不是只在最终回答提示中提一次。

#### 7.2.2 从 Overleaf 场景构建一次动态提示

下面是候选流程，当前尚未实现：

1. 输入包括当前任务“毕业论文”、最近讨论“参考文献”、当前相关应用 Overleaf，以及用户明确确认过的方法名和人名。只取与当前交流有关的事实，不扫描后把全部长期记忆注入识别器。
2. 构建候选词，把当前界面和任务直接相关的名称优先保留；合并重复写法，删除过时任务和无关游戏人物。别名用于找回同一名称，不代表所有同音词必须替换。
3. 根据目标模型能力生成配置；在新一段输入开始前更新，并确认服务端接受。若接口不能按所需时机更新，先验证可行的会话边界，不在宿主假装已经生效。
4. 为这次输入关联所用提示版本、识别模型和 input itemId，避免一句话中途换了词表却无法解释结果。版本记录是建议的复现信息，不是当前已存在的用户画像流水线。
5. 收到转写后评估名称是否识别正确，保留明确纠正；下一次相关任务才使用新词条，不立即生成无限扩张的全局词表。

对于当前 whisper-1 接口，最接近现有做法的实验是扩展关键词 prompt，例如：

```json
{
  "model": "whisper-1",
  "prompt": "简体中文, English, Overleaf, LaTeX, BibTeX, CharaMate"
}
```

这是候选配置片段，不是修改后的生产值。[Realtime 官方接口](https://developers.openai.com/api/reference/resources/realtime/subresources/client_secrets/methods/create)把 whisper-1 的 prompt 描述为关键词提示。它帮助识别候选，不要求输出必须包含每个词，也没有提供一个可随意套用的逐词加权参数。

对明确支持更丰富字段的转写模型，可以区分背景、字面词汇和语言提示：

```json
{
  "prompt": "用户正在讨论毕业论文写作、排版和参考文献管理。",
  "keywords": ["Overleaf", "LaTeX", "BibTeX", "CharaMate"],
  "languages": ["zh", "en"]
}
```

这个对象只展示输入上下文，不是可直接提交到当前 Azure 的完整请求。`prompt` 描述录音话题，`keywords` 给可能出现的具体拼写，`languages` 表达可能中英混说。2026-11-01 阅读的 [OpenAI transcription 文档](https://developers.openai.com/api/docs/guides/transcription)将这组能力列在 gpt-transcribe／gpt-live-transcribe 下；不能把字段原样塞给 whisper-1，也不能由 OpenAI 公共 API 推断 Azure deployment 一定支持。原生音频模型如何理解，与独立转写如何落字，还要分别验收。

#### 7.2.3 热词加权和普通提示有什么不同

有些识别器提供明确的 phrase list，在识别时提高列出词汇的候选权重。下面是 Azure Speech SDK 的使用示意，不是当前项目依赖或 Realtime 配置：

```ts
const phrases = sdk.PhraseListGrammar.fromRecognizer(recognizer);
phrases.addPhrase("栖木咖啡馆");
phrases.addPhrase("Overleaf");
phrases.setWeight(selectedWeight);
```

`recognizer` 是该 SDK 的识别器，`selectedWeight` 是实验选定值，不是在这里拍定的数字。[Azure phrase list 官方文档](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/improve-accuracy-phrase-list)说明这种提示在运行时使用，不需要重新训练模型。它属于 Azure Speech 的能力，不能因为同属 Azure 就声称当前 OpenAI Realtime 路径已经具有该 SDK 接口。

加权改变的是候选偏好，不是结果字符串替换。名单太大或权重太强，可能把普通词硬听成某个热词。因此实验必须同时录“周六我们一起去看展”和“把仪器放在桌上”；只统计前一句被修好，会漏掉后一句被改坏的代价。对“一起／仪器”这类常见近音词，相关语境、声学信息和必要确认通常比全局强推一个词更合理。

### 7.3 对关键歧义确认，对普通口误保持自然

| 情况 | 合理处理 | 不合适的处理 |
| --- | --- | --- |
| “我们仪器去看展”，只是随口邀约 | 可自然回应“一起去的话，你想先看哪个展？”；这仍是暂定理解 | 把“仪器”永久记成兴趣 |
| “把仪器放到桌上” | 保留真实器具含义 | 全局正则把仪器替换成一起 |
| “给小琪转五百／五千” | 针对对象与金额确认，未明确前不执行 | 选语言概率更高的值直接执行 |
| “周五……不，周六” | 以完整改口及最新确认解释，并修订旧事实 | 把两半都存成当前约定 |
| 用户说“我说的是一起” | 保存明确纠正和来源关联，更新依赖它的事实 | 只改字幕，错误 Memory 留着 |
| 非用户讲话或 Agent 回声 | 不形成用户承诺 | 用内容流畅作为来源可信的证明 |

低影响闲聊可用轻量的确认式表达；长期承诺、身份、日期、金额、对象和外部动作应更谨慎。原则是按**误解的代价**分配确认，不是所有句子都问“你是不是说……”。

### 7.4 置信度从哪来，阈值怎么定

当前代码没有提供一个可靠的逐词“识别正确概率”，也没有可以直接取用的 whisper-1 混淆候选列表。不能让 Agent 自报 0.92 后当作校准概率，更不能把转写模型的 token log probability 当作整个动作成功率。

若候选端点提供合法的 logprobs／候选／音频质量特征，可在独立标注集验证它们是否预测错误；字段可用性要按接口确认。若没有，就用可观察的语义冲突、关键槽位、用户改口、已有事实冲突等提议澄清，并诚实保留不确定性。

教学上可写：

```text
确认的期望代价 = 确认负担 + 确认后剩余错误概率 × 误执行代价
直接执行的期望代价 = 当前错误概率 × 误执行代价
```
只有实际标注能估计概率和剩余错误；确认也可能听错，不假设它万能。金额错误的代价高于闲聊近音，阈值当然不该相同。公式是方案解释，不是本项目已经训练过的决策器。

### 7.5 如果更换 ASR 或加入二次识别

先固定音频、任务、上下文与结果标准，比较当前路径和一个候选；不要同时改变 VAD、麦克风处理和模型后只报告“识别好了”。

选择性二次识别可以作为实验：只在重要歧义时重读获准保留的短音频，比较收益、延迟、费用以及两模型共同出错。但它不是当前已存在的备用管线，也不保证投票就对。用户原音频无法取得时，不能假装还有声学证据；应直接做必要澄清。

最终若候选胜出，保留一条选定生产实现。不是为了面试把多 ASR、多 TTS、多种连接都长期放进产品。

### 7.6 用户画像怎样参与，而不是把所有记忆交给 ASR

适合个人化的是有依据、范围明确的语言使用信息，不是模型猜测的身份标签：

| 信息 | 可靠来源 | 作用位置 | 必须保留的边界 |
| --- | --- | --- | --- |
| 人名、店名、研究方法等正确拼写 | 用户明确输入或纠正 | 相关场景的词汇提示、实体匹配 | “小祈”正确不代表所有“小齐”都错误 |
| 一个实体的习惯叫法 | 用户说明或反复明确对应 | 查询词汇及别名解析 | 不能把未经确认的近音误识别登记成别名 |
| 中英混说需求 | 用户选择和可验证交流 | 语言提示、测试集分层 | 强行固定一种语言可能破坏混说 |
| 思考停顿、附和习惯 | 多次交流及实际反馈 | 话轮判断候选 | 不是提高 ASR 字词准确率的同一个开关 |
| 一次转写纠正 | 原输入与后续确认的关联 | 修正此次语义和受影响事实 | 不自动训练出个人声学模型 |

例如用户明确说“我朋友是小祈，祈祷的祈”，可以将这个已确认事实作为个人词汇来源。下一次谈论这位朋友时，构建词表的过程取出“小祈”；谈论姓齐的另一个人时，不应做全局替换。建议复用已有 Memory 的事实、来源和实体作用域，由语音域构造当轮提示，不为此先复制一份永久用户画像数据库。

个人词条至少要能说明它来自哪次确认、指的是哪个实体、适用什么场景、当前是否仍有效。频繁出现不等于正确，Agent 自己说过的名字也不等于用户确认过。用户纠正后，应使相关词条和受影响记忆更新；不能让旧错误在词表中不断提高权重。

话轮偏好的个人化也应保守。观察到一次长停顿，可能是用户临时找东西，不足以固定成“这个用户总是慢慢说”。在有多次证据和体验比较之前，先保留可撤销的场景判断；不凭口音推断籍贯再硬套替换规则。

### 7.7 口音适配为什么不能只靠热词

词汇提示回答“这里可能出现什么词”，声学识别要解决“这段声音更像哪个发音”。用户持续出现声母、韵母或声调混淆时，仅把正确词写进 prompt 并不等于改变了模型对该用户发音的建模。

合理的排查顺序是：先确认采集和切分 → 用同一录音测试当前模型 → 加入相关词汇背景，观察剩余错误 → 若特定口音仍持续出错，再比较候选识别模型 → 只有数据和成本都支持时才考虑定制。需要分别看专名错误、普通词错误、数字和否定错误，不能把所有错误统称为口音。

例如 [Azure Custom Speech](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/custom-speech-overview)允许用文本以及带参考转写的录音改进领域或音频条件适配。可借鉴的流程是收集合法取得的代表性音频、人工核对文字、分离训练和评测、比较基础模型与定制模型，再评估部署成本。这不是当前 Realtime 的个人化训练能力，也不意味着每个用户都应训练并运行一个专属模型。

如果识别器支持发音词典，还需要核对目标语言和接口；给 TTS 指定怎么读一个名字，不会自动改变 ASR 怎样听这个名字。若采用音频重识别，必须真的能够取得那段音频；当前只持有转写时，不能把文字模型的猜测称为声学复核。

### 7.8 一次纠错怎样贯穿提示、确认和记忆

下面是拟建流程的教学例子，用来串起前面的措施，不是已经跑通的新实验。用户在 Overleaf 写论文，准备与朋友去咖啡馆讨论参考文献：

1. **输入前构建背景。** 当前任务给出论文／参考文献主题，用户以前确认过店名“栖木咖啡馆”。按目标接口能力提供 Overleaf、BibTeX、栖木咖啡馆等相关词；记录本段输入所用配置版本。
2. **用户说话。** “周六我们一起去栖木咖啡馆，顺便看看 BibTeX。”假设 ASR 仍返回“周六我们仪器去西木咖啡馆，顺便看看比特克斯”。提示没有保证成功，原始结果要如实保留为本次识别输出。
3. **提出暂定解释。** 结合主题和已确认店名，系统可以提出“一起／栖木咖啡馆／BibTeX”的解释。但文字合理不代表声音已经复核，也不能据此登记一件“带仪器出行”的事实。
4. **确认会影响计划的内容。** Agent 问“你是说周六一起去栖木咖啡馆讨论参考文献，对吗？”用户回答“对，一起去，栖木是栖息的栖、木头的木。”确认引用当前计划，而不是泛泛问一句“对吗”却不说明确认对象。
5. **形成记忆。** 如果需要调用当前 `memory.record`，仍由宿主解析真实 episode；原输入、错误转写和用户后续纠正应能关联。形成结果依据用户确认的计划，不把语义修饰器的猜测当用户原话。这里要求的 ASR 歧义表示及消费者处理尚未完整实现，不能因为已有来源机制就声称自动解决。
6. **更新后续提示。** 在以后相关讨论中使用已确认店名。若此前错误事实已经形成，还要走 Memory 的修订、索引更新与读取当前版本，而不只是改字幕或更新一个热词。当前章负责语音来源，完整修订机制见[第 17 章](17-memory-control-and-retrieval-evolution.md)。
7. **保留反例。** 用户下一次说“实验室的仪器坏了”，应正常识别仪器，不能因前一次纠错创建全局“仪器→一起”规则。

为复盘这类问题，建议最少关联 input itemId、识别配置版本、原转写、暂定解释、明确确认来源和产生的 Memory／Tool 身份。它们是需要对齐的证据，不是在普通产品界面展示的技术字段，也不要求默认上传原音频。原生语音模型可能已经听懂、转写却错了，这两种结果应分别保留观察，不用其中一个替另一个背书。

## 8. 如何测试，才算证明了改进

### 8.1 三类验证分开

| 验证 | 输入 | 可以证明 | 不能证明 |
| --- | --- | --- | --- |
| 确定性事件回放 | response／input／tool 的乱序与重复事件 | 代际、幂等、取消、状态转换 | 真实回声消除和口音效果 |
| 固定录音与真实 Provider | 同样音频、模型配置与语料标签 | 识别、端点行为、工具及回答差异 | 房间和设备变化下的全部体验 |
| 真人设备对话 | 耳机／外放、距离、噪声、附和、真正插话 | 声学与交互体验 | 无限制规模或所有人群稳定性 |

现有[驱动测试](../../../src/renderer/features/voice/WebRtcVoiceDriver.component.test.tsx)与[跨域语音测试](../../../tests/integration/voiceRuntime.test.ts)是第一类的重要基础。本次只读测试定义，没有执行，不把它们当当前真实声学验证。

建议最小语料覆盖：一起／仪器、取消／继续、周五／周六、五百／五千、两个近音 NPC 名、中文夹英文装备名、句中停顿改口、外放回声。正例和反例都要有，不能为了修“一起”只录一起。按说话人／句式分组切分，保留未参与调词表的人和表达。

作为收集成本算例，40 个语义场景 × 3 名说话人 × 2 类设备 × 2 种环境为 480 段；同一人重复录制不是 480 个独立用户。实际规模随误差区间和成本确定，不把这个数当门槛。

### 8.2 指标怎样定义

- 中文字符错误率 CER：替换、删除、插入数量除以参考字符数。参考“一起去看展”与“仪器去看展”是 2 次替换／5 字，即 40%；这个短句比例不代表整体语料 CER。
- 关键槽位正确率：对象、时间、地点、否定、金额分别标注；一句话只错一个“别”可能比十个无关虚词严重。
- 意图／工具参数正确率：转写是否最终导致错事；原生语音正确但字幕错与两者都错分开。
- 错误进入长期记忆的比例：分母是被检查的形成机会或新形成事实，不能混用；记录后来纠正是否完整修复。
- 误打断率：标为非打断的附和／噪声中，被系统终止回答的比例。
- 漏打断率与打断延迟：真人要求让话却没有停，以及从用户开始说话到旧音频停止的时长。
- 首响应、转写、工具接续分别计时；记录样本数、失败、超时和设备条件，不能只看成功请求 p50。
- 重复效果与旧回复复活是正确性事件，应逐次核对，不能被平均自然度掩盖。

延迟至少拆为采集与端点等待、最终转写等待、宿主准备、网络／模型、音频缓冲和实际播放。协议 audio.started 或 buffer.started 是代理观测，不等于已经由耳机传到人耳。客户端单调时钟适合局部耗时，跨服务要保留时钟边界。

### 8.3 针对这次追问，怎样验证而不只看演示

下表是补充的验收设计，不代表本次已添加或运行这些测试：

| 验证场景 | 输入和观察点 | 需要成立的结果 |
| --- | --- | --- |
| 服务端已自动打断 | 回放 speech_started、cancelled、cleared，以及重复／迟到回执 | 本地任务只终止一次，旧结果不复活；不把重复 cancel 当作必需步骤 |
| 点击停止，模型没有检测到新讲话 | 分别在生成中和生成完但仍播放时点击 | 停止生成与停止剩余播放都得到处理，不依赖 VAD |
| 生成完成后打断 | 先 transcript.done／response.done，音频仍在播，再新输入 | 能记录播放中断；全文不能在重建历史时被无条件视为已完整播出 |
| 旧截断回执晚于新回合 | 旧 itemId 的 truncated 到达时已有新 turn | 回执归属旧输出，不更新新回合，也不重新开启旧输出 |
| 三种“嗯” | 句中附和、对问题的肯定、随后接“别执行” | 分别统计继续讲话、有效短答、及时让话；不按词面一刀切 |
| 审批输入与点击竞态 | A1 等待时先取消或改参数，再到达旧批准；再交换到达顺序 | 参数变化后旧批准无效；已提交效果如实说明，原函数调用有真实结果 |
| 动态词表正反例 | 同一录音分别用固定背景、相关背景；加入仪器和非热词反例 | 报告专名收益和误插入代价，不只展示被修好的词 |
| 个人化可迁移性 | 个人词条来自早期确认，在该用户后续未见录音验证；另测未适配用户 | 不把记住原测试句当作识别能力提升，不损害普通用户和常用词 |

语音体验实验要用相同录音做配对比较，分阶段只改变一个因素，例如先比词汇背景，再比识别模型；话轮检测与音频采集不要同时换后归功于某一个改动。开发集用来选配置，保留集用于最终检查。个人化测试区分“同一个用户的未来新表达”和“新用户”，两者回答的产品问题不同。

除原有指标，再记录用户尚未结束就抢答的比例、有效短回答丢失率、热词误插入率和澄清负担。统计单位分别说明是输入段、关键槽位、需要确认的操作还是用户；同一用户多段录音有相关性，不能当作大量独立用户。阈值和采样规模应在正式实验中确定，本章不追加一个未经验证的固定毫秒数或“置信度 0.9”。

最终判断要同时看交互质量、任务成功、尾部延迟、资源成本和实现复杂度。通过关掉所有打断来降低误打断率，或通过永远询问来降低误执行率，都不足以证明体验更好。

## 9. 二面回答与闭卷验收

两分钟回答可以这样组织：

> 当前是原生 Realtime 语音，声音直接进模型；转写用于聊天落盘和宿主编排。我让宿主显式开始回复，是为了先建立 Run、上下文和工具执行合同。代价是转写和准备会影响首答延迟。
>
> 当前 WebRTC 自动打断由服务端处理响应和输出缓冲；宿主仍要取消在途工具、处理审批并阻止旧结果继续。不能把这两层都称为自己实现了音频截断。我们曾把同一回合里的不同 response 混在一起，导致旧停止事件把新音频静音，后来按 responseId 管理播放。当前有双向媒体和打断基础，但审批期间禁用输入音轨，自然附和也没有完整实测，所以不夸大成完全拟人的全双工。
>
> 识别错误先分清原音频、转写、模型理解和下游记忆。当前已有固定关键词提示，动态任务词表和个人词典仍是改进方案；它们不等于训练个人口音模型。还要分别记录生成和播放进度，不能把全文字幕当成已经完整播报。优化要同时看误打断、漏打断、关键识别错误和错误有没有进入工具与长期记忆。

闭卷交付：

1. 画出媒体、DataChannel、Main 与 SQLite 四条路径，解释为何原生音频仍被转写时机影响。
2. 同一 generation 下 R-A 停止事件在 R-B 开始后到达，写出正确输出状态；再把它改成旧 generation，重新推演。
3. 预约工具已被服务端接受而用户打断，说明能取消什么、需要核实什么、最终怎样回复。
4. 用户在审批界面说“算了”，分别回答当前实现和拟建方案的行为，不能混为已实现。
5. 分别处理“一起去看展”和“仪器放桌上”，给出采集、识别、确认、形成与修订的检查点。
6. 解释为什么三段合成 WAV、一次物理扬声器冒烟和通过离线测试，都不足以证明稳定全双工。
7. 不看文档说明 server_vad、semantic_vad、create_response 和 interrupt_response 的不同职责，并举例说明为什么 semantic VAD 不能保证忽略附和。
8. 分别推演“服务端 VAD 已自动打断”“用户点击停止”“宿主关闭自动打断后确认插话”三条路径，指出谁发 cancel／clear、谁负责服务端截断、谁负责本地任务；再说明换成 WebSocket 后哪个职责改变。
9. 页面全文已出现、模型已生成结束、音频只播一半时用户插话，解释当前代码会走到哪里、源码暴露什么风险，以及同一连接下一轮与断线重建历史分别要检查什么。
10. 对“嗯嗯附和”“嗯，继续吧”“嗯？别执行”给出不同处理，说明使用的声学／对话特征和误判后的复盘方式，不给一个脱离场景的固定阈值。
11. 从 Overleaf 当前任务出发，现场构建给 whisper-1 的关键词提示，以及给支持更多上下文字段的转写模型的背景／词汇示例；解释两者与 Persona instructions 的区别，再用“仪器放桌上”检查过度纠正。
12. A1 待批准时用户把周六改成周日，随后旧批准点击到达，写出动作、参数、审批与工具回执的完整状态变化。必须覆盖反过来先提交效果、后收到取消的顺序。

上述 7—12 项通过的条件是能够用具体事件、身份、消息内容和状态解释过程，并区分已实现、静态发现、官方能力与待验证方案；只背术语或把建议说成当前功能不算通过。
