# 08 数据闭环与评测：把一次失败变成能验证的改进

从完整产品发布者角度处理问题的连续案例见[第 19 章第 7–11 节](19-proactivity-and-product-feedback.md)：本地能力与线上缺口、最小遥测、问题报告、断音复现、记错约定定位、发布与回归。

对应 R07、R09；验收 A11、A12。当前项目有运行事件、记忆来源与修订、回归测试、真实模型实验和经验复盘，但没有线上玩家数据平台、持续训练平台或游戏灰度发布系统。本章沿着一个失败案例给出建设方案，所有咖啡馆数据与数值演算均为教学示例，不是项目实测。

NPC 对话的具体标注样本、Kappa 与成本演算、项目各层评测集的真实构建和失败、建议回流节奏，以及特征和阈值选择，见 [第 16 章第 5、7、8 节](16-npc-persona-hints-and-evaluation.md)。现有模型／分区复核不能冒称人类双标，教学节奏不能冒称已上线服务。

## 1. 闭环究竟要闭合什么

假设玩家说“刚才说错了，我不要冰咖啡”，NPC 仍然回答“那我给你做冰的”。把这段聊天收入数据库，再训练一轮模型，不一定能解决问题。错误至少可能发生在五处：纠正事件没有送到 NPC；记忆形成遗漏了否定；新记忆尚未形成，旧行动却没有失效；检索选中了被纠正的版本；模型已看到正确证据，仍然生成错误台词。

这些原因需要完全不同的改动。前三类可能首先需要修事件与一致性合同，最后一类才可能需要改善生成器。数据闭环的起点是让失败能够定位，终点是证明改动改善了同类问题，并且没有破坏原本正确的行为。

在这个项目上，可以这样表述自己的建设顺序：

> 我已经有按运行、输入版本和记忆修订关联的基础证据。我会先把一条错误回答追溯到观察、检索、供给、提议、提交和曝光，形成可重放样本；再由独立标签判断正确行为，选择代码修复、检索改进或训练；最后在未参与调参的场景上比较效果。只有上线后的新失败能持续回流并再次完成这个过程，才构成数据飞轮。

其中“独立”指标签不能由待评估方案自己决定。“可重放”也有层次：保存模型请求可以重放输入，不代表下一次模型输出逐字相同；保存环境快照和事件顺序，才能检查同一个行动在相同条件下是否合法。

## 2. 从一条失败中收集哪些数据

先固定一条事件链：

1. 玩家 A 公开点了冰咖啡，订单尚未提交。
2. NPC 开始生成确认台词，引用记忆 `m7/r2`。
3. 玩家 A 纠正为热咖啡，输入版本由 8 变成 9。
4. 旧模型请求返回，仍建议冰咖啡。
5. 世界动作提交器拒绝了旧订单，但旧字幕已经出现在客户端。
6. 玩家反馈“你没听我说话”。

如果日志只有“订单拒绝，运行成功结束”，开发者容易认为保护机制有效。实际问题却是字幕发布早于资格检查。要定位它，至少需要保留以下关系：

| 阶段 | 记录内容 | 缺少它会误判什么 |
| --- | --- | --- |
| 感知 | 原始事件引用、说话人、接收顺序、可见范围 | 无法区分没有听见和理解错误 |
| 决策输入 | 当前输入版本、工作状态版本、模型与提示版本 | 无法证明模型是否见过纠正 |
| 检索 | 查询、合法候选、被选条目、最终送入模型的精确修订 | 把索引遗漏、选择遗漏和预算裁剪混为一谈 |
| 行动提议 | 提议 ID、目标、依据、前置条件、生成起止 | 无法判断提议基于哪个时刻 |
| 提交 | 幂等键、检查结果、拒绝原因、实际效果回执 | 把请求已发送当作世界已经改变 |
| 曝光 | 字幕/音频开始与结束、已播放片段、取消结果 | 把后端拒绝当作玩家没看到 |
| 反馈 | 对哪个曝光的反馈、反馈时间、是否明确表达不满 | 把玩家离开直接解释成不喜欢 |

标识符用于关联，文本和环境快照用引用获取，不需要把私聊、截图和凭据复制到每条指标中。当前 [memorySuppliedReferences.ts](../../../src/main/agent/memorySuppliedReferences.ts) 可以追踪供给过的记忆引用；它只证明模型收到哪些证据，不能单独证明模型正确使用或玩家看到输出。

下面是拟建的数据样本，不是当前数据库表：

```json
{
  "case_id": "cafe-correction-001",
  "scenario_group": "order-change-during-generation",
  "manifest_ref": "code-model-prompt-environment-manifest",
  "events_ref": "ordered-events-001",
  "snapshot_ref": "visible-world-before-decision",
  "request_input_revision": 8,
  "latest_input_revision": 9,
  "supplied_memory": [{"memory_id": "m7", "revision_id": "r2"}],
  "proposal_ref": "proposal-27",
  "effect": {"status": "rejected", "reason": "input_changed"},
  "exposure": {"subtitle": "shown", "audio": "not_started"},
  "label_ref": "annotation-001-v1"
}
```

`manifest_ref` 应能解析到代码提交、模型完整标识、提示版本、工具 Schema、检索配置、数据版本和环境版本。模型服务没有提供内部权重版本时如实记录可获得的标识与调用日期，不能虚构完全可复现。

## 3. 如何做失败归因，避免“所有问题都怪模型”

对刚才的案例，可以按最早偏离合同的位置检查：

**第一步，输入是否到达。** 纠正事件是否进入该 NPC 的事件序列？如果 NPC 根本没有观察权限，不应补造观察；如果按规则应该收到却漏了，先修感知或路由。

**第二步，决定是否仍然有效。** 模型请求基于输入版本 8，但版本 9 已经纠正订单。这时无论模型有没有能力理解纠正，旧提议都应该失效。让后台长期记忆稍后完成形成，不能替代当前行动的取消。

**第三步，效果与展示是否共用资格结果。** 订单提交器挡住了旧订单，字幕发布器却没有检查。这是发布边界的实现缺陷。优先把字幕发布纳入行动资格控制，再建立可重复的并发回归。

**第四步，再看新一轮回答。** 如果新请求已收到“热咖啡”却仍然回答冰咖啡，才继续检查证据排序、提示理解和生成质量。一次事故可能有多处缺陷，不应为了单一分类把后续问题删掉。

| 归因 | 需要的反证 | 优先改动 |
| --- | --- | --- |
| 记忆形成漏事实 | 原话中存在，但形成结果没有或主客体错误 | 形成输入、抽取合同、来源校验 |
| 检索没找到 | 合法必要证据存在于库中，但没有进入候选 | 查询规划、分词、向量或索引 |
| 候选选择失败 | 必要证据已在候选中，最终没有送出 | 选择提示、排序、多证据覆盖 |
| 预算损失 | 选择正确，但最终请求缺少关键限定条件 | 上下文组织与预算计算 |
| 模型使用错误 | 正确证据已供给，输出仍相反 | 提示、示例、训练或模型比较 |
| 动作过时 | 生成后相关状态改变，仍被提交或曝光 | 版本与前置条件检查 |
| 执行不确定 | 请求超时，但服务端可能已生效 | 幂等、查询结果、恢复协议 |

这也是训练价值判断：没有检索到证据时，收集“正确答案”训练生成器，可能只让模型更会猜；对异步事务错误做 SFT，则不会补出缺失的原子操作。

## 4. 样本标签怎样写，才能经得起复核

一个标签不应只有“好/不好”。为案例 `cafe-correction-001`，标签可以包含：

- **必要输入**：纠正来自玩家 A 的当前直接表达，作用于尚未提交的这杯咖啡。
- **可接受结果**：取消旧确认；新一轮简短确认热咖啡；若缺少订单信息则澄清。
- **明确错误**：继续确认冰咖啡；声称订单已改但没有回执；把 A 的纠正写成朋友 B 的偏好。
- **必要证据**：事件中的主体、否定对象与替代值；无需借助“玩家今天心情不好”的推断。
- **不确定项**：已经播放出去的旧话无法撤回，应单独记录补救是否及时。
- **原因与版本**：标签依据的产品合同、审阅人、争议处理、标签版本。

对插话任务，标签应允许多个合理动作：继续工作、点头、等待服务机会可能都合格。不能把设计者喜欢的一句台词设为唯一答案，否则系统优化的是复现文案。

角色一致性也要拆开。可以使用三个等级的行为锚点：明确违背角色事实或价值；未违背但动机不足；与角色目标和当前情境一致。语气是否可爱另作偏好评价，不把“说得不够俏皮”和“提前泄露主线秘密”放进同一个分数。

试标时让两名标注者独立判断同一批样本，再检查分歧。如果一人把“空隙”当邀请，另一人只接受直接点名，需要先补产品规则，而不是取平均数消除分歧。正式标注隐藏方案名称；争议样本保留原判断和裁决原因，避免标签悄悄随结果移动。

## 5. 数据如何拆分，才能检验泛化

最危险的拆法是把同一段纠正对话换三个名字，然后随机分到训练、开发和测试。模型见过的其实是同一个因果结构，测试结果会偏乐观。

建议先给样本分组，再切分：

| 分组依据 | 为什么要一起划分 | 要检验的能力 |
| --- | --- | --- |
| 同一玩家或同一连续会话 | 历史、措辞与关系高度相关 | 面对新玩家仍有效 |
| 同一剧情模板与改写版本 | 换名字不等于新任务 | 未见过的冲突结构 |
| 同一订单/任务的完整事件链 | 前半段可能泄露后半段答案 | 长过程中的更新与恢复 |
| 时间 | 新内容、模型与玩家习惯会变化 | 后续版本是否仍然可靠 |
| 地点、人物和关系组合 | 单个因素见过，组合没见过 | 组合泛化而非背诵案例 |

开发集用于分析和修改；冻结测试集只用于阶段性验收。测试集暴露出失败后，允许把它转成回归样本，但此后不能继续把它叫“未见测试”。应保留测试集版本并补新的独立样本。

难例采样和总体估计也要分开。纠错、不同方案判断不一致、超时恢复等样本适合优先标注，因为修复价值高；与此同时，要随机抽取普通交互，否则不能用全是难例的数据推算真实失败率。记录抽样方式比单纯扩大样本量更重要。

## 6. 指标要沿着链路定义分母

下面用一组**人工构造的数据**演示。一次评估有 100 个合法观察场景，其中 20 个是应该回应的直接请求。系统提出 40 次发言，32 次实际曝光，5 次在曝光前取消，3 次曝光状态未知。人工判断已曝光的 32 次中有 8 次不合时宜；20 个直接请求中有 3 个没有得到适当回应。

因此：

- 已曝光插话的不合适比例为 `8 / 32 = 25%`。
- 已知曝光次数为每 100 个场景 32 次；另有 3 次未知，必须保留。
- 应回应机会的漏响应比例为 `3 / 20 = 15%`。
- 不能把未曝光的 8 次全部算作“正确沉默”，也不能把漏响应写成 `3 / 100` 来冲淡问题。

如果新方案只说 4 次话，其中没有错误，它的插话质量可能很好，也可能只是放弃了所有服务。必须同时报告漏机会、总频率、任务完成和未知比例。

| 指标 | 分子与分母 | 典型误读 |
| --- | --- | --- |
| 任务完成 | 完成全部必要目标且没有禁止副作用的场景 / 全部合格任务场景 | 只统计运行正常结束 |
| 候选证据覆盖 | 候选包含全部必要证据的问题 / 可回答问题 | 把命中一条当成满足多跳问题 |
| 最终证据覆盖 | 最终供给包含全部必要证据的问题 / 可回答问题 | 和候选覆盖混用 |
| 事实使用正确 | 主体、条件、时间与结论都正确的回答 / 已标注可回答问题 | 只看向量相似度 |
| 适当拒答 | 正确指出证据不足的问题 / 应拒答问题 | 把沉默全算成功 |
| 行动合法性 | 提交时条件仍满足的行动 / 已提交行动 | 不统计被拒绝的错误提议 |
| 角色与叙事 | 分别统计明确角色违背、剧情不变量破坏 | 用好听台词抵消事实错误 |
| 成本 | 全部场景的实际模型用量和资源耗时 | 排除失败、重试和未完成任务 |
| 体验延迟 | 感知到首个有效行为、发言开始、任务完成分别统计 | 首 token 快等于玩家感觉快 |

未标注、未知曝光和缺失用量不能填零。需要按任务、人群或场景分层报告时，同时展示每层样本数，避免总体均值掩盖罕见但严重的错误。

## 7. 怎样公平比较两个方案

以“整份快照变化就取消行动”对比“只检查选中行动依赖”为例，先冻结输入和提议。第一轮只比较两套资格检查规则，避免把模型输出差异混入机制效果；第二轮再让模型生成依赖，检验它会不会漏报或乱报。

实验前写清：

1. 研究问题：能否减少无关变化导致的误取消，同时挡住相关变化产生的过时行动。
2. 输入：相关对象变化、无关对象变化、用户纠正、历史引用、离店、多人发言等场景。
3. 唯一主要变化：行动资格的判断依据。模型、提议、事件顺序、环境相同。
4. 主指标：合法行动保持率、过时行动拒绝率。另报成本、延迟与复杂度。
5. 失败处理：超时、输出格式错误、无法判定和基础设施失败都保留。
6. 选择原则：先满足具体正确性要求，再综合效果与代价；没有可辨别收益时采用更简单的实现。
7. 证据产物：输入版本、结果、分母、失败例、选择理由、被淘汰代码的删除说明。

**人工构造的配对比较：**100 个相同场景中，两个方案都成功 80 个；只有新方案成功 12 个；只有旧方案成功 3 个；都失败 5 个。旧方案成功 `83/100`，新方案 `92/100`，净改善 9 个百分点。面试不能只报“提升约 11%”而不说明那是相对提升，且有 3 个原本正确的案例退化。

真正应分析的是这 15 个结果不同的场景。如果 12 个改善都来自同一模板的换名版本，证据强度远弱于 12 类独立困难。对于相关样本，应按会话或模板分组重采样，不能把每个检查点当独立试验。

二项比例可以报告 Wilson 区间；在独立样本假设下，`92/100` 的 95% 区间约为 85.0%–95.9%，说明点估计并非精确总体水平。配对比较还需要分析不一致样本，不能靠两个边际区间是否重叠直接下结论。方法依据见 [NIST 二项比例区间说明](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm)。

若某个预设性能阈值略微越界，保留原始判定，再记录为什么整体质量、成本和复杂度仍支持某种选择。不能事后改阈值，让实验看起来从未失败。项目工具发现的选择就是可用于讨论这种取舍的实际例子，见第 07 章。

## 8. 评测器本身也需要评测

模型评审适合初筛语气、关系与叙事合理性，但它可能偏好更长的答案，也可能被格式或方案顺序影响。至少做四件事：

- 给评审者相同的可见输入和明确标准，不把隐藏剧情答案泄露给待测 NPC。
- 交换两个答案的展示顺序，检查判断是否稳定。
- 用人工复核的样本校准各类判断，分开看误判为好和误判为坏。
- 保留争议队列，重要正确性条件优先用代码与环境状态验证。

“订单是否真正创建”可以查服务器回执；“两个 NPC 是否同时持有发言权”可以检查状态机。没有必要让另一个语言模型猜这些事实。相反，“这次玩笑是否符合人物”常需要设计师与玩家判断，不应强行写成字符串相等。

质量检查中的生成器和评审器即使是不同模型，也不自动构成独立真值。两者可能共享训练偏差或相同的错误背景。独立的世界状态、来源和人工标签仍然有价值。

## 9. 回归、环境回放与真人试验怎样分工

确定性回归负责机械合同：重复事件只应用一次、纠正先到时旧动作不能提交、精确修订不能被偷偷换成新内容。使用可控异步屏障，在模型等待时注入变化，不靠睡眠碰运气。

环境回放负责时序与实际效果：保存初始房间状态和事件序列，用固定规则恢复订单、发言权和曝光记录。比较时先让两个方案面对相同事件，再研究策略改变后环境会如何演化；后者不能假装仍然是完全相同的轨迹。

真实模型实验负责语义质量和不稳定性：固定可控版本，重复关键难例，保留实际请求与响应标识。服务不支持确定性种子时，要接受输出分布并报告波动。

真人试验负责打扰感、人物可信度与玩法体验：离线评分合格不代表插话时机自然。多人房间中，一名玩家的 NPC 会影响其他人，应优先按房间或完整会话分配方案，避免同一桌同时混用策略造成干扰。

不应一开始就建立复杂训练集群。最小可用系统可以是版本化样本文件、一个回放器、一份标注规范和自动汇总报告；当数据规模与协作需求增长，再拆服务。

## 10. 什么问题值得训练，数据如何进入训练

| 手段 | 可以解决的瓶颈 | 样本具体长什么样 | 不应承担的工作 |
| --- | --- | --- | --- |
| SFT | 在相同合法输入下反复抽错主体、参数或角色表达 | 可见状态、允许工具、经过复核的目标输出 | 修复丢事件、事务竞态 |
| 检索器训练 | 语义相近但主体/条件不同的证据难区分 | 问题、必要证据、同玩家过时记录或朋友记录等难负例 | 弥补库里从未形成的事实 |
| 偏好优化 | 两个事实都正确的回答在表达或时机上有稳定偏好 | 相同输入和证据下的一对可比结果及理由 | 把事实错误与风格偏好混成一个喜欢分 |
| 小模型蒸馏 | 已验证任务的成本或延迟过高 | 教师成功、澄清、拒答、纠错与失败恢复轨迹 | 只模仿漂亮成功例 |
| 策略学习 | 有可重复环境和可归因长期收益的决策 | 状态、合法候选、实际动作、采样概率与结果 | 从玩家离开猜测负奖励 |

DPO 将偏好数据转成直接优化目标；它简化了某种偏好训练过程，但不替你产生可靠偏好，也不解决日志缺失与因果归因。[原始论文](https://arxiv.org/abs/2305.18290)

例如训练“何时插话”，同一状态下应比较“等待”与“说一句服务提示”，并标注两者的任务收益和打扰代价。若一个答案拥有纠正信息而另一个没有，比较结果首先反映输入不公平，不能直接拿来训练风格偏好。

不能仅优化回复次数：频繁打扰也能迫使玩家回复。奖励应反映任务、叙事、角色和打扰的共同约束。长期策略评估还需要覆盖假设；确定性旧策略从未做过的动作，不能凭旧日志可靠推算后果。首版优先做受控实验，不急于把所有反馈转换成强化学习奖励。

## 11. 发布怎样形成下一轮数据

对字幕提前曝光的修复，一个完整交付应包括：

1. 新增最小复现场景：模型悬停时注入纠正，随后释放旧输出。
2. 在旧版本复现错误，在新版本验证旧字幕不曝光。
3. 增加相邻正常场景：无关灯光变化不应取消合法订单确认。
4. 在冻结场景集上检查角色表达、漏响应与延迟没有明显退化。
5. 发布时记录版本，保留恢复旧版本的方法；不能靠清空所有记忆隐藏问题。
6. 上线观察类似纠正的数量、实际曝光错误、未知结果与资源成本。
7. 将新失败补入下一版数据，保留旧版本成绩，不覆盖历史报告。

这里“修复了一个已知错误”与“总体错误率下降”是两种不同结论。前者由复现与回归支持；后者还需要有代表性的样本和足够观察。面试时把这两句分开，反而更能说明你理解工程与实验。

## 12. 分阶段建设与交付物

| 阶段 | 实际交付 | 完成条件 |
| --- | --- | --- |
| D0 可归因 | 统一关联标识、版本清单、最小轨迹导出 | 任取一条错误能追到输入、证据、提交和曝光 |
| D1 可标注 | 标签规范、试标分歧记录、数据切分 | 两人能解释一致与不一致的原因 |
| D2 可比较 | 机械回放、模型评测、配对统计报告 | 相同问题的改进与退化都能定位 |
| D3 可体验 | 小范围房间试验与回滚 | 离线收益没有转化成明显打扰或漏响应 |
| D4 可训练 | 确认瓶颈后建立训练集与独立测试 | 新场景受益，代码正确性与邻近能力不退化 |
| D5 可持续 | 新故障回流、版本发布与漂移观察 | 每次迭代可说明数据来自哪里、为何修改、怎样验证 |

## 13. 本章练习与追问

请交付三份小材料，而不是复述“收集、训练、上线”。

第一份是刚才咖啡纠错的样本：写出原始事件、两种版本、旧提议、拒绝回执和错误曝光，定位最早失守边界。第二份是比较表：用本章 100 例教学数据算出两种成功率和退化数，说明为什么场景相关性会影响结论。第三份是实验卡：为“加入角色经历摘要”设计一个只改变主要变量的比较，说明角色可信度、错误泛化、成本和未知样本如何处理。

追问：“如果标注很贵？”先标高价值分歧和代表性随机样本，分开承担修复与总体估计；不要让模型自评代替全部真值。追问：“为什么先不训练？”因为要先找到错误发生的层；训练只有在输入、标签与目标匹配时才是有效干预。追问：“现在做到了哪一步？”当前有单机证据和实验基础，上述游戏数据与发布链路是可实施方案，尚未上线。
