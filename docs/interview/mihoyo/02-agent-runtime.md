# 02 Agent Runtime：怎样把模型的一步建议变成可恢复的执行

本章围绕一个具体任务展开：用户要求读取资料、整理成文件；第一个工具已经执行时，用户又补充“先不要覆盖原文件”。要解释清楚这件事，需要同时理解模型调用、工具效果、输入版本、事件持久化和恢复。对应 R01、R02、R06，验收 A01、A02、A07。

## 1. 为什么有模型接口还要写运行时

一次模型请求只能返回文字或工具调用建议。它本身不知道数据库已经提交了哪些记录，也不能替应用判断外部动作是否真的完成、用户是否在等待期间改变了要求。

CharaMate 的运行时负责这些执行事实。模型负责理解任务并提出下一步，工具负责与环境交互，运行时负责把多轮生成、审批、等待、取消和结果组织成一个过程。Provider Adapter 则负责把不同服务端协议转换成统一事件。

当前所谓“统一运行时”，主要指 Chat、Run、Item、工具执行、审批、事件和持久化合同。文字与原生 Realtime 语音有不同的模型驱动循环，不能说它们逐行执行同一个 `#drive`。本章介绍文字及自主文字 Run，语音的差异见第 07 章。

## 2. Chat、Run、Item、Event 分别为什么存在

假设用户说“读取这份计划，帮我整理成摘要”，模型先读文件、再写摘要、最后回答。整个过程可能涉及三次模型请求，但仍属于一次 Run。

| 对象 | 在例子中的含义 | 生命周期 |
| --- | --- | --- |
| Chat | 用户与角色所在的会话 | 可包含很多次任务 |
| Run | 这次整理资料的执行 | 可运行、等待、恢复和结束 |
| Item | 用户消息、工具调用、结果、计划等过程单元 | 有自己的身份与状态 |
| Event | 某个过程单元开始、变化或结束的记录 | 按 Run 顺序持久化 |

区分这些对象的直接收益是恢复：UI 重新连接时不需要猜模型是否还在生成，而是从最后收到的事件序号继续读取；工具结果与原调用有稳定对应关系；一个 Run 在等待审批时也不用伪装成“结束，稍后重建另一个任务”。

同样，模型服务的单次请求超时不等于整个 Run 最多只能活那么久。任务可能需要多次请求和用户补充，应用必须自己定义执行边界。

## 3. 持久化为什么先于 UI 发布

[RunEventService.append](../../../src/main/agent/runEventService.ts) 先调用 Repository，只有实际插入新事件后才通知消费者。Repository 在事务内校验序号和状态，再更新事件与 Run/Item 投影。

[RunRepository.appendEvent](../../../src/main/agent/runRepository.ts) 有几项关键约束：

- 新 Run 从序号 1 开始，不能重复启动不同事实。
- 后续事件必须接在已提交序号之后，不能无声跳号。
- 同一序号重放相同事件可以识别；同一序号换成不同事件会报错。
- 自主行动的 Run 分配绑定回调可以进入同一个事务，避免行动资格与实际分配分离。

为什么不能先发 UI 再存库？因为进程可能在两步之间崩溃。用户刚看见“已完成”，重启后数据库却没有这个结果。先存后发仍可能遇到“已经提交但 UI 没收到”，但这可以通过按序号重放恢复。

这种设计并不保证所有外部工具效果也与本地事件处在同一个事务里。文件系统、浏览器和远端服务有独立边界，恢复时必须看它们的效果语义。

## 4. 开始一次 Run：哪些东西在等待后需要重新检查

[AgentRuntime.#start](../../../src/main/agent/agentRuntime.ts) 在同一 Chat 的串行分配边界中准备模型、附件、执行模式和上下文。模型能力解析、文件读取、输入容量测量等可能异步进行。

一个重要原则是：准备开始时成立的条件，到真正分配时不一定仍成立。例如用户已经取消，另一个入口已经完成分配，或者认知行动依赖的意图刚被撤销。每个相关等待结束后，都要复查这些条件。

可以按下面的教学时序理解：

```text
读请求及当前执行配置
  → 准备附件、模型能力和上下文
  → 等待期间允许用户交互
  → 再查取消、输入与分配状态
  → 短事务保存 run.started，并绑定实际分配
  → 提交后发布事件
  → 进入模型驱动循环
```

如果把“分配”仅实现为内存里创建一个对象，进程退出后就无法知道它是否已经开始；如果太早保存“开始执行”，后续准备失败又容易产生假的运行事实。因此准备与真正开始之间需要清晰边界。

## 5. 模型循环如何推进任务

`#drive` 根据当前持久化边界恢复或继续，然后发送一个模型步骤。模型可以输出文本、计划、工具调用，或者提出需要用户补充的问题。

工具不是直接在 Provider 回调里任意执行。运行时先根据当前输入版本、工具合同、范围和审批决定能否开始，再通过 `#executeTool` 创建过程 Item、保存待执行状态、调用执行器、接收结果并写入终局。下一次模型请求读取实际结果，决定继续还是结束。

以整理资料为例：

1. 模型提出 `file.read`，运行时确认只读能力合法。
2. 文件工具实际返回正文，结果归属于这个 call 和 Item。
3. 模型看到正文，提出摘要文件写入。
4. 运行时依据执行模式决定是否等待批准。
5. 工具报告写入结果，模型才能总结交付情况。

这里至少有三种不同“成功”：工具参数通过检查、工具报告执行成功、用户任务最终达成。参数合法不能证明文件内容正确；写入成功也不能证明摘要没有漏掉关键内容。复杂任务应有独立验证步骤或环境结果。

## 6. 用户中途补充时，怎样避免旧计划继续执行

假设旧模型步骤基于 `inputRevision=7`，提出读取原文件和覆盖摘要。用户在读取过程中说：“保留原文件，另存一份。”

当前用户输入进入后，Run 的输入版本前进。旧模型步骤仍可能返回，因为取消只是尽力通知，网络和模型并不一定立即停止。因此运行时在执行后续工具前要比较输入版本，过时且尚未开始的调用通过 `#skipSupersededCall` 跳过；随后用新输入和已经完成的真实结果继续生成。

这里不能说“整轮回滚”。已经读到的文件仍是合法观察；如果写入已经发生，也必须保留事实。可以停止后续覆盖，必要时执行有明确授权的补偿，但不能把已完成效果从历史中抹掉。

`steer` 还会验证活动 Run、预期输入版本和等待边界。在 `beforeUserInteraction` 异步让路后再检查一次，防止期间状态发生变化。批准某个工具、回答某个确认问题和自由补充一条新要求也不能混成一种输入：它们各自对应不同待解决对象。

## 7. 取消与崩溃恢复为什么不能只靠 AbortController

AbortSignal 是通知，不是时间倒流。它能取消排队任务、结束支持取消的请求，或者让宿主停止采用迟到结果；无法保证外部系统还没完成动作。

| 崩溃或取消位置 | 可以确定什么 | 恢复时怎么办 |
| --- | --- | --- |
| 工具尚未开始 | 没有该次工具效果 | 根据当前输入决定取消或重新发起 |
| 工具正在执行，明确回报未完成 | 有可确认的失败或中止状态 | 按工具语义决定是否重试 |
| 外部系统已接受，但响应丢失 | 本地无法直接判断效果 | 有操作 ID 就先查状态 |
| 效果已完成，本地结果未保存 | 现实可能已改变 | 通过去重键、产物或目标状态核对 |
| 结果已保存，UI 未收到 | 数据库已有执行事实 | 重放事件，不重做工具 |

只读和幂等必须结合业务含义。重复读文件通常不会重复副作用，但可能读到新版本；重复发消息可能真的发两次。工具没有操作 ID、状态查询或去重支持时，应保留不确定状态，不能用自动重试包装成“恰好执行一次”。

游戏里同样如此：`grant_reward` 的网络超时不代表奖励没到账。服务端应以动作身份去重；桌面运行时不能替游戏服务器证明这一点。

## 8. 为什么没有给每个任务先调用一个 Planner

历史研究比较了三种方式：

| 方案 | 怎么做 | 额外成本 |
| --- | --- | --- |
| 按需规划 | 普通模型响应自行决定是否创建或更新计划 | 没有固定额外往返 |
| 首轮强制计划 | 多步任务的第一个响应必须先给计划 | 增加规划约束和输出 |
| 独立规划请求 | 执行前单独调用一次只生成计划的模型请求 | 固定多一次模型往返 |

初筛的 96 个任务中，按需和首轮强制分别完成 81、79 个；独立规划只完成 9 个，并出现 73 次错误宣称完成，因此没有进入后续比较。这个失败属于当时具体提示、运行时和任务组合，不能泛化成“独立规划理论无效”。

后续 600 个配对任务中，按需规划成功 585/600，首轮强制成功 586/600；精确工具选择分别为 512/520、509/520。质量差异很小，而独立测量中的首段响应第 95 百分位从约 5.538 秒升到 7.134 秒。综合效果与额外约束，保留按需计划。[HARNESS-LOOP](../../benchmarks/harness-loop.md)

这段结论在面试中应该说成：当前任务不值得每次强制规划；复杂目标仍可以有 Plan Item。计划是运行中的可更新状态，前提改变时应修订或放弃，而不是为了满足“先规划”而生成一份之后不再使用的清单。

## 9. 没有固定步数上限，如何识别无进展循环

“最多执行十二步”会误伤长任务；“模型想做多久就做多久”又可能无限重试。当前 [loopGuard.ts](../../../src/main/agent/loopGuard.ts) 观察工具的语义签名和结果，识别重复模式。

签名包含工具名、效果、稳定参数、结果状态和错误类型，同时去掉 request_id、timestamp、retry_count 等噪声。否则模型每次换一个请求 ID，就能把完全相同的失败伪装成新动作。

当前代码检查长度 1–5 的模式是否完整重复 5 次。这是项目实验后保留的启发式，不是模型协议规定。检测器本身只发现重复，是否有恢复路径、是否允许重试仍需要结合环境和工具元数据处理。

早期“连续失败二、三、四次就触发”的检测方案，在 140 条正常轨迹上分别只正确放过 36、72、106 条，误伤很多合法过程。后续引入语义模式，在冻结的选择集上识别 480/480 条循环，正确放过 720/720 条正常轨迹，再对独立留出轨迹验证。这样的数字说明该数据集上的检测效果，不代表所有真实长任务永不误判。[检测实验](../../benchmarks/harness-loop.md)

应该准备两组对照：同一错误无新证据的重复调用；同一工具但文件、页面或分页位置已经实质改变的合法继续。只测第一组，会得到一个很会“阻止工作”的检测器。

## 10. 检测到循环后为什么不能一律叫模型重想

恢复至少要回答：有没有不同能力可用、该能力是否独立、当前操作是否可重试、环境是否提供了新观察。

例如浏览器页面读取失败，而产品有合法 DOM 或另一种当前目标读取能力，可以把候选能力明确告知模型；如果只是同一路请求换个名字，则没有真正增加恢复路径。对于没有新信息、没有合法替代方式的任务，应以明确原因结束，而不是不断生成“让我再试一次”。

历史实验将“检测器是否正确”与“检测后怎样引导恢复”分开比较，避免某种提示效果掩盖误检。迁移到游戏也要这样拆：NPC 判断路被堵住是一层，选择等待、绕行或放弃是另一层。

## 11. 上下文压缩怎么保证继续做对事

长任务需要压缩时，必须保留当前目标、决定、约束、已经完成的效果、未解决问题及最新用户纠正。摘要若只写“已基本完成”，恢复后可能重复不可逆工具，或把已撤销的要求重新执行。

历史比较分别研究触发时机、交接摘要结构和旧工具结果表示。一个关键实验方法是只在两套方案都实际发生压缩的任务上比较压缩内容的效果。否则某组任务根本没触发压缩，却被拿来证明摘要格式更好，因果关系不成立。

例如摘要结构比较有 200 个任务，两种结构整体成功 186 与 185；共同发生压缩的 69 个任务，两者都成功 69/69。更复杂的字段没有显示可归因收益，最终保留较简单的进度、决定、约束和下一步交接结构。[压缩比较](../../benchmarks/harness-loop.md)

压缩后省掉原始工具输出，指的是下一次模型请求中的表示；持久化执行记录仍然存在。已发生效果、审批历史和产物身份不能因为 prompt 变短而被删除。

## 12. 多 Agent 何时有意义，当前实现有什么边界

适合并行的任务是独立读取，例如分别查两个文档集，结果由父 Run 汇总。共享可变浏览器、同时修改一个文件或依次依赖的操作，不会因为多开 Agent 就自然变快。

当前 [MULTI-AGENT](../../benchmarks/multi-agent.md) 提供有边界的只读协作入口，固定两个子任务，预先声明目标、读取动作与互斥资源，结果回到父 Run 的 subtask Item。它仍由主运行时管理生命周期，子模型不能私自扩大执行范围。

决定记录保留了机械判定无胜者、之后经产品取舍接受入口的过程。因此可介绍“项目具备受限并行读取能力”，不能说实验已证明所有任务并发更好。游戏里多名 NPC 共存，也不等于每个 NPC 的内部决策都需要多个 LLM Agent。

## 13. 联合验收的数字怎样讲才不会经不起追问

最终 Harness 组合做过 300 个未提前使用的工作流确认，覆盖不同工具规模、上下文长度、语言和任务类型。它是已经选定的一套实现的联合验证，不是再比较每个组件。

原严格路径评分通过 236/300，原注册业务完成 292/300；后续逐条按产品语义解释终局，报告 300/300 可接受终局，同时保留机械失败。这三个数字的评分定义不同，不能只挑最后一个说“任务成功率 100%”。

专门的最终时延队列没有继续运行。300 条质量轨迹的耗时是在混合长度和并发条件下观察到的描述数据，不能替代独立的延迟实验。面试讲清这类区别，通常比背一个好看的比例更有说服力。

## 14. 怎样把这套结构迁移到 NPC

可以复用的是高层任务、工具边界、版本检查和恢复思想。需要替换的是环境与效果来源：

- 文件读取变成角色可见的世界观察；
- 用户纠正变成玩家直接输入和权威事件；
- 工具执行变成导航、动画、发言、订单和任务动作；
- 外部效果由游戏服务器回执确认；
- NPC 的“决定插话”只是提议，真正发言还要取得会话发言权。

行为树或 GOAP 可以管理确定的动作前置条件和局部恢复，LLM 负责语义与高层意图；两者可以通过同一个动作合同协作。第 09 章将这套映射用于咖啡馆。

## 15. 练习与连续追问

画一条包含两个工具的 Run 时序，标出模型请求版本、待执行 Item、审批、工具结果和最后回答。在四个位置分别注入故障：准备后未分配、工具开始后、外部成功但未保存、保存后未发布。

每个位置要回答：数据库里有什么，外部世界可能有什么，重启时读什么，哪些操作能重试，用户会看到什么。随后解释为什么按需规划被选中、循环检测如何误伤合法任务，以及压缩实验为什么要看实际发生压缩的子集。

能回答这些问题，才说明理解了运行时如何承担执行责任，而不只是知道“模型会调用工具”。

压缩时机、完整请求预算、Run handoff、持久 Chat 摘要、新 Chat 与恢复检查点的逐步区别，继续读 [第 15 章第 1 节](15-context-activity-retrieval-walkthrough.md)。其中明确说明压缩不删历史 Items，也不能保证任意大的必要输入都可容纳。
