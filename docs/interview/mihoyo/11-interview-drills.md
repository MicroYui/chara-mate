# 11 项目追问与模拟面试

72 个核心追问。先独立回答，再读参考要点；每题至少能举一个具体反例。回答中“实现/记录/方案”的边界沿用对应章节。时间均为练习建议。

后续七组 NPC 追问集中在 [第 16 章](16-npc-persona-hints-and-evaluation.md)：未知问题与 Persona、战斗响应、卡关提示、多角色一致性、标注、攻略更新和实际评测。按其第 10 节做闭卷变式，并用第 8 节继续追问特征、校准、阈值和误判归因；不把新例子混入原 72 题的历史编号。

## 1. 项目与架构：Q01–Q08

展开依据：[01 项目口径](01-project-and-evidence.md)、[02 Runtime](02-agent-runtime.md)。

**Q01：你最有技术含量的工作是什么？**

选择一条自己实际参与且能跟代码的链：用户纠正后，前台输入、异步记忆与自主行动如何保持一致。解释 inputRevision、短事务、精确 revision 和发布检查，再讲一个真实失败。追问“你具体写了哪一段”时按事实回答，不把仓库全部成果据为个人贡献。

面试时从一个具体窗口开始：“旧模型还在生成提醒，用户突然说不用提醒。”再依次说明当前输入先更新、旧生成结果要复查、后台记忆稍后形成、已发生效果不能回滚。这样面试官能沿同一案例继续问。最后指出一处自己能现场定位的提交函数和一项对应测试，个人贡献按真实参与情况填写。

**Q02：为什么这与游戏 NPC 有关？**

两者都有不完整观察、持续目标、长期经历和过时行动。可迁移证据/状态/效果边界；游戏必须补多人会话、世界权威、导航和 剧情事实。追问“什么不能直接复用”时，明确 Electron Main 与本地 SQLite 不是游戏服务器容量方案。

把桌面事件换成“玩家进入咖啡馆”，把用户纠正换成“先别打扰”，旧行动失效问题几乎不变。变化最大的是执行环境：游戏中的订单、位置和任务阶段由服务端裁定，多 NPC 还需要发言仲裁。迁移应先冻结事件与动作合同，再考虑部署方式，不能只把提示词里的“用户”换成“玩家”。

**Q03：Agent 和聊天机器人的区别在哪里？**

区别在任务和环境闭环：维护执行状态，调用工具，根据真实结果继续，处理等待、取消和恢复。不是只看有没有循环或独立 Planner。反例：模型输出一段计划却没有执行证据，仍不能算完成了任务。

可以用“帮我整理文件”作检验：系统是否先读取真实目录，是否在写入前满足执行条件，写入失败是否调整方案，结束时是否依据实际结果汇报。仅有工具调用接口仍不够；如果模型说完成就直接结束，没有效果确认与恢复语义，闭环仍然缺了一段。

**Q04：为什么一个 Run 要跨多次模型请求？**

工具结果、新输入、审批和检索需要后续继续；一次 HTTP response 只是一步。Run 承担可追踪的用户任务身份。追问 timeout：单请求 timeout 不等于全 Run 必须结束，是否继续要看错误、当前状态和合法恢复路径。

如果把每次模型返回都当作一个任务，审批期间的等待、用户改口和工具继续执行就会失去共同身份，界面也难以恢复完整过程。Run 记录任务生命周期，Item 记录过程中的消息或动作，事件序列负责增量投射。模型请求是可失败、可重试的步骤，但其重试不能擅自重放已经完成的外部操作。

**Q05：Planning 是独立服务吗？**

当前按任务需要产生 Plan Item，没有每轮强制独立规划请求。历史比较不能证明复杂任务不需要计划，只支持此处保留简单基线。游戏可用高层语义目标配合 GOAP/行为树，规划层级与动作层级分别解释。

实际比较中，600 个配对任务的两种规划方案分别完成 585 和 586 个，工具选择完全符合预期为 512/520 与 509/520，较复杂方案没有形成稳定净收益，还增加首响应延迟。结论是这批任务保留按需规划。若换成长任务或开放游戏目标，应建立新任务集，不能把一次选择推广为“规划没用”。

**Q06：状态机是不是太复杂？**

每个状态必须对应真实等待、效果或恢复边界；删除没有独立生命周期价值的状态。用“等审批”和“工具已执行但结果未知”的不同恢复策略证明必要性，不以状态越多越严谨为理由。

可以逐个问：重启后恢复策略是否不同，界面是否需要不同反馈，允许的下一步是否不同。如果都相同，两个状态可能应该合并；如果一个可以安全重试，另一个可能重复扣款，就必须区分。复杂度评价看状态是否解决真实分歧，而不是追求图最小或名词最全。

**Q07：你项目已经 100% 成功了吗？**

没有通用 100% 的证据。历史 Harness 的产品终局与 strict path 分数不同；原分母与修订不能隐藏。给出测试环境、任务范围和失败，并说明本次文档未重跑历史 suite。能解释分数为什么不同，比背最好看的数字重要。

例如 H7 的 300 个任务，严格执行路径通过 236 个，原业务结果通过 292 个，后来按产品终局重新解释后为 300 个。三个数字对应不同判定，不应只取最后一个。回答时举出“预期工具路径没满足但业务结果完成”这类差异，并说明修订依据；没有复测的链路也不能随新版本自动升级为通过。

**Q08：多 Agent 为什么只做受限只读？**

当前 Decision 的能力边界是两个明确互斥资源的只读 child，由父 Run 汇合，避免共享可变环境冲突。机械执行 判定条件 没证明平均收益，接受入口是透明产品取舍。不能把它包装成多 Agent 普遍胜过单 Agent。

追问“以后能否并行写入”时，先谈资源所有权：两个任务是否操作同一文件、数据库行或浏览器会话，父任务怎样取消和汇合，部分成功如何保留。只有分工明确且收益超过协调成本，才考虑扩大能力。只读限制是当前被接受的范围，不是说所有多 Agent 系统都只能只读。

## 2. Cognition 与注意力：Q09–Q16

展开依据：[03 Cognition](03-cognition-attention-persona.md)，尤其是入口、调度、事务与四组连续案例；纠正进入长期记忆后的过程见 [06 完整链](06-correction-and-consistency.md)。

**Q09：Cognition 与 AgentRuntime 为什么不是重复？事件到底从哪里来？**

Cognition 的 Attempt 负责基于有来源的状态作判断，Agent 的 Run 负责实际生成、工具执行与交付。分析模型没有工具权限，不直接向用户说话。普通用户提交走 AgentRuntime.start，不必等后台选择 respond 才回答。

要继续讲出两条实际链。用户提交先经过 beforeUserInteraction → yieldToUser，记录 user_engaged 并让旧认知 Run 让路；实际文本稍后通过 user_message Item → Run 事件 → observeRun / itemEvidence → observeFeedback → ingest 保存。窗口变化则走 ActiveApplicationSource → ActivityCaptureCoordinator → ActivityService 先保存活动 → Main listener → observeActivity → ingest。

追问“凭什么说消息已送达”：Run completed 只证明运行终态；主动消息还要通过 publishCompleted 的资格检查并被界面接受，随后有 surface:offered 回执。用户读过、理解或满意是更后面的事实。Activity 监听与 Cognition 入库也不是一个跨领域原子事务，不能把“有监听”说成端到端恰好一次。

继续追问“正常聊天会读它吗”：会，在预算允许时由 prepareTurn 读取已提交状态，再投影为背景；当前选择以 Persona 的注意状态为主，没有先拿 chatId 与本轮问题做语义路由。多个 Situation 不是多个独立 Agent。主动选择最终绑定一个 Chat：优先真实 Journey 的 homeChatId，再用有来源的 choice.chatId；没有可靠关联时可建立临时邀请。首次文字接话或在绑定 Chat 开始语音，才正式保留这个临时 Chat，随后就是同一套 Run 的正常对话。详见第 03 章第 27 节。

**Q10：你的 attention 和 Transformer attention 什么关系？究竟谁判断重要？**

应用层先按来源与变化规则安排考虑：重复对象观察合并，纯计数缓冲，真实内容变化和到期条件安排分析。模型收到有预算的来源、目标、Persona 和可用状态后，比较具体行为，输出状态提议和选择。当前没有额外的情绪分数或重要性分类模型。

Transformer attention 只在已给定的模型输入里起作用，不能替宿主获取未送入的纠正。玩家感到“被关注”还取决于最后何时行动、有没有打扰，不能从某个 Attention 字段推导体验优秀。

追问像素变化：notifyVisualChange 只记录需要刷新并安排检查；真正到期时 beforeAnalysis 拉最新帧，保存带来源版本的图像证据，Driver 再给模型实际图片。frame 入库不再给自己安排分析，避免刷新触发刷新。

放大到多人 NPC，先在模型外按角色感知、会话和任务依赖选事件，再按语义合并；取消和目标消失先改变执行资格。相关不等于值得重新推理，优先级也不增加处理能力。给定每秒 40 次请求、平均 2 秒、并发 20，理想持续处理能力只有每秒 10 次；必须讨论准入、公平、背压和明确反馈。这是教学容量演算与拟建方案，不能称为当前服务端实测。完整方案见第 03 章第 29 节。

**Q11：三个事件先后唤醒，第一轮模型还没返回，怎么办？**

先辨别正在等待的是认知分析还是已分配的 Agent Run。CognitionService 的 #task 让多个 runDue 返回同一个 Promise；AutomationScheduler 的 #checking / #checkRequested 合并检查。因此新普通观察会入库、安排再检查，通常不会取消当前认知分析，也不会立即发第二个认知请求。

用户接管/停止等控制会增加用户控制代际并 abort 当前分析链，相关已分配认知 Run 另走实际取消。旧模型忽略取消后返回，仍要过 await 后的 signal 检查；#task 结束之后才有下一轮认知分析。普通用户 Run 不需要等待这份后台分析结果。

连续例子：A1 看旧文稿；切到 B 又返回 A，来源与前台版本改变；A1 返回后历史状态可能仍能提交，但基于旧当前前台的动作失效；随后 A2 读取未处理来源。若 A1 的 Promise 永不结束，现有单槽会阻塞后续认知，abort 不能被说成强制终止保证。若在途的是已绑定 Run，认知分析可以再次发生，但执行/发布受占用与依赖检查约束。

再问“是不是每来一条把一秒延后”：不是。schedule 保存现有到期时间与 now+batchWindow 中较早的一个。当前一秒是本地配置，不是已证明最优的阈值。

**Q12：什么叫角色的 belief，而非世界事实？状态怎样连续更新？**

Claim 区分 observed、reported、inferred，并记录支持、反证、替代解释与状态。看到 A 看钟表不能直接断言焦虑；A 说“五分钟后要走”是用户报告，也不是服务器全知事实。当前没有显式校准的概率信念分布，自评分不等于后验概率。

用户从“先听我说”改为“只看语气”时，旧要求保留为历史，当前 Intent 的目标和范围根据新来源修改。先用用户控制阻止旧执行，再异步更新语义状态，不必等模型完整理解情绪后才让路。原支持退出当前集合时可以保留历史出处，但不自动成为反证。

追问任务完成：completed_reply 可以支持有限对话目标的完成；performed_effect 支持实际动作范围；user_report 只表示用户报告。三个依据不能互换，Run completed 也不能证明订单已交付。

换成 Overleaf 案例：查论文指标、搜索网页与访问 ChatGPT 可以继续属于论文 Situation，虽然物理焦点不断变化；进入 B 站也可能在看论文课程。只有证据支持时才判断为休息，更不能从站点名推断疲劳。论文目标保留不代表要持续催促；是否切 Chat 还需单独判断真实会话关联。把第 03 章第 28 节逐步讲完，不能只答“语义分类会解决”。

**Q13：分析提交查哪些版本？为什么行动不用同一套检查？**

commitAnalysis 在短事务中检查 Attempt 状态、userGeneration、本轮实际读过的 Situation/Intent 版本、实际供给范围与部分更新合同。这是防止旧提议覆盖已更新实体，不是要求所有新事件和全局状态都静止。新观察或焦点改变不一定使整份状态提交失败。

最终动作只绑定所选 Intent、相关情境生命周期、Claim 实质内容、所用当前对象和回忆等。分析读过订单与天气，但动作只提醒订单完成；天气实体改变在提交阶段可能要求重读，已经提交的动作却不该因无关天气变化一直取消。订单取消、所用判断增加反证则应使动作失效。

追问“为什么提交完才编译依赖”：本轮可能刚把 Intent 从 revision 4 改成 5，行动应绑定 5，否则会被自己的更新立即判旧。Claim 检查也要覆盖支持、反证和替代解释，不能只比较句子。模型漏声明必要依赖仍要用行为评测发现，机械校验不能替代语义判断。

**Q14：为什么只查 userGeneration 不够？补检索能否顺便更新接收边界？**

不能。A1 在 generation 7、receivedThroughSequence 150 下开始，检索期间新 utterance e151 到达而代际不变。完成阶段补了记忆，仍要保留边界 150。行动检查查到该边界之后同 Persona 的真实用户 utterance/control，返回 control_changed，旧动作不执行。

这条检查在行动资格层，不代表 commitAnalysis 一定先失败。网页里引用相同句子是 observation，不是当前用户发言；同一观察时间戳也不能抹去真实接收顺序。

再问“收到 150 条为什么只说读到 108”：receivedThroughSequence 是快照建立时已经收到的位置；连续处理边界可能只到 108，同时专门给出了最新用户消息 150。提前供给新消息不能把中间 109–149 也标成已读。来源目录审阅进度还应与原文阅读区分。

**Q15：quiet、失败与等待有什么区别？怎样保证后来还能继续？**

quiet 是合法选择；被 Runtime 门槛挡住是 deferred；模型或合同错误是 failed 或 superseded，不能都算“没有打扰所以成功”。恢复条件里明确的未来 after 可以安排 nextWakeAt；其他事件经实际入口重新触发判断。当前没有能自动理解任意条件描述的通用订阅引擎。

Provider 失败后持久化到期工作保留，同时用进程内 failedContexts 抑制相同条件反复调用。纯计数、重复 refresh 和 prepareTurn 不解除它；新的有效输入、配置、独立未来条件或重启恢复分别有具体路径。若新消息在旧请求失败前到达，失败记录保存旧的恢复代际，不能把新消息也封住。

追问恢复：未绑定的 analyzing/ready 尝试可废弃后重新考虑；已绑定 Run 则找原 Run。消息已生成但未投递时应复查并复用原消息，不能因重启再写一份。评测同时看误打扰、漏响应、恢复等待和无变化时调用量。

**Q16：脑科学怎样启发你，为什么拒绝更复杂的 Appraisal？**

目标维持启发持久化 Intent 与约束，显著事件切换启发结构合并与用户控制优先，快慢记忆启发原始经历与异步形成。它们提出工程问题，不直接证明软件模块或参数正确，更不要求把脑区一一变成 Agent。

Appraisal 比较用了四组连续故事、每组四个检查点。行为判断从 14/16 到 15/16，连同执行终态和材料供给一起满足要求的仍是 11/16；输入和输出成本分别增加约 10.29% 和 10.92%。因此保留较简单结构。样本相关且小，不能宣称复杂方案普遍无效。

追问模块是否在本条回答前生效：13 次普通上下文准备里，9 次读到此前已有 Appraisal；prepareTurn 没有先对当前消息新评估。下一轮应先修好共同执行问题，再独立比较行为、实际交付、成本和复杂度，不能把别的修复收益算给新心理结构。

## 3. 记忆形成与历史：Q17–Q24

展开依据：[04 Memory](04-memory-lifecycle.md)、[06 完整链](06-correction-and-consistency.md)。这一组先讲完整执行，再逐层追到字段、事务和历史。

**Q17：用户说了一段话，怎样真正形成长期记忆？为什么还需要两种 ID？**

以“林岚喜欢不加糖的燕麦拿铁，我更喜欢美式”为例：回答模型调用无参数 memory.record，宿主读取当前 Run 及前一轮允许的完成消息，按真实身份登记来源和形成工作。形成模型先提出两人的偏好，再按候选内容查旧记忆；比较材料变了才重新提议。宿主检查主体、引文、范围和目标版本，填写 ID 等字段，在短事务中提交事实、语义、引文、全文索引、编码任务与片段进度。

Memory ID 保持这条知识的连续身份；Revision ID 固定当时读到的正文。若以后林岚改喝卡布奇诺，应沿用 Memory、新建 Revision，再移动当前指针。不能覆盖旧正文，让先前模型像是读过尚未出现的新事实。

继续追问：工具参数为何是空对象？第一次提议说 create，为什么还要检索？本次完整形成可能有几次模型调用？需要分别回答防止自编来源、比较旧知识以及调用次数取决于分段、检索、重提议和修复，不能固定说一次。

**Q18：新增、修订、补充支持和纠错，各写什么？**

新增创建 Memory 和 Revision。修订沿用 Memory、创建新 Revision，保存前驱和旧内容处置，写新正文的索引任务。support 沿用原 Revision，只补合格来源和引文；不为了重复陈述换个说法就生成新版本，也不自动增加置信度或检索分数。

“以前喜欢拿铁，现在改喝美式”可保留旧偏好作为历史；“刚才说错了，从来喜欢的都是美式”则不能继续把旧内容当真实过去。这就是 retained_history 与 corrected 的差别。物理删除有另一套生命周期，不该用它替代对旧内容的语义判断。

继续追问：同一消息经认知入口再来一次算新支持吗？两条新消息一定是两次独立经历吗？回答都需要追到真实来源身份和实际事件，不能数 Revision 或只数消息条数。

**Q19：用户直接编辑了正文，旧证据和时间能不能全部继承？**

不能。编辑可能是纠错、更新、删减或换一种表述；当前手动修订对前版使用 unresolved，不凭文本差异猜旧版一定错误。新的正文也不能盲目继承已失去支持的语义和效果状态。

形成模型进行有证据的修订时，要用 retainedCitations 指明仍要采用的旧引文，宿主检查它确实来自已供给目标。本例只纠正咖啡品种、不改变糖量，可以保留支持“不加糖”的子句；不能自动复制仍含错误品种的整段话。新用户原话重新确认了糖量，也可以直接采用新来源。

继续追问：记录时间、原消息时间、事件发生时间、适用时间分别是什么？“她最近换口味了”没有明确日期时，应保留措辞和不确定性，不能把系统写入时钟假装成变化发生时间。

**Q20：完整记忆有哪些字段，哪些由模型生成，哪些用于索引？**

原始消息提供来源 ID、渠道、说话人、引用身份、发生时间和原文；模型提议 content、type、kind、owner、basis、主体、关系、条件、时间解释和逐字引文；宿主生成实体与记忆／修订 ID、写入时间、当前指针、引文位置和工作状态。当前形成创建的 importance 固定 0.5，非 inference 的 confidence 为 1，不是模型评出的记忆价值与正确概率。

owner 说明知识范围，subject 说明说的是谁。“用户告诉我林岚喜欢拿铁”可以是 user 范围的记忆，但主体是林岚。关系表与普通索引组织身份、时间和范围；FTS 与向量都从 Revision 正文产生，qualifier JSON 不会自动全部进入向量输入。

继续追问：糖量只存在 qualifier，正文遗漏会怎样？同名实体为什么不能只靠别名唯一合并？为什么不能说 confidence=1 就百分之百可信？要落到当前索引输入、别名主键与依据赋值规则，而不是重复“结构化很重要”。

**Q21：形成事务里究竟写了哪些表，第二条失败会怎样？**

模型等待在事务外。提交时先确认工作执行者与目标版本，再写实体与别名、Memory、Revision、FTS、待编码任务、来源关联、语义、实体角色、精确引文和后续工作；最后把同一片段的变化及下一游标一起提交。Memory 先引用尚未插入的 Revision，由延迟检查的复合外键在事务提交时核验所属关系。

同片段第二条写入失败，第一条事实及其索引、关联、进度都回滚；更早的来源入队已经提交，原文和工作仍在。若前一片段早已成功，它不随后一片段失败撤销，恢复从已保存游标继续。

继续追问：用户在模型等待期间编辑了目标，为什么不直接重试旧 SQL？因为模型理解的基线变了，必须重新绑定当前版本、重新比较未完成部分；仅把网络请求移出事务还不够，真正提交时仍要复查。

**Q22：认知交接、普通记录与后台工作是什么关系？**

普通 memory.record 等待形成回执，之后才确认保存；向量仍异步。认知经历通过持久交接把来源送入 Memory 队列，交接方无需把整次模型等待放进事务。

本地同库时，入队与确认交接在同一事务完成，提交后唤醒处理。若先确认再入队，崩溃可能丢任务；若分开入队与确认，需要处理重复。完成回执与稳定来源身份负责重放，不能只靠内存布尔值。

继续追问：改成游戏服务端两个数据库怎么办？需要明确投递、消费去重和回执合同，不能说桌面 SQLite 的一次事务自动跨越网络，也不能把“后台已入队”说成“NPC 已经学会”。

**Q23：记忆保存了但向量未完成，用户能听到“记住了”吗？旧向量迟到呢？**

收到 source_and_revision_committed 回执后可以确认保存，不能提前确认于只入队阶段。全文索引和待编码工作已在形成事务中持久化，语义索引在后台继续。编码失败不撤销已保存事实，应保留失败任务并如实报告检索缺口。

后台读取确定 Revision 的正文，按真实 tokenizer 分块，编码后在短事务检查版本仍存在、未删除、正文哈希相同以及向量有效，再写分块、向量和完成状态。旧 Revision 只要仍合法存在，可以完成历史索引；它的完成时间不移动 currentRevisionId。当前读取仍按最新版本和历史用途筛选。

继续追问：为什么原文物理块、形成片段和向量分块不是一回事？如果任务处理器改变了同一块序号对应的文字，哪些旧向量要清理？需要讲清输入身份和绑定关系，不能统称“缓存失效”。

**Q24：错记忆已经进入摘要，改原记录就结束了吗？**

没有。摘要必须记录依赖的确切原始版本和用途。原依据被 corrected 后，派生摘要作为当前证据的资格要重新检查；不能只让原事实的向量更新，却保留依然驱动回答的错误总结。

如果摘要引用原事实只是为解释“当时系统曾这样认为”，与把它当“现在仍成立”需要的资格不同。正常释放冗余原文且保留合法精确引文，也不等于用户纠错或删除必要来源。应逐项解释影响，不是无条件删光摘要或继续全用。

继续追问：四个摘要都生成成功，能说明压缩有效吗？不能。还要比较条件保留、最终答案、预处理与查询的总成本，并保留原记录里成本上升和上游形成失败的案例。

## 4. RAG、向量与性能：Q25–Q32

展开依据：[05 检索](05-retrieval-and-context.md)。

**Q25：混合检索为什么有必要？**

词法适合名称/编号，向量适合同义语义，结构过滤限定主体/时间，精确 ID 用于已知证据。它们各有盲点。否定和条件需要最终证据判断，不能以“余弦很高”直接认定事实正确。

查询“订单 A17 改期了吗”，编号适合词法；“他现在是不是不方便喝冰的”可能需要语义；“他”是谁和今天是什么时间需要结构化范围。三个环节是互补的。真正比较时固定语料和最终证据预算，分别看必要证据覆盖与回答，不因为多一个检索器就默认质量提高。

**Q26：当前用 RRF 吗？**

当前按问题/通道排名轮转并按 Revision 去重，旧 RRF 已替换。理由是通道覆盖与重复候选偏置，而非 RRF 普遍不行。这批真实模型比较每题只有一个信息问题，不能外推多问题容量分配。能写出一个共享宽泛候选挤掉少数问题证据的例子。

作为机制推演，可以构造三个问题都返回同一条宽泛总结，它在排名融合中得到多路加分；只有一个问题返回的关键例外可能被挤到后面。轮转方法轮流照顾问题和通道，再去重，以降低这种挤占。项目主测试两者同为 27/28，有限预算压力中必要证据出现数为 2/7 与 7/7；这是选择覆盖策略的依据，不是通用排名算法结论。

**Q27：topK 应该设多少？**

没有跨场景最优常数。看候选序列化预算、问题数量、作用范围、选择器成本和必要证据覆盖。当前 Memory 预算与长尾 Tool Search 的 8 项上限不同；不能把一个数字用在所有检索层。

先问预算限制在候选池还是最终供给。候选更多会提高覆盖，也增加选择成本；最终供给过多会引入干扰。项目使用序列化后的预算和多问题覆盖，而不是只看条数。面试应提出预算曲线：在多个预算点测覆盖、答案、用量和延迟，再选择满足体验的最简单方案。

**Q28：4B/512 是如何选的？**

按项目有限配对配置比较，质量未证明更大 8B/1024 值得成本；512 是支持 MRL 模型的前缀再归一化，非任意截向量。量化权重与保存 Float32 向量是两回事。0.6B 未完成相同最终比较，不能说 4B 是下限。

先比较多个模型和输出维度，再让最有竞争力的两组进入相同证据选择流程。28 个问题中，两组都能在候选中找到必要证据，最终都在 27 个问题上选全预先标定的证据；8B 的单向量排序更好，却没有转成这一步的收益。4B 的权重、内存与编码耗时更低，因此保留它。这个小开发集不能证明一般等效，也没有最终答案生成准确率结论。

**Q29：为什么没用 ANN？**

当前 exact scan 及 worker 有透明正确性与维护成本；规模/延迟不足时再比较 ANN 的召回损失、过滤、删除和内存。worker 保护 Main，不降低 O(Nd) 扫描计算量。十万条本地压力不等于万人同时查询。

若未来选 HNSW，需要与精确扫描对比相同过滤范围下的最近邻覆盖、最终回答、构建时间、删除更新和内存。还要调搜索宽度等参数形成代价曲线。十万条 512 维 Float32 原始向量约 204.8 MB，只是向量本体；图边、元数据、数据库和工作缓冲都会增加内存。先测瓶颈，不能看到十万条就机械换数据库。

**Q30：召回命中了为什么还答错？**

可能 query 丢条件、证据选择器 漏选、预算没供给、证据读时已失效、生成器误用或错误引用。看 candidate→selected→delivered→answer 四段。只看最后答案或向量 Recall@K 都无法完整归因。

沿一条错误问题检查八步：来源、形成、索引、触发、候选、选择、供给、使用。例如库里有记录但没调用搜索，修召回模型不会触及失败；候选齐全却漏掉“今天不喝冰的”，应检查选择和预算。项目实际出现过记忆与索引完好却没有触发搜索的失败，这是很好的归因案例。

**Q31：选择器后为什么还要重读？**

选择/预算测量有 await，期间记忆可能被修订或删除。重读准确版本，删掉不合格项并更新 coverage，不能偷偷替换成新正文。一次同步事务的快照保证不能跨后续异步网络调用无限延长。

假设选择器依据 r2 的“只在周末喝咖啡”选中了它，等待预算测量时用户把它改成 r3“暂时戒咖啡”。若直接读当前正文替换，选择理由和证据不再对应。应重新检查 r2 的使用资格，必要时移除并标出缺口，再启动新的选择或限定回答；不能把一次旧选择套在新事实上。

**Q32：怎么验证优化不是缓存作弊？**

分别固定并报告 cold/warm 条件、缓存命中、请求字节/版本、模型、输入输出长度和并发。配对同一任务，同时测最终质量和完整 关键链路，不能用缓存向量的阶段数字证明新编码器吞吐。

例如暖模型批量编码的 142.1 毫秒，不能代表下载、加载、长文本编码或整次回答。要记录批量大小、文本长度、维度、设备、是否复用进程和输出向量是否真实计算。查询链路还包括 SQL、扫描、选择器与生成；只有端到端比较能说明用户等待变短，阶段测量用于定位原因。

## 5. 工具、语音与反思：Q33–Q40

展开依据：[02 Runtime](02-agent-runtime.md)、[07 动作与反思](07-tools-action-reflection.md)。

**Q33：Tool JSON Schema 通过是否可以立即执行？**

还需工具 作用范围、执行模式、审批、当前输入和环境前置条件。Schema 是结构合法，不是业务授权或事实判断。玩家 ID 是合法字符串不代表玩家在场、订单有效或可以获奖。

一个合法的 orderId 字符串仍可能指向已经取消的订单。执行前要根据当前状态检查它属于谁、是否仍可修改，以及当前模式和审批是否允许。审批通过之后世界还会变化，所以业务前置条件应在真正提交效果时复核。批准执行不等于锁住世界，也不替代版本检查。

**Q34：为何保留核心工具常驻？**

历史能力发现漏掉基础文件工具造成错误“无法访问”回答；稳定核心原语按模式常驻能避免可用性依赖搜索。长尾仍用同一发现路径。常驻不表示允许调用，更不跳过审批。

工具发现的完整过程是先让模型知道如何搜索能力，再返回可用工具的 Schema，最终按模式和审批执行。若基础读取工具也完全依赖搜索，模型可能在尚未发现时就说不能访问文件。项目保留少量核心原语、长尾按需发现，是成本与可用性的取舍；效果要看实际任务完成和误调用，不能只看提示长度减少。

**Q35：取消后已经发生的副作用怎么办？**

取消尽力阻止后续动作，已完成的真实效果保留。未知效果先查询/核对，无法确定时明确 unknown；补偿要是产品定义的独立动作，不能偷偷重放或改日志。给一个“订单接受但网络超时”的例子。

订单接口超时后直接重试，会有重复出单风险。优先用原 actionId 查询或重试同一个幂等请求；确认已生效就记录完成，确认未生效才决定重新提交。若外部系统无法查询且没有幂等能力，应保留结果未知并向用户说明。取消只影响仍可取消的阶段，补偿操作也要有自己的身份与回执。

**Q36：循环检测为何不用固定步数？**

合法长任务可能每步都推进。当前规范化语义失败签名，去掉 request_id、timestamp 等噪声，结合新观察和条件恢复识别无进展。参数是项目启发式；还要测合法重试的误触发。

同一个失败每次带不同 request_id，按原始文本比较就识别不出循环；去掉这些无语义字段，再比较动作、参数和失败条件，才能发现没有新信息的重复。另一方面，“等待文件出现”遇到相关文件事件后可以继续。当前阈值来自项目实验，不是模型协议限制，合法长任务与恢复后的重试应单独测试。

**Q37：语音与文字共用同一个模型循环吗？**

不是。文字走 AgentRuntime，语音是原生 Realtime 驱动；共享 Run/Item、工具、审批和持久化。当前不是文字回答后 TTS，语音工具串行 continuation。说“同一个 runtime”时要明确统一的到底是什么。

统一的是用户任务身份、过程项、工具与审批以及持久化合同。原生语音有自己的输入转写、远端响应、播放和打断事件，不能强行塞进文字模型的同一循环。若面试官追问为何历史上改架构，要同时讲体验目标和小样本延迟证据，并说明不能把少量样本称为稳定尾延迟。

**Q38：Voice interruption 的难点是什么？**

播放、远端生成、工具、turn 身份和迟到事件各有生命周期。已播文本不能撤回；已完成动作不能假装取消。语音用户纠正还需区分真实转写和旧 generation 迟到事件。

玩家说“等等”，需要同时考虑停止远端继续生成、停止客户端后续播放、拒绝迟到旧片段，以及是否已有工具效果。每个动作应绑定当前会话和响应身份。只关闭播放器，远端仍可能返回旧工具调用；只取消模型，缓存音频仍可能播放。验收必须检查玩家实际听到的片段。

**Q39：自进化是不是让模型自己改代码？**

当前只能提出 Memory、Persona preference、Skill patch/new Skill 草稿，用户接受后按类型应用；不改源代码、Schema、Provider 或审批规则。触发是有局限的启发式，不是完美发现学习机会。

复盘输出是待接受的学习候选，应用前仍需检查当前对象是否与生成草稿时一致。例如 Skill 在等待用户确认期间已被修改，旧草稿不应直接覆盖新文件。经验候选的价值还要看后续任务是否受益；草稿数量多不是学习能力强，触发式复盘减少调用的同时必须检查漏掉了什么。

**Q40：Skill replay 通过能证明执行安全吗？**

当前 replay 是无工具模型按 case 输出评估，不能证明真实环境执行、成本或副作用。要有独立 独立判定依据、真实/模拟工具回放和未见案例。用户接受和 replay 是产品边界，不等于形式化正确性证明。

模型可以根据案例猜测技能会通过，但它没有实际触发游戏订单、页面变化或文件修改。项目注入的 10 个坏补丁中，仅靠这一类复盘挡住了 5 个，说明它不能单独作为执行证明。更强验证应运行受控工具或环境，并使用独立于候选生成器的成功条件，保留未见场景。

## 6. 咖啡馆与 AI 叙事：Q41–Q48

展开依据：[09 NPC 设计](09-cafe-npc-design.md)。

**Q41：NPC 看到玩家进店就应该打招呼吗？**

可能用快路径点头，也可能继续工作；语义插话要看忙碌、轮次、邀请、相关目标与角色。先定义可接受动作集合，再评价，不能把每次开口作为唯一成功。

把目标拆成接待、服务与当前玩家活动。玩家进店看向柜台，可以点头；玩家立刻与朋友讨论，可以继续工作；玩家直接叫店员，则应回应。模型可以帮助理解含蓄邀请，但明确规则应建立基线。测试同时统计打扰和漏回应，不以“台词很自然”掩盖时机错误。

**Q42：怎么知道玩家在和别人说话？**

优先消费游戏会话系统的 speaker/channel/turn 语义事件，结合允许的感知范围。不要仅靠截图或“嘴在动”推断内容；私聊根本不进入 NPC 输入，沉默不自动等于邀请。

游戏通常有比视觉识别更明确的语义信息：谁正在发言、哪种频道、谁在听觉范围。NPC 的感知投射应先过滤这些条件，再形成输入。服务器知道私聊内容不等于角色可听见；把全量聊天送进去再要求模型忽略，会失去清晰的信息边界。

**Q43：两个 NPC 同时决定插话？**

各自只生成提议，房间 权威处理器 对 conversation speech epoch 原子仲裁。生成前不长时间占锁；提交时重查 turn、audience 和依据。未获权者等相关条件或放弃，不把两份台词都广播。

两个提议可以并行生成，但不能各自宣布自己获得发言权。房间处理器按当前会话状态接受一个，分配发言代次并保存待发送动作，另一个得到等待或拒绝结果。不要在模型生成的几秒内持有独占锁。等待者在恢复时重新核对邀请和对象，旧台词未必仍适用。

**Q44：台词生成时玩家已经离开？**

相关 presence/目标版本变化使提议过期，提交和曝光前检查并放弃。若已经播出一部分，记录真实曝光，不把完整段落写成玩家已听到，也不声称什么都没发生。

只检查玩家当前在场还不够：玩家可能离开又回来。应区分此次在场的代次，旧邀请未必自动恢复。音频播放还要绑定发言代次，客户端收到迟到数据也能拒绝。这个例子可以检验设计是否真正覆盖异步变化，而不只是多加一个布尔值。

**Q45：玩家告诉 NPC 一个与 剧情事实 冲突的故事？**

记录“玩家这样说”与 NPC 的暂时理解，不能自动修改世界真相。角色可以在允许范围内怀疑或追问，剧情/任务状态由权威系统决定。生成器不应获得角色未解锁的全局秘密。

可以保存“玩家 A 声称配方在仓库”，并让角色在可见范围内求证；不能直接把配方位置改成仓库。若 NPC 已知反证，可解释或询问。作者知道的真实位置与角色知道的线索应分开投射，防止为了让模型判断真假而把未公开剧情全部提供给它。

**Q46：怎么让关系有成长而不是亲密度刷分？**

先记录有来源的经历、承诺、帮助、冲突与修复，让行为引用这些事实；数值关系变量仅在玩法需要并能验证时增加。不能按聊天次数就推出信任，也不能把长期互动优化成强迫玩家回复。

关系成长可以表现为记得上次帮助、兑现承诺、提及共同经历、在冲突后改变互动方式。这些都能追溯到事件。若某玩法确实需要信任数值，应说明数值影响什么动作、如何变化和如何防刷，而不把所有亲密感压成一个分数。项目本身没有任意亲密度系统，不能在面试中误报为已有。

**Q47：LLM、行为树、GOAP 怎么分工？**

LLM 处理语义与高层意图，行为树组织可预期反应，GOAP 可处理有前置条件/效果的行动规划，导航与动画由游戏系统做。分工按瓶颈与动作空间选择，不要求三个都上。

拿“送咖啡”举例：语言模型理解玩家请求和偏好；动作系统确认订单；导航移动；行为树处理被叫住；若多步骤前置条件变化频繁，可考虑 GOAP 重规划。没有复杂组合规划需求时，明确状态机可能更简单。选择依据是场景和维护成本，不是框架必须凑齐。

**Q48：AI 叙事和随机编故事区别是什么？**

要有可玩的状态变化、稳定因果与玩家可理解的后果。自由措辞不等于自由发奖励或改 剧情事实。Director 控制机会/节奏，NPC 保持自身知识与动机，权威世界确认效果，再评测体验与剧情一致性。

让玩家寻找遗失配方时，自由度可以在询问对象、线索顺序和台词；奖励与章节推进仍由任务系统确认。NPC 提议去查账本，世界反馈是否可读，再更新假设。玩家因此能理解因果并纠正方向。若每次都由模型临时编造真相，难以形成稳定可玩的规则，也无法做重复评测。

## 7. 数据与实验：Q49–Q56

展开依据：[08 数据闭环](08-data-flywheel-and-evals.md)。

**Q49：你现在的数据飞轮在哪里？**

当前有可追踪执行、Memory 来源依据、测试/Decision 和局部复盘，没有大规模线上玩家训练闭环。先复用事件建立归因和独立标签，再回放比较，最后受控上线；不要把日志量或草稿数量当飞轮收益。

举一条能闭合的链：玩家投诉纠正没生效，追到旧字幕提前曝光，形成带版本的复现样本，补标可接受行为，修提交与展示边界，在冻结集比较，再观察发布后的同类失败。当前项目具备其中若干基础，游戏线上采样和发布体系尚未建设，应作为下一阶段方案说明。

**Q50：你会采集哪些数据？**

最小必要的事件范围、版本、提议、候选/最终供给引用、动作回执、曝光和反馈身份。正文按用途受控保留，凭据不入日志。能回答“玩家是否真的听到”才能解释后续没回复是否有意义。

至少关联可见输入、模型请求版本、检索候选与最终供给、提议、动作回执和曝光。正文按实际目的保存，指标中使用引用。没有曝光数据时，“玩家没回复”无法区分没听到、忙于别事和不喜欢。采集设计首先服务于可归因问题，而不是先把所有内容都塞进日志。

**Q51：没有真人数据，评测如何开始？**

设计师定义场景与独立 独立判定依据，确定性 fake 环境做正确性；真实模型做语义质量；经授权的有限玩家实验验证体验。合成数据可扩充难例，不能证明真实人群分布或长期满意度。

先用设计师给出的合理动作集合建立小基准，包括正常、纠错、过时、私聊、多人抢话和结果未知。确定性环境检验机械合同，真实模型检验语义理解。合成改写可以扩充措辞，但同一模板仍属于同一组；不能用大量换名样本假装广泛覆盖。

**Q52：LLM judge 能代替人工吗？**

可筛查和辅助归类，需要盲化、顺序交换、行为评价标准 和人工校准/分歧复核。世界奖励、动作 ID、版本失效等优先用规则 独立判定依据。让生成器自己写预期再自评，证据强度有限。

对“订单是否创建”，查询环境即可；对“这句玩笑是否合适”，才需要有行为锚点的评审。让评审隐藏方案名称、交换顺序，并与人工判断对照。特别检查它是否偏爱长回答、是否把角色热情当作总是应该插话。分歧是改进标准的信号，不应悄悄删去。

**Q53：如何防止数据泄漏？**

按玩家、会话、剧情族和时间切分；同一故事的近义改写不跨训练/冻结测试集。评测器的隐藏真值不进模型材料。新失败可以生成新集，但不回写旧分数或反复看 冻结测试集 调参。

例如“周五改周六”和换名后的“星期五改星期六”不能分别放训练与测试。还要防止答案通过摘要或派生记忆进入输入，及评测器拥有的全局剧情泄露给 NPC。冻结测试暴露后可以成为回归，但后续调参再使用它时必须承认它已不是未见数据。

**Q54：指标好 1% 就上线吗？**

看分母、区间、配对差、样本相关性、实际效应、成本和复杂度；硬正确性单独检查。16 个同源 检查点 不是 16 个独立玩家。数值 判定条件 与整体证据冲突时透明修订，不能篡改原计划。

问清楚改善来自多少个配对不同样本，同时列退化。第 08 章教学例中旧方案 83/100，新方案 92/100，背后是 12 个改善和 3 个退化；若改善集中在一个模板，证据弱于分散在独立场景。还要看额外成本与尾延迟，不能只比较两个百分比。

**Q55：什么时候用 SFT/DPO/RL？**

先定位瓶颈。有合格抽取/工具轨迹可 SFT，有同状态偏好对可考虑 DPO，有可重复环境与可归因回报才考虑 RL。事务错误、输入缺失或曝光未知靠训练无法根治。

例如正确候选始终出现，但模型常漏掉否定条件，可以研究读取器提示或训练；候选根本不出现，应先修检索；旧动作在用户取消后仍提交，应修版本检查。偏好训练还要求两个输出基于同样输入和证据。先证明问题所在，再选训练方法，避免把训练当通用修复按钮。

**Q56：如何 A/B 测插话策略？**

同场景公平分配，关注多玩家相互影响，可按房间/会话分组；同时测误插话、漏响应、频率、角色/叙事、延迟与成本。对未曝光、断线、现实中断单列，不能都记成“不喜欢 NPC”。

可以先离线配对重放同一事件，随后在有限玩家试验中按房间分组。预先定义曝光插话是否合适、应回应机会是否遗漏、总体频率和未知结果。若 NPC 影响同桌其他人，就不能假设每名玩家相互独立。试验期间还应固定模型和提示版本，否则策略差异会混入其他变更。

## 8. 来源、优化与诚实表达：Q57–Q64

展开依据：[10 外部研究](10-research-and-industry.md)、[13 来源](13-source-index.md)。

**Q57：你从脑科学到底学到了什么？**

目标维持、选择相关信息、显著事件触发切换、经历与稳定知识分层的研究问题。它们是功能启发，不是脑区到 Agent 的一一映射。用被否决 Appraisal 实验说明自己愿意用结果纠正架构偏好。

把目标维持转成“被无关事件打断后是否恢复任务”，把选择性注意转成“无关变化不重算、关键纠正不漏掉”，把经历整合转成“跨独立来源归纳且可纠错”。每项都提出基线、可测行为与失败反例。这样的回答比把 SQLite 类比海马体更有研究价值。

**Q58：Generative Agents 为什么不直接照搬？**

它为经历、反思和行为连续性提供研究范式；当前游戏还需要多人权威动作、长时更新与真实曝光。受控模拟的行为可读性不等于线上正确性，须加自己场景的测试。

它的经历—反思—计划结构有助于提出问题，但当前项目首先要处理精确版本、纠正传播和真实效果。若借鉴反思，应固定原始经历和预算，比较是否改善后续行为，同时统计错误归纳。不能用受控模拟中的社会互动展示，替代长时间真人使用和多人并发验证。

**Q59：为什么学老游戏 AI，不只看最新 LLM？**

导航、动作生命周期、抢占、队伍协作和节奏已有实际交付经验。LLM 带来语义自由度，也引入延迟和不确定性；传统系统可提供稳定执行底座，具体结合用场景验证。

老游戏给的是已经处理过的执行问题：动作何时暂停、怎样恢复、谁负责感知、如何调节整体节奏。LLM 更适合扩大语义与表达空间。将两者结合的价值在于让模型提出丰富意图，同时保持可预测效果。面试应给一个具体动作例子，而不是泛称“混合架构更好”。

**Q60：开源项目比你成熟，为什么自己写？**

先承认其成熟点，比较合同与部署需求。当前要求单机、唯一 Run/Item、用户可解释修订及桌面恢复，自有实现能直接控制这些边界；代价是维护与测试成本。不因自己写就宣称更先进，也不因开源有某项功能 就认为满足所有需求。

回答不能停在“不符合需求”。拿更新记忆举例，比较对方如何处理旧内容、来源、删除与异步写入，再解释自己为何需要当前合同。若对方已有可靠实现且适配成本更低，应承认可以借鉴；自研的代价包括测试、性能维护和协议跟进。成熟度与适用性是需要具体比较的问题。

**Q61：你说的当前源码是哪一版？**

本套 CharaMate 固定 README 的 Git 基线，历史 Decision 用各自版本；外部资料有论文版本/访问日期。对未逐文件读过的 OSS 只讲官方文档描述，不说审计过最新完整实现。

报出本套材料的代码基线，并区分历史实验各自使用的源码与模型。外部仓库的 README 只是当前入口，若没固定提交并跟完写入、更新、检索和删除，就不声称审计了实现。发生代码变动时优先刷新对应事实与测试，再继续使用旧面试稿。

**Q62：十倍数据和十倍并发分别怎样优化？**

数据增长影响扫描、索引构建、磁盘和更新；并发增长影响排队、模型容量、共享资源与尾延迟。分别测 过滤后的数据规模、请求到达速率与处理速率。Worker 不自动增加模型吞吐，ANN 也不解决话轮抢占。

十倍数据时先测过滤后的扫描规模、编码积压、SQL 和磁盘；十倍并发时先测排队、模型在途量和尾延迟。将向量扫描放入 Worker 可能改善主线程响应，却不减少总计算；增加模型并发可能反而提高拥堵。分别建立负载曲线，再选择索引、缓存或调度改进。

**Q63：如果把费用减半，先动哪里？**

先看真实成本分解：无意义唤醒、重复上下文、证据选择往返和长输出，再试小模型/缓存/蒸馏。每项要保留纠错与旁路任务质量；不能砍掉最终版本检查或不记录 usage 来“降本”。

把一次请求的总成本拆成触发判断、检索选择、工具后续模型步骤和最终表达。先去掉没有行为收益的重复调用，再研究上下文组织或更小模型。每次只改主要变量，保留纠正、拒答和长链任务作为旁路检查。少花一半钱但多说错旧事实，不是同质量降本。

**Q64：你下一项最有价值的研究是什么？**

可选“插话时机与漏机会的联合评测”或“必要证据到最终回答的供给可靠性”。说明失败依据、单一变量、场景族、独立判定依据、成本指标与晋级条件。不要只说“加多 Agent、加图、上 RL”。

一个完整提案可以是：已有案例显示多问题检索容易漏掉限定条件；固定候选，比较逐条相关性选择与按问题覆盖选择；按故事分组切分；报告必要证据覆盖、最终回答、过时内容误用和成本。写清预期失败与停止条件，研究才有可执行起点。

## 9. Dot 与持续型 Agent：Q65–Q72

展开依据：[14 Dot 专题](14-dot-and-persistent-agents.md)。下面既考察公开材料，也考察自己的工程推导；回答时要说清是哪一层。

**Q65：你调研 Dot 后，认为它与 CharaMate 最接近的地方是什么？**

是跨对话的连续状态与责任：保留相关背景，追踪没做完的事，等待时间或事件，重新判断后继续，并决定何时通知用户。CharaMate 的认知意图、记忆修订、到期唤醒与 Run 合同提供了部分基础；多人世界和云端常驻仍需补充。

举例说，玩家说“等我聊完帮我取蛋糕”，系统需要持续保存这项责任。只检索到“玩家想取蛋糕”不能证明现在可以执行。还要确认当前约定、订单、在场身份和发言时机。这是能力对应，不能据此声称两者采用相同内部架构。

**Q66：Dot 的记忆到底用什么向量库和索引？**

本次读到的官方资料说明了相关 ChatGPT 记忆、自有笔记、历史对话检索和任务上下文的作用，没有披露足以确认其向量库、embedding 或完整索引算法的信息。我不会按产品演示倒推它一定用了知识图或某种 ANN。

可以继续讲自己的证据：CharaMate 的索引结构和选型有源码与 Decision，模型比较要说明数据规模、必要证据覆盖、资源代价及限制。能解释自己为何这样选，比猜对方的数据库名更有价值。

**Q67：为什么不能把所有未完任务都写进 Memory，定时检索一下？**

事实检索解决“有什么相关知识”，持续责任还需要状态、触发、完成条件和恢复。纯语义检索可能漏掉某项责任，也不天然提供重复触发去重、取消后失效和效果确认。可以用记忆辅助理解任务，但任务状态要有明确拥有者。

现有 Intent 或 Automation 能承担时就复用。不要再建一个相同职责的任务表。用重启后恢复、取消后不再执行和重复通知不产生双重效果来验证合同，而不只是检查记忆文本里有没有那句话。

**Q68：用户改要求时，后台任务已经快完成了，应该全部取消吗？**

先区分结果中的事实和行动。到货查询返回的事实可能仍有价值，但基于旧约定准备的交付或通知已经不适用。尽力取消可以减少浪费，提交和使用结果时仍要检查当前责任与所选依据。

例如从今天取改成明天，旧任务得到“蛋糕已到”可以更新来源明确的订单观察；不能接着播放“我现在给你拿”。独立查询可完成，依赖旧目标的动作要停止。只有一个全局 cancelled 布尔值，无法表达这些差别。

**Q69：你实际从 Codex 开源代码学到了什么？**

我固定了第 14 章登记的提交，跟了 TypeScript SDK 的 Thread、执行器和事件定义。Thread 保存连续会话身份；执行器启动一次进程并消费 JSON 行；有既有 ID 时继续该会话；条目完成、整轮完成与失败分别表达不同边界；清理在 finally 中处理。

这说明持续身份可以跨执行过程保留，过程事件也不能直接等同业务成功。它帮助我解释 Run/Item 和恢复边界，但我没有据此声称读过 Dot 的服务端实现，也没有运行这份 SDK 验证其所有异常路径。

**Q70：为什么暂停主 Agent 不一定让所有后台工作停止？**

主对话、分派任务和未来计划有各自生命周期。Dot 的控制文档明确区分这些操作。设计自己的系统时，需要明确一次取消针对当前响应、一个责任、相关执行，还是整项循环计划。

游戏里，玩家说“先别说话”可以暂停当前音频，不一定取消取蛋糕的责任；说“这张订单不要了”才会使相关交付失效。已经交付的蛋糕不能靠取消消息从现实撤回，仍需业务上的后续处理。

**Q71：主动研究怎样迁移成 NPC 主动性，如何评价好不好？**

先让角色获得合法观察，判断是否与目标相关，再形成候选；行动前检查当前控制、对象和发言机会。公开资料中的主动研究帮助提出这种分工，但具体事件规则、版本和阈值是自己的方案。

评价同时包含应响应机会、实际曝光、错误打扰、重复、等待和成本。不能只统计发出的好消息，也不能把完全沉默当零打扰的成功方案。固定候选内容，再比较触发或通知策略，才能归因到时机选择。

**Q72：本地系统如何达到 Dot 那种用户关机后仍继续的能力？**

当前本地调度能在进程启动和系统恢复后检查持久待办，不能在设备关闭时凭空执行。需要云端承担责任时，首先明确状态归属、执行环境、离线等待和效果查询，再决定部署与同步。浏览器会话和文件也不能假定随任务自动迁移。

我会先证明本地的修改、等待、恢复和取消闭环，再验证玩法收益，最后按真实需求扩展持续执行环境。论文、Dot 演示或一个定时器，都不能代替这些运行和维护证据。

## 10. 两轮模拟面试安排

**第一轮：项目深挖，建议 40 分钟。** 90 秒介绍；8 分钟讲统一执行与 Cognition；12 分钟讲纠错链，面试官在随机 await 插入新 revision；8 分钟讲一次失败与一次被否决方案；剩余时间讨论数据闭环。只允许开始时看目录，回答中不查正文。

**第二轮：系统设计，建议 45 分钟。** 5 分钟明确咖啡馆需求与玩家知识范围；10 分钟画状态与架构；10 分钟推演多人插话及中断；10 分钟谈规模/评测/数据；10 分钟处理追加条件“私聊、断线、旧记忆纠正、两 NPC 抢话、旧后台任务与定时唤醒迟到”。不要提前猜面试官要哪个模型。

两轮都记录：答错的事实、讲不清的 await/事务、未说明的假设、误报为已实现的方案。按第 12 章逐项补学，不用“感觉发挥不错”作结论。

## 11. 可以反问团队的技术问题

面试官愿意展开时，可选择两三个：目前最难的是时机、角色一致性还是规模成本？如何区分 NPC 的真实世界状态与主观所知？目前离线评测和真人体验分歧主要在哪？模型能力提升后，哪些宿主约束仍必须保留？能否介绍允许公开的实验复盘方式？

问题以了解实际工作为目的，不套取未公开架构，也不先假定团队一定采用某种“类脑”实现。
