# 19 一面复盘：主动陪伴的分寸与发布者的问题闭环

本章回答第 4、6 问。代码基线 `8e50d50f47fd961fbed9174d76f145a5e22b58d1`，核对日期为 2026-10-27 至 10-28。前半解释当前主动聊天与可验证的改善；后半从产品发布者视角，完整推演用户报错到发布修复。游戏场景和多人运营均是设计方案，不代表米哈游内部实现，也不代表项目已有线上用户证据。

## 1. 当前不是“想聊就聊”，而是四层判断

| 层次 | 谁负责 | 判断内容 |
| --- | --- | --- |
| 来源与持续理解 | Activity／Cognition | 实际发生什么、属于谁、与哪个持续事项有关 |
| 行动选择 | 认知模型及其持久状态 | 保持安静、继续自己的活动、回应／发起交流等；理由必须有材料 |
| 执行与展示准入 | 宿主代码 | 用户是否正交流、旧依据是否失效、频率与免打扰、是否已有气泡 |
| 展示结果与反馈 | 会话 surface＋历史仓储 | 真的展示、回复、关闭、过期、中断，反馈回 Cognition 与频率策略 |

不是每个桌面事件都启动模型，也不是模型想说就立即显示。[第 03 章](03-cognition-attention-persona.md) 展开来源、水位、一个在途分析、下一次唤醒与版本检查；本章补的是“不烦人”到底由哪些现有机制承担。

## 2. 当前明确有哪些限制

### 2.1 真实的频率设置和退避

[companionInitiativePolicy.ts](../../../src/main/journey/companionInitiativePolicy.ts) 目前写明：

| 设置 | 基础最小间隔 | 说明 |
| --- | ---: | --- |
| off | 不主动发起 | 用户明确关闭 |
| lively | 15 分钟 | 只是当前产品值 |
| balanced | 60 分钟 | 默认档位 |
| quiet | 240 分钟 | 四小时 |
| 绝对下限 | 5 分钟 | 当前各档基础值已经更大，不能误说默认每五分钟搭话 |
| 默认免打扰 | 本地时间 22:00–08:00 | 可设置；跨午夜按真实本地分钟判断 |

设置默认值见[settings 合同](../../../src/shared/contracts/settings.ts)。这些数值是现有代码行为，没有找到它们已通过长期真人随机试验的证据，不称行业最佳或脑科学常数。

历史仓储只保留最近三条主动记录，按最近连续 `dismissed`／`expired` 个数 n，计算：

```text
本次需要等待 = max(5 分钟, 当前档位基础间隔 × (1 + n))
n 最大为 3
```

默认 balanced 下，最近连续 0、1、2、3 次关闭／过期分别要求等待 60、120、180、240 分钟。比较起点是最近一次 `acceptedAt`。这个字段在此处表示系统已把主动消息交到展示面，**不是用户已接受邀请**；真实回复由 replied 单独记录。

“减少打扰”操作会保存更低档位：lively→balanced→quiet，quiet 保持 quiet，off 保持 off。源码在 [Main 装配](../../../src/main/index.ts) 调用 stepDownCompanionInitiativeLevel。用户偏好能改变产品行为，不只是给模型加一句话。

### 2.2 当前占用与状态资格

[choiceBlockReason](../../../src/main/cognition/cognitionProjection.ts) 会阻止以下可选行为：

- 系统睡眠、模型选择以后再做；
- 用户有活动 Run 或正在语音中；
- 已有角色 Run、Chat 活跃回合、等待原输入的任务不允许另开替代路径；
- 相关 Intent 不存在或不再 active；
- 想执行外部动作，但依据只是推断用户意图；
- 不允许主动会话，或已有尚未结束的气泡。

可见这里 `userEngaged` 主要由活跃用户 Run／语音推导。**用户在 Overleaf 连续写字不自动等于这个字段为 true。** 专注度需要从 Activity 与持续情境理解，不能把宿主占用锁说成已经准确知道用户的认知负荷。

[认知运行时](../../../src/main/app/cognitionRuntime.ts) 对有依据的 requested continuation 还有独立合法性检查，不能把所有已请求继续、普通主动邀请都解释成机械受相同冷却。明确要求的结果反馈和无请求搭话是不同产品语义，但都要避免陈旧内容和重复执行。

### 2.3 发出去之前再核对

分析完成后先检查当前 Persona、userGeneration、来源／实体 revision、最新用户接收及行动依据，再决定执行。生成完准备展示时还会再次检查状态。

原因很具体：模型在用户写论文时决定“推荐一点参考资料”，等待期间用户已经说“先别打扰”，旧推理文本本身不会变。必须由宿主阻止旧结果展示，而不是期待模型提前猜到将来的拒绝。

实际展示成功后才写主动历史并回灌 offered 观察；仅模型生成不算曝光。展示失败不能算用户忽略。表面的 accepted、replied、expired 等状态含义必须讲准确。

### 2.4 气泡与正常 Chat 如何衔接

当前临时邀请的回复窗口为 20 秒，见[proactiveConversationSurface](../../../src/main/journey/proactiveConversationSurface.ts)。用户接话后进入同一 Chat／Run 路径；没有接话的临时邀请可以清除、丢弃 provisional Chat，避免用未参与邀请占满聊天列表。已建立会话不能按临时邀请随便删除。

20 秒是展示生命周期值，既不是最佳主动间隔，也不是情绪标签。用户可能正在看另一块屏幕，所以代码给 Cognition 的反馈明确说明：关闭／过期不建立用户感受；真实回复由真实消息提供依据。

## 3. 用 Overleaf→浏览器→B 站串一次完整过程

以下时间为教学示例，按当前默认 balanced 推演。不是一条本次实际采集的桌面轨迹。

| 时间与事件 | 当前系统应怎样理解／执行 | 容易讲错的地方 |
| --- | --- | --- |
| 09:00 打开论文项目 | Activity 给真实应用／对象／局部内容；Cognition 可关联原有论文事项 | 打开应用不是创建一个新 Agent |
| 09:02 选中摘要，原来有“等你写完一起检查”的约定 | 结合持续 Intent 和有效来源提出一个相关选择；频率、占用、状态允许才展示 | 有约定不意味着可以无限插话 |
| 09:03 提议“你写完这段，我可以一起看摘要”并展示 | 此时记录一次 offered／acceptedAt，等待用户是否参与 | 生成完但没展示，不能记成用户收到 |
| 用户回复“好，先让我写完” | 成为正常 Chat 输入；当前约束是暂时安静，持续事项保留 | 不能为了维持活跃隔几分钟问进度 |
| 09:10 浏览器搜论文、问 ChatGPT | 可能仍是同一论文目标的子活动，更新证据 | App 切换不等于目标切换，不要再次自我介绍 |
| 09:25 保存／编译，暂时无新请求 | 可以重新理解状态，但安静仍是合法选择 | 定时唤醒是考虑机会，不是发送许可 |
| 09:40 打开 B 站 | 看具体内容；可能休息，也可能查教程 | 不能直接断言疲劳或心情不好 |
| 09:41 模型认为有合适话题 | 普通新邀请距09:03不足60分钟，默认策略仍拦截 | 语义“有趣”不能绕开已选频率 |
| 10:05 有明确休息语境且没有安静约束 | 如果资格成立，可以一句轻量交流，也可以继续安静 | 不能为了用满机会硬说话 |
| 邀请过期 | 最近负反馈数增加，下一次间隔拉长；保留不确定性 | 不可直接记“用户讨厌 B 站聊天” |

如果用户在09:41主动问“这个视频你怎么看”，这是用户输入，应正常回答，不等主动间隔。若是先前明确要求“资料查到马上告诉我”，还要按有效的已请求继续处理，不能简单用普通闲聊冷却挡掉所有结果。

## 4. 现有设计合理在哪里，缺口在哪里

合理之处是：安静是显式行为；有用户控制、免打扰与退避；背景理解、执行和曝光分开；旧结果要检查；用户优先。这比每隔固定时间生成一句问候可靠。

缺口也具体：

1. 最近三条结果只表达很短的近期反馈，不能学习某用户在不同活动中的长期偏好。
2. expired 把“没看见”“正在忙”“不想理这次内容”混在一起。退避是保守控制，但不能用于语义画像或直接做负例训练。
3. 频率由“距离上次展示多久”决定，不能单独衡量一条消息的价值、内容长度、是否要求用户做事。
4. 当前活动占用不等于真实专注度，AX／DOM／图像也只代表获得的局部内容，不等于知道用户内心。
5. 角色回应策略有小型文本比较，未证明连续几周的陪伴感、打扰感或留存改善。
6. 咖啡馆里还需要共享的发言权；一百个 NPC 各自遵守间隔，玩家仍可能被一百个角色轮番打扰。

[回应策略 Pilot](../../benchmarks/COMPANION-RESPONSE-STRATEGY.md) 使用24个合成场景，共48次文本生成；单名研究 Agent 盲评结果为策略4胜、20平、0负，输入 Token 增加16.7%。最终生产提示又经过压缩。它支持一些回应方向的取舍，不能称真人长期实验，也不能把4/24直接归因给最后压缩版。

## 5. 行业研究怎样转化成“陪伴的分寸”

### 5.1 Dot：先发现有用内容，再决定是否告诉用户

[Dot tasks and memory](https://learn.chatgpt.com/docs/dots/tasks-and-memory) 公开描述后台研究可读取获准资料、形成私有笔记；研究本身不直接发消息或改应用，而是把发现报告给 Dot。此页截至2026-10-27没有公开其注意力打分、阈值或内部调度代码。

启发是把“值得后台了解”与“值得现在打扰”分成两次决定。NPC 可以默默注意到玩家最近在找材料，等玩家走到柜台或询问时再自然提起；不会每发现一件事就播报。这个映射是我们的方案，不是 Dot 或米哈游公开实现。

### 5.2 Oasis：任务的自然边界比空闲秒数更有意义

Iqbal 与 Bailey 的 [Oasis 论文](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/TOCHI-Oasis-final.pdf)（TOCHI 2010）根据系统／应用交互识别任务中的阶段边界，把通知安排与这些时刻结合；论文还说明训练边界识别模型的方法。它不是 LLM 游戏论文，也没有给本项目一个通用冷却常数。

迁移到论文场景：编译结束、一次编辑保存、用户明确说“写完这一段”比“鼠标20秒没动”更有解释力；去洗手间也可能不动鼠标。迁移到游戏：战斗结算、对话轮结束、玩家靠近柜台，比每帧判断“是不是无聊”更好测试。边界依然只是时机特征，不自动构成开口理由。

### 5.3 新研究：少问与问得值得要分开评价

[Ask Less, Ask Better v1](https://arxiv.org/html/2610.24411v1)（2026-10-17）同时研究提问数量和注意力负担；其方案用已知用户回答与任务证据检查待提问题，决定保留、改写或取消。对照包含只限制次数、只有自检、没有原始用户记录等。主要任务是英语模拟客服和交互研究，不能直接外推中文陪伴；额外自检也有模型调用成本。

可迁移的点：NPC要问“你想玩什么”之前，先检查玩家刚说过的选择；重复询问不是亲切。我们可先在现有决策中加入“答案是否已知、是否真需要用户决定”的检查，再验证是否值得增加独立模型步骤，不照搬一个常驻 Review Agent。

### 5.4 游戏里的自主行为不要求每个行为都找玩家聊天

[Generative Agents v2](https://arxiv.org/abs/2304.03442v2) 展示25个模拟角色如何结合经历、反思和计划形成可理解行为，研究讲解见[第10章](10-research-and-industry.md)。那不等于已经证明多人线上玩家不会厌烦。

对咖啡馆NPC，整理桌面、继续手头工作、记住未完成订单、在玩家问起时接上前文，都能让角色显得持续存在。“像人”不应该被实现成“提高主动发言次数”。真正的问题是角色能否在当前世界和关系中做适合的事情。

## 6. 建议的改善方案：分别评价机会、内容和时机

在现有 Cognition→行动→展示流程内改进，不再建第二个持续主动聊天循环。

### 6.1 一条机会至少要回答这些问题

| 判断 | 例子 | 适合的处理者 |
| --- | --- | --- |
| 有真实且相关的理由吗 | 用户约定的检查时机、已完成结果、共同看到的内容 | 语义模型＋来源校验 |
| 用户是否需要现在知道 | 订单快过期与普通趣事价值不同 | 业务事件规则＋语义判断 |
| 此刻打扰成本多大 | 战斗／正在对话／写段落／阶段结束 | 权威状态和任务边界特征 |
| 这条消息会让用户多做多少事 | 一句告知与连续五个问题不同 | 内容评价 |
| 用户是否已经拒绝或回答过 | “让我先写完”；前一分钟已选饮品 | 当前约束、Memory 和本会话 |
| 能否等待或不说 | 保留信息、等到柜台、只做环境动作 | 同一行动选择 |

游戏服务端可以先按距离、视线、会话成员、战斗阶段和对象订阅过滤事件，再交模型。近百个 NPC 不应各自读取全世界日志。最后由玩家／会话范围的发言仲裁控制实际曝光；不能只限制单 NPC 的频率。

### 6.2 怎样决定阈值而不是拍脑袋

用一个解释性目标表达取舍即可：

```text
现在开口的净收益
= 对当前任务／陪伴的帮助
- 打断和恢复任务的代价
- 重复信息或索取回应的负担
- 内容或时机误判的代价
```

这是产品目标，不是说现在已实现一个按四个随意权重求和的神经分数。先人工标注“有理由但应稍后”“适合现在”“无需告知”“必须按约定通知”，并记录依据。只选择能观察且在上线时取得的特征：近期真实回应、明确安静约束、任务阶段、同类信息是否已展示、候选消息长度及需要几个决定等。

如果训练概率模型，按用户／会话留出数据，检查校准和各活动分组；模型自己说0.9不等于90%准确。对漏掉重要结果和打扰写作给不同代价。开发集选择阈值，独立集看完整代价曲线；不要复制现有15／60／240分钟作为“学出来的参数”。

### 6.3 怎样获得有效反馈

曝光、看见、回复、有帮助、烦人是不同标签。当前只能可靠记录部分交互，不能从没有回复推断“烦人”。真实反馈可由用户主动选择“现在不方便”“以后少提此类”“这个有帮助”，配合有限、获同意的体验研究。

用户关闭时，系统可以保守减少频率；训练时则保留原因未知。不要把点击关闭100次直接称为100个讨厌该话题的标注。内容讨厌与时机不合适也要分开，否则模型可能永远不再提真正重要的信息。

### 6.4 怎样检验陪伴感而非刷活跃

分三步进行：

1. **离线事件回放**：固定世界／桌面轨迹，检查忙碌、安静约束、旧结果、重复曝光、已知信息再问等正确性。
2. **同一机会的内容配对**：给相同背景，比较两种消息／沉默选择；评者看来源和边界，不看策略名称。
3. **获同意的连续使用研究**：比较当前策略与一个修改版本，按用户或会话安排条件，处理顺序和长期记忆的残留影响；观察跨日体验，而不是只看一次演示。

同时报告：实际曝光数、被判断可发的机会数、错过的已约定通知、打扰反馈、重复询问、任务恢复时间、用户报告的被理解／被陪伴感，以及推理成本。机会数需要抽样审查包括保持安静的时刻，否则只检查已发消息会漏掉“总是沉默”。

主动消息点击率不能单独当目标。诱使用户不断回复可能提高点击，却破坏陪伴。阈值及频率选择必须保留这种收益／代价的实测证据。

## 7. 从发布者视角：不可能收齐所有问题，但要能发现并定位

没有异常日志不代表没问题。模型可能答错却HTTP200；应用可能在日志上传前崩溃；用户可能觉得烦但不反馈。成熟产品要把三类信号接起来：

| 信号 | 例子 | 负责发现什么 |
| --- | --- | --- |
| 可用性与性能 | 启动失败、native crash、连接断开、队列积压、首音频变慢 | 工程故障 |
| 执行与内容质量 | 旧事实使用、错误工具参数、重复动作、只播半句、莫名插话 | 成功返回中的错误 |
| 用户体验反馈 | “你记错了”“别打扰”“声音断了”、主动提交的问题报告 | 自动指标不能判断的体验 |

不能保证“收集所有”；目标是覆盖关键失败、量化观测缺口，并让一个问题可以关联到所用版本和执行阶段。

### 7.1 当前已经有什么，缺什么

当前 [Pino logger](../../../src/main/observability/logger.ts) 在日志边界做秘密信息清理；[RuntimeObservability](../../../src/main/observability/runtimeObservability.ts) 保存有界本地 trace，含 Chat、Run、Item、Provider、model、状态、错误码和工具等；[VoiceMetrics](../../../src/main/voice/voiceMetrics.ts) 有连接阶段、转写／首音频、工具接续、迟到事件和 usage 覆盖；[ProductMetrics](../../../src/main/observability/productMetrics.ts) 有 Memory 与本地存储等统计。

这些是基础，不是已部署的跨用户监控平台。当前 Runtime trace 窗口为500；Voice 的耗时数组另有自己的生命周期，不能因为一个模块有界就认为所有进程统计都已验证长期有界。usage 没返回应记缺失，不能算零费用。

秘密清理也不等于个人数据匿名化：用户姓名、日程、论文内容仍可能是普通文本。不能直接把当前含 payload 的本地 trace 全部上传中央服务器。

## 8. 最小产品级收集方案

以下都是拟建的发布体系，不是本轮新增服务、依赖或遥测默认行为。

### 8.1 先有版本和关联，再有更多日志

建议每次运行记录可用于复现的非内容元数据：

| 字段组 | 建议内容 | 原因 |
| --- | --- | --- |
| 发布环境 | app build、Git／构建标识、OS／架构、数据库 schema、native依赖版本 | 区分只在某版本或某设备出现 |
| AI 配置 | Provider类型／部署标识、模型版本、指令／工具Schema版本、Persona revision | 相同代码也可能因模型配置变化而行为不同 |
| 记忆链路 | formation处理器、编码器modelKey、索引代际、当前revision及候选计数 | 区分没形成、没索引、没查和查后丢弃 |
| 执行关联 | 本地session／run／item／response／tool call ID、事件序号 | 把多个异步结果连起来 |
| 阶段状态 | 起止时刻、耗时、状态／错误码、取消原因、是否实际展示 | 定位延迟或曝光所在层 |
| 观测覆盖 | 是否抽样、采样概率、是否丢事件、usage是否缺失 | 没看到和没发生分开 |

ID 本身也要按产品数据范围处理；聚合不需要真实姓名。版本组合是复现入口，不应把每个用户、每个runId都做成指标标签，避免无限高基数。

[OpenTelemetry Traces](https://opentelemetry.io/docs/concepts/signals/traces/) 把工作段建成 span，并可通过 link 关联异步因果。可借鉴这个结构：一次聊天已结束，后来异步索引形成另一段工作，仍能关联来源。无需现在为一个本地产品安装整套遥测平台，也不要把一次异步队列等待伪装成永远不结束的HTTP请求。

### 8.2 采集、发送、接收怎么做

1. **客户端就地记录**：保存小而有界的阶段事件；统计和详细轨迹分开。崩溃报告要能识别构建和原生符号版本。
2. **用户可理解的反馈入口**：在出错或具体回答旁提交问题，自动带入问题所在Run及非内容元数据，允许预览要分享的内容。
3. **最小化上传**：默认设计不依赖中央收集全量音频、截图、对话或向量；无法靠元数据定位时，再使用用户明确选择的短片段或复现材料。
4. **离线队列**：可重试、限量、带事件ID和批次序号；联网恢复不重复计数，不把失败上传无限占盘。正常关闭、崩溃后重启各有可核验结果。
5. **服务端接收**：校验schema版本，按ID去重，把详细轨迹放到受控的诊断存储；聚合指标另建低基数视图。
6. **问题归并**：错误码＋阶段＋版本＋规范化堆栈作为初始归并；语义报错再用主题辅助聚类，最终由负责人确认是不是同一根因。

只采失败轨迹无法计算失败率。需要保留总体计数和一定的正常对照；对稀少错误提高保留率，也要保存抽样信息。聚合比例按真实暴露或适当加权估计，不能把“我们收到了20份错误报告”除以“我们只上传了30份异常日志”。

在本地BYOK应用中，发布者也不天然拥有用户Provider侧日志；要记录可获得的请求关联ID和端点类别，明确哪些远端阶段仍不可见。

### 8.3 告警怎样避免误导

优先看用户影响：受影响会话／用户、失败阶段、持续时间、版本集中度。Voice断线按会话、重复副作用按实际执行机会、主动打扰按实际曝光统计；不能共享一个模糊“成功率”。

尾部延迟只统计成功请求会隐藏超时。慢请求、失败、取消、用户主动打断应分别保留，既不把正常打断全算故障，也不把超时剔除后宣布系统很快。

告警阈值先来自历史基线、最小可检测变化和服务目标。某模型升级后出现新错误码，即使样本少也值得排查；正常高峰时延轻微波动不能每分钟轰炸负责人。具体数值须有负载证据，不在面试中虚构已验证的SLO。

## 9. 一个完整事故：用户报告“总是只听见前半句”

这里采用仓库已有的 responseId 播放竞态作为根因，模拟它若发生在一个已发布产品中的处理流程。用户数量、时间线与发布过程没有真实线上证据，均为方案；当前代码已经包含按responseId保护的修复，不能再说这个缺陷仍未修。

### 9.1 收到报告，先确定用户说的是什么

用户在对应回答点“声音断了”，可选说明“说完‘我查一下’就没了”。反馈关联应用版本、会话、Run与时间，不要求用户先理解responseId。

需要区分：没有生成后半句、生成但未发送、收到但被应用静音、设备没有播出、用户打断了它。这五种表面上都叫“声音断了”，负责人不能直接归因网络。

### 9.2 用因果事件重建，而不是只搜 error

教学轨迹如下：

```text
run U，generation 7
R-A response.created
R-A audio.started                 “我查一下”
call C memory.search 完成
R-B response.created              同一个 generation 7
R-B audio.started                 “已经改为周六三点”
R-A output_audio_buffer.stopped   迟到
播放器变为 disabled
R-B response.done
```

如果没有speech_started、用户静音、设备切换或取消，而播放器正好在R-A迟到停止时关闭，就强烈指向状态归属错误。R-B模型完成、工具成功、HTTP正常仍然可以发生用户可见故障；只看错误码找不到。

这里仍应核对实际播放状态，不把“看见audio.started事件”当作用户确实听见。元数据只能缩小原因；必要时用测试设备复现音轨和播放状态。

### 9.3 复现与最小修复

用假DataChannel和可控顺序，回放“B已开始、A才停止”。不需要每次花钱调用真实模型碰运气。再加入：

- A停止在B开始之前，不能误拦B；
- 旧generation的created／stopped迟到，不能进入当前播放；
- 用户真的开口，必须停B；
- B结束后释放正确资源；
- 暂停、结束或重连后的旧事件不能复活。

修复围绕一个不变量：**停止事件只能关闭它所属且仍在播放的response**。不能加一个固定等待，让A“应该先结束”；网络顺序仍会改变。也不应直接把generation拆成每段声音一份新Run，这会破坏工具接续与产品任务语义。

### 9.4 验证和发布

先跑驱动定向及Voice跨域回归，再用真实Provider验证正常工具接续，用真实耳机／外放确认能听完并能打断。带上受影响的OS和构建，不只在开发机点一下。

发布新构建给获准的少量更新人群或既定发布渠道，比较相同条件下的断音反馈、异常播放事件、正常打断和延迟；新问题出现则退回上一个兼容构建。按发布版本分批，不在产品保留两套可选语音算法作为长期模式。

若涉及数据库变化，回退还要确认数据兼容；本例是播放状态修复，可以避免为了修一个客户端竞态顺手改Memory schema。宣布解决前，确认真实用户问题和事件指标共同改善，而不只是CI变绿。

### 9.5 关闭事故之后留下什么

留下最小可复现事件序列、根因、修复版本、回归用例和结果。重复用户报告归到同一问题但保留影响人数；旧版本仍在报错不能误算成新版本修复失败。用户希望收到处理结果时，由既有支持流程回告。

原始隐私片段遵循既定保留／删除约定；回归优先使用人工合成事件和必要的脱敏片段。不要把整份私人聊天永久放进测试仓库。

## 10. 另一个案例：用户说“你把我约定的时间记错了”

这个问题不能只看是否有数据库异常，应沿一条问题单串联：

1. 找到用户说的那次交流。若用户只记得大概时间，先让本地检索帮其定位，由用户选择分享范围。
2. 比较原始输入来源和转写：是否“一起／仪器”、周五／周六在此处就错？无音频时如实说无法核对声学原话。
3. 检查形成工作是否存在、处理结果是什么；没有就定位漏触发，而非修改查询权重。
4. 检查Memory／revision／来源：抽错人物、误解取消、还是用户确实后来改了安排？
5. 检查索引及modelKey；旧向量未退休不必然错误，关键在是否以旧事实回答当前问题。
6. 检查当时Agent是否搜索，搜索参数是否错误限定，正确材料是否进入候选和最终Pack。
7. 比较回答和真实行动结果；不能因为工具“预约成功”就认为用户本来就要这个时间。
8. 修正确根因，并给受影响用户提供具体记忆更正；不能静默重算全部用户历史而不知道会改什么。

如果根因是转写误识别，补相近发音与关键时间数据；如果是旧revision资格失效，补数据库竞态测试；如果是没查，补历史依赖评测。修复类别决定数据怎么回流，不是所有badcase最后都进入微调。

## 11. 问题如何变成数据和持续改进

[OpenAI eval best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices) 建议定义目标、收集有代表性的数据、比较并持续扩展评测。其文档示例里的阈值不是本项目标准。这里落实成一条有负责人的流程：

```text
报告／指标异常
→ 去重与影响范围
→ 复现并定位根因
→ 正确性修复或语义候选
→ 标注／测试样本
→ 开发比较＋独立确认
→ 发布与回退观察
→ 问题关闭＋回归保留
```

| 问题类型 | 主要产物 | 通常怎么解决 |
| --- | --- | --- |
| 状态机／事务／幂等 | 可控事件序列、数据库前后状态 | 修代码与回归 |
| 工具Schema／Provider兼容 | 实际请求合同、错误及版本 | 修单一适配边界，真实端点确认 |
| 记忆形成／召回 | 有来源的多轮场景、必要证据和反证 | 修入口、数据、计划或算法，配对评价 |
| OOC／剧透／错误提示 | 角色和世界快照、可接受／禁止输出 | 角色或知识供给、指令；有足够稳定数据再训练 |
| 打扰／缺少陪伴 | 实际机会、展示、时机原因与体验反馈 | 调整决策与交互，通过连续体验验证 |

节奏也要按性质分：新崩溃、重复动作等及时处理；日常去重分诊可每日；语义标注与成组复盘可按周；涉及模型、提示、检索或记忆协议的发布前都跑相应回归。这是建议工作节奏，不是项目已经在运行的日程，也没有创建自动化任务。

稳定测试集不能天天把看过的失败塞进去再称“独立测试”。新事故进入回归集；开发集可更新；保留集按人物、故事、说话人、版本和任务隔离，并记录何时用过。人工抽检自动评审的一致性，按分歧修标签规范；没回流足够同类样本前，不要为了“数据飞轮”先训练模型。

闭环是否有效看同类问题复发率、定位耗时、修复覆盖和真实质量变化，不看收集了多少条日志。对语义问题，还要看修一个场景是否把另一个场景修坏。

## 12. 面试口述与验收

可以这样回答主动陪伴：

> 我现在分开做持续理解、是否值得说、能否执行和实际展示。代码已有主动档位、免打扰、连续忽略后的退避，也会让用户当前Run和语音优先。局限是过期不等于反感，频率也不等于时机，所以还需要任务边界、内容价值和连续体验评测。Dot给我的启发是后台研究不直接等于打扰，游戏里还要把发言预算放在玩家会话层。

从发布者视角可以这样回答：

> 我会先补版本、事件关联和有界诊断，再接用户可理解的反馈；默认不需要把用户所有内容传回服务器。收到问题后按采集、模型、工具、记忆、播放和展示逐层定位，形成可复现样本。像只播半句，可能所有API都成功，真正问题是旧response的停止事件关掉了新音频。这样的错误要修状态机，不是微调模型。发布之后还要验证影响下降并保留回归。

闭卷验收：

1. 手算balanced档最近0／1／2／3次连续过期的间隔，解释acceptedAt不等于用户接受。
2. 推演用户写论文、查资料、开B站又说“别打扰”；区分考虑、生成、准入与曝光，每步指出证据。
3. 为咖啡馆中十个同时想发言的NPC设计玩家级仲裁；用户求助与可选闲聊不能机械同等排队。
4. 在“不回复、关闭、没展示、明确说烦”四种情况中标出能确定什么、不能训练什么标签。
5. 从上述R-A／R-B轨迹定位断音，提出回归顺序和发布观察；不能用增加sleep解答。
6. 对“记错约定”列出各层证据、修复负责人和数据产物，并解释什么情况下根本不需要训练。
7. 给出三种观测缺口：用户未反馈、未上传、Provider不可见；报告里不能把未知写成成功。
