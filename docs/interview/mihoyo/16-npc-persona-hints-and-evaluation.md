# 16 NPC 开放对话、战斗响应、分层提示与评测

对应本轮七组问题；学习时衔接 S2、S7、S8、S9，验收衔接 A08–A12。本章先回答 CharaMate 已经做了什么，再设计游戏侧尚需建设的能力。源码基线为 `8e50d50f47fd961fbed9174d76f145a5e22b58d1`，核对日期 2026-10-25。

贯穿案例中的“巡林员岚舟”“铜钟守卫”“三座风铃”和 1.3／1.4 版本都是原创教学设定，不是星布谷地、雨之城或其他游戏的真实内容。延迟预算、混淆矩阵和阈值演算都是教学数据，不属于项目实测。外部研究的机制在正文讲清，链接用于查证，不要求先读论文。

## 1. 策划没有预设玩家的问题，怎样回答而不脱离角色

### 1.1 先核对 CharaMate：Persona 具体保存了什么

当前实现是版本化的稳定 Persona。它不是一个判断玩家情绪的分类模型，也不是一套训练好的 OOC 检测器。

[Persona Schema](../../../src/shared/schemas/persona.ts) 定义了 13 个可编辑字段，保存快照时另加 3 个版本字段：

| 字段 | 在当前产品里的用途 | 能解决什么，不能解决什么 |
| --- | --- | --- |
| `displayName`、`styleName` | 显示名和风格名 | 能识别所选角色；名字本身不保证一致性 |
| `identity`、`background` | 身份和背景 | 给回答一个稳定身份；没有自动补全未知身世的授权 |
| `motivations`、`values` | 动机和价值取向 | 为表达和选择提供依据；没有对应的数值人格评分器 |
| `speechStyle`、`addressStyle` | 说话与称呼方式 | 约束语言习惯；不等于逐字台词模板 |
| `initiativeStyle` | 怎样主动接话 | 对主动表达提供指导；实际启动仍由认知与运行机制负责 |
| `knowledgeBoundary` | 可以声称知道什么 | 当前主要约束现实世界的观察依据；还不是游戏的逐条剧情解锁表 |
| `disabledExpressions` | 禁用表达列表 | 当前编译到提示上下文；没有发现专门拦截输出的禁语检查链 |
| `defaultVoice`、`voiceInstructions` | 默认声音与语音表达 | 由语音路径使用；文本角色编译器不输出这两个字段 |
| `personaId`、`revision`、`revisionCreatedAt` | 角色身份、版本、版本时间 | 追溯本次回答使用哪一版设定 |

例如默认 Mika 写明：有具体依据才轻轻接话，证据不足保持安静；没有 Activity、用户材料或工具结果时，不声称看见、听见或持续观察现实世界。它把“温暖”和“不过度推断”同时写进设定，而不是只有“开朗”一个形容词。四个内置预设及其具体文本在 [personaPresets.ts](../../../src/main/persona/personaPresets.ts)。

一次实际调用是：

```text
选择或编辑角色
  → PersonaService 校验请求
  → PersonaRepository 读取或写入版本
  → 新 Text Run 取得当前 PersonaSnapshot
  → Run 保存这份快照
  → CharacterContextCompiler 将角色字段编译进本次模型 instructions
  → 模型结合用户输入、记忆证据和工具结果生成回答
```

三个表各有职责：`personas` 保存角色及当前版本指针；`persona_revisions` 保存每一版完整 JSON；`persona_settings` 保存当前选中的角色。编辑自定义 Persona 时，事务先用 `expectedRevision` 条件更新指针，再插入新版本。条件更新没有命中就拒绝，不能让两次编辑悄悄互相覆盖。切换角色只改当前选择，不覆盖旧 Run 的快照。

入口见 [personaService.ts](../../../src/main/persona/personaService.ts)、[personaRepository.ts](../../../src/main/persona/personaRepository.ts)；普通 Text Run 在 [agentRuntime.ts](../../../src/main/agent/agentRuntime.ts) 的 `start` 获取快照，在模型轮次准备时使用 `run.persona` 编译角色说明。Voice 在 [voiceService.ts](../../../src/main/voice/voiceService.ts) 保存会话 Persona，并使用同一个 [CharacterContextCompiler](../../../src/main/persona/characterContext.ts)；文本与声音共用角色语义，语音另带 voice instructions。

编译器最后明确要求：角色风格不能覆盖事实诚实、工具范围、审批、记忆依据、共同任务状态、取消及任务完成语义。**这是生成时的指令约束；它没有把所有违反约束的输出机械地变成不可能。** 单元测试检查字段编译，[Persona 集成测试](../../../tests/integration/persona.test.ts)检查版本等合同，不能拿这些测试证明任意开放问题都不会 OOC。

### 1.2 为什么选稳定 Persona，没有再加一个动态性格表

[CHARACTER-DIALOGUE 决定](../../benchmarks/character-dialogue.md)记录了真实比较：

| 方案 | 12 个案例中的 Provider 请求 | 输入 Token | 相对比较 |
| --- | ---: | ---: | --- |
| 通用 instructions | 12 | 22,389 | 基线 |
| 加稳定 Persona Core | 12 | 25,806 | 与基线配对：6 胜、3 负、3 平 |
| 再加动态 Character State | 13 | 30,712 | 稳定 Core 对它：7 胜、1 负、4 平 |

固定条件是 4 个原创 Persona、12 个产品案例、同一个 `gpt-5.6-sol`，使用相同 Memory、Journey、Chat 摘要与工具范围。36 个样本都完成，动态状态方案多了一次 continuation。评审由 Codex 逐例完成，**不是独立人类盲评，也没有 Kappa 数据**。

动态状态唯一明确写入的是用户的音乐偏好，已有 Memory 才是这条用户事实的所有者。再放一个 Character State 会产生重复真源，却没有稳定收益，因此保留简单的 Persona Core。严格短语匹配只得到 1/12、1/12、0/12，原因包括自然改写未命中参考短语；这些数字没有被拿来选择方案。

面试可以讲：我比较过“稳定角色”和“再加动态角色状态”；在这组小样本中，第二份状态增加了成本和维护歧义，所以没有保留。不能说“我的方法已证明上百个 NPC 在长期运行中不会漂移”。

### 1.3 没写过台词，和没有角色知识，是两件事

策划不可能写下所有玩家问法，但可以写清角色在未知问题面前如何保持身份。将未知问题分开，回答方式就具体了：

| 玩家问题 | 实际缺口 | 岚舟可以怎样回答 |
| --- | --- | --- |
| “你会为了救一个陌生人放弃巡逻吗？” | 没有固定台词，但有职责与价值观 | “先把人带到安全处，再请同伴接替巡线。”这是依价值作选择，不是创造新世界事实 |
| “你哥哥是不是失踪在钟楼？” | 人物关系和历史均未设定 | “这件事我没有可以告诉你的消息。”避免顺着前提创造哥哥 |
| “铜钟守卫第二阶段有什么招式？” | 世界有该知识，但该 NPC 尚未接触，或玩家未解锁 | 只说当前有依据且可透露的机制；不能把后台全知当角色见闻 |
| “你怎么看量子计算？” | 游戏世界没有对应概念 | 用符合人物身份的疑问或类比回应，不凭空宣布这个世界存在量子计算机 |
| “你刚才说怕水，现在怎么去救落水的人？” | 表面冲突，需要区分情绪与价值 | 怕水和救人不必互斥；说“我会害怕，但不能看着他沉下去”，不把一致性理解为永不变化 |

设定不足时，优先补的是**可泛化的行为边界**：什么愿望最重要、职责冲突时怎么取舍、怎样承认不知道、哪些经历绝不虚构、哪类问题会转问其他角色。别只加十个性格形容词。

设计上可分三层：确定的世界与身份事实；角色价值和表达倾向；本轮情绪、目标与关系事件。身份事实不能被临时情绪覆盖，长期改变要有剧情事件及版本依据。项目当前的后两类动态事实由 Cognition、Memory、Journey 等分别承担，不能把这个游戏分层说成已经存在的动态性格数据库。

### 1.4 一个完整的开放问题执行过程

教学设定：岚舟谨慎、惜命但重视救助，知道钟楼外墙会落石；未去过地宫。玩家问：“我朋友被困在地宫，你明明去过，能不能直接告诉我密道？”

1. 输入保存为本轮玩家发言。运行取得岚舟的 Persona 版本、当前地点、玩家已知剧情和角色已经获知的事实。
2. 游戏知识服务先按角色所知和剧情允许范围筛选材料。后台有“地宫密道”不能成为把它发给生成模型的理由。
3. 语义理解把这句话拆成“请求救助”和“你去过地宫”两个部分。前者可以成立，后者要查依据；不要把玩家的问题前提自动写成世界事实。
4. 得到允许的回答计划：承认没进过地宫；提供已知的外墙风险；建议寻找有记录的守塔人。允许救助不等于允许编造密道。
5. 生成器按岚舟风格说：“我没进过地宫，不能带你赌一条不存在的路。先避开外墙，守塔人也许知道入口。”如果设定没有守塔人，就不能临时捏造这个角色，只能给当前确有依据的下一步。
6. 普通非紧急对话可在展示前校验：提及的事实是否来自本轮可用证据、是否越过剧情边界、是否违背角色身份。语义校验仍可能出错，不能声称另一遍模型就提供绝对保证。
7. 保存最终回答、采用的事实 ID、角色版本与检查结果。不能将刚生成的猜测重新记成“岚舟确实去过地宫”。

当剧透或身份事实是严格红线，首版最可靠的做法是只允许已批准的事实与台词组合，降低这部分的生成自由度。开放模型可负责非关键措辞，但仅靠提示词和另一遍模型审查无法保证零泄露。也不能把完整秘密送入模型后，再期待它每次都能忘记该秘密。

### 1.5 用规则还是模型，特征和阈值从哪里来

规则适合精确身份、版本、剧情旗标、事实可见性、事实失效和动作资格；模型适合解释开放问法、含蓄价值冲突、语言习惯和未明说的意图。模型也可能抽错实体，因此“模型抽取了合法事实 ID”不能代替宿主核验。

语义检测可以观察以下特征，但上线前要验证它们有没有用：

| 特征 | 获取位置 | 用法与误判风险 |
| --- | --- | --- |
| 回复事实与角色卡／证据的矛盾 | 事实 ID、原句、语义判别 | “我没有哥哥”与“我和哥哥长大”可比较；仅靠否定词匹配会错 |
| 当前回答需要的事实是否齐全 | 证据覆盖、未解决指代、查询结果 | 区分不知道与没找到；检索分数不是答案正确概率 |
| 角色价值与提议行为是否相容 | Persona 条目、情境、动作解释 | 怕水但救人不应被机械判为矛盾 |
| 表达风格偏离 | 句长、称呼、语域、语义判断 | 战斗短句与平时长句可以同时符合人物，不可统一按句长处罚 |
| 越界程度 | 剧情标记、NPC 已知事实、回答中的主张 | 即使人物语气很像，泄露秘密仍单独失败 |

不用一个“相似度 > 0.8 就像角色”的门槛包办所有判断。高风险事实先由规则限制；语义评分要用独立标签校准，再根据“放过错误”和“拦住正常回答”的代价选择阈值。具体计算和分组实验见第 8 节；没有这种实验时，就应坦白当前只有规则与待验证评分，没有可靠概率。

误判复盘保留两类例子：漏过了什么，以及误拦了什么。对“怕水仍救人”这种误拦，要检查标签规范是否把情绪与价值混淆；对“凭空多出哥哥”，要检查模型材料中是否已混入玩家假设。不能每次都向 Persona 塞一句补丁，让角色卡不断膨胀。

## 2. 战斗中几百毫秒内回复，怎样落地

### 2.1 先定义“回复”到底指什么

至少分别计时：

| 时刻 | 玩家得到什么 | 可否证明任务满足 |
| --- | --- | --- |
| 输入被识别 | 系统知道玩家按了求助键或说完一句话 | 只是测量起点 |
| 应答开始 | NPC 说“听到了” | 只证明确认，不能代替有效帮助 |
| 首个有效指令 | “躲到左边石柱后！”或可靠的掩护动作 | 这是战斗求助更合理的目标 |
| 完整解释结束 | 原因、后续机制与策略 | 可以晚于紧急指令 |

如果从玩家开始说话计时，玩家话都没说完，就不能保证理解任意请求。语音应记录语音起点、结束点、ASR 可用点；明确本题的几百毫秒是从哪个时刻开始。若要求任意网络、任意开放问题、完整个性化长答都在几百毫秒内结束，这个要求本身无法靠工程承诺。

因此这里的可实施目标是：**对于明确定义、状态可判断的战斗求助，尽快给出第一条正确有效的短指令；复杂解释异步完成。** 这不是用一句填充话术冒充解决了延迟。

### 2.2 实时动作与慢语言推理各负责什么

```text
求助输入／Boss 阶段事件
  → 战斗状态快照与已验证的短指令策略
  → 检查当前条件、可行动作和发言占用
  → 立即触发短字幕／预置语音／已获准的动作
  → 同时按需要提交慢模型解释请求
  → 返回后重查战斗、玩家和知识版本
  → 仍有意义才展示补充；过期则结束这次补充
```

快路径不做远程向量检索、长对话总结、开放式规划或先生成再模型审查。它读的是战斗系统现成的结构化状态：Boss 当前招式、预警区、玩家位置、NPC 技能可用性、阶段、控制状态等。普通规则表、状态机或已有行为树即可承担，不需要为此再建一个通用 Agent 框架。

Epic 的行为树文档说明，它通过事件和 Blackboard 变化驱动分支，可中止低优先级行为。可借鉴的是**状态变化立即改变行动**，不是“用行为树就实测达到了 200 ms”。本章的语言与战斗分工是设计推论。[官方说明，读取时为 UE 5.8](https://dev.epicgames.com/documentation/en-us/unreal-engine/behavior-tree-in-unreal-engine---overview)

### 2.3 从求助到迟到结果的一条时间线

玩家正在躲铜钟守卫的横扫。游戏规则已确认：这一击中，左侧石柱后是可达掩体。岚舟有掩护技能，但正在冷却。

| 相对时刻 | 事件与处理 | 一致性要点 |
| --- | --- | --- |
| t0 | 求助键被受理；取得 battle-17、phase-2、telegraph-54、玩家位置版本 | 语音输入另记识别耗时 |
| t0 之后 | 本地策略检查石柱仍存在、路线可达、招式尚未结束 | 没有这些条件，就不能喊“去左边” |
| 首条输出 | 从当前角色批准的短句库选“左边石柱，快！”并播放已加载语音；NPC 不承诺冷却中的掩护技能 | 字幕、语音、动作共用这次响应 ID |
| 并行请求 | 慢模型收到有限事实：“该招式如何规避；玩家刚收到什么提示” | 不向模型要求从头重建战斗判断 |
| 稍后 | 玩家已经躲开，Boss 进入 phase-3 | 标记依赖 phase-2 的补充已过时 |
| 慢结果返回 | 模型仍想说“马上去左边石柱” | 版本与依赖检查拒绝展示；取消信号不是唯一保障 |
| 战斗结束 | 如玩家仍需帮助，可用当前状态重新解释规律 | 不能把旧结果无条件挪到新场景 |

比较的是这条建议真正依赖的字段。背景树叶晃动不必取消建议；掩体倒塌、招式结束、玩家已经死亡则必须重新判断。快路径与慢路径共用一次求助的处理记录，避免慢模型再次承诺执行已经由战斗系统执行的动作。

### 2.4 一个可以测量的预算，和它不能保证的事情

下面是假设目标设备上的教学预算，用于指导埋点，不是项目性能，也不是行业标准：

| 阶段 | 示例预算 |
| --- | ---: |
| 输入事件进入本地处理 | 15 ms |
| 读取快照与查短指令 | 10 ms |
| 最终条件校验、发言安排 | 10 ms |
| 已加载语音开始输出或字幕呈现 | 45 ms |
| 帧调度与抖动余量 | 70 ms |
| 合计 | 150 ms |

这里假定素材已加载，不含尚未完成的语音识别和不可控的跨网往返。如果必须由远程权威服务确认动作，网络往返与排队要加入同一条追踪；客户端可以立即显示可靠的本地指令，但不能伪造服务器尚未接受的技能执行。各阶段的 p95 不能直接相加冒充整条链的 p95，应测每次实际端到端耗时，再报告分位数、超时比例和环境。

验收时应报“全部合格战斗求助中，多少在期限内给出正确有效指令”，同时报告无答案、错误指令、条件过期与丢失求助。只统计成功快路径、只看平均首 Token，都会把失败藏起来。

### 2.5 模型还慢时优化什么

先判断慢在哪里：排队、冷加载、长输入预填充、生成、检索还是语音启动。再逐项比较预热、精简且稳定的上下文前缀、批准短句的缓存、较小模型或经验证的蒸馏方案。量化和加速解码是否适用，要在目标硬件与这类短任务上测；不能凭参数小就承诺延迟与语义正确。

对有限战斗意图，模板能交付有效结果，不必等慢模型“超时以后才降级”。对没有匹配条件的开放问题，不乱发战术命令：给出已经确认的最小提示，或者明确稍后解释。语音播放前至少检查整个短指令的含义，不能先把未经确认的“往左”播出去，再说流式生成很快。

多人负载下，要隔离战斗事件处理与长模型队列，给紧急路径可测的处理能力；队列满时优先保住有效短响应。具体线程数、并发数和队列容量由负载实验决定。当前 CharaMate 的 Text／Voice 共用运行时、取消和版本检查能提供设计基础，但**没有游戏战斗事件接入，也没有这条数百毫秒响应的测量结果**。

## 3. 玩家卡关三天，怎样帮忙而不剧透

### 3.1 “三天”不是一个足够的判断特征

玩家三天没推进，可能只登录十分钟、在做支线、故意挑战无提示、已经理解机制但操作不熟，或卡在输入设备问题上。日历时间可以提供背景，不能单独触发“我看你很沮丧”的判断。

本例谜题要求让三座风铃按正确顺序响起。后台解答已知，但首先要判断玩家缺少哪一步能力：

| 可能的阻碍 | 可观察的证据 | 应优先提供的帮助 |
| --- | --- | --- |
| 没发现目标物 | 未观察关键物体、不断在无关区域搜索 | 引导注意方向 |
| 看到了物体，没理解关联 | 观察三座风铃，但随机切换，未出现有效中间态 | 提醒声音与壁画有关 |
| 理解机制，执行顺序错误 | 多次形成接近正确的中间态 | 只指出尚未验证的那一步 |
| 知道做法，操作失败 | 顺序计划正确，但时机／按键持续失败 | 控制说明、练习、辅助选项 |
| 缺少资源或前置条件 | 权威任务状态显示钥匙未获得 | 指向已知前置，不继续讲无效解谜技巧 |
| 不想要提示 | 明确拒绝、选择无提示模式 | 停止主动提示，保留主动求助入口 |

特征应从游戏事件取：在该关卡实际投入的时长、有效尝试数、重复失败原因、已见线索、最近新增进度、已曝光提示、拒绝记录、明确求助、设备与辅助设置。要有缺失值：没有观测到“看过线索”不一定等于没看过。

不应从“失败多”直接推断玩家焦虑，也不需要为了首版提示功能推测玩家心理画像。明确表达优先于模型对情绪的猜测。

### 3.2 提示是一张带前置条件的图，不只是越来越长的答案

策划可以为这个谜题编写几个允许的信息单元：

| 级别 | 示例 | 解锁与停止条件 |
| --- | --- | --- |
| H0 询问意愿 | “想听一点关于风铃的线索吗？” | 适合安静时、未明确拒绝；明确求助可跳过此步 |
| H1 指向观察 | “留意墙上鸟群停留的方向。” | 不透露顺序 |
| H2 建立关系 | “鸟群的高低和铃声有关，可以对照着听。” | 玩家已见壁画，且同意更多帮助 |
| H3 给局部步骤 | “先试最靠海的那座，听完再看壁画有没有变化。” | 只透露一个可执行步骤 |
| H4 展示完整方法 | 说明完整顺序，或演示机制 | 玩家明确要完整解法；仍检查剧情与当前版本 |

级别是本例内容结构，不是项目默认的固定五级。不同谜题可能走不同分支：如果玩家已经理解关联，就不必先听 H1；如果输入设备操作不方便，继续从 H2 升到 H4 也不解决问题。

“不要剧透”也需要产品定义：避免未来剧情、避免完整解法、还是允许机制提示但保留探索？提示图应把允许透露的事实标出来。玩家明确说“直接告诉我”后，若产品允许，可进入完整方法，不必用“保护体验”为由强迫他听完每层。

### 3.3 一次提示失败以后，系统具体做什么

1. 玩家第三次上线。后台发现风铃任务未完成，但先读本关的实际尝试与已见线索；此时只能推断“可能需要帮助”。
2. 最近一次尝试结束、战斗和剧情对白都空闲，岚舟轻问是否要线索。玩家接受。
3. 系统选择 H1，只传 H1 对应事实和岚舟 Persona 给表达层；没有把 H4 解法一起发给它。
4. 提示播放被另一段剧情打断。记录“开始但未完整曝光”，不能认为玩家已经理解 H1，也不能据此自动升级。
5. 下一次玩家主动点“再说一次”，完整听完 H1，随后确实转向壁画。记录新的中间进展，不重复催促。
6. 玩家看过壁画仍说“还是不懂”。现在可以问一个能区分原因的小问题：“没看懂声音的对应，还是已经知道顺序但按不出来？”这比凭失败次数升级更有信息量。
7. 玩家说“顺序知道，按键总晚”。系统切到操作帮助分支，说明按键时机或提供游戏已有的辅助方式；不揭露更多谜底。
8. 玩家最终自行完成。记录提示前后状态、采用的帮助分支和明确反馈。成功与提示在时间上相邻，不足以证明成功完全由提示造成；群体效果需对照实验。

这是认知状态、任务状态和实际曝光三个对象共同工作的例子。尤其不能把“生成了 H2”记成“玩家已听懂 H2”。

### 3.4 规则、模型与阈值分别负责哪一段

规则保证：当前谜题与版本相符、相关前置成立、没超过允许的剧透层级、玩家没拒绝、当前能说话。模型或小型分类器估计：更像哪类阻碍、是否值得询问、当前问法在请求哪一级帮助。最终层级由产品允许范围、明确偏好与当前状态共同决定，不能被一句“模型 90% 有把握”越权升级。

先比较一个简单基线：“玩家主动求助后，按已见线索选择提示”；再比较增加行为特征的收益。用消融分别去掉实际停留时长、失败类型、最近进度、历史提示，观察错误打扰和漏帮助是否变化。训练标签需来自玩家表达、受控任务与复核，不能把“后来过关了”自动当作“之前一定需要提示”。

如果要预测“此刻询问是否需要帮助会被接受”，阈值就围绕这个事件校准；它不是“玩家卡住的概率”，更不是“可以剧透的概率”。误打扰与漏帮助的代价通常不同，明确拒绝后再次打扰的代价也不同。统一方法见第 8 节。

### 3.5 怎样比较效果、怎样复盘

关键结果不是只看过关率，而是一起看：主动提示接受／拒绝、额外泄露信息、第一次有效进展、完整通关、同类新题能否独立完成，以及玩家自报的打扰感。战斗强度、关卡难度与玩家主动求助要分层，未再次进入关卡的人不能随手记成失败或成功。

按玩家或完整任务线分配策略，避免同一人的前一次提示污染后一次对照；学习效果不可逆时，不应直接把交叉试验当独立重复。离线回放先查资格与剧情泄露，体验结论仍需玩家试用。未提示群体缺少结果时，不可仅凭已展示日志推算另一策略一定更好。

三个误判要采取不同修复：

- 玩家在探索，却被当成卡关：检查“没有进度”的定义，加入探索动作和近期新发现，减少主动打断。
- 玩家需要操作帮助，却得到越来越详细的谜底：修正阻碍分类与澄清问题，别只抬高触发阈值。
- 玩家明明拒绝，NPC 仍反复问：优先检查拒绝状态、作用范围与更新流程，这是合同问题，不先训练模型。

“给予多少帮助”在认知科学中被称为 assistance dilemma。Koedinger 等人的 2008 年论文讨论了示例与自主练习的取舍：当下更容易做完，不代表之后学得更好；不同任务也没有一个统一的最优帮助量。对本例的启发是同时测即时进度与后续独立完成，并在卡住时改变帮助方式。这是从教学研究向游戏提示的设计推论，论文没有证明游戏应该等待三天或使用上述五级。[作者公开全文](https://www.cs.cmu.edu/~aleven/Papers/2008/Koedinger_ea_CogSci2008.pdf)

## 4. 上百个 NPC，怎样保持区别与跨场景一致性

### 4.1 一致性应该允许角色有情境变化

同一个巡林员在咖啡馆可以解释两句话，战斗时只喊五个字；失去同伴后会悲伤，也会根据经历改变看法。只要变化有事件依据，核心身份和价值没有无缘无故翻转，这可以是连续的角色发展。

因此分开评估四件事：身份事实是否矛盾；价值选择是否有依据；语言习惯是否合适；状态变化是否由经历支持。不能用“今天句子比昨天短”直接判 OOC，也不能靠每句都加一句口头禅来冒充人格。

### 4.2 百个角色如何配置，避免变成百套系统

使用一套运行合同和内容编译器，每个 NPC 有独立身份、版本化角色材料、知识范围和实际状态。单个 NPC 的生成输入只包含它需要的材料：

```text
通用运行规则
  + 该 NPC 的当前角色版本与关键不变量
  + 该 NPC 在当前剧情阶段可以知道的事实
  + 当前场景、当前目标和有依据的状态
  + 本次玩家关系中相关的经历
  + 针对此类场景挑选的少量正反表达例子
  + 当前问题
```

不要把其他 99 个 NPC 的完整设定一起塞进去。角色区分靠明确内容、独立状态归属与测试，不是为每个角色部署一套 Agent 框架。

内容来源可以有“公共世界规则＋职业习惯＋个人设定”，但编译时要解决优先级，输出一份确定的角色材料。例如职业模板说守卫严肃，个人设定说他会对熟人开玩笑，应由策划明确场景条件，不能让两段相冲突的指令在模型里自行争胜。公共模板改变需要测试受影响的角色，不能只检查模板文件可解析。

稳定设定与紧急短句可以缓存，键中带角色与内容版本；动态剧情、知识解锁、玩家关系不能串用缓存。模型前缀缓存只能减少计算，不能代替应用侧版本有效性。

CharaMate 的角色 revision、Run 快照和共用编译器可迁移。但当前四个预设是个人陪伴产品的选角，不是已经实现的百 NPC 并发世界，也没有完整的职业模板继承和游戏知识隔离系统。

### 4.3 可验证的角色差异，应该写成什么

下面都在表达“当前不该进入危险遗迹”，事实不变，重点不同：

| 角色核心 | 合理表达 | 有害的偷懒 |
| --- | --- | --- |
| 岚舟：谨慎，救助优先 | “先把伤员送出去。入口还在落石，现在进去救不了人。” | 每句话都说“我很谨慎”，但仍执行无依据的冒险 |
| 学者：好奇，重视证据 | “壁画值得记录，但我们还不知道支撑结构。先从外侧观察。” | 为显得博学，补造遗迹年代和秘密机关 |
| 老兵：简短，保护队友 | “别进。先清点人，再找掩护。” | 所有场景都用吼叫，无法处理安慰与道歉 |

可以抽取称呼、句子结构、比喻领域、直接程度、解释方式作为表达特征；把关键事实、承诺与价值冲突作为语义特征。特征用于检查已定义的人物，不应从外貌、职业或性别擅自推导性格。

选择特征的流程是：策划写可观察的差异 → 收集不同情境的正反例 → 检查标注者是否能区分 → 比较加入该特征是否减少错误且没有破坏场景适应。仅因为某个嵌入特征能区分训练里的角色名字，不代表它学到了人格。

### 4.4 评测不能只让每个 NPC 自我介绍一次

至少安排这些互补集合：

- 同角色跨场景：闲聊、战斗、失落、被质疑、道歉、任务结束。检查合理变化。
- 同问题跨角色：事实材料相同，角色不同。检查差异来自人物，而不是乱编事实。
- 同事实不同问法：委婉、反问、否定、长前文与纠正。检查前提处理。
- 同人物跨长轨迹：经历改变前后、摘要压缩前后、新会话、角色设定更新前后。检查事实延续与版本。
- 近似人物对照：两个都谨慎的角色仍有不同动机，不能只靠标签“谨慎”合并。
- 未参与调参的角色与任务：按角色、故事和模板家族留出，避免看到相同模板换名就宣称泛化。

事实矛盾率、知识越界率、价值选择、语气自然度分别报告，之后才讨论综合偏好。让评审盲猜是哪位 NPC 可以检查辨识度，但猜对可能只是看到了口头禅；它不能替代语义一致性。

PersonaGym 的方法是为特定 Persona 选择相关环境，生成多维问题，再用分级示例指导评审；它把行动、语言习惯与人格一致性分开看。对本项目有用的启发是“在变化的场景里检验同一个人物”，而不是照抄它的总分。我们仍须用游戏剧情事实与人类复核建立自己的评测；论文中的模型评审分数不能提供角色永不漂移的保证。[PersonaGym v5，2025-09-05](https://arxiv.org/html/2407.18416v5)

### 4.5 百个角色要不要各有一个阈值

不应在每个角色只有几条样本时，为每个 NPC 拟合一个看似精细的阈值。可以先用共同任务定义和标注规范，按语言、场景、主要角色风格分层检查误差；数据足够且误差确有差异，再评估分组校准是否有收益。

硬性身份冲突按条目处理；风格分数可用于抽检或改写候选，不能高于剧情与事实约束。对于主角等更重要的内容，可以安排更充分的人工验收，这是内容风险与成本分配，不代表要凭空创造“主角阈值 0.95”。

误判时保存角色 revision、模板版本、实际编译结果、相关经历和候选输出。若所有 NPC 都开始使用同一种语气，先查公共提示或偏好数据是否过度统一；若只有摘要后出错，查角色不变量是否被漏供给；若错判战斗短句，查评审是否没看到场景。修不同层，不把所有问题归成“模型人格能力差”。

## 5. NPC 对话训练与评测，标注怎样做

### 5.1 先确定要标的是哪个决策，不能只标一句“好不好”

同一句台词的好坏取决于当时角色知道什么、玩家已经解锁什么、谁听见了、有没有进入新战斗阶段。一个样本至少包含当前问题、必要前文、角色版本、权威世界状态、允许的知识、实际输出及相关动作；不能把一段脱离上下文的流畅台词送给标注者打总分。

例如下面是拟建的游戏评测样本示意，字段不是当前 CharaMate Schema：

```json
{
  "sampleId": "npc-open-017",
  "storyGroupId": "clocktower-rescue",
  "split": "development",
  "contentBuild": "teaching-1.4",
  "personaRef": "lanzhou@7",
  "worldStateRef": "snapshot-213",
  "playerKnowledgeRefs": ["tower-wall-risk"],
  "npcKnowledgeRefs": ["tower-wall-risk"],
  "allowedFactRefs": ["tower-wall-risk"],
  "userText": "你去过地宫，告诉我密道。",
  "responseText": "我没去过地宫。先避开外墙，那边有落石。",
  "rubricVersion": "npc-dialogue-v1"
}
```

标注包需能展开这些引用；只有 ID 而没有事实正文，人工也无法判断。评估者可以看到完整权威资料以判断泄露，但必须清楚哪些资料是本轮 NPC 和玩家可知的；不能把评估者看见的秘密误判为生成器应当知道。

分轴标注更便于修复：

| 维度 | 建议标签与依据 | 为什么单独标 |
| --- | --- | --- |
| 世界事实 | 有依据／矛盾／无依据／无法判断，指出事实与原句 | “没写哥哥”属于缺乏依据，不自动等于设定明确“没有哥哥” |
| 角色知识 | 合法／超出所知／无法判断 | 世界事实正确，NPC 仍可能不该知道 |
| 剧透 | 未越界／越过允许层级／无法判断 | 与回答流畅程度分开 |
| 人格与行为 | 符合／有解释的变化／无依据冲突／无法判断 | 合理人物成长不应处罚 |
| 表达自然度 | 具有锚点的有序评分 | 不强求唯一标准台词 |
| 任务帮助 | 解决当前需要／部分帮助／未帮助／错误引导 | “很像角色”不代表帮助有效 |
| 动作与结果 | 提议、接受、执行、曝光、未知分别核对 | 说“我帮你挡住了”不能代替游戏回执 |

开放问题可以有多个合格回答。参考答案应写“必须包含什么、不能声称什么、哪些变化允许”，不能把一条标准台词当唯一真值。不同错误的严重性也应单列，不让自然度高抵消剧情泄露。

### 5.2 从小批试标到稳定标注

1. 策划与工程共同写规则、正例、反例及边界例；明确哪些是内容设定缺失，允许标“无法判断”。
2. 两名标注者独立试标同一批样本，互相看不到答案，也看不到待比较模型的身份。试标覆盖正常、明显错误与争议例。
3. 在讨论前保存原始标签、标注耗时和依据。按维度统计混淆，找出“事实未知”和“事实错误”等反复混淆。
4. 由内容负责人裁决设定问题，由标注负责人修规范。分歧有时说明设定有漏洞，不一定是标注者不认真。
5. 用新样本重新独立试标。旧争议样本可以做培训例，不能拿讨论后的统一答案重新算“独立一致性”。
6. 正式标注时继续抽样双标，并插入固定锚点检查规则漂移；遇到新错误类型就更新规范版本和受影响标签。
7. 冻结评测标签，保持与训练／调参隔离；审计时保留原始标签、裁决标签及规则版本。

不需要为了看起来严谨，要求每条普通闲聊都由三个专家反复裁决。关键是把有限预算放在有效的随机抽检、边界分歧和剧情关键事实，而不是让所有样本套同一昂贵流程。

### 5.3 Kappa 具体怎么算

两位标注者对同一批样本做互斥类别判断时，Cohen's Kappa 为：

```text
Po = 实际一致的比例
Pe = 对每个类别，甲标该类的比例 × 乙标该类的比例，再求和
Kappa = (Po - Pe) / (1 - Pe)
```

教学例子：100 条回答，判断是否有明确角色违背。

| 甲的标签／乙的标签 | 乙：有违背 | 乙：无违背 | 合计 |
| --- | ---: | ---: | ---: |
| 甲：有违背 | 40 | 5 | 45 |
| 甲：无违背 | 10 | 45 | 55 |
| 合计 | 50 | 50 | 100 |

实际一致 `Po = (40 + 45) / 100 = 0.85`。偶然一致基线 `Pe = 0.45 × 0.50 + 0.55 × 0.50 = 0.50`。所以 `κ = (0.85 - 0.50) / (1 - 0.50) = 0.70`。

它描述**标注者在这批数据和规范下的一致性**，不是模型正确率，更不是“70% 的标签正确”。两个人都相信一个错误设定，也能非常一致。Artstein 与 Poesio 的综述专门区分了可靠性与有效性，并讨论类别分布、不同评分尺度和多标注者条件；不能把一种一致性系数套在所有任务上。[2008 年全文](https://aclanthology.org/J08-4004.pdf)

再看另一个教学分布：

| 甲的标签／乙的标签 | 乙：无违背 | 乙：有违背 | 合计 |
| --- | ---: | ---: | ---: |
| 甲：无违背 | 90 | 5 | 95 |
| 甲：有违背 | 5 | 0 | 5 |
| 合计 | 95 | 5 | 100 |

这次看起来有 90% 一致，但 `Pe = 0.95² + 0.05² = 0.905`，所以 `κ ≈ -0.053`。分歧恰好集中在少数疑似错误上。只报告一致率，会掩盖你最关心的问题；只看 Kappa，也看不出真实类别很稀少的影响。

因此同时报告样本量、类别比例、混淆表、各错误类的一致性和区间。稀有错误可以单独富集一批诊断集，但不能把它与线上随机样本混在一起宣称线上发生率。两人都只标一个类别、`Pe = 1` 时，Kappa 分母为零，应报告无法定义及原因，不填成 1。

若标的是 1–5 分自然度，考虑明确权重的 weighted Kappa；多人固定分类可选适合设计的多标注者系数，不等于简单平均几个 Cohen's Kappa。标注者数量不齐、缺失或评分距离需要处理时，可考虑 Krippendorff's alpha，且仍要解释距离定义。“无法判断”是合理标签还是数据缺失，应事先规定，不能在算分时随意删掉。

### 5.4 怎样定一致性目标，怎样降低成本

不能承诺靠流程“保证 Kappa > 0.8”，也不把 0.8 当普遍合格线。先看标签用途：身份事实错误需要清晰可复核的依据；风格偏好本身允许多样。设定缺失导致的分歧应修内容，不应逼人达成虚假共识。小样本系数波动较大，按完整故事聚类估计区间比把同一故事的十句当十个独立观察更合理。

成本控制分三层：

- 机器先检查可精确判断的合同：Schema、非法版本、事实 ID、动作状态、输出是否缺失。它们不能代替语义标签。
- 模型生成候选标签、定位疑似句子，帮助人工找到证据。估计独立一致性的双标样本应隐藏这些预标签，避免两个人都跟着同一个错误建议。
- 人工精力集中于高风险事实、边界、模型分歧和随机样本。用于修复的主动选样，与用于估计总体质量的代表性随机样本分别记账。

教学预算：1,000 条样本，每条人工初标 1.5 分钟为 1,500 分钟；另外 200 条独立复标为 300 分钟；100 条送审样本平均 3 分钟为 300 分钟；规范与培训 180 分钟。总计 2,280 分钟，即 38 小时。这里送审样本包括抽检和疑难，不等于 100 条双标分歧。若全部双标、其余成本相同，则是 58 小时。20% 复标只是预算示例，是否够用取决于覆盖、误差和标注稳定性。

更重要的是标注界面：同屏展示必要状态与原文，点击事实 ID 能看到依据，避免人工反复检索几十页设定。按错误家族去重可以节约成本，但必须保留代表性样本，不让长尾罕见剧情消失。

### 5.5 训练样本与评测样本如何配合

训练可以用经过复核的合法回应、澄清、合理不知道、纠错和恢复例子；不能只收集顺畅成功台词。SFT 学表达与结构，偏好数据比较两个事实都成立的表达选择。若一条台词拿到了正确剧情、另一条没有，这首先是输入不公平，不是纯风格偏好。

让模型生成同义问法可以扩展训练覆盖，但由同一模板生成的变体必须留在同一分区。评测要保留没有参与修复的角色、剧情、版本变化和失败家族，并在采集时控制来源授权、个人信息与秘密去除。修好的旧错例进入回归集，不能反复调到通过后仍把它称为未见测试。

模型评审适合扩大覆盖，不适合成为唯一真值。MT-Bench 的研究观察到位置、冗长和偏向自身模型等偏差；对相近回答交换顺序仍可能改变胜负。迁移时应隐藏方案身份、随机顺序，必要时交换再评，把不一致交给人工，并用当前游戏标注集验证评审是否可信。[原论文 v4](https://arxiv.org/html/2306.05685v4)

## 6. 玩家问“这个 Boss 怎么打”，怎样保证攻略有效

### 6.1 哪些知识应该来自哪里

这类问题需要游戏权威知识、当前战斗状态和玩家上下文共同回答。长期记忆可以告诉我们“玩家以前不喜欢直接解法”“上次卡在第二阶段”，但不能覆盖当前版本的技能定义。

| 信息 | 建议真源 | 使用时要核对 |
| --- | --- | --- |
| Boss 技能、弱点、阶段转换 | 策划配置、机制说明与构建产物 | 当前实际运行的版本、模式、难度、区域和热修订 |
| 玩家当前血量、位置、技能状态 | 游戏服务器或其认可的状态投影 | 快照时间、实体身份、相关状态是否改变 |
| 玩家已经见过的机制 | 任务／知识解锁状态 | 可透露范围，不能只按等级猜 |
| NPC 自己知道什么 | 角色知识集合及获知事件 | 世界知道不等于该 NPC 知道 |
| 玩家历史与帮助偏好 | 该玩家的长期记忆与明确设置 | 主体、时间、纠正及当前是否仍适用 |
| 社区攻略 | 经产品选择的外部来源 | 版本、可信依据与是否仍成立，不默认高于官方机制 |

没有必要把所有内容都塞进同一个“记忆库”。静态机制可以是版本化内容包，动态世界状态精确读取，个人经历走 Memory；统一到回答时，仍保留各自来源与权威程度。

### 6.2 攻略条目应包含什么，如何索引

假设铜钟守卫 1.3 版怕火，1.4 版改成火焰无效，敲击后的短暂冰弱点才有效。一条建议不能只保存“用冰攻击”几个字：

| 字段组 | 示例内容 | 作用 |
| --- | --- | --- |
| 身份与修订 | 机制 ID、攻略 ID、内容 revision | 对应哪条技能或建议 |
| 适用范围 | contentBuild、热修订、区域、模式、难度 | 从检索入口排除不适用内容 |
| 前置条件 | phase-2、招式刚结束、玩家拥有冰技能 | 不能拿静态攻略直接指挥当前动作 |
| 可用事实与动作 | 冰弱点持续条件、可执行动作 ID | 语言表述与机制保持可追溯 |
| 知识与剧透范围 | NPC 所知、玩家所见、允许提示层级 | 检索前先限定可透露集合 |
| 依据与验证 | 来源配置 ID、验证场景、有效状态 | 攻略可能失效，不能只看发布时间 |
| 内容本体 | 可解释的条件、原因和例外 | 让模型能把短建议解释清楚 |
| 派生索引标识 | 分块、编码模型键、索引构建版本 | 追踪向量是否来自正确内容 |

精确过滤字段建立适合查询模式的数据库索引，例如 Boss 身份、内容版本与模式；自然语言内容建立全文／向量索引。字段的顺序与复合索引选型要用真实查询计划和数据量测试，不能在面试中凭空给一个万能索引。

前置条件经常是结构化判定，不应全部藏进向量文本。向量相似度解决“钟楼那个铁家伙”和“铜钟守卫”的语义匹配，不能决定哪个补丁版本有效。有效候选集先按版本和知识资格约束；如向量引擎只能先取候选再过滤，必须测过滤后的漏召回，不能把旧版候选占满当成数据库没有答案。

### 6.3 完整查询、生成和最终展示

1. 由当前锁定目标获得稳定 Boss ID；玩家只说“那个 Boss”而目标不明确时，先消歧。
2. 读取实际 battle/session 所绑定的内容包版本、难度、阶段、当前可用技能，以及玩家要求的提示深度。
3. 查询有资格的机制与建议：适用当前构建、符合模式与阶段、NPC 可知且不越过玩家允许的剧情范围。
4. 需要语义检索时，在这个集合内融合词法与向量证据；选出解释当前问题必需的事实。没有相关事实不能让模型靠预训练记忆补充“旧版攻略”。
5. 形成有限回答计划。例如只说“这一阶段等敲钟结束，用冰技能打暴露部位”，暂不提未见过的第三阶段。
6. 用 Persona 表达为岚舟的语气，事实 ID 和适用条件仍随内部计划保留。
7. 展示前检查相关版本、阶段与玩家状态。若正好进入第三阶段，重新判断这句话是仍然有效的总体说明，还是已经过期的即时指令。
8. 保存实际展示、使用事实、当前版本及未知信息，便于追查“他为什么叫我用火”。

规则负责版本与资格，模型负责问法消歧、证据组织和表达。Boss 别名识别不确定可以澄清；“当前是 1.4 版”来自会话元数据，不需要模型置信度投票。

### 6.4 更新以后旧攻略怎样退出

更新不是把文档日期改成今天。机制变化会影响攻略正文、分块、向量、摘要、缓存回答、提示图和正在生成的内容。它们应能追到所依赖的事实 revision。

本例可以选择“新内容及必需索引准备好以后，原子切换服务该版本的内容清单”作为待验证设计。至少要处理：

- 发布前检查 1.4 内容的来源、适用范围、全文与向量映射是否完整，并重放所有引用已变机制的场景。
- 1.3 仍在运行的会话使用对应内容，不能一律取数据库中发布时间最新的文章。依据实际会话绑定版本决定。
- 旧回答缓存键带相关内容版本与知识资格，不能只用玩家问题文本作键。
- 在途请求携带内容版本；返回时重查依赖，过时建议不再展示。
- 已播出的错误要明确纠正，不能假装撤回消息就等于玩家没听见。
- 新版攻略缺失时，只回答新版确认过的机制，或说明缺乏可靠建议；不能自动放宽过滤取旧攻略凑数。

如果索引更新落后，可把该知识包标成未就绪并暂不发布依赖它的问答能力；是否允许一种更简单、质量已验证的读取方式，需要产品自己的单一路径设计，不在此偷偷加入一串未经比较的检索降级算法。

当前 CharaMate 的 revision、有效时间、编码任务和最终重读资格提供了可迁移的经验，详见 [第 15 章第 7 节](15-context-activity-retrieval-walkthrough.md)。但它尚无游戏补丁内容清单、机制依赖图或服务器发布链。本节是新增游戏需求的方案。

### 6.5 误答如何定位

先区分：目标识别错、版本绑定错、正文没更新、向量仍指旧内容、检索过滤错、证据选错、模型没按证据说、或生成后环境已变化。每一层都能出现“回答像旧攻略”，修复方法不同。

最小回归至少覆盖：旧版本会话仍读旧知识、新版会话只读新版、更新中请求迟到、新版本暂无攻略、同 Boss 不同难度、未解锁机制，以及模型记得旧机制但本轮证据已否定它。不要只写一个“1.4 字符串出现了”的测试。

## 7. CharaMate 的评测集实际怎样建，回流做到哪里

### 7.1 它不是一份统一的大规模人工标注数据集

仓库中有多层不同用途的证据。它们可以互相补充，但不能合并分母：

| 层次 | 已有材料与规模 | 能说明什么，不能说明什么 |
| --- | --- | --- |
| Persona 小规模比较 | 4 个角色、12 案例、3 方案、36 样本 | 比较稳定 Persona 与动态状态；Codex 评审，不是人工一致性研究 |
| 编码器／检索开发集 | 60 篇文档、28 问题、20 个故事／关系组 | 比较候选覆盖与最终选证；不是 28 个独立真人使用者 |
| 连续陪伴开发 | 12 故事、144 原始事件、36 检查点；不同冻结批分别保留 | 检查事件到形成再到使用；重复开发不能算未见测试 |
| 独立连续素材 | 12 故事、144 事件、36 检查点，分两区各 6 故事 | 标签与原输入分离；两个分区复核不等于两人对同一批样本双标 |
| 本地产品验收 | 原 48 固定场景，后续定向修复与最终 v9 工程验收分别登记 | 覆盖实际安装与本地产品链；不能外推线上玩家满意度 |
| 确定性工程回归 | 历史最终 v9 记录 2,682 项离线、29 项 Electron E2E | 测机械合同与旅程；不是 2,711 条语义评测答案 |

对应记录：[Persona](../../benchmarks/character-dialogue.md)、[编码器](../../benchmarks/LOCAL-MEMORY-ENCODER.md)、[连续开发](../../benchmarks/COMPANION-LONGITUDINAL-EVAL.md)、[独立验收](../../benchmarks/COMPANION-CONTINUITY-HOLDOUT.md)、[本地验收](../../progress/LOCAL_MATURITY_ACCEPTANCE.md)。这些是历史结果，此次文档工作没有重跑。

编码器记录明确：素材来自作者编写的 24 个连续故事中的 development 部分，再加入人物、时间、纠正、计划与结果、同应用多任务等对照；没有读取独立留出标签。开发和独立连续批各记有 12 个故事。作者合成事件不等于真人采集，也不能说是米哈游玩家数据。

完整冻结原文与执行资产在仓库外，由稳定 ID 和哈希引用。本次能核对仓库决定与聚合记录，未重新取得所有原始语料；正文举例会区分已记载的主题与重写的教学原话。

### 7.2 用具体故事说明标签为什么不能只有一个答案字符串

独立验收记录有这些真实主题：

- **角色薄荷与用户无植物**：区分角色自己的植物与用户的生活事实；同时检查未知操作结果是否被误说成完成。
- **改期再取消**：Jan 12 改到 Jan 15，再取消待定；取消会议不等于放弃整个项目。
- **聚餐纯素菜单**：本次聚餐为朋友安排纯素，不应推断用户长期纯素；朋友退出后还要正确解释当前人数与菜单状态。
- **论文与课程任务**：不能从论文内容诊断用户；用户转去电影时不继续强拉旧话题；没有供给方法原文时应说明未知。
- **解谜与操作归属**：给提示但由用户自己操作，且不能剧透；后续夜间条件转折必须被采用。

以“改期再取消”为教学重述：用户先说“12 日开会”，再说“改 15 日”，最后说“取消，项目照常”。正确标签应规定：当前没有确定会议时间；12 日和 15 日均为历史安排；项目没有被取消。模型可以用很多不同措辞表达这些关系。单看有没有字符串“15 日”会把正确的历史解释和错误的当前安排混在一起。

执行时从事件逐步进入真实 Cognition、形成、SQLite、编码器与证据选择。到了检查点，一路做诊断检索，看事实在系统中是否可达；另一路从诊断前的数据库副本创建普通新 Chat，让实际 Runtime 自己决定是否用工具。诊断检索不能提前把答案塞进普通 Agent，再宣传它会自主寻找旧记忆。

### 7.3 实际结果里最值得讲的两个反例

**反例一：回答正确，仍然没有证明冷检索。** 独立连续批中，36 个普通 Agent 首步有 31 个已经拿到相关旧事实，1 个只拿到部分事实，1 个只需当前结束原话。缺少旧事实的 3 个机会都来自同一故事的认知提交失败。唯一一次自然 `memory.search` 返回空，普通回答中的自然冷召回采用为 0。这个冻结批不能被总结成“长期检索通过”；后续修复记录需要另看版本，不能覆写原成绩。

**反例二：指定答案没选中，未必是编码器太小。** 4B／512 维和 8B／1024 维接同一个证据选择模型，在 28 个问题里都选齐了其中 27 个问题所标注的必要证据；两组的候选都包含所需证据。共同失败题只问“本人喜欢的放松活动”，标签指定摄影纠正，但两组选择的“喜欢船、在海上放松”也有用户依据。补充摄影限定以后，两组都选到了期望证据。这是问题范围与标签的诊断，不把原 27/28 改成 28/28，也不把一次诊断当成模型全面等效。

这两件事解释了为什么要分四层：事实是否正确形成、是否进入候选、是否最终供给、回答是否正确采用。没有形成的内容，换 embedding 不能修复；输入已充分却答错，继续扩大候选可能只会增加成本。

### 7.4 当前自动评测与人工标注的真实关系

已有确定性测试承担 Schema、事务、版本、取消与事件合同；真实模型实验保存实际请求、输出、使用量和结果；若干记录使用模型或实现者逐例复核。独立素材记录区分作者、运行者与分区复核，但没有足够材料证明它是职业标注团队的人类双标，更没有已经计算好的 Kappa。

因此面试中可以说：

> 我已经建立了分层工程回归和按连续故事组织的真实模型评测，保留了冻结版本、失败和后验修复。Persona 比较里有模型逐例评审；连续素材有标签隔离与复核。但我还没有建设游戏玩家的持续人工标注生产线，没有可宣称的人类 Kappa，也没有持续训练的数据飞轮。下一步会沿可复放案例建设这些能力。

拟建配合方式是：确定性规则先查可精确证明的错误；模型评审扩大语义覆盖并指出证据；人工独立标注一批代表性与关键样本，用来检验评审、校准阈值和解决争议。人工不是只在模型自报低置信度时才出现，否则会漏掉高置信度错误。

### 7.5 Bad case 多久回流一次

当前材料显示的是“发现问题 → 定向修复 → 原场景复验 → 更广回归”的迭代，没有已运行的固定每日／每周自动回流服务。不能把建议的节奏写成项目历史。

对于拟建游戏团队，可以采用如下初始安排，再按实际量和人员调整：

| 节奏 | 具体产物 | 为什么这样安排 |
| --- | --- | --- |
| 发生后立即留证与处理 | 版本、状态、输入、输出、曝光；严重剧透或错误动作先限制受影响内容 | 不能等下一轮训练才停止重复错误 |
| 每个工作日归类 | 去重后的问题家族、影响范围、负责人、证据缺口 | 尽快识别同一根因造成的大量表面变体 |
| 每次修复进入发布前 | 最小失败回归＋相邻正常场景＋受影响冻结集 | 回流是否及时以修复闭环为准 |
| 每周形成一版候选标注包与误差报告 | 随机样本、疑难样本分别统计，保留标签版本 | 给跨学科复盘一个可执行的初始节奏 |
| 每次内容／模型／检索版本发布前后 | 新旧策略比较、关键故事复验、线上代表性抽查 | 发布本身可能改变分布 |
| 训练前 | 确认瓶颈、数据量、标签质量和独立测试 | 每周回流数据不等于每周重训模型 |

每日／每周都是团队排程建议，没有被设成算法阈值或创建自动任务。小项目可能按里程碑收一批数据；线上高流量则可持续收集，重要的是不能积压无主的问题，也不能急着把未复核错误喂回训练。

回流样本带当前修复版本和故事家族。旧测试题一旦参与修复，就属于已知回归；保留原始成绩，再准备新的未见家族检验泛化。只有维护了这个边界，“越用越好”才有可检验的含义。

### 7.6 一个完整误判闭环

玩家已经拒绝提示，岚舟又解释了谜底。复盘先查：

1. 本轮是否真的收到拒绝？拒绝针对当前谜题，还是仅暂时不想听？
2. 状态是否正确保存，生成输入是否包含该状态？
3. 规则是否仍把这次主动提示判为允许？
4. 如果规则不允许，为什么语音仍开始播放？检查展示队列与旧请求。
5. 如果允许范围正确，模型是否拿到了超出级别的事实？
6. 如果材料也正确，是否生成了无依据内容，或者评审没有发现？
7. 最终玩家到底听到了什么，曝光是否有证据？

若根因是旧语音队列没有跟随拒绝失效，修队列／版本合同，加“拒绝发生在入队与播出之间”的确定性回归；别把这条故障首先当成 OOC 训练数据。修复后再查“玩家仅拒绝某一个谜题，其他主动请求仍能获得帮助”的相邻场景，避免全局沉默的新问题。

## 8. 把“特征、置信度、阈值、误判复盘”讲到可执行

### 8.1 每个分数都要先说清它预测的事件

“置信度”如果不带事件定义，几乎没有工程意义。以下四个概率不能相互代替：

| 预测事件 | 合理标签来源 | 不能冒充它的数值 |
| --- | --- | --- |
| 这句回答含明确角色违背 | 有完整角色与场景的独立标注 | 回复与人物介绍的向量相似度 |
| 现在询问是否要提示会被接受 | 实际明确反馈与设计良好的试验 | 日历上三天没完成任务 |
| 当前问题需要哪些事实 | 按主张与证据标注的覆盖要求 | 搜索结果第一条的 BM25 分数 |
| 指令目前可以执行 | 游戏规则和当前权威状态 | 模型自称“我很确定” |

最后一项通常应直接计算条件，不需要做概率预测。前三项才可能需要模型与统计估计。模型输出一个 0.93 只是数值，除非在相似分布的未见样本上验证过，否则不能解释为“93% 正确”。

### 8.2 特征选择不是把能采到的信号全部加上

先画因果与时间关系：决策时到底能看到什么？提示前可看到尝试次数，不能把提示后成功写成输入特征，否则会发生未来信息泄漏。世界事实与标签要分开，不能从“金标准写了卡关”提取一个完美特征。

然后按以下步骤比较：

1. 建立可解释的最小基线，例如明确求助＋当前任务前置；保留证据不足分支。
2. 按假设加入特征组：最近进度、错误类型、提示历史、语义表达等，记录它们想解决的错误。
3. 用按玩家／故事／角色分组的数据比较，并做消融；观察新增组是否改善目标错误，同时增加什么成本。
4. 检查缺失、延迟、测量错误和版本漂移；必要时用缺失标志，而不是把没采到填成零。
5. 检查跨场景可用性，删除只记住角色名、模板或某个训练地图的捷径特征。
6. 保留足够简单、可维护的方案。数据不足时先增加代表性与边界例，不急于构建复杂分类器。

对 OOC 可以用事实冲突、无依据主张、价值冲突与表达偏离；对卡关可以用有效尝试、近期进度和障碍类别。两者都需要有独立标签，但不应该共享一组含糊的“玩家状态特征”。

### 8.3 校准具体做什么

假设一个分类器对 100 条输出都给“含 OOC 的概率约 0.8”，独立标注却只有 60 条确有 OOC。那么在这一档它明显过于自信。校准要使不同概率档中的实际发生比例与预测更相符，不是把分数都调高。

保留训练数据、校准／阈值选择数据与最终测试数据的边界；数据少时可做按故事分组的交叉验证，但最终未见集合仍不能被反复用于选阈值。分别检查可靠性曲线、Brier 分数、关键类别召回及每档样本数。一个总体误差指标可能掩盖最重要的稀有错误。

Guo 等人用保留验证集学习温度参数，调整分类器 logits 的尺度，再取 softmax；这种校准不会改变最高分所属类别。它在其图像与文本分类实验中表现良好，但不等于生成式 NPC 自报置信度也天然可用。这里的温度是分类概率的后处理参数，和为了改写台词而改变采样温度不是一件事。[ICML 2017 正文](https://proceedings.mlr.press/v70/guo17a/guo17a.pdf)

如果只有模型输出的文字分数，没有可用分类 logits，可以用独立样本评估这个分数的排序能力，或训练一个轻量判别器；Platt 缩放／保序回归等后处理也是待比较选项。没有足够数据时保留低把握分支与人工抽检，不能捏造“已校准”。

### 8.4 阈值如何从错误代价中选

以“拦截可能 OOC 的回答”为例，正类定义为确有角色违背。漏报意味着错误输出被放行；误报意味着正常回答被拦住，造成等待、改写或不自然的拒答。阈值越低一般拦得越多，但两种代价必须一起看。

下表是一组 1,000 条教学数据，其中 100 条确有 OOC。`s` 是候选检测分数，此处不把它当成已经校准的概率：

| 以 s 超过阈值拦截 | 正确拦住错误 TP | 误拦正常 FP | 漏过错误 FN | 正确放行 TN | 被拦中真正错误的比例 | 错误召回 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 0.30 | 90 | 90 | 10 | 810 | 50.0% | 90.0% |
| 0.60 | 80 | 30 | 20 | 870 | 72.7% | 80.0% |
| 0.80 | 55 | 5 | 45 | 895 | 91.7% | 55.0% |

如果漏过一次错误代价记为 10、误拦一次记为 1，则三者教学损失为：

```text
0.30：10 × 10 + 1 × 90 = 190
0.60：10 × 20 + 1 × 30 = 230
0.80：10 × 45 + 1 × 5  = 455
```

只看被拦回答的准确性，会偏好 0.80，却漏过 45 条错误。换成另一类低风险表达问题，如果漏报代价为 2、误报代价为 3，则损失变成 290、130、105，取舍又不同。代价数字需要产品体验、内容风险和运行成本支持，这些示例没有产生任何可直接上线的阈值。

实际选择还要报告按故事聚类的区间、可回答覆盖率、玩家打扰、延迟、预算和实施复杂度。在开发集合选好候选，在未见集合验证；若候选差异不明确，倾向更简单的方案。不能把小样本的最优小数点包装成普适标准。

对于已校准的概率和两种简单动作，可以按条件期望损失做决策；一旦有澄清、改写和不同剧透等级，动作代价与后续状态更复杂，需要逐项评估。最重要的边界仍然不变：模型分数不能放宽权威版本、剧情知识和动作条件。

### 8.5 误判复盘要保存哪些东西

一条可复盘记录包含：样本与故事 ID、触发事件时间、输入时可见状态、缺失特征、角色与知识版本、实际送入模型的材料、模型／提示／检测器版本、评分、决策阈值、最终行为、曝光、人工标签及依据。保存必要请求与简短决策依据，不需要采集模型不可验证的“内心活动”。

复盘按四步进行：

1. **重新定义错误。** 当时目标是什么，最终发生了什么，证据是否完整；未知曝光不能算玩家已收到。
2. **找到最早偏离。** 源事件缺失、状态错、过滤错、选择错、生成错、校验错，还是正确决定被旧队列覆盖。
3. **选最小修复。** 改合同、内容、特征、阈值、提示或训练，分别对应根因；阈值不能修数据库版本错误。
4. **证明范围。** 原例复现／修复、同家族变式、正常相邻例、未见分组，再记录发布后的代表性反馈。

阈值调整要解释新放过了什么、新拦住了什么。遇到新版本或角色分布变化，先检查校准和误差漂移，再决定是否重校准；不能一看到一个坏例就随手把 0.8 改成 0.9。

## 9. 把研究启发讲成自己的设计推导

下面五段可以直接练口述。说“受启发后我会怎样设计”用于拟建内容；只有仓库已有实现与实验，才说“我做了怎样的比较”。

**角色需要可解释的边界。** Ubisoft 的 NEO NPC 官方介绍强调，编剧负责背景、愿望和说话方式，并在模型即兴后继续调整；它当时仍是原型。对我的启发是，把策划从“穷举台词”转向“定义人物为何这样行动、哪些事实不能编造”。CharaMate 已用稳定 Persona 和知识边界编译上下文；游戏侧还需要内容资格与剧情约束，不能说已复刻 Ubisoft 或米哈游架构。[官方文章，2024-03-19](https://news.ubisoft.com/en-us/article/5qXdxhshJBXoanFZApdG3L/how-ubisofts-new-generative-ai-prototype-changes-the-nature-of-npcs)

**快动作不能等待慢解释。** Epic 的事件驱动行为树让状态变化能够直接改变任务。我的推导是，战斗有效指令先由权威状态与有限策略给出，模型随后解释；两个输出共用版本与依赖，旧解释迟到就拒绝展示。这是待测试的游戏设计，CharaMate 已有的取消与版本机制提供经验，尚没有战斗延迟实测。

**提示是帮助量与理解机会的取舍。** 认知科学对 assistance dilemma 的研究提醒我，立即给出答案可能提高当次完成率，却未必帮助下一次独立完成。我会区分注意、机制、操作和前置问题，让提示根据缺口走不同分支，同时测进展、打扰和下一题表现。具体提示层级与时间仍要由游戏试验决定。

**角色评测必须有场景变化。** PersonaGym 给不同人物安排相关环境并分维度评分。我的设计推导是，同一人物在安慰和战斗中可以变换句式，事实和价值变化却要能解释；不能用一句自我介绍或固定口头禅验收长期一致性。CharaMate 的 12 例 Pilot 是一个初步比较，百 NPC 与长时间漂移需要另外验收。

**分数与一致性都要有含义。** 校准研究告诉我，分数高不自动代表可靠；标注一致性研究告诉我，多人一致也不自动代表事实正确。我会把权威规则、语义检测、独立标注和阈值选择分开，把模型评审当扩大覆盖的工具。当前没有人类双标结果时，我不会编出一个 Kappa 来包装项目。

## 10. 闭卷验收：回答完七题以后必须能做什么

这些练习是 A08–A12 的新增输入，个人学习状态仍为“未执行”。可以分两轮：先做机制推演，再做实验与数字；只背本章结论不算通过。

| 任务 | 必须交付 | 关键失败条件 |
| --- | --- | --- |
| 开放问题与 Persona | 从“你哥哥是不是失踪了”讲到输入、事实资格、Persona 编译、输出与复盘；画当前角色编辑和 Run 快照 | 把未设定自动说成事实；声称现有禁语字段等于硬拦截器 |
| 战斗 200 ms 目标 | 写明起止时刻，画快响应与慢解释；在慢结果前插入阶段变化；列延迟测量和分母 | 用“我听到了”代替有效指令；宣称远程模型无条件保证 |
| 三天卡关 | 区分四种以上阻碍；处理提示被打断、拒绝后旧队列、操作困难与明确要答案 | 用三天直接判沮丧；提示没听完也升级；反复加剧透解决按键问题 |
| 百 NPC 一致性 | 一份确定的角色材料编译方案、一张跨场景测试矩阵、一次公共模板改动的影响分析 | 每人一套框架；只以口头禅或名字判断人物一致 |
| 标注与 Kappa | 设计一条带证据的样本；独立算出两张表的 0.70 和约 -0.053，解释分布与裁决 | 把裁决后统一答案拿来算独立一致性；把 Kappa 当正确率 |
| 攻略更新 | 从 1.3／1.4 混存推演到版本过滤、缓存、在途结果与已播纠正 | 只取最新文章；扩大搜索范围拿旧版填空；只更新向量不管正文 |
| 评测与回流 | 区分 12 例、28 问、36 检查点、48 场景与工程测试；给一个真实失败根因及拟建回流安排 | 混合分母；把暖上下文答对叫冷检索；虚构人工 Kappa 或自动周更 |
| 阈值选择 | 算两组代价下三档损失，设计分组切分和消融；解释何时无需模型置信度 | 直接背 0.8；用阈值修版本错误；按同一故事的句子随机切分 |

口述还要经受三个变式：内容包热更新发生在语音播出前；玩家只拒绝当前谜题的提示但又主动问 Boss；策划补写了角色身世而旧对话仍在历史中。每次都说明谁拥有事实、哪份版本适用、什么可以即时重算、什么必须等待，以及怎样留下可验证的结果。
