## 1. 记忆故事：从搜到相关文字，到真正记得同一个人的经历

### 1.1 可以直接讲的口述稿

> 我最开始做记忆时，优先解决的是本地能稳定运行、能查到记录。选的是 SQLite FTS5 加 BM25，中文先做归一化和分词。这不是随便挑的：早期比较里，混合检索在部分中文问题上更好，但最终回答的配对改善很小，还出现额外无依据的主张。因此当时保留简单词法方案是合理的。
>
> 后来我在做陪伴体验时，意识到“搜到有关这件事的文字”和“记得这个人经历过什么”差别很大。参加米哈游的交流也让我更关注这种连续性。用户不会每次复述原来的关键词，还会改口、提朋友的事情、把临时安排和长期偏好混着说。例如，用户以前说某个日子想安静纪念亲人，今天只说“照我们之前说的来”，单靠词面重合就很难找到关键背景。另一个问题是，搜到了“周五见面”也不代表它还有效，因为用户后来可能改成周六。
>
> 所以我把问题拆成了形成、检索和使用。形成端保留真实来源，区分谁的经历、发生时间和判断依据；变化写成修订，不直接覆盖成一段越来越长的摘要。检索端保留词法，再加入语义和实体／事件时间通道。词法负责名称和明确术语，语义负责换一种说法，结构化通道负责人物和时间范围。
>
> 这里也不是通道越多越好。我遇到过结构化通道把“截至现在有效”误当成“与问题有关”，把大量近期材料放进候选，反而挤掉相机已经归还的记录。修复是把资格过滤和正向召回拆清楚：有效只是能用，还需要明确实体或事件线索才能补充相关候选。
>
> 候选融合我也比较过 RRF 和按通道交替取项。大预算下二者都是 28 个问题里 27 个取齐必要材料；差异在小预算下显现：一条只被语义通道直接找到的记录，在该通道排第三，却在 RRF 合并后排到第三十一。交替合并让它排到第五，后面的选择模型才有机会读到它。我最后保留交替去重，再让 LLM 根据问题选证和说明缺口，宿主重新读取真实原文。LLM 选证不能救回根本没进候选池的证据。
>
> 编码器上我选了本地 4B、512 维。在这组配对中它与 8B、1024 维的最终必要材料覆盖相同，因此先承担更小的本地资源成本。但这只支持当前配置选择，不能声称完整三路已经在大规模真人陪伴上胜出。下一步我会补通道消融和连续故事的端到端测试，尤其检查漏记、漏查、旧事实和最终表达。

上面的纪念日问法用于解释机制，具体措辞是教学改写；相机归还、排名 3→31／5 和 27/28 来自历史记录。实际例子的原始问题、额外可用证据和歧义不能被改写成更漂亮的失败率。[早期检索](../../benchmarks/memory-retrieval.md)、[融合比较](../../benchmarks/MEMORY-RANK-FUSION.md)、[结构化范围修复](../../benchmarks/MEMORY-RECALL-STRUCTURED-SCOPE.md)。

### 1.2 酒会和“类脑”怎样变成设计问题

可讲自己的学习路径：“交流让我从问答检索转向连续经历，回来后把问题拆成目标保持、具体经历、长期归纳和按需回忆，再读对应研究。”不用宣称已经拿到对方内部方案。仓库确实有两份相关调研：[记忆研究](../../research/ai-companion-memory-research-2026-09-15.md)与[认知及自主生活研究](../../research/ai-companion-cognition-and-life-2026-09-15.md)。

这里的“学到”要落到机制，而不是几个脑区名字：

- **互补学习系统给出快慢学习的启发。** 具体的新经历需要快速保留，跨经历的共性需要较慢整合，否则一次特殊事件容易改写全部印象。CharaMate 的工程对应是来源、修订和后台巩固；不是在线训练了海马体或皮层。[原论文摘要，1995](https://pubmed.ncbi.nlm.nih.gov/7624455/)；企鹅例子的既有讲解见[第 10 章第 3 节](10-research-and-industry.md)。
- **Generative Agents 把经历、反思与后续行为接起来。** 记忆不是被问到才展示的资料，还应影响计划。我的迁移是记录约定的形成、变更和实际结果，并在相关行为前取用；不照抄其重要性与时间权重。[论文 v2，2023-08-06](https://arxiv.org/abs/2304.03442v2)。
- **Mem0 让我重视抽取与更新的分工。** 新交流先提出候选，再判断与已有记忆的关系。项目在自己的领域层检查来源与修订，不能让模型直接随意覆盖原记录；这里借鉴的是论文机制，没有把其库接成第二套记忆系统。[论文 v1，2025-04-28](https://arxiv.org/abs/2504.19413v1)。
- **LongMemEval 让我把“忘了”拆成阶段故障。** 索引、检索、阅读分别可失败；更新、时间关系和无证据拒答需要单独测试。这直接转化成项目的分层定位方法。[论文 v2，2025-03-04](https://arxiv.org/abs/2410.10813v2)。

“他们怎么做”只回答拿到的公开事实。本次复查的[云栖官方入口](https://yunqi.aliyun.com/2026/session?agendaId=187)仍未提供可读取的完整讲稿，不能从转载补造米哈游的索引、模型、PFC 模块或私聊原话。面试时可以转回自己的结论：“我受到的触动是角色需要连续地理解和行动，下面是我把这个问题落地的方式。”

### 1.3 先讲清楚 FTS5 为什么一开始够用，后来在哪些问题上吃力

早期最终 reader 的公平配对仅 22 题：词法答对 16/22，混合答对 17/22；回答所有主张有依据的分别为 22/22、21/22。中文确认部分的 Hit@8 为词法 32/39、向量及混合各 38/39；但其他数据集不一致。**词法起步有成本与质量依据，需求变化后也确实存在继续优化的空间。**

下面是可现场手推的陪伴案例，均为教学材料，不是新增实测：

| 经历与后来提问 | 真正缺的能力 | 为什么不能只换一个排序公式 |
| --- | --- | --- |
| 过去：“每年今天想安静纪念外婆。”现在：“还是按之前说的陪我吧。” | 跨措辞检索和当前情境关联 | 原句没进词法候选，重排也看不到；同时需要避免无端提起敏感往事 |
| “我喜欢美式，小林怕苦。”后来：“给他点什么？” | 指代、人物归属和完整证据 | 向量把“咖啡偏好”找回来，也可能找错主人 |
| “平时喜欢自然光，今天录视频先拉帘。”后来：“哪些只是今天试一下？” | 长期偏好与临时条件区分 | 同主题高相似并不能决定适用范围 |
| “周五去陶艺，改周六。”后来：“原来定哪天，现在呢？” | 旧版、新版与问题的时间语义 | 当前问题不能读旧值，历史问题又不能把旧值永久删掉 |
| “小林借走相机，后来已经还了。”后来：“还要催吗？” | 当前状态及结束事件 | 检索到借出记录却漏掉归还，会触发错误行动 |

实际相机故障发生在扩展后的召回管线，不是“FTS5 原型的历史失败”。最后一行用于讲当前状态问题，不能拿它冒充早期单路曾测到的结果。

### 1.4 从一句话走完整条已实现流程

以“小林周五借了相机，周六还了”为教学输入。真正的工程不是把整句话做一个向量：

1. **保存真实来源。** Chat／Run 拥有用户输入，Activity 拥有观察；主体、来源和实际发生的内容有据可查。
2. **产生形成任务。** 普通聊天由模型调用无参数 `memory.record`，宿主从真实 Run 取来源；Cognition 也可提交持久 handoff，交接入队与确认在同一事务里完成。不是任何模型生成的句子都能自称用户原话。
3. **语义形成。** 模型提出经历、事实、人物、时间和变化关系；宿主验证 Schema、来源引用与版本。主体语义仍可能判断错，Schema 合法不代表含义正确。
4. **提交修订。** Memory 有稳定身份，Revision 表达某版内容。真实变化和原先说错需要区分；借出经历不因归还就从历史消失，当前未归还状态则必须失效。
5. **建立可查表示。** 词法记录和结构化关系服务各自查询，语义编码任务按修订与 modelKey 处理。形成成功与全部向量建完不是同一时刻；新纠正不能等待整库索引排空才影响本轮回答。
6. **提出信息问题。** `memory.search` 的计划说明需要哪些信息、人物或时间范围，以及最终上下文预算。给错全局过滤会在召回前排除正确事实。
7. **三类通道取候选。** 词法与语义按每个问题取候选；结构化通道按实体／事件时间取候选。当前源码还允许宿主提供候选实体线索，仅影响结构化补充，不把这些线索强加成全部通道的硬过滤。
8. **合并并选择。** 显式引用和每个问题／通道的首项优先保留，再按排名交替去重，在候选预算内提供给 Selector。Selector 返回已有 revision ID、对应问题及覆盖情况；必要时进行一次有预算的来源／关系扩展，再选证。
9. **重读并供给。** 宿主按真实记录组装 EvidencePack，检查当前性、来源和最终预算，保留形成／索引／覆盖缺口。回答模型据此说明相机已归还，不能把“没有查到”说成“用户从未说过”。

### 1.5 两路、三路、RRF、LLM 各自解决什么

可以画成下面一条线，不把不同时期的决策揉成一个分数：

```text
明确的问题、人物、时间与有效性约束
                ↓
词法候选     语义候选     有范围的实体／事件时间候选
                ↓
显式引用／通道首项 + 按排名交替去重 → 候选预算
                ↓
LLM 按问题选证、声明缺口 → 必要时一次关系扩展再选择
                ↓
宿主验证引用／版本、读取原文、适配最终预算 → 回答或行动
```

**为什么加语义？** 给不同表达一个被找回的机会。**为什么加结构化？** 让明确的人物、事件区间成为检索线索，而不只依赖句子相似。**为什么保留词法？** “松柏工作室”、物品编号、专有名称有时就需要精确词面。

**为什么不用 RRF？** RRF 用各榜单的名次融合，通常以 `Σ 1/(k + rank)` 计分，避免直接相加不同尺度的 BM25 和向量分数。它合理，但会奖励多通道共同出现。教学计算：`k=60` 时，一个仅语义第 3 的事实得 `1/63≈0.01587`；一个在两路都第 20 的材料得 `2/80=0.025`。后者未必更能回答问题，却可能先占据有限预算。这是具体场景下的偏置，不是证明 RRF 普遍错误。公式依据[作者公开论文，SIGIR 2009](https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf)；其 pilot 选用的 60 也不是通用硬限制。

**交替就一定好吗？** 也不一定。一个质量差的通道会占位置，结构化无范围污染就是教训。项目采用交替，是因为已有小预算诊断显示它保住了单通道证据，主比较没发现必要覆盖损失，而且少了 RRF 常数。后面仍需要选择与独立评测。

**LLM rerank 是什么？** 面试可简称“LLM 选证”，比“直接 LLM rerank 全库”准确。它要判断多条材料能否共同回答问题，包括否定、纠正与时间关系；它只能选择已供应的 ID，正文由宿主读取。它仍会漏选、多选、误报覆盖，也增加一次或多次模型等待。它没有替代召回和确定性资格检查。

### 1.7 把尚缺的实验设计补完整：可以讲方案，不能补造胜率

这部分是本次补写、尚未执行的方案。可在面试说：“我现有实验是分项诊断，完整消融还要这样补。”

**数据单位用连续故事。** 每个故事按时间输入真实式对话和事件，包含正例、纠正、第三人的事实、无证据问题及无需回忆的闲聊。先固定人物与事件的原始材料，再在不同时间点提出自然问题。开发集与留出集按完整人物／故事／生成模板分组，不能把同一故事改个名字分到两边。合成材料标明合成；真实材料需获得使用许可并去除秘密。

**先写标签再跑。** 每题标注当时需要哪些事实、哪些旧值不能作为当前值、是否确实需要搜索、可以接受哪些不同答案、哪些情况应澄清。两名评审先独立判断难例，再处理分歧；没有人手时如实降低证据等级，不把模型裁判写成人工双标。摄影题多解的教训应落实成“可接受证据集合”，而非强迫唯一文档 ID。

**分四个实验，不一次改四件事。**

| 实验 | 比较方式 | 主要指标 |
| --- | --- | --- |
| 形成质量 | 相同顺序原话，固定检索与 reader；只改形成入口或形成策略之一 | 应记事实覆盖、误写人物／推断、纠错后有效状态、重复写和形成等待 |
| 通道贡献 | 同一人工核对库和问题，固定融合／Selector；完整三路分别去掉词法、语义、结构化 | 每类问题的必要证据覆盖、错误主体／版本进入率、最终回答正确性 |
| 融合与选择 | 同一冻结通道列表与预算，先只比较融合；再固定合并结果比较选证方式 | 候选可达、选证保留、多余材料、输入输出 tokens、端到端延迟 |
| 真实闭环 | 按时间由真实形成器建库，普通 Agent 自己决定搜索并最终回答 | 漏形成、漏搜索、召回丢失、选证丢失、回答误用分别占多少；整体任务是否完成 |

通道消融的完整三路与去掉一路做配对，每一对只变一个通道；如需回答“早期单词法到三路”的总收益，另列整体配置比较，不能把整体差当某一个模块的贡献。

预算至少覆盖正常和受压场景，候选额度与最终回答额度分开。额度先在开发数据按可接受等待和资源选择，然后冻结；不能看了留出答案再把关键记录刚好塞进来。对模型随机性预先固定重复办法，按故事汇总配对差与区间；失败、超时和无终态都保留。报告质量、漏查、误记、延迟分布、前后台成本与复杂度，不用一个总分盖住坏处。

样本规模由希望分辨的最小实际收益、开发集中的故事间差异和运行预算共同确定；可以先做小规模 pilot 估计，再锁定正式规模。本章没有凭空预定“300 个用户已经测完”。若三路总体与较简单方案难以区分，就选满足产品能力的简单方案；拟议 runner 和候选只存在于可删除实验环境，不向产品加检索模式。

### 1.8 追问时的短答案

- **为什么不直接长上下文塞全库？** 全库会同时放入过时、无关和冲突信息，也增加等待；先定义当前问题和有效事实，再按需供给。长上下文可以是实验对照，不能自动解决形成错误。
- **为什么没有图数据库？** 当前实体、关系与一次扩展能用现有 SQLite 表表达。有没有复杂多跳收益要单独测，三路不等于已经上图。
- **为什么不训练 embedding？** 当前明显故障包含没搜索、错过滤、候选被挤出和选证；先修这些。训练需要证明同域数据有可重复的表示缺口，且独立故事有净收益。
- **你的贡献是什么？** 按实际职责说清问题定义、链路拆解、实验选择和定位过的失败；不要把一个开源模型的训练成果当作自己的模型能力。

## 2. 语音故事：从能把答案读出来，到允许用户随时改变对话

### 2.1 可以直接讲的口述稿

> 我最早是用 Azure 的识别和合成服务，把语音接到文字 Agent 上。这条路容易起步，工具和记忆可以复用，但实际用起来会感觉它先把话听完、转成文字、想好，再念给我。后来即使按句流式播放，也会有分句等待，用户一插话，就要同时处理文本生成、句子队列、音频缓冲和工具执行。
>
> 让我真正改变架构的，不只是首句快慢，而是对话控制。用户说“周五……不，周六”，或者在它说话时说“先别查”，系统必须立刻让话，还要确保旧结果不会回来接着播。仓库里实际记录过分句空档、显示文字和口述不一致，以及打断后卡在思考的体验问题。
>
> 我后来选择了 Azure Realtime 的原生语音路径，当前仓库验证的部署是 gpt-realtime-2.1。麦克风和输出走 WebRTC，模型直接听音频、生成音频并决定工具调用。文字和语音不强求同一个回答模型，但共用角色设定、记忆、工具执行、审批以及 Run/Item 的产品状态。
>
> 同时我没有完全放任服务端检测到停顿就回答。我关闭自动创建 response，由宿主拿到最终转写、建立真实 Run、准备上下文后显式启动回复。这样工具、持久化和取消都有身份可以对齐，代价是转写和上下文准备仍在首答的关键路径上。原生语音不意味着 ASR 延迟已经消失。
>
> 打断我分成媒体和逻辑两部分：本地先停旧声音，服务端取消并清缓冲；Main 取消旧回合和待执行工作。异步结果回来时还要检查 session、turn 和 generation。已经提交的外部动作不能靠取消回滚，要根据真实回执解释。
>
> 后来还有一次很典型的半句故障：同一个用户回合里，模型先说“我查一下”，工具返回后再说结果，这是两个 response。前一个 response 的停止事件迟到，代码如果只认 generation，就会把后一个正在播放的声音关掉。我把播音生命周期按 responseId 关联，并区分生成完成和缓冲播放完成，才把这类跨响应干扰处理清楚。
>
> 现在它具备双向音频和打断接续，但我不会把它等同于自然的人类全双工：附和、咳嗽和对旁人说话仍需要评测，审批期间也还有关麦限制。下一步优先解决首答关键路径、误打断与转写污染记忆，而不是继续叠更多语音服务。

开头的“Azure STT/TTS”来自你的本轮回忆；当前 Git 未找到对应 Speech SDK 实现，不能编它的版本或历史延迟。仓库可独立确认的中间版本是 Realtime 转写→文字 Agent→分句朗读，以及随后恢复原生语音的决定。口述把这两个阶段连接起来，但不把它们的测量混用。[语音架构决定](../../benchmarks/voice-architecture.md)。

### 2.2 为什么串联方案有问题，为什么不把锅都推给 Azure

STT→文本模型→TTS 本身可以流式、也可以支持打断，不是架构上绝对不能做好。问题是本项目当时用它承担连续陪伴时，多了一组需要同步的边界：

| 阶段 | 当时需要等待／管理什么 | 对体验的影响 |
| --- | --- | --- |
| 识别 | 判断用户是否说完、稳定最终文字 | 结束判断过早会截断改口，过晚会让用户等 |
| 文字回答 | 生成稳定且适合朗读的句段 | 文本生成很快不等于马上能自然说话 |
| 分句合成／朗读 | 排队、发出下一段、对齐显示文本 | 句间空档、字幕与实际口述不同步 |
| 打断 | 同时停止多个生成与播放对象 | 只停音频会留下旧文本继续生成；只停 Run 会留下声音 |
| 工具接续 | 将进度话与结果话插回同一交流 | 状态协调比“接一个 TTS API”复杂得多 |

这段因果描述应限定为自己的实现和体验观察。不能拿没有对照的数据说“Azure STT 天生很慢”，也不能说“原生模型一定比所有串联方案快”。若工具本身慢，换音频模型也不会消除查询等待。

### 2.3 选 Realtime 后，哪些职责必须留在自己手里

当前路径可以用三个平面解释：

```text
媒体：麦克风音轨 → WebRTC → Realtime → 远端音轨／实际播放
协议：DataChannel → speech / transcript / response / function call 事件
产品：VoiceService → Chat / Run / Item → 共用 Tool / Approval / Memory
```

Main 以安全存储中的长期凭据申请短期 client secret；Renderer 用短期凭据交换 SDP，并建立音轨与数据通道。会话绑定启动它的 Chat，浏览别的 Chat 不迁移正在说话的上下文。暂停保留可复用连接，结束释放媒体及连接。[会话签发](../../../src/main/voice/azureWebRtcSession.ts)、[WebRTC 驱动](../../../src/renderer/features/voice/WebRtcVoiceDriver.ts)、[Microsoft WebRTC 指南，2026-10-30 复核](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/realtime-audio-webrtc)。

协议模型负责语音理解、表达和 function call 提议；宿主负责当前回合身份、有效上下文、工具参数校验、审批、执行结果和持久化。共享的是产品合同，不是把文字模型偷偷再接回来回答。

当前 `server_vad`、`create_response:false`、`interrupt_response:true` 是可核对配置；输入转写为 `whisper-1`，输出为 audio。语音最终转写非空后，宿主准备上下文、建立 Run，再 `response.create`。这段等待是一项明确的工程取舍。[VoiceService](../../../src/main/voice/voiceService.ts)。

OpenAI 的 server VAD 根据语音活动与静音判断边界；semantic VAD 尝试判断话是否说完。语义断句不自动判断“这句话是否对我说”，而且具体 Azure 部署是否支持某字段要单独验证。[VAD 官方说明](https://developers.openai.com/api/docs/guides/realtime-vad)。

### 2.4 用一次查记忆和改口讲清整个时序

以下是教学时序，协议与身份对应当前实现：

| 时刻 | 发生什么 | 需要保持的关系 |
| --- | --- | --- |
| t0 | 用户：“我们周五几点去陶艺？” | 输入音频有独立 input itemId |
| t1 | speech_stopped，最终转写到达 | 停止讲话不等于已经转写完成 |
| t2 | 宿主准备当前上下文并保存用户输入，创建 Run | 本次 turn／generation 仍有效才继续 |
| t3 | 显式创建 R-A；模型说“我查一下”并调用 memory.search | R-A、callId 与 Run 关联 |
| t4 | 工具沿共用执行边界返回 | 结果必须对应原 callId，不能重复执行或接错回合 |
| t5 | function_call_output 回注，显式继续 R-B | R-A、R-B 同 turn／generation，不同 responseId |
| t6 | R-B 正说“周五下午……”时用户插话 | speech_started 立即抑制旧音频，启动新输入代际 |
| t7 | 用户完整说“不是，已经改周六了” | 新回合用当前纠正更新回答及需要的记忆 |
| t8 | 旧工具／旧 R-A／旧 R-B 的事件迟到 | 记录必要终态，不允许恢复旧回答或关闭新回合的声音 |

会话、回合、Run、响应和工具调用不能压成一个 `isSpeaking`。一个用户回合可以有多个响应；模型生成完之后仍有音频等待播放；一次工具取消也可能晚于真实副作用。

### 2.5 半句故障：适合重点讲的一次定位

现象是“后半句话明明还在生成，却听不到了”。如果只看 API 成功率，会认为模型没问题、客户端也收到了数据；如果只看字幕，则看起来回答完整。

实际需要把三个事件按 ID 排起来：`R-A stopped`、`R-B started`、`R-B stopped`。当 `R-B started` 先到、`R-A stopped` 后到时，旧逻辑把同 generation 的停止都理解成当前播音结束。错误不是网络一定乱序，而是**应用把不同 response 的生命周期合并了**；跨媒体与控制事件也不能假设一个全局顺序。

修复后的 `output_audio_buffer.stopped` 先读取 responseId，只有等于 `currentPlayingResponseId` 才关闭当前输出。资源释放还要等待对应响应的生成终态和播放停止条件，不能因 `response.done` 就提前静音。[驱动源码](../../../src/renderer/features/voice/WebRtcVoiceDriver.ts)、[驱动回归](../../../src/renderer/features/voice/WebRtcVoiceDriver.component.test.tsx)。

最有价值的回归不是简单播一段音频，而是构造“R-A 已生成完、R-B 已开始、R-A 才停止”的事件顺序；再加旧 generation、重复 stopped、clear、暂停和结束的变式。真实设备验证还要看实际声音，而不止这些协议测试。

### 2.6 打断真正完成，需要四件事同时成立

1. **听觉上立即让话。** Renderer 收到 speech_started 先抑制输出，不等后台模型重新推理。
2. **停止旧生成与排队音频。** 取消响应并清服务端缓冲。当前 WebRTC 截断由服务端管理；应用接收截断回执，不在每次插话时自行猜一个毫秒值发送 truncate。WebSocket 客户端则需自行管理播放与截断，不能把两条协议写成一套。[官方中断说明](https://developers.openai.com/api/docs/guides/realtime-conversations)。
3. **终止旧逻辑的续接资格。** 旧上下文准备、工具和审批即使晚返回，也不能继续旧回合。Abort 是停止请求，身份校验才阻止迟到提交。
4. **承认已经发生的效果。** 已完成的数据库写入、文件修改或远端提交不因取消自动消失；后续根据真实结果核查、解释或另做撤销。

这也解释为什么自然全双工还没完全解决：传输可双向、应用能让话、模型能自然处理重叠，是三个不同层次。Moshi 的多流研究提醒我们，重叠、附和和静默还涉及模型及训练数据，不能靠换 WebRTC 就获得。[Moshi v1，2024-09-17](https://arxiv.org/abs/2410.00037v1)。

### 2.7 已有证据和仍然欠缺的体验

早期 V1 与 V2 的受控比较，改变的是 VAD 后由服务自动创建 response，还是宿主显式创建；**两组都是原生 Realtime**。每组只有三次同类合成输入，speech stop 到 first audio 分别为 673／705／727 ms 与 836／840／942 ms。它显示编排有等待成本，不是 Azure STT/TTS 对 Realtime 的成绩，也不是当前产品的 p95 或人耳首音时间。

还有真实的工具 Schema 故障：当前 Memory 工具的根级组合约束被目标 Azure 部署拒绝，导致会话都没建起来。修复放在适配边界，将原 Schema 嵌进 arguments 对象，执行前再严格解包并按原工具 Schema 校验；没有复制一套 Voice 工具。[架构记录末节](../../benchmarks/voice-architecture.md)。

后继记录包含两段 WAV 的记忆形成与改期、新进程新 Chat 的检索，以及内置麦克风／扬声器的有限问答验证。它们证明对应路径实际走通，不能代表复杂噪声和自然插话已经全面通过。

目前仍有三项适合主动说出的缺口：

- **首答依赖最终转写。** 不应宣传“完全绕过 ASR”。
- **审批期间关闭采集。** 当前难以在这一段靠语音说“算了”，始终全双工尚未实现。
- **原生模型可能听懂，转写仍可能错。** 如果转写成为 Memory 来源，错误会在后台形成并被再次检索。历史“陶艺课／淘逸客”等偏差没有证明普遍消除。

### 2.8 下一步怎么做：按关键路径和具体错误改

**第一步，量清时间。** 记录音频结束、speech_stopped、转写完成、上下文准备完成、response.create、首个下行音频以及实测可听首音。分别看冷启动与复用、普通回答与工具回答。流式阶段可能重叠，不把各服务耗时直接相加当作端到端；也不把 RTP 首包当用户已经听到。

**第二步，先优化不改变语义的等待。** 可复用连接与稳定 Persona／工具准备继续复用；每回合仍刷新会变化的事实。若实际瓶颈在最终转写，才研究“用音频提交身份先建回合、转写晚到后补记”的协议方案。那需要解决音频来源、文本修订和依赖转写的 Memory 入口，尚未实现，不能只把 `create_response` 改回 true 就宣称完成。

**第三步，分开解决断句和误打断。** 准备改口、长停顿、附和、咳嗽、背景说话、外放回声和中英专名录音；固定设备与材料，只改变目标部署支持的一种 VAD 设置。测过早切断、额外等待、漏打断和不必要打断，不能以“打断越快越好”奖励每声咳嗽都抢话。

**第四步，审批期间的语音接管作为明确改进。** 方案是保持采集，新输入进入现有串行控制路径；取消和参数修正使旧审批失效，含糊“嗯”不能自动等同于批准。新的动作重新核对当前参数和审批身份。正式落地前需要更新相应生命周期合同与集成测试，不新增第二个语音控制器。

**第五步，阻止 ASR 错误升级为确定事实。** 专名提示可来自当前任务，但不得强迫识别到某词；涉及日期、否定、人物、金额等改变行动的歧义，应澄清或保留未确认状态。不能全局把“仪器”替换成“一起”，也不能让文本润色器的猜测变成用户原话。后续明确纠正沿已有修订机制传播，原识别来源与纠正来源分别留存。

**实验怎样组织？** 固定原音频、目标部署、音色、工具结果和上下文，配对执行，交替顺序并预先规定重复次数；设备条件分组报告。每次只改编排、VAD、转写提示中的一项。真实用户自然插话另做交互测试，因为固定录音不能测对话双方互相适应。指标同时包括任务完成、实际首音与停止尾音、误切断、回合错接、工具重复、识别关键事实错误和费用。完整 transcript 与部分播放分开，不把生成后的未播放文字当作已完成交流。

### 2.9 追问时的短答案

- **为什么不用 Realtime 自动回复？** 当前需要先持久化输入、建立回合身份并准备可信上下文；我承担这段延迟以保证产品链路一致，下一步按测量结果减少关键路径。
- **为什么取消后还要 generation？** 取消不保证远端瞬间停止，旧结果可能已经在返回途中；generation 和对应对象身份决定它能否继续生效。
- **为什么既有 generation 又有 responseId？** generation 管本次用户回合的过时问题，responseId 管同回合里不同输出片段的生命周期，半句故障正是两者混淆。
- **原生语音还要转写干什么？** 用户可读历史、Run 输入以及 Cognition／Memory 消费仍需要文字；它是辅助来源，不能保证与模型实际听到的含义完全一致。

## 3. 认知与注意故事：从窗口变化触发，到维持一件正在发生的事

### 3.1 可以直接讲的口述稿

> 最开始主动陪伴的入口比较简单：前台应用或窗口发生变化，我就给模型一次判断机会，再用时间窗口和冷却控制频率。这能让角色偶尔主动说话，但它有一个很明显的缺陷：应用不是任务。用户从 Overleaf 切到搜索，再切到 ChatGPT，可能一直在改同一篇论文；反过来，同一个浏览器里也可能从写论文变成处理报销。
>
> 参加酒会后，我开始更认真地看类脑注意和前额叶相关研究。对我最有帮助的不是给软件划几个脑区，而是“目标怎样持续影响当前选择”。Miller 和 Cohen 讲目标与规则的维持，显著性网络研究又提示什么时候需要切换。这让我把问题改成：当前在做什么，新信息与它有什么关系，什么时候更新判断，什么时候必须让用户接管。
>
> 我先补感知，让 Activity 不只看到应用名，也能收到对象和内容变化、实际可访问的文字、操作计数、视觉变化及真实执行结果。但更细的事件不能逐条叫模型，所以来源侧先合并，同对象连续重复可以去重，纯键鼠计数不会单独触发语义分析。
>
> 在此基础上我设计 Cognition：Observation 保存看到了什么，Situation 保存正在发生哪件事，Claim 保存带依据的判断，Intent 保存目标与继续条件，Attention 保存当前关注和何时重新考虑。这些状态都有来源和版本。物理焦点变了，不一定要放弃原来的目标；用户说“先别改，我还没说完”，则必须让旧行动立刻失去继续资格。
>
> 我把收到、分析、执行和交付分开。后台模型只提出状态更新与行为选择，实际动作交给原来的 Run／Tool；新的用户输入不需要等待后台先理解完。分析返回时检查它依据的状态是否还有效，行动前再检查选中的具体依赖，避免旧结果覆盖新纠正，也避免任何无关变化都把合法动作取消。
>
> 这里有一个真实问题：用户从酒店页去报销表，再回到同一酒店页，旧去重因为页面正文没变化把重访吞了，系统还以为前台是表格，后续比较用了错误城市的报价。我后来把连续重复和跨对象重访分开，并记录合并观察的时钟，防止迟到回调把焦点拉回去。这说明注意力不是单纯写一个“请关注重要信息”的 prompt，输入身份和时序就可能决定模型有没有机会看对。
>
> 我也试过更显式的 Appraisal 表示。它在一个局部行为点上更好，但完整执行结果两边仍是 16 个检查点中 11 个，输入增加约 10%。因此没有为了更像心理学模型把额外状态留在生产。我保留较简单的 Claims、Intent 和 Choice，优先修复材料供给与执行链。下一步重点是连续语义输入的积压和时机评测，而不是继续增加脑区 Agent。

前台触发与时间控制属于早期阶段，当前已是持续情境实现。[早期注意记录](../../benchmarks/COMPANION-ATTENTION.md)明确标注被后续替代；不能把其“每应用一个最新观察”或 24 KiB 工作集说成今天的 Cognition。

### 3.2 三个反例推动了问题重新定义

**同一目标，多个应用。** Overleaf 编辑→浏览器搜资料→ChatGPT 推敲句子→回到 Overleaf。若每次切换都重新开场，角色像在评论用户的桌面，而没有理解用户在写论文。

**同一应用，多个目标。** 浏览器里论文、报销、旅游轮换。按 appId 保存一份最新状态会混淆对象，甚至把旅游价格当报销依据。应用名有用，但不足以成为事项身份。

**事件很多，真正的变化很少。** 连续输入、滚动和光标变化可能每秒都有；其中大多数只是活动证据。用户一句“别改了”则很短，却改变行动资格。不能靠频次或文本长度当重要性。

这三个反例分别要求**语义连续性、对象身份、控制优先级**。它们比“要做一个前额叶”更容易实现和测试。

### 3.3 论文具体启发了什么，没有实现什么

| 研究 | 可以解释的核心观点 | 在项目里的转化 |
| --- | --- | --- |
| Miller & Cohen，2001 | 目标与规则的持续表征可以偏置当前处理与行动 | Intent 跨事件维持；当前用户要求和持续目标共同约束选择，不让最新窗口自动接管全部任务 |
| Sridharan、Levitin、Menon，2008 | 大规模认知网络的参与和切换具有关联，右额岛区域与切换相关 | 区分普通观察与需要重新考虑／用户接管的事件；这是工程类比，不是把 fMRI 相关分析翻译成软件因果定律 |
| Generative Agents，2023 | 经历、反思和计划共同影响后续行为 | 当前情境与长期 Memory 协作，行动结果回到下一次决策；不只把过去聊天全文加到 prompt |
| Proactive Agent，2024 | 把主动任务预测及是否接受当成可以独立评价的问题 | 从“有没有生成”转到“有没有必要生成”，为沉默和主动选择建立标签 |
| 流式 ProactiveBench，2026 | 连续输入需要评价何时响应以及其他时候能否沉默 | 评测过早、合适窗口、遗漏、重复；不拿单次问答准确率代表持续注意 |

来源分别为[前额叶综述](https://www.annualreviews.org/content/journals/10.1146/annurev.neuro.24.1.167)、[网络切换论文](https://pubmed.ncbi.nlm.nih.gov/18723676/)、[Generative Agents v2](https://arxiv.org/abs/2304.03442v2)、[Proactive Agent v3](https://arxiv.org/abs/2410.12361v3)、[流式 ProactiveBench v1](https://arxiv.org/abs/2609.12658v1)，本次于 2026-10-30 复核相应摘要／页面。两篇名含 ProactiveBench 的研究并不是同一个数据集。

这里的“注意力”是产品中的信息选择、目标维持和调度，不是改造 Transformer 的 self-attention。项目没有训练一个脑模型，没有实现可校准的完整心理信念分布，也没有多个脑区各自跑一套 Agent。Persona 影响角色如何解释和表达，不能改变客观回执。

### 3.4 Cognition 的数据为什么要这样分

用“用户正在写给同事的信，但当前只想倾诉”说明：

| 对象 | 保存什么 | 若全部塞成一段摘要会丢什么 |
| --- | --- | --- |
| Evidence | 真实用户话语、文档内容、工具效果及其时间／来源 | 不知道某句话是用户说的、屏幕引语还是模型推测 |
| Situation | 写信这件持续事项、相关对象和当前阶段 | 切应用就容易被当成事情结束 |
| Episode | 讨论对象、写初稿、检查语气等有边界的片段 | 无法组织经历过程，也难以交接长期形成 |
| Claim | “目前希望倾听”等有支持／反证的解释 | 推断变成确定事实，纠正找不到对应判断 |
| Intent | 谁的目标、依据、目标状态、完成标准和继续条件 | 只记得讨论过写信，却不知道是否仍允许改稿 |
| Attention | 物理焦点、语义关注、读取进度、下一次考虑时间 | 当前窗口、当前任务和未读历史混为一件事 |
| Attempt／Choice | 本次实际读了什么、选了什么、对应哪个 Run | 无法解释旧模型结果为何还能或不能执行 |

不是所有字段都由模型决定。宿主管来源身份、顺序、版本和时钟；模型提出语义判断与选择。`explicit_user`、`inferred_user`、`character` 的 Intent 依据不同：看到用户编辑信，不等于得到修改或发送信的请求。详细合同见[认知 Schema](../../../src/shared/schemas/cognition.ts)。

有了这些对象，用户说“不是同事，是我妹妹”时，可以修正相关人物判断；用户说“先听我说”时，可以暂停协作意图而保留写信情境；后来真的贴来文稿并要求看语气，再继续同一件事。

### 3.5 事件变多以后，怎样避免模型被淹没

来源链是 ActivityCaptureCoordinator→ActivityService→CognitionRuntime.observeActivity→CognitionService.ingest。真实用户输入、完成的 Run Item、工具效果、主动表面反馈、重要时刻到期和系统控制也有各自入口。像素变化先记为信号，分析需要时再取实际图片；路径字符串不等于模型已经看过图。

处理按语义分工：

- 同一对象的连续相同观察可以合并；切走再回来是新的焦点事实。
- 纯点击、按键、滚动计数进入被动统计，不逐个调用模型；带真实正文变化时不能被计数分支吞掉。
- 普通内容变化保存并安排分析，默认不会每次 abort 在途分析，否则持续输入会让模型一直重来。
- 用户接管、停止、角色切换等控制改变 generation，并请求取消旧分析和需要让路的角色 Run。
- 到期表示重新考虑；仍要读取当前状态，不等于届时必定发消息。

当前普通批处理窗口为 Main 注入的 1 秒。新事件与已有 `nextWakeAt` 取更早值，不是每来一次都向后推迟的 debounce；所以持续变化不会无限延后第一次分析。它是工程配置，不是神经科学常数。CognitionService 实例只保留一个在途分析 Promise，新事件继续入库，之后再读真实待处理状态。[CognitionService](../../../src/main/cognition/cognitionService.ts)、[装配与入口](../../../src/main/app/cognitionRuntime.ts)。

“一个在途分析”也不等于所有前台 Agent 和领域任务都串行，更不等于支持所有 NPC 的并发服务。迁到游戏时，应先按玩家／场景／对象订阅筛事件，再按独立实体划分所有权，不能把本地实例级槽位直接称为百万 NPC 架构。

### 3.6 异步理解怎样跟得上不断变化的用户

一次分析大致是：读取有界快照→调用只读认知模型→验证来源与状态更新→短事务提交→检查行动资格→交给共享 Run→收到实际结果。网络等待不放在 SQLite 事务内。

关键是分清两个边界：

**分析提交检查这份理解有没有过时。** Persona、用户控制代际、读到的状态版本、新用户来源等不能被旧模型结果覆盖。模型提出的 delta 只能修改本轮允许修改的对象，未供应字段不能当作模型已理解后删掉。

**行动检查选择所依赖的东西有没有变化。** 某个无关文档多了一行，不应让所有合法动作都失败；用户撤回许可、所选 Memory 被修订、目标对象变化，才可能使该动作失效。检查还要发生在异步准备与真正展示／执行之间，不能只在生成前检查一次。

例如系统已收到序号 150，历史连续页只读到 108，另外预留了最新用户纠正 150。`receivedThroughSequence` 可为 150，但连续消费进度不能直接跳到 150，否则 109–149 会被误记为处理过。反过来，也不能拿 108 当本次接收边界，把已经供给的纠正 150 判成分析后新到的消息。当前输入优先与旧材料不丢需要同时满足。

普通聊天 `prepareTurn` 读取已提交的认知背景，不先启动一次新的认知分析。当前真实消息优先，后台随后追平。这减少等待，但背景可能稍旧，所以投影必须保留来源和边界。[快照读取](../../../src/main/cognition/cognitionSnapshotReader.ts)、[认知投影](../../../src/main/cognition/cognitionProjection.ts)。

### 3.7 两次具体失败，比“加入注意力模型”更能说明能力

**第一次：相同正文，不等于同一次观察。** 真实开发场景里，酒店页→表格→酒店页，最后重访被旧逻辑删除，分析没有收到青岛 1080 的页面，转而使用北京报价。修复按同 Persona／actor 的最近连续观察判重，同时检查物理焦点，而不是只问“这个对象上次是不是同样文字”。

独立检查又发现更细的问题：A@10、相同 A@20 被合并、迟到 B@15。如果只保存 A@10，B@15 会被误认为更新的焦点。于是将合并观察的有效时钟保存在已有 Attention 中，模型不能修改；不为此添加另一套事件日志。相同毫秒的不可比来源等边界仍要保留，不能声称解决任意时钟漂移。[连续观察决定](../../benchmarks/COGNITION-CONTINUOUS-OBSERVATION.md)。

**第二次：省了输入 token，模型却更慢。** 连续长正文曾尝试用 exact-splice 增量表示。六个开发场景中，输入从 42,252 降为 40,821 tokens，但输出从 13,406 增到 14,779，累计时长从 232.32 秒增到 262.13 秒。减少序列化文本并不保证推理更容易，最后没把这个额外表示留在生产。六对小样本不能代表全部负载，但足够否定“输入更短就肯定更快”的实现理由。[吞吐记录](../../benchmarks/COMPANION-COGNITION-THROUGHPUT.md)。

### 3.8 为什么没有保留更显式的 Appraisal

Appraisal 候选试图把对事件的意义解释进一步显式化，让倾听、玩耍、协作和自主行为有更完整的中间表示。比较固定共同基础、Memory、4B 编码器及实际 Runner，四个混合事件家族各四个检查点，每边跑完整流水线。

结果要分两层讲：行为准则 Common 为 14/16、Appraisal 为 15/16；结合必要 Run 终态和实际材料供给后，两边均为 11/16。Appraisal 的一个局部优势是真实的，但没有变成完整执行的额外成功。模型请求 258→265，输入 2,036,491→2,246,065 tokens，约增 10.29%，还增加状态、引用及校验复杂度。

因此选择现有 Claims／Intent／Choice。没有得出“心理学无用”或“二者严格等价”，而是判断当前额外表示的收益不足以承担复杂度。四个相关家族是开发比较，评审由实现者复核，不冒充真人随机盲验；共同失败后来单独修复，也不回填成候选当时的成绩。[Appraisal 决定](../../benchmarks/COGNITION-APPRAISAL-MODELING.md)。

面试可以概括为：“我用脑科学帮助提出问题，但让产品行为决定保留哪些结构。解释更漂亮，不等于系统做得更对。”

### 3.9 如何评估和进一步优化

当前有确定性回归、开发比较与有限连续场景验收；没有充分证据证明无限事件流下理解永远追得上。输入被可靠保存、读取有界和语义及时处理是三件事。

补充方案应沿四层展开，均为待执行：

| 层次 | 怎么构造比较 | 怎样判断有效 |
| --- | --- | --- |
| 感知覆盖 | 同一桌面／游戏轨迹，对照人工记录实际发生的对象与内容变化 | 哪些事件没收到、哪些可见内容被错称已读；先修供给再评价模型 |
| 连续情境 | 固定输入，比较无持续状态与当前状态；分别加入跨应用同任务、同应用不同任务 | 事项延续、人物归属、用户纠正、取消和重新参与是否正确 |
| 调度与预算 | 同轨迹、同模型、同状态合同，每次只改合并或分配策略之一 | 有效事件等待、最旧积压、用户响应、模型调用／tokens；不能只奖励少调用 |
| 实际行动 | 检查选择、Run、效果和展示四个阶段 | 选对但没执行、执行成功却错误失败、用户已停止仍曝光都算独立问题 |

每个连续故事在事件到来前定义“仍应保持的目标”“什么会让它失效”“此刻可以安静吗”。评审只看该时点以前的材料，未来结果不得提前泄漏。把无关变化、同对象重访、迟到来源、纠正和动作已提交都放进同一套变式，不只测顺序正确的幸福路径。

持续语义内容积压的下一步可先尝试**任务相关的来源选择与当前用户／明确到期事项预留**，在现有快照与覆盖机制内比较。未读事实继续可追溯；被合并的变化不能虚称完整理解。若再考虑便宜模型做筛选，必须独立比较漏掉关键纠正的代价、部署资源和额外复杂度，不直接把第二个常驻模型写成既成方案。

游戏的快反应应交给已有玩法权威和动作控制，例如战斗伤害、导航取消和交互锁；语言模型负责允许较慢推理的解释、计划与表达。这样慢模型不会成为每帧动作的前提，模型提出的动作仍需按当前世界状态验证。这个游戏迁移是设计，不是 CharaMate 已上线的服务端。

### 3.10 追问时的短答案

- **Cognition 和 Memory 有什么区别？** Cognition 维持现在的事项和工作状态，Memory 负责跨会话经历、修订与按需回忆；认知交接使用真实来源，不把推理摘要冒充长期事实。
- **为什么不只用一个大 prompt？** prompt 能指导解释，却不能保证重复事件、旧结果、版本提交和执行效果正确；这些需要宿主身份与事务。
- **事件到了就要调用模型吗？** 不需要。纯计数和连续重复可本地处理，重要控制先让路，普通语义变化合批；是否开口还要过后面的选择与展示检查。
- **用户消息来了要等 cognition 吗？** 当前用户交互先接管，普通 Agent 读取已提交背景，不等待旧后台分析完成；工具取消及 Provider 拥塞仍可能有延迟，不能保证零等待。

## 4. 主动陪伴故事：知道很多以后，学会什么时候值得开口

### 4.1 可以直接讲的口述稿

> 我做主动陪伴时，最开始想解决的是角色太被动：用户不找它，它就没有存在感。所以先利用前台应用变化给它搭话机会，再加冷却。很快我就在设计里遇到一个矛盾：触发多一点像打扰，少一点又容易失去连续性。把间隔调长只能降低次数，不能回答这一句到底值不值得说。
>
> 这个问题是我自己一直在想的，我在米哈游酒会上也向对方问过怎样做到陪伴又不烦人。后续我继续查资料，把它拆成三个问题：有没有值得关注的事，这件事是否值得告诉用户，以及是不是现在说。认知系统可以一直更新理解，但理解发生不等于要立即弹一条消息。
>
> 从任务边界研究里，我学到通知时机应考虑用户的活动阶段，而不只是鼠标多久没动。角色 Agent 的研究又让我意识到，自主存在也可以表现为它继续做自己的事，不必每次都要求用户回应。后来复盘 Dot 的公开设计，我更明确了后台发现和对外通知的区别：它可以先做研究、留笔记，再由负责当前交互的主体决定如何带回来。
>
> 我最终把主动流程做成几层：Activity 和 Cognition 提供有来源的持续情境，模型选择安静、继续事项或主动交流；宿主检查用户当前交互、频率、免打扰和依据是否过期；真的展示以后才记录一次曝光，再接收回复、关闭或到期反馈。模型觉得有趣，不能越过用户的“先别打扰”。
>
> 频率上我提供关闭和三个程度档位，连续关闭或过期会延长下次普通邀请的间隔，也有直接“少一点”的入口。这是保守控制，不把没回复解释成用户讨厌角色。默认间隔来自当前产品选择，没有长期用户实验支持我宣称它最优。对于用户明确约好的结果反馈，也不能拿普通搭话冷却一概压掉。
>
> 我已经做过确定性策略场景验证和小型回应策略比较：前者证明开关、免打扰、退避按规则运行；后者在一些例子里减少无关回忆和要求用户做决定的负担。但它们不能证明真人长期不烦。下一步我会同时看帮助价值、误打扰、漏掉的合适机会和用户恢复原任务的成本，而不是只看回复率。一个角色把用户问到不得不回话，回复率高也未必是好的陪伴。

这里特意没有安排“面试官告诉我一个方法，所以我照做”的桥段。问题来自你自己，酒会提供了讨论场景；方案来自后续研究、实现与反馈。

### 4.2 为什么冷却加长仍然不够

两条每小时一次的消息，负担可能完全不同：

- 用户正卡在论文一段推导时，角色问“要不要喝水？要不要休息？要不要听音乐？”即使没违反频率，仍可能要求用户切换注意和做决定。
- 用户明确让角色查某篇论文，结果刚返回，角色简短带回关键结论。这是在履行约定，用户可能正在等。

问题因此不只是“每小时多少条”，还包括**相关性、时机、是否重复、是否索取回应、用户是否已经表达边界**。不能把一条长篇连问与一句无需回答的告知都当成相同的一次打扰。

教学例子：用户说“我今天不想聊，陪着就行”。这时一直追问“你怎么了”是错的；角色保持安静、继续可见的虚拟日常，也能体现陪伴。之后用户主动问一句，不需要等主动冷却结束才能正常回答。

### 4.3 从现有产品和论文分别得到什么

以下是可解释的学习路径，不把所有资料说成同一次读完，也不假设它们共享内部算法。

**Character.AI：用户在意连续性，也需要能纠正系统记住的内容。** 其 2026-05-21 官方介绍将 Story Memory、固定重要消息和自动 Facts 分开。对本项目的启发是保留重要经历和可修订性，但不要让用户为了得到陪伴不断整理档案。这是从公开交互得到的产品推论；该页面不提供它的检索算法或“不会打扰”的验证。[官方介绍](https://blog.character.ai/memory/)。

**Generative Agents：角色可以有持续活动。** 从经历影响后续行为得到的启发是，角色的连续性也可以通过行动表现。CharaMate 已有角色 Intent 和真实领地回执，未完成或失败的活动不能写成已经生活过的经历。它不要求引入饥饿值、亲密分或每隔几分钟向用户汇报。[论文](https://arxiv.org/abs/2304.03442v2)。

**Oasis：任务的自然边界值得作为时机线索。** 该研究把通知调度与目标活动的阶段边界连接，并用可观测交互识别边界。迁到桌面，可以比较“正在编辑一段”与“明确完成这段”；迁到游戏，可以比较战斗中、结算后和靠近柜台。边界只是开口的机会，不是必须讲话的命令。[原论文，TOCHI 2010](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/TOCHI-Oasis-final.pdf)。

**Proactive Agent／流式评测：沉默也必须纳入答案。** 主动任务预测可以按接受／拒绝评价；连续事件还要看过早、遗漏和重复。项目因此不能用“总共发出了多少建议”作为进步，也不能把“永远闭嘴”评成最佳策略。[Proactive Agent v3](https://arxiv.org/abs/2410.12361v3)、[流式 ProactiveBench v1](https://arxiv.org/abs/2609.12658v1)。

**OpenAI Dot：后台工作的价值不依赖立即通知。** 公开文档描述后台研究先形成私有笔记并报告发现，再由 Dot 带回建议或问题。我的迁移是把持续理解与对外曝光分开；这不是断言 Dot 使用了项目的 Cognition、三路检索或冷却公式。该材料是现在复盘时核对的参照。[Tasks and memory，2026-10-30 复核](https://learn.chatgpt.com/docs/dots/tasks-and-memory)。

**Ask Less, Ask Better：问题少与问题值得问，要分别量。** 2026-10 的研究把提问数量与用户注意成本分开，并检查问题是否已能由用户此前回答和当前材料解决。迁到陪伴，先检查用户是否刚讲过偏好、是否真的需要他做决定，再决定询问。它晚于本轮生产实现，是下一步评估的启发；不宣称已有自动自检 Agent。[论文 v1，2026-10-17](https://arxiv.org/abs/2610.24411v1)。

这些参考没有直接给我“60 分钟就是正确答案”。它们帮助我确定需要观察哪些变量，数值仍应由自己的场景和体验验证。

### 4.4 当前产品具体怎么做

当前机制由同一条 Cognition→Run→展示链承担：

1. **持续理解。** 接收真实活动、用户输入、约定及反馈，维护当前情境与 Intent；并非每次都只看最近一次应用名。
2. **语义选择。** 可以 remain_quiet、continue_character、continue_shared 或 start_conversation。安静是合法结果，角色做事不必伴随通知。
3. **宿主准入。** 检查用户 Run／语音占用、休眠、当前角色与 Intent 状态、唯一气泡、主动设置及来源依赖。这里的运行占用不等于准确测得用户在其他应用里的专注程度。
4. **执行前后复核。** 生成等待期间如果用户说“先别打扰”，旧选择不能继续展示；若调用工具，实际效果由原执行链负责。
5. **真正曝光才记账。** 展示面接受后记录主动历史与 offered 反馈。仅生成成功不代表展示，更不代表用户看见或喜欢。
6. **用户接话进入正常交流。** 新邀请先是 provisional Chat；用户参与后成为正常 Chat。没有参与的临时邀请按生命周期清理，不让聊天列表积满未参与会话。

源码：[认知运行时](../../../src/main/app/cognitionRuntime.ts)、[选择准入](../../../src/main/cognition/cognitionProjection.ts)、[主动会话表面](../../../src/main/journey/proactiveConversationSurface.ts)。

普通未经请求的邀请，当前档位间隔是 lively 15 分钟、balanced 60 分钟、quiet 240 分钟；off 关闭，默认本地免打扰为 22:00–08:00。最近三条里连续关闭／过期数为 n 时，要求等待 `max(5分钟, 基础间隔×(1+n))`。默认档位因此为 60、120、180、240 分钟；不是每分钟轮询后必定说话。[频率策略](../../../src/main/journey/companionInitiativePolicy.ts)。

`acceptedAt` 在这条链里是**展示面接受消息的时刻**，用户回复另记 replied。20 秒临时回复窗口到期只说明没有在这个窗口接话；当前保守退避可以继续，但不能自动形成“用户讨厌这个话题”的长期记忆。“少一点”直接下调档位，比每次要求用户评分更低负担。

用户请求的继续与普通主动开场要分开。历史上就发生过系统理解了邀请，却被普通开场冷却挡住的情况；后来以实际用户 receipt、原 Chat、条件和一次投递资格处理 requested continuation。不能因有“等待”状态就另外开一个 Chat 来重复执行。[已请求续接决定](../../benchmarks/COGNITION-REQUESTED-CONTINUATION.md)。

### 4.5 用一个完整场景讲“陪着但不催着”

以下为基于当前机制的教学推演；未来任务边界策略另行标出：

| 场景 | 当前可解释的行为 | 如果继续改进 |
| --- | --- | --- |
| 用户在写论文，角色已有“帮忙找相关论文”的请求 | 按有效请求继续工作；普通新话题受准入控制 | 区分用户等结果与仅后台发现资料 |
| 用户说“先让我把这段写完” | 当前用户要求优先，旧搭话选择不能迟到曝光 | 将用户明确完成信号与已有约定关联，而不是猜固定时间到了 |
| 用户切去检索网站，再回来 | 持续事项仍可能是论文，不因切应用重新开场 | 用来源覆盖判断是否真的读到了新证据 |
| 后台找到一条普通补充资料 | 认知可保持安静；不因有新内容就绕过冷却 | 把价值、时效和可等待性纳入同一选择，等待自然边界 |
| 用户明确问“刚才找到什么了” | 正常用户回合响应，读取真实结果 | 不再请求一次多余确认 |
| 角色给了一个新邀请，用户没接话 | 按展示结果记 expired 并保守退避 | 将未知曝光／未回应与明确拒绝分开分析，别训练成同一种负例 |
| 用户明确说“这类事情以后别提醒” | 需要遵循当前表达及已有可用设置／记忆流程 | 若做稳定的分话题偏好，应明确字段、来源和更新语义，再验证；当前不能称已完成长期个性化策略学习 |

“写完这段”这样的自然语言条件，当前可以进入 Intent 的继续条件；它不是无条件可靠的外部事件检测器。想自动兑现，必须明确哪个可观测事件能满足条件，或者等待用户直接表达，不能把模型留下了描述当作已经有完整执行器。

### 4.6 已有两类实验，各能证明到哪里

**宿主策略实验验证规则一致性。** 48 个原创确定性场景覆盖关闭、跨午夜安静时段、间隔边界、连续负结果、回复恢复、中断中性和“少一点”。仅旧冷却为 18/48，加显式设置为 34/48，再加反馈退避为 48/48。共享同一语义机会输入，没有调用真实 Provider。结果证明规则满足预定行为，不能解释为用户满意度从 37.5% 提到 100%。[主动策略决定](../../benchmarks/proactive-policy.md)。

**回应策略 pilot 验证部分文字取舍。** 24 个合成情境，两条件各一次，共 48 次生成；同 Persona、历史材料和用户输入，仅增加回应策略。单名独立研究 Agent 盲评为 4 胜、20 平、0 负，输入 tokens 增加 16.7%。一个具体差异是普通问候不再无端提起过去的疲惫；另外几例少要求用户补材料或做决定。

这不是人类长期体验试验，四个非平局的事后双侧 sign test 为 p=0.125。生产随后把提示压缩成四段共用指令，原 pilot 也不能被说成最终压缩文本逐字重测。保留这一策略是有限证据下的透明产品取舍。[回应策略决定](../../benchmarks/COMPANION-RESPONSE-STRATEGY.md)。

这个结果能形成很好的面试表达：“我目前证明了控制规则一致，并在少量文本场景修正了不合适的表达；是否长期更受欢迎，仍需要连续使用来判断。”

### 4.7 一套真正能回答“不烦人”的后续实验

这是一份待执行的设计，不是已招募用户或已经测出结论。

**先建立机会级离线材料。** 每条连续轨迹同时包含适合立即说、有价值但应等、无需告知、用户明确要求到时通知四类时刻。标注候选内容、允许的时机窗口、当前任务和用户边界；只给模型截至该时点的材料。包括正在写作、检索、休息、刚完成一段、对话中、未回应邀请等条件。对含糊情绪保留不确定，不能拿“打字快”直接标焦虑。

**把时机与内容分开比较。** 先固定候选消息，只比较当前冷却策略与增加任务边界选择的策略；再固定同一曝光机会，只比较话术是否重复、是否提出无必要问题。最后才做完整组合。否则结果变好后，无法知道是少发了、发得更准，还是只换了更好听的句子。

**至少同时报告五类量。**

| 指标 | 明确分母／测量对象 | 防止走偏 |
| --- | --- | --- |
| 有价值曝光比例 | 真正展示的消息中，被评为有帮助或合适陪伴的比例 | 高比例可能只是只说最容易的几条，需同时报漏机会 |
| 不合适打扰 | 展示中不合时宜的比例，并另报每使用小时的次数 | 不能靠用户使用时间减少美化数量 |
| 合适机会覆盖 | 已标记的应告知机会中，在允许窗口内送达的比例 | 永远沉默会在这里失败；明确约定漏报单列 |
| 注意与任务负担 | 恢复原任务的时间、需要额外回答／决定的数量、用户主观感受 | 回复率和会话时长不等于喜爱 |
| 连续性与资源 | 重复话题、违背当前约束、真实用户纠正次数，以及模型调用／tokens／等待 | 不能用高成本反复自检换一个只在离线漂亮的结果 |

**再做小规模连续使用。** 一个可执行的探索起点是招募 12–16 名愿意试用的参与者，分配两段各一周的使用期，AB／BA 平衡顺序；这是研究资源安排，不是功效保证或产品默认时长。每段要包含工作和休息，按人保留显式偏好；阶段开始从同一参与者的相同初始化记忆开始，之后允许自然演进，并把跨阶段学习与期待变化记录为交叉设计局限。若携带效应明显，后续正式研究改用按用户随机分组，不能用所谓清空状态假装消除了人的记忆。

交互调查尽量放在短的阶段回顾，不每次弹窗索取评分。收集真实曝光／回复／关闭及用户对具体事件的回忆，按用户汇总效果及不确定性；一个人的一百条消息不是一百个独立用户。初次探索确定主要指标、可接受退化和样本规模后，再冻结正式方案。不能看到谁喜欢新方案才剔除谁。

**对没回复保持谨慎。** 未回复可能是没看到、忙、内容无需回答或确实不想聊；这些原因对后续策略不同。当前先用显式偏好和保守退避，未来个性化若要学习，优先使用明确反馈与可解释情境，不直接把所有 expired 训练成“反感”。

**选择规则。** 新策略需要在任务／陪伴价值不明显损失时减少负担，或者以用户接受的额外负担换来重要约定更可靠。看分组、效应大小和成本，不只看一个 p 值；若差异不清楚则保留简单机制。删除未选策略和临时 runner，生产仍只有一个主动决定与展示流程。

### 4.8 游戏里还需要补的一层：玩家拥有有限的注意

桌面产品通常是一个角色对一个用户；咖啡馆可能多个 NPC 同时发现合适话题。如果每个 NPC 都遵守“一小时一次”，玩家仍可能一小时收到十次不同角色的发言。

迁移方案是在玩家／会话层仲裁发言：先由世界权威限制谁能感知、谁处于当前对话、是否在战斗或交易；NPC 提交带理由、时效与目标的交流机会；玩家会话选一个合适机会，其他可延后或通过环境动作表达。已有明确订单结果、玩家刚提出的问题与无请求闲聊分别处理。消息真正展示后才更新反馈，不能各 NPC 独立假定自己已经与玩家聊过。

这复用前面的持续事项、实际回执和旧选择失效原则，新增的是多人世界的范围与发言权。还未在 CharaMate 实现或压测，详细方案接[咖啡馆 NPC](09-cafe-npc-design.md)。

### 4.9 追问时的短答案

- **你怎么知道用户烦了？** 我不能从一次没回复知道。现在用显式设置与保守退避控制行为，语义偏好仍需要真实表达或后续验证。
- **为什么不是每个事件都提醒？** 持续理解可以后台发生，通知要有额外价值和合适时机；角色自主活动也可以保持安静。
- **为什么不是只优化回复率？** 用户可能因为被追问而回复，也可能因信息已经有用而无需回复；需要帮助价值、负担、漏机会一起看。
- **模型是否可以越过冷却？** 普通自主搭话不能因为自称重要就绕过控制；用户明确约定的结果反馈走对应续接语义，也要检查事实、状态和一次投递资格。

## 5. 四条故事合在一起，怎样讲成一个项目

如果只有一分钟，可以这样起头：

> 我做 CharaMate 时，逐渐把重点从“模型能不能回答”转到“角色能不能持续地理解和参与”。记忆从词法检索扩展到带来源和修订的形成、三路召回与选证；认知从窗口变化触发转成维护当前事项和意图；主动陪伴把理解、开口和曝光分开，让沉默也是正常选择；语音则从串联朗读转向原生 Realtime，并把打断和工具接续放回同一套产品状态。几条线共同的问题都是：旧信息或旧任务不能在用户改口之后继续生效，模型认为完成也不等于用户实际收到。
>
> 我最想展开的是几个真实取舍：单通道证据被 RRF 挤出、重访被误判重复、同回合旧响应停掉新声音，以及 Appraisal 更复杂但没有改善完整执行。它们让我更重视逐层定位和实际结果。局部实验能说明选择依据，长时间真人体验仍需要另外补证。

再按面试官的兴趣展开一条，不同时背完四套架构。每条故事都准备五个锚点：**一个原始目标、一个具体失败、一项有机制的改动、一份带分母的证据、一个能继续推进的缺口。**

| 故事 | 最适合展开的失败 | 讲到最后应体现的判断 |
| --- | --- | --- |
| 记忆 | 语义第 3 的证据在 RRF 总表掉到 31；相机归还被无范围通道挤出 | 候选可达、当前性、选证和最终使用要分别定位 |
| 语音 | R-A 的 stopped 误关 R-B；显示生成完但实际没播完 | 回合身份、响应身份和实际播放是不同生命周期 |

## 6. 四条故事共用的上下文机制：拼装、handoff 与自动压缩

### 6.1 可以直接讲的口述稿

> 我把上下文工程理解为：每次模型要继续工作时，系统决定它应该读到哪些规则、当前要求和真实材料，而不是把数据库里保存的所有内容重新发送一遍。记忆负责找回相关经历，认知负责提供当前事项，最终仍要把这些材料与聊天历史、工具结果和执行约束一起组织成一次有预算的请求。
>
> 在 CharaMate 的文字 Agent 中，一次请求分为 instructions、input 和工具声明。instructions 包含基础规则、当前时间、执行模式和本次 Run 的角色快照；input 初始包含同一 Chat 的历史摘要、尚未被摘要覆盖的消息、本轮认知与记忆背景、当前用户输入。模型调用工具后，真实调用和结果按 call_id 加入当前工作输入，再请求下一步。
>
> 工具多了以后，我区分两种整理。同一 Chat 的旧对话由模型总结，并记录摘要覆盖到哪条消息，后续只加载边界之后的原消息。正在执行的 Run 则主要由宿主重建输入：保留 handoff、已有 Chat 摘要、必要背景、最近工具结果、失败回执、当前计划和用户要求。这里的 handoff 是执行交接信息，不是把任务交给另一个 Agent。
>
> Handoff 从 Run 开始就维护，但通常到 Run 压缩时才作为一条背景消息交给模型。它主要来自工具结果的简述、用户补充、审批决定和待办状态，不是每次额外调用一个模型通读所有工具记录。压缩发生时，新的输入替换旧的工作输入，因此不会“加了摘要，又把全部旧工具结果原样带回来”。
>
> 我也不会声称完全没有重复：摘要里说已经读过某篇文档，同时保留那次读取的详细结果，是进度和证据的重叠。真正需要控制的是重复塞入全部旧过程、丢掉用户纠正，以及工具调用和结果失去对应关系。当前 handoff 仍会累积，旧工具的细节也可能被移出上下文；需要精确引用时必须重新读取，不能因为数据库里有记录就假设模型仍然知道。

这段口述描述当前文字／工具 Agent 的实现，不是新的实验结论。语音共享 Run、工具和持久化合同，但 Realtime 的会话输入和媒体截断还有自己的协议，接第 18 章。下文的论文任务、消息编号、工具编号及预算数字均会标明教学用途。

### 6.2 先区分 Chat、Run、模型请求和存档

贯穿例子：用户一直在同一个 Chat 里讨论毕业论文，这次说：“帮我检查第三章的几处引用，查一下原始资料。先给修改建议，不要直接修改论文。”Agent 读取论文、检索和阅读资料，期间用户又说：“只参考官方文档，别引用论坛。”

| 对象 | 在这个例子中的含义 | 是否等于本次模型输入 |
| --- | --- | --- |
| Chat | 持续讨论毕业论文的聊天 | 否；历史可能已有摘要，也不会带入全部内部执行记录 |
| Run | 执行“检查第三章引用”这次目标的过程 | 否；一个 Run 可能有多次模型调用、工具执行和审批 |
| 一次模型请求 | 让模型决定下一步、读取工具结果或生成回答的一次调用 | 是本次实际需要核算的输入范围 |
| `run_items` 等持久记录 | 保存实际执行过程、消息、结果及状态 | 否；保存下来不等于每次全部发送 |
| `active.data.input` | 当前 Run 为后续模型调用维护的工作输入 | 最接近模型输入，但图片引用、认知内部对象等还需要转换 |

因此，“这次对话调用了二十次工具”可以是一个 Run 的二十个执行步骤；它不是二十个 Chat，也不代表下一次用户发消息就会重新带上二十份工具结果。历史 Chat 投影读取用户／助手消息；`getAssistantMessages` 只读取完成的 `assistant_message` 表示，没有把过去所有工具 Item 一起回放。[聊天历史投影](../../../src/main/agent/chatContextService.ts)、[助手消息读取](../../../src/main/agent/runRepository.ts)。

### 6.3 第一次请求究竟按什么内容拼装

`AgentRuntime.#modelRequest` 的请求可以简化成下面的结构。这里只省略与本问题无关的配置，不表示所有 Provider 的外部 JSON 字段完全相同：

```text
ModelRequest
├─ instructions
│  ├─ TEXT_AGENT_BASE_INSTRUCTIONS：基础行为规则
│  ├─ modelTimeInstructions：当前时间
│  ├─ executionInstructions：本次执行模式与审批约束
│  ├─ CharacterContextCompiler：这个 Run 的 Persona 快照
│  └─ additionalInstructions：额外指令
├─ input
│  ├─ 同一个 Chat 已有的历史摘要（如果存在）
│  ├─ 摘要尚未覆盖的历史消息
│  ├─ 本轮选中的 Cognition / Memory 背景（如果存在）
│  └─ 当前用户输入及其附件表示
└─ toolNamespaces / allowedTools 等
   └─ 按执行范围提供的工具声明与调用限制
```

**Instructions 不是历史聊天。** Persona 包括身份、背景、动机、价值观、说话方式、称呼方式、主动性风格、知识边界和禁用表达，使用本次 Run 冻结的快照。角色风格不能推翻事实、工具执行范围或审批要求。当前时间则在组装请求时生成。[角色编译](../../../src/main/persona/characterContext.ts)。

**Input 也不是所有 Memory 的拼接。** 本轮背景由 Cognition 准备，可能包括当前事项和选中的长期记忆证据。记忆材料会说明适用状态、被纠正或未确定的状态、记录／发生／有效时间、来源类型和覆盖缺口。宿主还保存 memoryId、revisionId、来源引用等用于追溯；内部对象在发送前会转换，不是把带所有元数据的对象再原样重复给模型。[认知背景转换](../../../src/main/agent/cognitionContext.ts)、[记忆证据文本](../../../src/main/agent/memoryContext.ts)。

在论文例子中，模型可能读到的是：

```text
历史摘要：用户正在写毕业论文，第三章讨论 Agent 记忆系统……
近期对话：用户说相关工作已写完，准备检查引用。
本轮背景：当前事项是论文；选中的记忆说明用户希望保留自己的行文风格。
当前请求：检查第三章引用，先给建议，不直接修改论文。
```

这些背景是教学示例，不是声称每次都会检索到这些内容。普通 `prepareTurn` 读取已提交的认知状态，不要求先等后台重新分析完；背景可能稍旧，当前用户原话仍必须进入请求。附加背景按实际请求的剩余空间分配，不因数据库里有材料就无限装入。

**工具声明同样占输入。** 模型不仅需要知道过去发生什么，还需要知道现在允许调用什么工具、参数怎样写。实际预算检查包含 Provider 适配后的请求，不能只用聊天正文的字数判断是否超限。[请求组装与初始输入](../../../src/main/agent/agentRuntime.ts)中的入口分别是 `#modelRequest` 和 `initialCheckpoint`。

### 6.4 同一个 Run 中，工具结果与用户补充怎样进入下一次请求

以下 C1、C2 是教学调用编号，R1、R2 是各自结果；“读取论文”等描述不是伪造的已注册工具名：

```text
请求 1：历史 + 本轮背景 + 当前用户请求
模型提出 C1：读取论文第三章
宿主执行，得到 R1：实际读取内容与状态

请求 2：历史 + 本轮背景 + 当前用户请求 + C1 + R1
模型提出 C2：查找引用对应的官方资料
宿主执行，得到 R2：实际返回的材料

用户追加：只参考官方文档，别引用论坛

请求 3：此前工作输入 + C2 + R2 + 用户追加要求
```

没有触发压缩时，工作输入随执行增长。具体是模型返回的可回放输出加入 `active.data.input`，工具完成后再追加 `function_call_output`；结果用 `call_id` 对应原调用。`hasToolOutput` 防止同一个调用的结果重复追加。这里的可回放输出会过滤 `reasoning` 和 `compaction` 类型，不能把它讲成“完整保留并回传模型所有内部思考”。

工具完成还会把“工具名称 + `result.summary`”记入 `handoff.currentProgress`。这是在维护内部交接状态；**此刻不等于向模型输入又追加了一份 handoff 消息。** 成功的计划更新则写入独立的 `currentPlan`，不会仅靠一句工具摘要表示最新计划。

用户补充通过 `#mergeSteering` 进入两处：原始消息追加到当前 `input`；要求同时追加到 handoff 的 `constraints`，并更新 `latestUserInput`。只记摘要而丢掉用户最新原话会影响准确理解，所以压缩时也会保留初始请求和不同于初始请求的最新补充。

每次模型调用前的顺序如下：

```text
合并尚未纳入的用户补充，记下 inputRevision
    ↓
移除需要刷新的普通 Cognition 背景
    ↓
检查当前 Run 的输入是否需要压缩
    ↓
按剩余预算刷新本轮 Cognition 背景
    ↓
转换图片引用等内部表示，构造实际模型请求
    ↓
Provider 检查完整请求，再发送
```

其中每个异步准备阶段都会复查输入版本。假设准备背景时用户又补了一句“只检查第一处引用”，版本已经变化，宿主就重新准备，避免把旧请求多发一次。

Cognition 刷新还会比较 `cognitionInputRevision`：同一版用户输入已经准备过，不会因为又执行了一次工具就必然再做一次普通背景准备。刷新时去掉旧的普通背景，新的背景放到工作输入前部；主动选择已经依赖的证据另有保留规则。因此初始排列与刷新后的排列可以不同，不能把第一次的排列顺序当成始终不变的模板。[主执行循环与工具结果](../../../src/main/agent/agentRuntime.ts)中的入口为 `#modelTurn`、`completedToolState`、`#mergeSteering`、`#removeStaleCognitionContext` 和 `#refreshCognitionContext`。

### 6.5 Handoff 什么时候维护，什么时候真正给模型看

这里的 `HandoffSummary` 只有四组字段，完整计划独立保存在 `currentPlan`：

| 字段 | 当前主要写入时机 | 论文例子中的含义 |
| --- | --- | --- |
| `currentProgress` | 工具返回；用户补充信息等执行进展到达 | 某个读取工具返回了第三章；某次查询失败也可能有对应简述 |
| `decisions` | 工具审批通过、拒绝或取消等决定 | 用户是否允许执行待审批的动作 |
| `constraints` | 用户在 Run 中追加要求 | “只参考官方文档，别引用论坛” |
| `nextSteps` | 等待审批、执行待处理工具或等待用户补充 | 当前正在等待什么；处理完成后相应清空 |

不要把 `decisions` 夸大成模型自动提炼的全部技术决策，也不要把每条 `currentProgress` 都视为成功证明。当前程序主要把真实结果的简述拼进去，是否成功仍要看原结果状态。`nextSteps` 也不是另一份自动生成的完整计划。[字段定义](../../../src/main/agent/contextCompiler.ts)、[状态写入点](../../../src/main/agent/agentRuntime.ts)。

可以把它的生命周期分成三个阶段：

1. **Run 刚开始。** 四个数组初始化为空，初始 `input` 没有 handoff 消息。
2. **尚未触发压缩。** 工具和用户事件持续更新 handoff 对象；模型主要读取原有消息及实际调用结果。短任务可能从头到尾都不通过 handoff 消息读取这份对象。
3. **Run 发生压缩。** `ContextCompiler` 把当前对象转换成一条 developer 消息，标题为 `Context handoff:`，与保留材料一起替换旧工作输入。后续请求会带着这条消息继续执行。

第一次压缩之后，后台维护的 handoff 对象仍会更新，已经注入的那条消息不会因为每次字段更新就自动改写。模型通过后来追加的工具记录看到新进展；再次压缩时，再按最新对象生成一份新的 handoff。**不是每个工具后多塞一份，也不是只有崩溃恢复时才用。**

本章 1.4 的 Cognition→Memory “持久 handoff”是另一件事：它负责把带来源的材料可靠交给记忆形成流程。这里的 `HandoffSummary` 是 Run 输入整理用的执行摘要；二者名称相同，不能把事务入队确认和上下文压缩说成同一机制。

### 6.6 自动压缩的时机：按完整请求预算，而不是按 Item 数量

当前不是每十次工具、每一分钟或每次聊天结束就固定压缩。主要判断是：**下一次实际请求是否还能放进当前输入预算。** 新 Run 准备 Chat 历史时检查一次；运行中的每次模型调用前再检查当前工作输入；Provider 真正发送前还会检查最终请求。

预算计算取有效约束的最小值：

```text
输入预算 = min(
  项目输入上限,
  模型的 effectiveInputTokens（若提供）,
  模型的 maxPromptTokens（若提供）,
  模型总上下文 - 本次预留输出（若提供总上下文）
)
```

源码中的 `MAX_MODEL_INPUT_TOKENS = 258000` 注释明确归于 2026-09-15 的用户要求；`INPUT_BUDGET_ESTIMATE_RATIO = 0.9` 是本地估算余量。前者不是所有模型共有的协议窗口，后者不是经过证明的通用最优压缩比例。

例如仅为教学，假定项目上限为 258000、模型总窗口为 128000、预留输出为 8000，且没有其他更低约束，那么输入预算是 120000，而不是 258000。若估算已达到这个预算的 90% 附近，系统会进一步尝试精确计数；精确结果仍在预算内，就不因“碰到 90%”本身强制压缩。

当前 OpenAI 适配器会对实际请求中的输入、instructions、工具声明等计数。发送前要求精确计数，支持时调用 `responses.inputTokens.count`，同一计数载荷已有完成结果时可以复用；若该端点不支持，就使用受限制的保守估算。存在无法可靠估算的输入，或估算仍过大时会报错，不能假装未知附件免费。这里描述本地适配器的行为，不保证任意 OpenAI-compatible 服务都提供这个端点。[预算实现](../../../src/main/providers/inputBudget.ts)、[Provider 计数和发送](../../../src/main/providers/openaiModelProvider.ts)。

若准备后仍收到 `PROVIDER.CONTEXT_LIMIT_EXCEEDED`，运行时会尝试一次受控的强制整理：符合首请求条件时先尝试持久 Chat 历史整理，否则或未改变时尝试 Run 整理。只有输入确实变化或用户输入版本变化等条件成立，才再次请求。`forcedCompactionAttempted` 防止同一失败链无限重试；一次模型请求成功后会重置，所以也不是“整个 Run 一生只能压缩一次”。

### 6.7 第一种压缩：模型总结旧 Chat 历史，并保存覆盖边界

同一个 Chat 长期积累很多消息时，`ChatContextService.prepare` 会选择较早的完整执行片段，调用模型生成摘要。它不是固定保留最后 N 条：选多少要看预算，分组会尽量保持同一 Run 的聊天消息片段完整；摘要请求本身也要放得进预算，因此可能分批处理。

下面的 M1–M40 和边界 M30 仅为教学示意，M30 假设恰好是一个被选中的完整片段边界：

```text
整理前：M1 … M30 + M31 … M40

摘要请求：已有历史摘要（如果有）+ 本次纳入的较早消息
模型返回：新摘要 S

整理后：S（覆盖到 M30）+ M31 … M40
```

摘要要求保留目标、约束、完成动作、决定、未解决事项和用户纠正，不能把助手“准备做什么”的话总结成已经完成。但这个输入来自 Chat 投影，**不是另外扫描所有历史工具输出并逐条写进摘要**；遗漏和语义失真仍是需要验证的风险。

保存的快照包含 `summary`、`generation`、`coveredThroughMessageId`、`coveredThroughCreatedAt`、格式版本及更新时间等。查询历史时按覆盖边界读取后续消息，所以不会生成“摘要 S + M1 到 M40 全部原文”这种机械重复。

异步提交要检查版本。假设开始总结时读取到 generation 4，模型返回前其他合法操作已把摘要推进到 generation 5，这次提交的 `expectedGeneration=4` 就不能覆盖新快照。仓储在事务中检查版本与边界，再保存新摘要；模型网络等待不包含在这段数据库事务里。检查失败时会明确要求重试，不静默覆盖。

旧消息仍在数据库和聊天历史里。变化的是后续模型输入的投影，不是把用户过去聊过的话删除。[摘要准备及分批](../../../src/main/agent/chatContextService.ts)、[摘要边界与事务提交](../../../src/main/chat/chatRepository.ts)。

### 6.8 第二种压缩：宿主重建当前 Run 输入，并让 handoff 接替较早过程

正在执行的 Run 不会在每次超限时都额外请求模型通读所有工具结果。`ContextCompiler.compile` 在预算触发或强制整理时，按现有状态构造下面的输入；没有触发则复制原工作输入继续使用：

```text
[
  当前 handoff 的 developer 消息,
  已有 Chat 历史摘要（如果存在）,
  保留的 Cognition 背景,
  保留的工具调用／结果及相关图片,
  当前完整计划（如果有）,
  本次 Run 原始用户请求,
  最新用户补充（与原始请求不同时）
]
```

这里有三组选择规则值得单独讲清楚。

**工具不是随便截断成最后几条。** `retainedToolContextInputs` 从结果向前匹配相同 `call_id` 的调用，成对保留；主要保留最近一次实际工具调用与结果、最近一次失败／拒绝／取消的结果。如果最新一次是 `image.inspect`，还保留最近一次其他工具结果。成功图片检查在当前输入里确实有对应图片引用时，保留相应调用、结果和图片，并按来源去重；不是仅凭缓存里有图片就认定模型仍能看到。

**最新状态替代重复状态过程。** `plan.update` 和结构化用户询问等宿主状态调用不按普通工具结果保留；完整计划通过 `currentPlan` 表达。普通 Cognition 背景保留最近一份；带已选行为依据的背景有独立保留规则，不能简单当作旧闲聊丢掉。当前请求与最新请求相同则只留一次，不同则都保留。

**替换工作输入，不重建成全部历史。** `#applyCompaction` 把新数组赋给 `active.data.input`，清掉不再适合新输入的旧 usage 信息，并保存 checkpoint。输入状态变化与“字节一定减少”也分开：代码在字节确实减少时才记录对应的 `context_compaction` Item，不把每次重排都宣称节省了空间。之后继续执行时，只在这份新工作输入后追加新模型输出和新工具结果。

一次完整的输入变化可以写成：

```text
压缩前：历史 + 背景 + 原始请求 + C1/R1 … C20/R20 + 最新补充
压缩后：handoff + 已有 Chat 摘要 + 保留背景 + 选中调用/结果 + 计划 + 用户要求
继续后：压缩后的输入 + C21/R21 + C22/R22
再压缩：按最新状态重新构造一份 handoff 和选中材料
```

不会生成“旧 handoff + 新 handoff + 更新的 handoff + 全部原始工具记录”的无限堆叠。源码入口为 [ContextCompiler](../../../src/main/agent/contextCompiler.ts) 的 `#compact`、`retainedToolContextInputs`，以及 [AgentRuntime](../../../src/main/agent/agentRuntime.ts) 的 `#compact`、`#applyCompaction`。

### 6.9 会不会重叠：必须区分跨请求重复、机械重复和语义重叠

| 现象 | 当前是否发生 | 为什么／如何处理 |
| --- | --- | --- |
| 同一背景同时出现在连续两次模型请求 | 会 | 下一次仍需已有背景；不是单次输入里装了两份，也不能因此断言没有重复处理成本 |
| 压缩后又把全部旧工具记录从数据库加回来 | 当前这条路径不会这样做 | 工作输入被替换，后续追加新的执行结果 |
| 一份工具结果因重复完成回调被追加两次 | 有明确防护 | 按 `call_id` 检查已有结果；不是仅按文本相似度猜重复 |
| 最近结果同时满足“最近调用”和“最近失败” | 可能满足，但不留两份 | 保留索引用 Set 去重，再按原顺序输出 |
| Chat 摘要与其已覆盖的原始消息同时全量回放 | 边界查询避免 | 只读取覆盖边界之后的消息 |
| handoff 说“已读取文档 A”，同时留着读取 A 的详细结果 | 会 | 前者表示进度，后者提供原文和状态，两者有语义重叠 |
| 用户最新补充同时出现在 `constraints` 和用户原话 | 会 | 要求摘要与用户原始表达各有作用，没有全局语义去重器 |

最容易被追问的是最后两项。回答不能是“完全没有重复”，而应说：“我去掉重复携带的整段旧过程，但允许必要的进度摘要与可核对证据重叠。”

例如 handoff 写“已找到官方文档关于有效期的说明”，只能证明执行交接里有这条简述。最终回答需要具体适用范围和原文时，保留的工具结果仍有价值。反过来，如果这份详细结果已经被移出输入，只剩一句“读过文档”，就不能假装模型还记得全部数字。需要重新读取，而不是靠摘要补造。

### 6.10 接着聊、开新 Chat、崩溃恢复：什么会继承

| 对象 | 主要作用 | 后续何时使用 |
| --- | --- | --- |
| 当前 Run 工作输入 | 让这次执行继续 | 同一 Run 下一次模型调用 |
| `HandoffSummary` | 较早执行过程被移出后，提供进展和约束 | 当前 Run 压缩时注入，随后随工作输入继续使用 |
| Chat 历史摘要 | 让长聊天可继续加载 | 同一 Chat 的后续 Run 准备历史时 |
| Checkpoint | 恢复未完成 Run 的执行状态 | 恢复时读取当前输入、计划、待执行工具、待回答问题等 |
| 长期 Memory | 按需使用跨任务、跨聊天的事实与经历 | 被检索并选中时，不是整个库自动继承 |

Checkpoint 包含 `input`、`handoff`、`currentPlan`、原始／最新用户输入、`pendingTool`、`pendingInput`、预算和恢复相关状态等。它比一份摘要完整，保存的是“程序如何继续”的信息；本身不负责压缩，也不会整个序列化后发给模型。[Checkpoint 定义](../../../src/main/agent/runtimeCheckpoint.ts)。

在论文例子中，可以分别回答三个追问：

- **任务还没结束，继续下一次模型调用。** 用当前 Run 的工作输入；已压缩就从压缩后的版本继续，不恢复成原始全集。
- **这次任务结束，用户在同一 Chat 说“再检查第四章”。** 新 Run 重新准备这个 Chat 的摘要和未覆盖消息，不把上一次整个 checkpoint、handoff 和所有工具结果原样继承。重要结论若未进入可用历史或证据，仍需再读。
- **用户新建另一个 Chat 说“继续论文”。** 不自动复制旧 Chat 历史；可能经适用的 Cognition／Memory 找回相关背景，材料不足时需要检索或澄清。

这里的运行时 checkpoint 也与 SQLite 的 WAL checkpoint 无关，不能把数据库日志整理讲成 Agent 上下文摘要。

### 6.11 用一次论文检查把全部机制串起来

以下是教学执行时序，不是一次新增实测，也不以 C20 代表固定的压缩次数门槛：

| 时刻 | 用户／系统发生什么 | 模型实际获得什么，哪些状态另外保存 |
| --- | --- | --- |
| t0 | 用户在已有 Chat 请求检查第三章引用，暂不修改论文 | 组装规则、Persona、允许工具、Chat 历史、本轮背景和原始请求；handoff 为空 |
| t1 | 模型要求读取论文，宿主得到 C1/R1 | 工作输入追加调用和结果；handoff 对象另记工具简述，尚未额外注入消息 |
| t2 | 检索、阅读多份资料，积累 C2/R2 等 | 每步使用当前工作输入；尚有预算时不固定按条数整理 |
| t3 | 用户补充“只参考官方文档” | 原话加入 input，同时进入 handoff.constraints；若准备请求期间收到，则检查版本并重新准备 |
| t4 | 下一次实际请求检查发现预算不足 | 由 ContextCompiler 选择材料，生成一条 handoff，保留最新请求、计划和必要调用结果，替换旧工作输入 |
| t5 | 模型继续核对某个具体数字，但对应旧网页正文已不在输入 | 需要重新读取真实材料；不能只根据“已经看过”就编数字 |
| t6 | 新的 C21/R21 到达 | 追加到压缩后的输入，并更新内部 handoff；不会重新加载 C1–C20 全部结果 |
| t7 | 模型根据实际材料完成修改建议 | 保存本次用户／助手消息与真实执行记录；“建议完成”不等于已经修改文件 |
| t8 | 同一 Chat 开始检查第四章，累计聊天历史本身已超预算 | ChatContextService 调用模型总结较早消息，事务保存摘要和覆盖边界，再用摘要、未覆盖消息及新请求启动新 Run |
| t9 | 若未完成 Run 在某个工具边界中断后恢复 | 从 checkpoint 恢复执行状态，仍按实际工具身份与结果继续；摘要本身不授权重复执行已完成动作 |

这条时序解释了两种压缩的配合：Chat 摘要管理跨 Run 的聊天历史，Run 整理管理当前任务中不断积累的执行输入。两种机制也可能在同一任务准备期间先后发生，但不能把它们的产物都称为“模型自动总结了一遍全部记录”。

### 6.12 当前限制、追问短答与掌握验收

当前实现有四个需要主动说明的边界：

1. **Handoff 本身还会增长。** `currentProgress` 和 `constraints` 主要追加，没有在 Run 整理时自动交给模型做第二次语义归并。重复工具摘要、多次改口可能仍占空间；“交接信息更短”不是永远成立的保证。
2. **Run 压缩可能移除有用细节。** 它保留已有 Chat 摘要，但不会在这里把所有被移除的普通聊天原文先生成一份新摘要。旧工具内容也只按既有规则保留，不能声称已经实现逐条相关性最优选择。
3. **必要内容也可能过大。** 原始用户请求、保留图片或工具结果本身超预算时，整理不一定解决，最终应明确失败。Checkpoint 里存得下与模型窗口装得下是两回事。
4. **摘要不是事实正确性的保证。** Chat 摘要可能漏写或误解；handoff 的工具简述也不能替代原回执。这个章节没有给出压缩后的事实保真率、长期任务成功率或延迟提升实测。

若被问怎样继续优化，可以提出待验证方案：先定位是重复进度、过大结果还是缺少关键证据，再比较按任务／工具身份更新进度、对大结果按需读取、保留明确事实引用等改动。用相同任务和原始执行记录比较事实保留、纠错约束、后续任务完成、输入量、重新读取次数与等待；不能只因为摘要更短就宣布更好。这些是后续实验方向，本次没有更改生产机制。

追问时可以直接这样回答：

- **Handoff 是不是每次模型调用都重新生成？** 内部状态持续更新，但主要在 Run 压缩时转换成一条消息；之后会保留，下一次压缩再重建，不是每步额外模型总结。
- **自动压缩是不是 Item 到某个数量就触发？** 主要按完整请求预算判断，工具声明和附件也要算；压缩失败还有受控恢复，不是无限重试。
- **摘要和工具会不会重复？** 不重复携带全部旧工具过程，但摘要与必要详细结果有语义重叠；调用结果按身份、历史消息按覆盖边界避免机械重复。
- **新一轮聊天还带着刚才所有工具吗？** 同一 Run 继续使用当前工作输入；新 Run 重新准备 Chat 历史，不继承旧 checkpoint 全集；新 Chat 也不会自动复制旧聊天。
- **数据库记录都还在，为什么模型会忘？** 存储保证可追溯，模型本次只能使用实际供给的内容。被移出上下文的细节需要重新读取，不能靠“以前看过”补全。

学完后的验收是能独立手推下面这些情境，而不是只背名词。这是学习验收清单，不是声称所有情境已在本次运行测试：

| 验收题 | 能算掌握的回答 |
| --- | --- |
| 画出第一次请求 | 分开 instructions、input、工具声明；说出 Persona 快照、Chat 边界、本轮证据、当前用户输入的位置，并说明内部元数据不全部发送 |
| 一个工具执行完后，第二次请求多什么 | 能写出匹配的 call_id、调用和结果，说明 input 追加与 handoff 对象更新是两件事 |
| 用户补充要求恰好发生在异步上下文准备中 | 能说明原话、约束、latestUserInput 和 inputRevision 的作用，不能让旧准备直接发出 |
| 任务很短，从未压缩 | 能说明 handoff 已维护但未必被注入，不声称每步都调用摘要模型 |
| 任务很多工具，输入超预算 | 能列出重建后的输入，说明调用／结果成对保留、当前计划、原始与最新要求、Cognition 背景和图片规则 |
| 问“为什么摘要里说读过 A，下面还有 A 的结果” | 能区分进度摘要与细节证据，承认语义重叠，不误判为整段历史重复回放 |
| 已有 S 覆盖 M30，下一轮加载历史 | 能写出 S + M31 之后消息，并说明原消息没有被删除、版本检查防止旧摘要覆盖新摘要 |
| 同 Chat 新 Run、全新 Chat、崩溃恢复分别怎么处理 | 能分别说出历史投影、按需记忆和 checkpoint，不把三种继承关系混用 |
| 压缩后仍无法放进窗口 | 承认必要内容可能过大，说明受控整理和明确失败，不能承诺无限压缩继续运行 |
| 面试官要求压缩效果的数据 | 能指向已存在证据的实际测量对象；本节没有测量的质量／速度收益明确说未测，不编造提升数字 |
