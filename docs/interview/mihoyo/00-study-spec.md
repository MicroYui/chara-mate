# SDD：面试研习需求、完整大纲与学习安排

版本：2026-10-30；在第 17–19 章机制复盘之上，新增第 20 章四条优化叙事。负责范围：`docs/interview/mihoyo/` 与 STATUS 中的文档工作包。这里规定整套材料应当达到的深度、学习顺序、实际产物和验收方式；它不修改产品合同，也不新增运行时功能。

## 1. 目标：面对连续追问仍能把事情讲完整

用户要求准备米哈游游戏 Agent 方向面试。目标能力是：从玩家的一次输入或环境事件开始，解释系统如何感知、维持状态、寻找证据、形成计划、调用工具、执行动作、处理变化，再把结果变成下一次可用的经历。

“完整”不仅指模块齐全，还包括为什么需要这些模块、实际怎么做、比较过什么、得到什么结果、付出什么代价，以及证据不足时还能说到哪里。记忆检索只是这个标准的一例；运行时、认知、工具、语音、反思、数据闭环、游戏设计和研究讲解全部采用相同要求。

最终应能回答三种不同问题：

1. **实现题**：代码怎样工作？指出对象、函数、读写顺序、异步边界、事务和失败恢复。
2. **研究题**：为什么这样选？说明基线、候选、数据、比较方法、指标、结果、失败和限制。
3. **设计题**：尚未实现的能力怎样建设？给出合同、负责模块、实施顺序和验证办法，不虚构结果。

## 3. 每章必须满足的深度

### 3.1 从问题讲到执行

不能只有“采用向量检索”“加入反思”“维护状态机”。实现章节至少要回答：

- 具体输入是什么，哪个模块拥有它。
- 哪些对象是稳定身份，哪些是可变状态或不可变修订。
- 一条正常路径按什么顺序读取、等待和写入。
- 哪一步可能同时遇到新输入、删除、崩溃或重复回执。
- 什么操作可以重试，什么结果需要查询，什么必须保留未知。
- 玩家最终看到什么；后端成功与实际曝光有没有差别。

同样要求应用于认知：不能只列 Claim、Intent、Attention；要解释同一事件如何改变它们、分析何时提交、旧行动何时失效，以及无关变化为什么不应该取消合法行动。

### 3.2 从选项讲到决定

每个有实际比较记录的主题都应讲清“问题—候选—公平条件—指标—结果—取舍”。数字必须带含义，例如：

> 在 28 个测试问题中，两种模型配置产生的候选都包含必要证据；经过同一个证据选择流程后，两者均有 27 个问题选全了预先标注的证据。

这句话说明测的是证据选择，没有把它说成最终答案正确率。模型大小与维度、原始分母、标签歧义、资源成本随后再解释。所有分数先解释测量对象，再说明结果，避免用内部术语代替完整含义。

没有实验结果的主题，必须给可执行的比较方案。不能为了让章节看起来完整而编造咖啡馆吞吐、玩家满意度或训练收益。

研究章节由作者先读一手材料，正文讲清原问题、机制、研究结果、项目启发、实际承接与尚未验证的推论。论文链接只作来源，不把“自行读原文”当完成本章的前置条件。第一人称叙述须与真实经历一致；外部研究结果不替代项目实验。

### 3.3 从结论讲到边界

每个重要结论至少准备一个反例。比如“版本检查能防止旧行动”还要说明已发生效果不能回滚；“记忆保留历史”还要区分历史真实与被纠正错误；“小模型足够”还要说明只在当前任务集和后续流程中得到支持。

必要技术词可以使用，但首次出现要解释它在本系统中的含义。代码标识保留原名，方便查找；普通中文叙述不用一串内部缩写代替因果关系。

## 5. 学习方式：每单元都要读、画、算、讲

每个单元分成四轮，不按“今天读完几页”计算完成：

1. **建立问题**：先看场景，独立猜测故障发生在哪里。
2. **跟代码与记录**：沿函数入口查读写，沿 Decision 查比较过程；不要从文件第一行机械读到最后一行。
3. **形成产物**：画时序、填写状态表、计算指标或写实验卡。
4. **闭卷追问**：换一个名字、时间、并发顺序或故障，检查自己能否迁移解释。

建议每个普通单元安排两次 60–90 分钟学习；S4、S5、S8 可增加一次推演。这里只是排程建议，实际以产物和验收为准。已有基础可以缩短阅读，但不能省略独立推演；没有基础就分多次完成。

## 6. 十一个学习单元的具体安排

### S1：项目定位与统一执行

**要解决的问题：**为什么不能直接把一次模型请求当成整个 Agent？统一到底统一哪些东西？

先读 01，再读 02。代码看 `agentRuntime.ts` 中运行开始、执行循环、工具调用与新输入处理，随后看 `runEventService.ts` 与 `runRepository.ts` 的事件保存。实验读 `harness-loop.md` 的规划和最终联合确认，区分不同成功定义。

交付：90 秒项目介绍；Run/Item/Event 图；两工具任务在四个时刻收到取消的处理表；一段按需规划的选型解释。用 Q01–Q08 自测，对应 A01、A02。退出条件是能说明请求、任务、真实效果和界面投射的不同身份，而不是背一张架构图。

### S2：认知、注意与角色连续性

**要解决的问题：**事件怎样进入，为什么唤醒，旧分析未返回时怎样接收新输入，状态结果和实际动作分别何时失效？

分六轮学习第 03 章，每轮都先看正文中的完整例子，再用源码定位复核；不要求先自己读懂整个模块。

1. **入口与触发（第 1–5 节）**：沿 Main 装配到 ActivityCaptureCoordinator、CognitionRuntime.observeActivity / observeRun，再到 Service.ingest。画出用户控制与用户原话、像素通知与图片材料的两组区别，填八类输入的触发表。
2. **调度与模型（第 6–9 节）**：解释 nextWakeAt 的最早时间规则、Scheduler 的检查合并与 Service 的单个在途 Promise。列出实际给模型的材料和宿主未提供的材料；说明 prepareTurn 为什么不等待分类模型。
3. **事务与并发（第 10–19 节）**：手推普通窗口变化、用户接管、检索期间同代际新话语三条时间线。每个 await 后写出检查对象、期望值、失败后续；区分 analyzing Attempt 与 dispatched Run。
4. **失败恢复与迁移（第 20–22 节）**：做四处退出恢复表与失败期间新输入案例，再迁移到咖啡馆，补出世界权威、多玩家路由和发言竞争。
5. **理论、取舍与证据（第 23–26 节）**：把研究启发接回具体机制，复盘 Appraisal 的四组故事、16 个检查点与成本；选择一项尚未做的优化，写公平比较方案和不能宣称的结果。
6. **Chat 归属与规模变化（第 27–29 节）**：区分单个 Cognition 服务、多条 Situation、一个当前注意指针和多个 Chat；沿 Overleaf→查资料→B 站→返回解释背景注入、安静与主动接话。再把输入规模放大到多人 NPC，先筛选、按语义合并、检查任务依赖，最后计算模型容量和公平排队。

交付：入口图、触发表、三条时间线、恢复表、NPC 迁移说明，另附一次已做实验的复盘与一次未做实验的方案。用 Q09–Q16 自测，按 A03 的五项评分和关键错误检查验收。退出条件不再是能说“纠正要取消”：要能具体说明谁发控制、谁保存新来源、旧请求何时结束、下一轮何时开始、哪个事务能提交、哪个动作仍不能执行。

第六轮追加两份必交材料：一张把物理焦点、Situation、Intent、Chat 和实际发言分开记录的连续案例表；一份包含订阅、关键事件保留、在途失效检查与容量演算的 NPC 方案。交由 A03 追加验收，并与 A08、A09、A13 联合检查。不能把当前 persona 级背景投影说成已经实现按当前问题自动路由，也不能把拟建的服务端调度说成现有能力。

字段与实际注入另读 [第 15 章](15-context-activity-retrieval-walkthrough.md) 第 2 节：把数据库完整对象与普通回答实际收到的字段分开，标出 developer 背景的位置、输入代次刷新和宿主／模型各自的更新时机。

Persona 另读 [第 16 章](16-npc-persona-hints-and-evaluation.md) 第 1、4 节：从 13 个设定字段、3 个版本字段、3 张表讲到 Run 快照和实际编译，再复盘 4 个角色、12 个案例的比较。交付“设定缺失”与“没有固定台词”的区别表，以及同一人物在闲聊、战斗、悲伤场景中的合理变化。不得声称现有禁语字段就是 OOC 硬拦截器。

一面追加到 S2 的学习任务：读[第 19 章第 1–6 节](19-proactivity-and-product-feedback.md)，手算三档频率、连续负反馈与默认免打扰；给 Overleaf 连续场景标出分析、准入、曝光、回应四个时刻，说明当前占用状态并不代表真正的专注度。产物是一张当前策略表与一份按真实任务边界评价的改进实验，交 A03／A08／A11。

### S3：从用户原话到长期记忆与后续修订

**要解决的问题：**一句话进入哪些函数，哪些字段由谁填写，最终变成哪些数据库行；模型、写库、索引和用户回应的时间边界分别在哪里？

以第 04 章的“替林岚点咖啡”为共同输入，分五轮学习。建议分三至四次完成，每次结束都留下独立产物，不用先通读所有源文件。

1. **来源与模型输入（第 1–6 节）**：画回答模型调用空参数工具、宿主读取完成消息、主要／上下文来源、规范原文入队、来源窗口、第一次提议及旧记忆比较。分别解释三种分块，不把形成片段当成向量块。
2. **提议与字段（第 7–10 节）**：自己写出两条偏好的内部提议，标原输入、模型、宿主、派生值四类来源。计算引文区间，解释 owner 与主体、type 与 kind、用户陈述与置信度数值的区别。给同一输入换三种旧库状态，决定 create、revise 或 support。
3. **事务与可用性（第 11–15 节）**：逐步写出事务内的表变更，核对两条记忆、两条版本、两段引文、四条实体角色关系和两个待编码任务。再画后台分块、向量提交与最终回应，解释哪些索引从正文构建、哪些字段仅保存或参与过滤。
4. **修订与并发（第 16–18 节）**：手推明确纠错、真实口味变化、无解释手动编辑；在模型等待、片段提交、最终完成、编码返回四处插入新输入或崩溃，说明保留什么、重读什么、如何续跑。
5. **长期维护与取舍（第 19–27 节）**：复盘早期形成规则、巩固实验、独立来源、派生失效、原文保留与 WAL/FULL 选择。把已有结果、实现局限和游戏迁移方案分别讲清，不用概念名替代因果解释。

交付：完整调用图、两条结构化提议、字段归属表、数据库核账表、事务与索引时序、修订图和故障表。用 Q17–Q24 自测，按 A04 验收；向 A05 交接已经保存且索引状态明确的记录，向 A07 交接恢复边界。退出条件是能够从一句新原话连续讲到保存成功的回执，并在随机故障发生后重新推导结果，而不是只会画 Memory 与 Revision 两个方框。

一面追加到 S3 的学习任务：读[第 17 章第 1–5 节](17-memory-control-and-retrieval-evolution.md)，画出普通 record、认知后台交接和普通 search 三条链，标出模型选择与宿主保证；推演改期时形成／索引未结束的情况。产物为职责表、漏记／漏查诊断树与一张只改变处理入口的实验卡，交 A04／A06／A11。

### S4：索引、向量、选择与性能

**要解决的问题：**为什么选这些索引和模型？比较究竟测了什么？
