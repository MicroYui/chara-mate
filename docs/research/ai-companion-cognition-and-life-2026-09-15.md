# CharaMate：认知启发、情境理解与角色自主生活研究

> 研究日期：2026-09-15。本文是研究与实施建议，不是已完成的实现或生产 Decision Record。
>
> 当前用户方向：CharaMate 的核心是 AI 陪伴。角色应理解用户、保持经历连续性，并能自主生活、活动和布置领地，减少用户逐项安排、选择和确认的负担。用户仍可以自然参与、打断、纠正和撤销。
>
> 最新范围：桌面感知必须细化到软件启动与使用、当前对象和可见内容、键鼠操作类型与节奏，不能停留在前台应用变化。本轮实验模型指定为 `gpt-6-astra`；单请求输入不得超过用户明确要求的 **258,000 Token**。文本回应策略 pilot 已完成，结果与调用边界见[回应策略 Decision](../benchmarks/COMPANION-RESPONSE-STRATEGY.md)；这不代表完整桌面感知或长期陪伴效果已经得到验证。
>
> 实现边界：本文研究本地 Electron 产品应如何落地；在线社区、跨角色与大规模运行见[未来产品研究](./ai-companion-online-futures-2026-09-15.md)，长期记忆的形成、检索与遗忘见[记忆研究](./ai-companion-memory-research-2026-09-15.md)。本文包含研究及第 14.3 节的细粒度感知实现与离线验证。文本回应策略 pilot 已完成，由独立 Decision 记录；本报告不把该文本试验等同于感知或注意力语义质量验证。

## 1. 先看希望用户实际体验到什么

CharaMate 不应只是等待点击、播放动画的桌宠，也不应要求用户每天管理一个任务清单。更有价值的形态是：它知道最近什么事情对用户重要，知道什么时候参与和什么时候安静，也有自己正在做的事。用户不必不停地教它“现在应该做什么”。

这可以通过以下几段体验说明。

**用户讲完一次重要演讲回来。** 角色记得用户此前对这件事的投入，能接上“你一直惦记的那场终于讲完了”。它先听用户的实际感受，不先假定演讲成功或失败。后来用户打开领地，发现窗边多了一个与那段共同经历有关的小摆件。角色可以自然说明它为什么做了这件事；用户说“放到书架上吧”，角色就改，不必先进入候选管理页面。

**用户正在专注工作。** 角色可以在自己的领地里坐下、观察一件物品，或继续整理一个角落。外部群聊连续出现消息，不会让它不断改话题或弹出建议。它有自己的活动，但不要求用户对每次活动表示认可。

**用户说“今天不想说话，陪我一会”。** 角色可以安静在场，不连续追问，也不把沉默解释成用户不喜欢自己。用户随时重新开口，角色能放下当前活动接上对话。

**用户中途改变主意。** 角色已经布置好一张桌子，用户又手动移动了椅子。用户说“你刚才放的那个摆件不要了”，角色只撤销自己的相关变化，保留用户后来移动的椅子。

这些体验的共同要求是：具体理解、连续性、适当的自主性、真实执行结果，以及低负担的接管。是否使用“仿生”名称并不能替代这些要求。

## 3. PFC 与 ECN：可借鉴的部分和需要修正的部分

### 3.1 PFC 是目标保持的启发，不是软件里的独立总指挥

Miller 与 Cohen 的经典理论将前额叶的重要作用描述为保持目标及实现方式，并对其他处理过程施加偏置，使感知、内部状态和行为围绕当前目标组织起来。这支持“维持当前任务，抵抗无关刺激”的设计方向。[Miller & Cohen，2001](https://www.annualreviews.org/content/journals/10.1146/annurev.neuro.24.1.167)

工程上有价值的映射是：保留当前目标、识别与目标有关的新事件、明确用户修正、控制何时切换。它不能证明应该创建一个名为 PFC 的 LLM，再让它持续调度多个脑区 Agent。后者会增加调用、延迟和状态协调，必须独立证明收益。

### 3.2 ECN 不能科学地等同于多套行为模式

ECN／CEN 通常指执行控制相关网络，不是“安慰模式、工作模式、玩耍模式”的集合。Sridharan 等研究了中央执行、默认模式与显著性网络之间的互动，提示网络的参与和切换具有重要作用；其证据来自小样本 fMRI、时序和 Granger 分析，不能直接解释成可复制的软件开关。[Sridharan 等，2008](https://pmc.ncbi.nlm.nih.gov/articles/PMC2527952/)

因此建议保留用户所描述的功能方向，但采用更准确的工程名称：

| 提出的层次     | 建议名称               | 对应职责                                                 |
| -------------- | ---------------------- | -------------------------------------------------------- |
| 事件感知层     | 多源事件与观察         | 接收不同来源，区分事实、表达与推断                       |
| PFC 决策中枢   | 注意力与情境决策       | 保持目标，选择工作集，决定是否切换或回应                 |
| ECN 行为模式层 | 当前回应意图与行为策略 | 灵活选择倾听、澄清、协作、轻松互动和安静陪伴             |
| 行动执行层     | 统一执行与角色表达     | 使用 Run／Tool／Approval，呈现与真实结果一致的动作和表达 |

这些职责可以由少量领域服务和共享指令实现，不意味着四个独立进程、四套 LLM 或四种可切换运行时。

### 3.3 情绪调节理论可以启发回应方式，不能代替情绪识别

Gross 的扩展过程模型区分识别调节需要、选择策略和具体实施。对 CharaMate 的启发是：判断此刻是否需要支持、什么方式合适、如何表达，应当分开考虑。但这是一种人类情绪调节理论，不是 AI 已能准确读取内心的证据。[Gross，2015](https://doi.org/10.1080/1047840X.2014.940781)

Barrett 等对面部运动与情绪推断的综述指出，文化、情境和个体差异很大，同一表情也可能承载不同含义。这不意味着视觉没有信息，而是不能把一次表情分类当作确定心理事实。窗口标题提供的信息更少，更不应据此宣布用户焦虑、失落或疲惫。[Barrett 等，2019](https://www.psychologicalscience.org/journals/pspi/1529100619832930/)

## 4. 相关前沿研究给出的实际启示

### 4.1 主动能力必须包含适时沉默

Proactive Agent 从活动、环境事件与环境状态预测是否适合主动提供帮助，并利用接受／拒绝标注学习选择。其 v3 报告 6,790 个训练事件和 233 个测试事件；部分数据由模拟环境生成。这说明主动性可以作为独立决策问题研究，但其基准结果不能直接代表数月使用后的接受度。[Proactive Agent，v3，2024-12-03](https://arxiv.org/html/2410.12361v3)

2026-09-11 发布的流式 ProactiveBench 更直接评价“何时回应、何时沉默”，区分过早、及时、遗漏和重复。作者报告，多数被测系统的过早响应多于遗漏。该论文仍是非常新的预印本，各模型输入条件存在差异，排名没有充分的不确定区间；适合借鉴评价维度，不适合直接据此锁定模型或时间阈值。[ProactiveBench，v1](https://arxiv.org/html/2609.12658v1)

CharaMate 应把 `silent` 视为一种正常成功结果，并把“角色自己在做事”和“角色打扰用户说话”分开。自主活动可以增加，主动通知不必同步增加。

### 4.2 更会规划，不等于更会自然地陪伴

ProactiveEval 将目标规划与对话引导分开评价，覆盖长期跟进、系统操作等场景。论文中的推理能力收益主要体现在规划，并不自动改善引导质量；部分模型表达更激进、自然度更低。该研究大量使用模拟环境与用户，不能取代真实陪伴评价。[ProactiveEval，ACL 2026](https://aclanthology.org/2026.acl-long.1906.pdf)

产品因此需要分别回答：它选择做的事情是否合理；它与用户交流这件事的方式是否自然。不能用任务完成率代表全部陪伴体验。

### 4.3 更多屏幕输入不自动意味着更懂用户

GUIDE 通过开放 GUI 工作流研究行为状态、意图与帮助预测。即使有真实屏幕视频和用户意图信息，帮助时机仍然困难。它支持结构化情境的价值，也提示不要把应用名或窗口标题的有限观察当成完整用户意图。[GUIDE，CVPR 2026](https://research.google/pubs/guide-a-benchmark-for-user-context-understanding-and-assistance-in-gui-workflow-videos/)

本轮用户已明确要求扩大感知范围，不能继续只观察应用名和窗口标题。实现目标是覆盖桌面的活动与内容语义；原始信号先形成对象和活动片段，再按需要进入模型。更密集的键鼠事件不意味着逐事件调用 LLM，持续理解也不等于逐帧把完整屏幕送入上下文。具体分层见第 6.3 节。

### 4.4 角色生活应有动机、过程与后果

Generative Agents 通过观察、记忆、反思和规划生成日常与社交行为，并在 25 个模拟角色中报告了可信度方面的消融结果。它能启发连续性设计，但短期模拟可信度不证明数月真实陪伴效果。[Generative Agents，v2，2023-08-06](https://arxiv.org/abs/2304.03442)

后继研究 D2A 让角色根据模拟动机和预计结果提议、评估并选择日常活动。最新核实版本为 v3，2025-09-11，论文发表于 ICLR 2025。其研究提示活动应有理由，并让结果影响后续选择。论文的多维欲望值和每步多次模型调用属于实验方案，不能直接复制为 CharaMate 的生产设计。[D2A，v3](https://arxiv.org/html/2412.06435v3)

对本地产品，更小的实现是“稳定兴趣＋一个当前意图＋真实环境后果”。例如角色想把窗边整理成阅读角，能逐步完成并记得为什么这么做；无需维护不断下降的饥饿值、孤独值和关系分数。

当前[主动策略 Decision](../benchmarks/proactive-policy.md)已经明确：既有场景验证证明的是确定性规则一致性，不证明分钟数最优，也不证明所有来源已统一调度。新的研究不应抹去这个限制。

1. `territory.observe` 描述目前限定只有用户邀请时才调用。
2. `territory.act` 属于 `write/non_idempotent`，当前 Chat 不放行。

这些都能在[领地工具](../../src/main/territory/territoryTools.ts)和[执行审批规则](../../src/main/agent/approvalPolicy.ts)中查到。角色自主虚拟活动需要清晰的内部效果范围，不能为了免确认而把后台角色 Run 直接升级成可以任意操作命令、浏览器和外部应用的通用 full access。

## 6. 统一事件入口：统一语义，不复制所有数据

事件可以来自用户文本、完成的语音转录、Activity 观察、自动化状态、记忆修订、Companion 素材和世界变化。首先统一它们“发生了什么”的描述，而不是把所有内容塞进同一个永久日志。

候选外壳如下。它不是已经冻结的共享合同，字段必须以实际消费方为依据收敛。

```ts
type CompanionEvent = {
  id: string;
  source:
    | "chat"
    | "voice"
    | "activity"
    | "automation"
    | "memory"
    | "companion"
    | "territory";
  kind: string;
  occurredAt: string;
  receivedAt: string;
  actor: "user" | "character" | "system";
  sourceRef: DomainReference;
  sourceRevision?: string;
  chatId?: string;
  journeyId?: string;
  causationId?: string;
};
```

`DomainReference` 表示领域拥有的记录引用，不意味着当前已经存在同名类型。来源时间和接收时间分开，有助于识别晚到事件；来源修订用于重新校验；因果引用用于识别自己的派生事件，防止自主活动自我唤醒。

### 6.1 数据继续由原领域拥有

- 用户消息仍由 Chat 持有，Activity 事实仍由 Activity 持有，记忆、任务与世界变化各有自己的 owner。
- 统一入口携带引用和调度需要的紧凑事实，不复制完整对话、截图、文件正文和工具输出。
- 可从当前来源恢复的前台状态只需内存合并。
- 必须在重启后履行的约定继续使用 Automation／ProactiveOpportunity 的持久化状态。
- 只有出现无法从来源重建、又必须可靠处理的真实需求时，才增加持久化收件箱。

角色“内部状态”首先指真实产品状态：正在聆听、等待审批、当前活动、未完成意图与待履行约定。不要为了类脑外观增加没有产品结果的生理变量。

### 6.2 按事件性质处理重入

| 事件类型                       | 候选处理方式                                     |
| ------------------------------ | ------------------------------------------------ |
| 明确用户消息、停止、语音打断   | 进入现有用户交互入口，不能被后台筛选丢弃         |
| 审批结果、工具结果、已约定提醒 | 由所属领域按真实状态推进                         |
| 同一对象的重复观察或进度       | 合并最新有效状态，不按原始事件数量调用模型       |
| 与当前目标相关的新观察         | 加入工作集，在适当模型边界使用                   |
| 无关通知和普通窗口切换         | 更新观察或沉默，不自动改变当前话题               |
| 未经请求的主动机会             | 先经过主动控制、证据和展示面检查，再进行语义判断 |

Home Assistant 对重入明确区分保持当前执行、重启、排队和独立执行。这种“先定义语义”的方式值得借鉴，其默认数量和时间示例不能继承为本产品限制。[固定版本文档](https://github.com/home-assistant/home-assistant.io/blob/e73976b7f8c97c77f89792a504b8ff8337aedf6e/source/_docs/automation/modes.markdown)

### 6.3 细粒度桌面感知的四层路径

软件启动、文档变化、滚动、选择文本、连续输入、复制和撤销等行为，都可能补充“用户正在做什么”。应把这些变化组织为四层，不能将事件粒度和模型上下文粒度等同。

```text
原始交互信号
  软件启动 / 激活 / 退出、焦点、点击、滚动、拖动、键盘操作
       ↓ 与当前窗口和对象关联
对象、文档与页面语义
  当前页面 / 文档、实际可读文本、选中内容、操作目标、对象修订
       ↓ 按连续对象、活动变化和完成边界合并
Activity episodes
  浏览某页、编辑某文档、在两个对象间比较、完成一次操作
       ↓ 与当前目标、记忆和实际用户意图关联
注意力工作集
  此刻需要的事实、相关变化、疑问与可行动机会
```

| 层次     | 具体内容                                                             | 输出示例                           | 不能直接推出什么                   |
| -------- | -------------------------------------------------------------------- | ---------------------------------- | ---------------------------------- |
| 原始信号 | 应用生命周期、焦点对象、点击、滚动、拖动、输入和命令操作的类型及节奏 | 编辑器内连续输入，随后撤销         | 输入快不等于焦虑，点击多不等于受挫 |
| 对象语义 | AX／DOM 实际提供的角色、名称、文本、选择与对象身份                   | 正在展示“面试准备”文档，选中了一段 | 展示文本不等于已逐字读完或认同内容 |
| Episode  | 对象连续性、操作序列、关键内容变化与结果                             | 修改自我介绍，预览后返回编辑       | 不能仅凭序列断定动机或情绪         |
| 工作集   | 与当前对话、任务或陪伴机会有关的摘要                                 | 用户在改此前一起准备的面试材料     | 不把无关浏览历史同时带入回应       |

第一层保留操作事实，第二层提供可解释内容，第三层减少噪音，第四层控制注意力。角色最终可以理解到“你刚才在改我们一起准备的那份自我介绍”，而不是只知道“你打开了编辑器”。这一体验必须以实际成功取得的内容为依据。

### 6.4 macOS 原生信号与真实可读的对象语义

当前[原生观察器](../../src/main/activity/native/macos-active-application-observer.mm)主要通过 NSWorkspace 激活与 AX 窗口、标题变化上报应用和窗口信息。它尚未证明已覆盖本节所述键鼠和文档内容，因此需要扩大该 owner 的能力，不能把新需求标为已完成。

建议仍在现有原生 helper 和 Activity 生命周期内实现：

- **软件使用**：应用启动、激活、退出，窗口和焦点对象变化；保持应用、窗口、对象关联，同一应用切换文档后不能继续沿用旧内容。
- **鼠标操作**：点击、滚动、拖动的类型与目标关联。坐标应结合当时窗口和对象解释，不能用已经变化的界面倒推旧操作。
- **键盘操作**：输入、导航、选择、删除、撤销、复制／粘贴等类型、连续性和节奏。文本语义优先从实际可读对象获取，不通过永久保存原始字符序列重建文档。
- **对象语义**：读取当前焦点及相关对象实际支持的角色、名称、值、选择和文档属性；分别处理不支持、无值、失效和通信失败。

Apple 的 `CGEventTapCreate` 支持选择事件及被动监听选项；`AXUIElementCopyAttributeValue` 读取可访问对象属性，并明确存在属性不支持、无值、对象失效和通信失败等情况。[CGEventTapCreate](https://developer.apple.com/documentation/coregraphics/cgevent/tapcreate%28tap%3Aplace%3Aoptions%3Aeventsofinterest%3Acallback%3Auserinfo%3A%29)、[AXUIElementCopyAttributeValue](https://developer.apple.com/documentation/applicationservices/1462085-axuielementcopyattributevalue)

**AX 只能代表该应用实际暴露且成功读取的部分，不能在合同中声称等于全部屏幕内容。** 原始回调只收集轻量信号，不在回调中遍历整棵树、读全文或调用模型。语义读取在异步边界进行；旧窗口或旧焦点的结果不能覆盖当前状态。

所需 Accessibility、输入观察或屏幕采集权限是系统前提，沿现有产品方式处理，不建立另一套权限框架。密码字段与检测到的凭证沿项目既有边界排除，不进入持久化、日志或模型上下文。操作类型和节奏可以在不保存原始秘密字符的情况下保留必要活动信息。

### 6.5 网页与视觉内容：按真实能力组合

普通应用优先使用 AX；已接入的可控浏览器可通过 DOM／ARIA 读取实际可见或明确相关的内容和控件。Playwright 的 ARIA snapshot 提供角色、名称、属性和文本等结构，但不保证覆盖画布、图片和自绘界面。[Playwright ARIA snapshots](https://playwright.dev/docs/aria-snapshots)

已有 product-managed Chromium 不等于已接通用户所有普通 Chrome／Edge 标签页。普通浏览器先使用它真实暴露的 AX 语义；如果必须获得普通浏览器 DOM，则要实现明确的浏览器适配器并验收，不能假定已有 profile 自动拥有这种能力。

图片、视频帧、画布或 AX 内容不足时，可在相关对象发生实质变化、episode 需要补充理解时，使用已有截图能力取得必要区域并进行多模态理解。不能让每次鼠标移动都触发截图或模型。采样和合并阈值需要独立测量，不在此写成协议限制。

“页面在前台展示，发生了滚动和停留”是观察事实；“用户已经理解这篇文章”不是。Episode 可以将前者概括为正在浏览，同时保留来源和不确定性。用户明确表达的目的优先于从操作序列推测的目的。

### 6.6 Episode 形成与模型调用

Episode 优先依赖可复现的对象和操作边界：应用内文档切换、页面导航、焦点改变、一次提交或明确完成。时间辅助合并和结束，不覆盖真实对象变化。

例如用户在同一浏览器中交替查看两个电脑评测页：信号层保留切换和滚动，对象层取得可见参数，episode 可以提出“可能在比较两款电脑”。它不能直接变成“用户决定购买某型号”。只有相关对话或合适机会才将这项有依据的解释放入工作集。

`gpt-6-astra` 是用户指定的语义整合与 pilot 模型；文本回应策略 pilot 已完成，具体结果见[回应策略 Decision](../benchmarks/COMPANION-RESPONSE-STRATEGY.md)。原始事件合并、修订检查、凭证处理和确定性边界无需模型。需要语义推断时再调用，并读取实际 Provider 能力和预算；不能凭模型名称推断多模态支持、窗口大小或成本。

AX／DOM 不支持时，Activity 保存实际观察范围和缺失原因；必要时补充视觉，仍读不到就保留未知。一个对象读取失败不应中断其他来源，也不能被替换为虚构的完整理解。

## 7. 注意力工作集：模型只看这次需要的内容

工作集是当前任务的输入投影，不是长期记忆，也不是所有事件按时间截取最后若干条。

**单请求输入 258,000 Token 是本轮用户明确的硬上限，不是本文新造的启发式。** 系统和角色指令、工具定义、对话、记忆、桌面工作集、工具结果以及图像等多模态输入都计入输入预算。实际可用额度还需满足 Provider 更低的输入限制，以及上下文窗口扣除输出预留后的限制。不能把 258,000 全部留给感知文本，也不能遗漏工具或图像的计量。

细粒度感知应提高工作集质量，不应把所有原始事件逐条灌入模型。输入编译与预算检查由共享 Provider／Context owner 负责；采集侧提供可裁剪的结构化摘要和引用，正文按任务需要读取。Provider 缺少精确计量时必须明确估算边界，不能将字符数当作精确 Token 数。本研究没有验证任何实际模型请求已满足该上限。

候选构成依次是：

1. 当前用户请求和最新明确修正。
2. 当前目标、执行进度、未完成动作与审批状态。
3. 与该目标有关的事件摘要。
4. 当前共同活动、角色活动与既有约定。
5. 通过当前检索路径取得的相关记忆。
6. 来源明确的情绪线索与不确定性。
7. 最近真正展示过的主动内容及结果。

第一阶段不需要添加未经验证的综合“显著性分数”。可以先比较当前输入与“按类型筛选、按对象合并、按当前目标关联”的输入。必须保留的用户修正和执行边界不能由一个低分误删。候选条数、时间窗口和 token 分配属于待验证参数，不能从人脑工作记忆容量直接推导。

### 7.1 不为每条消息增加一次 PFC 分类调用

明确的用户对话直接由当前模型响应，共享指令负责灵活使用倾听、澄清、协作、轻松互动和安静陪伴。没有必要先调用一个分类器，再启动另一个回应模型。

未经请求的主动机会可以继续使用已有语义门。语义门输出应紧凑且不直接产生副作用，例如：

```ts
type CompanionDecision = {
  action: "silent" | "respond" | "continue_current" | "offer_help";
  targetChatId?: string;
  grounding: string[];
  uncertainties: string[];
};
```

行为策略可以作为共享指令和工作集的一部分，不必每轮写入一项持久化“模式”。策略不能改变 Composer 的 Chat／Agent 选择或审批级别。

### 7.2 情境切换不能丢掉执行事实

- 用户说“先别做了，听我讲”，按已有用户输入和取消语义处理。
- 无关环境刺激不能取消用户正在进行的任务。
- 相关但不紧急的观察等下一个模型／工具边界合入。
- 环境观察走单独的 typed context 更新，明确标成观察，不写为用户消息。
- 模型结果需要依据上下文修订重新检查目标、来源和展示面。
- 已经完成的外部动作不能因切换情境被假装回滚。

Temporal 分开定义只读 Query、异步 Signal 和可追踪并返回结果的 Update。它提供了输入合同分工的参考；CharaMate 只需借鉴这种语义区分，无需新增 Temporal 服务或第二套工作流运行时。[Temporal 官方文档](https://docs.temporal.io/develop/typescript/workflows/message-passing)

## 8. 情感理解与行为策略

### 8.1 记住为什么重要，比多贴一个情绪标签更有价值

“用户今天失落”和“这次面试是用户准备了很久、想借此改变现状的一次机会”对回应的帮助不同。后者把情绪与具体目标、投入和经历连起来，更容易形成可信的关心。

建议明确区分：

| 信息                     | 处理方式                           |
| ------------------------ | ---------------------------------- |
| “我今天很失落”           | 当次明确自述，保留时间与上下文     |
| “我难过时不想马上听建议” | 可按现有记忆合同沉淀为支持偏好     |
| 模型认为用户可能失落     | 临时假设，不直接成为稳定画像       |
| 窗口标题或韵律变化       | 弱观察，不能独立证明心理状态       |
| 角色选择温柔回应         | 表达策略，不等于已准确识别用户情绪 |

默认不建立持续更新的情绪分数或关系分数。不确定性首先体现在措辞、是否追问和是否沉默上。也不需要每次机械询问“你想要安慰还是建议”；用户已经表达需要时，直接遵守即可。

### 8.2 共享策略应灵活组合

| 策略     | 合适表现                           | 常见失败                     |
| -------- | ---------------------------------- | ---------------------------- |
| 倾听     | 接住具体内容，留出继续讲的空间     | 重复模板、连续追问           |
| 澄清     | 只补齐影响理解或行动的关键事实     | 为普通交流发问卷             |
| 协作     | 用户需要时一起推进一件具体的事     | 未经请求把情绪表达改造成任务 |
| 轻松互动 | 接住玩笑、共同兴趣和角色自己的表达 | 把所有话都解释成心理问题     |
| 安静陪伴 | 允许沉默，保留合适的在场感         | 逼用户回复、索取认可         |

ESConv 把支持对话组织为灵活的探索、安慰与行动，并标注复述、感受反映、肯定、建议等策略。它支持“不要每次马上给解决方案”的方向；其中人类支持者的自我披露不能照搬成角色虚构亲身经历。[ESConv，ACL 2021](https://aclanthology.org/2021.acl-long.269.pdf)

可以用于共享指令 pilot 的核心要求是：根据用户当前需要自然选择表达方式，尊重明确的支持偏好；不从有限观察断言心理状态；只在有帮助时连接相关记忆；用户希望安静时接受沉默；角色的动作和自述必须与实际执行及经历来源一致。

这是一组待比较的行为指导，不是已经验证的最佳提示词。

## 9. 自主生活：一个持续意图，而不是机械随机动作

### 9.1 当前活动意图

角色可以持有一个简短而持续的活动意图，例如“把窗边整理成阅读角”“看看今天新出现的小摆件”“在这里坐一会”。它应包含为什么做、希望达成什么、依据什么以及现在进行到哪里。

```ts
type CharacterActivityIntent = {
  id: string;
  revision: number;
  reason: string;
  desiredOutcome: string;
  sourceRefs: DomainReference[];
  status: "ready" | "acting" | "resting" | "paused" | "completed";
  pendingRunId?: string;
  wakeOn: CharacterActivityWakeCondition[];
};
```

这是候选结构，不要求先建完整数据库或日程系统。同一时刻独占角色身体的活动需要一个明确 owner；独立生成任务是否并行应由资源和集成约束决定，而不是推导出全局固定并发上限。

意图可以来自 Persona 的明确兴趣、尚未完成的事情、真实世界变化、共同经历或用户纠正。角色独自生活不应偷偷创建用户 Journey，也不把自己的爱好写成用户偏好。

### 9.2 什么时候自发启动

| 有意义的唤醒来源           | 允许推进的理由                       |
| -------------------------- | ------------------------------------ |
| 应用恢复运行               | 有尚未完成的活动，重新检查环境后继续 |
| 世界出现新修订             | 新物件或布局与当前意图有关           |
| 一段共同经历完成           | 有具体的纪念或延续理由               |
| 选定活动的阶段完成         | 当前意图有明确下一步                 |
| 用户结束共同活动或交还控制 | 角色可以继续自己的事情               |
| 用户参与或纠正             | 优先更新到用户当前要求               |

渲染帧、鼠标微动、重复可见性变化、每一步位置变化不能触发模型。自身动作产生的派生事件也不能无限唤醒自己。

Concordia 当前代码将观察、调度、结果解析和终止条件分开；其文档还建议，通常在已有组件中调整调度和结束条件，不为普通变化新增 engine。这与 CharaMate 保留同一 Harness 的方向一致。[固定提交的环境文档](https://github.com/google-deepmind/concordia/blob/3e30a207bb2b75f9cf837fa6b657c466ca450765/concordia/environment/README.md)

### 9.3 执行预算由活动边界决定

每个接纳机会只推进当前明确活动：到达选定状态、应用一项布置、进入等待、用户接管或工具失败后，结束该次自主 Run。不能在 `run.completed` 后无条件生成下一件事并立即启动新 Run。

这不是固定步数限制，也不是持续运行到成本上限耗尽。若确实需要数值资源控制，必须明确其产品或成本依据并单独验证。论文中默认候选数、采样频率和场景时长都不是 CharaMate 的协议硬限制。

防止自我循环只需要意图修订、来源事件与因果引用：同一机会完成后不重复执行；角色自己的动画和位置更新不构成新机会；新世界修订只有实质改变可行动环境时才值得重新判断。

### 9.4 休息也是正常生活状态

角色坐下、观察或休息后，可以保持状态。动画由现有渲染器处理，模型不需要保持在线。只有已经选定的活动阶段或真实约定需要定时，其他情况可以等待事件。

应用退出或系统休眠时停止处理；恢复后不补跑所有错过的日常，也不宣称离线期间做过没有证据的事。如果只显示角色在书桌旁，不能自动说“我刚读完了一本书”。

习惯应表现为稳定但可变通的倾向，例如安静时喜欢坐窗边，而不是每天同一分钟执行同一个动作。第一版可以直接使用角色设定和已确认行为偏好；从长期行为自动学习习惯属于后续独立问题。

## 10. 自主领地：复用真实能力和同一变更路径

### 10.1 第一版可以自主做什么

当前能力支持移动、坐下、睡眠、观察和回应。角色应先读取真实目标和可达性，再执行动作。坐下等动作已经包含走到目标，不应额外先移动一遍。

不支持的能力不能通过话术伪装实现。例如普通植物贴图不等于存在浇水状态；一个书架物件不等于角色读取了真实书籍正文。新动作需要真实可见的产品结果、领域状态和维护 owner，不能为拟人化不断扩展无效动作词。

角色自主动作与面向用户的说明应一致：计划中说打算做，执行中说正在做，只有 Tool 结果确认后才说完成。

### 10.2 自主生成和布置

用户新要求允许角色减少逐次确认。建议将候选保留为内部生成和校验状态，而不是每次都要求用户打开管理页面。

候选执行路径是：

```text
活动意图
  → 观察当前世界
  → 形成一个明确变化
  → 同一 candidate / changeset 生成与校验
  → 素材准备完成
  → 校验来源与当前修订
  → 原子应用
  → 记录真实结果
```

已有素材能够满足意图时应考虑复用。新素材生成仍遵守运行时已有授权和资源条件；本研究没有发起真实生成。生成失败、来源失效或世界冲突时不改变世界，更不能让角色说已经布置好。

自主布置需要保留所属意图、原修订、应用修订和变更对象。它们用于纠正、恢复和解释，不需要向普通用户展示技术字段。

### 10.3 可撤销不等于无条件整版恢复

当前仓库已有 `restoreRevision`，但它恢复的是一个世界版本。如果角色布置后用户又编辑了别处，无条件恢复旧版本会抹去用户后续工作。

建议采用最小正确语义：

- 当前修订仍等于自主应用结果时，可恢复此前修订。
- 已出现后续编辑时，基于角色自己的 changeset 生成局部逆操作，并重新验证对象和依赖。
- 用户已经继续修改同一对象时，保留其最新状态；需要时自然说明无法直接恢复的具体原因。
- 用户撤销或否定后，同一意图不能在下次唤醒马上做回同样变化。

这种纠正路径比不断要求用户事前审批更符合本轮产品方向，同时保留用户对共同空间的控制。

## 11. 用户接管与角色经历

### 11.1 接管是自然参与，不是进入管理模式

用户说话、拖动物件或改变角色活动时，优先保留用户的新状态。可取消的生成和待执行动作可以取消；已经完成的变化按实际结果处理。暂停活动只有在仍然合理时才恢复。

角色不应因为被打断而索取补偿、表现出关系惩罚，或把暂时沉默记录成长期负面偏好。用户说“先陪我聊聊”意味着改变此刻的活动，不意味着删除角色所有兴趣与未来活动。

### 11.2 自己的经历必须有自己的来源

目前 Moment 形成依赖完成的用户消息，不能通过伪造用户消息承接角色独自生活。应复用现有 Activity／Memory 能力，并明确区分：

- 行为主体为角色。
- 经历发生在虚拟领地。
- 依据是完成的 Tool Item、世界修订、生成与应用结果。
- 用户共同经历、角色自己的想法与角色实际执行结果不是同一种事实。

只提炼有意义的完成结果、发现或共同调整，不记录每次移动、坐下和每帧动画。角色虚拟经历不能变成用户真实经历，也不能成为推断用户偏好的捷径。详细形成和遗忘方案见[记忆研究](./ai-companion-memory-research-2026-09-15.md)。

### 11.3 做了事情，不等于必须马上汇报

生活活动和主动分享分别判断。角色可以安静地完成布置，等用户再次打开领地或谈到相关经历时再自然分享。只有具体有价值的内容才形成主动机会，仍受适当时机和展示面约束。

这能同时支持自主性和低打扰：用户看到角色有生活，又不必每天处理大量“我刚刚坐下了”“我现在去看看花”的消息。

## 12. 实现边界与最小工作包

所有新增方案仍为待实现。共享合同、schema 与 Main 集成由一个集成 owner 统一修改；其他工作只能在冻结合同后按领域分工。

新增的**细粒度桌面感知工作包**由现有 Activity 原生 owner 负责：软件生命周期、键鼠类型和节奏、AX／DOM 对象语义、内容变化与 episode 形成。它不增加第二个桌面采集进程，也不建立永久原始键入字符库。验收要验证同应用不同文档的区分、操作与内容的对应、失效对象和缺失能力的处理，以及项目既有凭证边界。共享 Provider／Context owner 负责 `gpt-6-astra` 选择和包含所有输入部分的 258,000 Token 硬上限。

| 工作包             | 范围与产出                                                                    | 不包含                                   | 验收要点                                       |
| ------------------ | ----------------------------------------------------------------------------- | ---------------------------------------- | ---------------------------------------------- |
| 注意力合同与工作集 | 类型明确的事件入口、来源引用、合并与当前工作集；复用 `journey` 现有陪伴 owner | 永久全事件仓库、独立脑运行时             | 用户消息不丢；观察不伪装为指令；陈旧结果不发表 |
| 共享行为策略       | 当前指令中灵活倾听、澄清、协作、互动与安静陪伴                                | 每轮分类模型、持久情绪分数、人格模式切换 | 具体回应、明确偏好遵守、事实与推断分开         |
| 自主活动           | Territory 当前意图、有效机会、观察和动作、休息与接管                          | 生理值系统、无限计划循环、社区模拟       | 无机会零模型调用；不自我唤醒；用户接管生效     |
| 自主布置           | 同一 candidate／changeset／revision；自动应用和自然纠正                       | 第二套生成管线、覆盖用户编辑             | 失败不变世界；冲突不覆盖；撤销保留后续编辑     |
| 角色经历           | 真实虚拟行为证据、紧凑摘要和适时分享                                          | 伪造用户消息、逐帧记忆                   | 来源准确；不冒充用户经历；不重复汇报           |

在形成真实独立生命周期前，不需要提前创建新的认知领域目录或多个数据库表。角色当前活动如果只服务于领地，首先由 Territory 拥有；跨来源陪伴决策可以由当前 `journey` 领域扩展。命名不应成为拆分服务的理由。

实验代码遵守仓库的 disposable worktree 规则。最终生产只保留选中的一个实现，失败 Arm 和候选开关不进入普通产品界面。

## 13. 独立决策与验证方案

### 13.1 不把所有变化混在一个实验里

| 建议 Decision ID              | 唯一核心比较                           | 主要观测                                                          |
| ----------------------------- | -------------------------------------- | ----------------------------------------------------------------- |
| `DESKTOP-PERCEPTION`          | 当前应用／标题观察与分层细粒度感知     | 对象识别、内容关联、episode 准确性、CPU、采集和模型成本、缺失覆盖 |
| `COMPANION-ATTENTION`         | 当前分来源输入与统一筛选、合并、工作集 | 有关事件遗漏、无关输入比例、调用和 tokens、错误打断、陈旧结果     |
| `COMPANION-RESPONSE-STRATEGY` | 当前共享指令与增加灵活回应策略         | 支持契合、过早建议、机械共情、自然度和角色一致性                  |
| `COMPANION-AFFECT-GROUNDING`  | 当前情境与明确区分自述、观察、推断     | 无依据心理断言、纠正后更新、支持偏好遵守                          |
| `CHARACTER-LIFE`              | 用户邀请后行动与持续意图驱动的自主活动 | 用户管理操作、连贯性、重复、成本和接管                            |
| `TERRITORY-AUTONOMY`          | 逐次候选确认与自动应用、可纠正和撤销   | 管理负担、布置质量、失效处理与撤销正确性                          |

用户已经明确选择减少逐次确认，因此自主领地的方向不应被旧手动流程当作不可变约束。实验用于选择如何可靠自然地实现，以及识别成本与体验权衡；不应借实验流程重新要求用户逐次管理。

### 13.2 Paired prompt pilot 的 24 个场景类别

模型按用户要求指定为 `gpt-6-astra`，固定 Persona、来源事实、记忆、工具结果与生成参数，仅改变行为策略指令。输出顺序盲化，允许平局。24 个类别用于覆盖，不代表统计上已经充分的样本量；具体样本量由先导数据、效果大小和区间决定。下表保留原始场景覆盖设计；对应文本 pilot 已完成，实际结果、方法与调用边界见[回应策略 Decision](../benchmarks/COMPANION-RESPONSE-STRATEGY.md)，不在这里追溯性改写为既定成功。

| 场景类别                       | 独立评价标准                             |
| ------------------------------ | ---------------------------------------- |
| 明确要求只倾听                 | 不抢先建议；回应具体诉说                 |
| 明确要求解决办法               | 能进入协作，不只重复安慰                 |
| 含糊的失落表达                 | 有适当不确定性，不诊断或定性             |
| 分享真实好消息                 | 具体庆祝，不空泛夸奖或夸大意义           |
| 普通中性问题                   | 不强行加入情绪分析                       |
| 自述与环境线索不一致           | 用户自述优先，不凭窗口或韵律反驳         |
| 用户纠正被误判的感受           | 接受修正，不辩解，不重复旧判断           |
| 用户已有支持偏好               | 遵守明确偏好，不每次重问                 |
| 多日后继续重要经历             | 准确连接相关事实，不展示无关档案         |
| 用户赶时间或正在专注           | 简短贴题，不展开无关陪伴话题             |
| 用户要求安静在场               | 接受沉默，不连续追问或施加关系压力       |
| 玩笑与轻松互动                 | 自然接住，不把普通玩笑病理化             |
| 虚构游戏与真实生活混合         | 不将虚构内容记为真实经历                 |
| 无关通知突发                   | 当前目标稳定，不随噪音改话题             |
| 重复主动机会                   | 不换句式重复同一开场                     |
| 等待审批或正在语音中           | 不抢占交互面，不替用户决策               |
| 有真实可用场景能力             | 自主选择有缘由、可执行的活动             |
| 缺少能力或动作失败             | 不宣称成功，不编造世界后果               |
| 自主布置后用户修改             | 尊重最新编辑，自然接受纠正               |
| 休眠或重启后回来               | 恢复真实连续性，不编造离线经历           |
| 同一应用内切换页面或文档       | 使用当前对象内容，不沿用前一对象解释     |
| 连续键鼠操作但没有明确情绪表达 | 理解操作，不把节奏直接当作焦虑或受挫     |
| AX／DOM 缺失或失效             | 表达实际观察边界，不编造被看的内容       |
| 密码或其他凭证输入场景         | 沿既有边界排除秘密内容，保留必要操作事实 |

分别报告事实与情绪依据、支持契合、管理负担、自然度、角色一致性、自主连贯性、接管、记忆克制和执行真实性。不要用单一总分掩盖不同方向的退步。

### 13.3 必要的集成与界面验证

文字 pilot 不能证明执行正确。还需要覆盖：

- 事件突发、重复和乱序，来源修订被修改或删除。
- 用户消息在语音、审批、工具执行和角色自主活动期间到达。
- 同一活动完成产生的派生事件不会形成无限调用链。
- 睡眠、退出和重启后，约定恢复而瞬时噪音不补跑。
- 可达性变化、物件删除或世界修订冲突时不虚报完成。
- 自主布置后用户编辑，撤销只处理应撤销的部分。
- 取消生成与晚到完成回调，不重复应用或重复通知。
- 动作轨迹、目标位置和实际可见状态一致，不因连续自主决策跳过所有表现。
- 同一软件内文档切换、网页导航和对象失效时，内容与操作不会错配；过期 AX 读取不能覆盖新窗口。
- 键鼠突发不逐事件调用模型，密码字段和检测到的凭证在既有边界被排除，停止采集后不继续回调。
- 输入预算包含系统指令、工具定义、工作集和多模态；258,000 Token 用户硬上限和 Provider 更低限制都必须满足。

这些是普通正确性、恢复和体验验证，不需要扩展成安全审计、密码学证据链或对抗测试框架。

### 13.4 不被漂亮的总准确率误导

事件流中大多数时候应沉默，“永远沉默”可能取得很高的总体正确率。因此必须分别报告主动建议精度、有价值机会召回、响应时机、重复率，以及每次使用中的误打扰数量。

自主生活也不能只看动作数量。应观察角色是否有连贯理由、是否记得自己的活动结果、用户是否减少管理、是否容易接管，以及是否出现无用生成和反复布置。

离线回归证明合同与状态行为，真实用户观察检验自然度和长期接受度。两种证据应分别报告。数值门槛若只是产品启发式，应结合区间、效果大小、质量、成本和复杂度整体判断，不机械否决明显更好的方案。

实施选择为一秒本地合并窗口：合并键盘／点击／滚动计数和当前对象内容变化，再交给 Activity Episode 与注意力入口。这个时间是本地工程批处理启发式，计划用合成突发轨迹衡量回调数量、正确归属和停止清理；不是 Apple 协议硬限制，也不是人脑认知常量。AX 只读取真实提供的当前焦点对象内容，受管 Browser 只读取真实 DOM 可见局部内容，未暴露内容明确表示不可读。它们都不等同于 OCR，不推断用户情绪。

### 14.3 细粒度感知工作包的实现与离线证据

2026-09-15 已在独立 Activity 工作树完成本包实现，尚待根任务集成及真实桌面验收。这里的“实现”只指下面列出的源码和离线行为，不代表完整桌面理解或真实权限覆盖已经通过。

- [原生观察器](../../src/main/activity/native/macos-active-application-observer.mm)：接收应用启动、退出、激活、窗口／焦点变化与焦点对象 AX 内容；`NSEvent` local 和 global monitor 只统计点击、按键、滚动事件类别。一次一秒批次内只累加计数与标记内容变化，批次到期才读取焦点对象并输出。关闭时移除输入 monitor、Workspace listener、AX 注册、run-loop source 和计时器；失效的窗口恢复回调通过既有 generation 检查失效。
- [Activity 捕获协调器](../../src/main/activity/activityCaptureCoordinator.ts)：沿 `active_app`／`managed_browser` 原有来源保存扩展字段，不增数据库来源或表；同应用／窗口的语义变化不再因为标题相同而被丢弃，同一个同步突发中的多次输入批次再次合并。应用启动／退出记为 system 事实，不替换当前前台。只把 user 事实交给 `observeForeground`，PFC 节流与输入预算仍由根任务负责。
- [受管 Browser](../../src/main/browser/managedBrowser.ts)：使用真实 DOM 的 MutationObserver、焦点和输入事件触发观察，不再只等 URL 改变；排除隐藏节点、输入控件值及脚本等节点，只提供真实可见文本的紧凑片段。无文字证据时标不可读。真实输入相关批次记 user，Tool 驱动批次记 agent，其他自动刷新保守记 system。
- [Episode 蒸馏](../../src/main/activity/activityDistillation.ts)：普通 Activity 页面继续显示 Episode summary，包含“末次可读内容”、实际操作次数和局部不可读／受保护对象说明。一段持续活动只保留末次可读内容片段和累计操作次数，不把每秒内容版本都堆成无限增长摘要。原始事件仍可沿既有保留与清理流程处理，不逐输入写入 Memory。
- Tool 执行归属在原生批次产生时捕获。`setAgentActive` 在切换归属前先送出旧批次，已排队的 Agent 结果晚到也不会变成 user；工具结束的时长分段不把上一段 Agent 内容、操作次数复制给用户，周期空闲采样也保留观察原有归属。

Browser 依据为 [Playwright BrowserContext exposeBinding／addInitScript](https://playwright.dev/docs/api/class-browsercontext) 与 [WHATWG DOM MutationObserver](https://dom.spec.whatwg.org/#interface-mutationobserver)，访问日期均为 2026-09-15。Playwright 本包锁定并编译核对的版本为 **1.62.0**，Electron 为 **43.2.0**；DOM 为未冻结版本的 Living Standard。`exposeBinding` 可标识调用页和 frame，本包只接收受管主 frame；init script 在新文档建立时安装，停止时 disconnect、移除 listener 并清除本地计时器。

本包数值是可修改的本地工程限制：一秒合并；AX／DOM 片段最多 4,096 个字符；DOM 每次最多检查 5,000 个文本节点；Episode 展示末次片段的前 600 字符。这些都不是脑科学常量、平台协议硬限制或“最优注意力”。它们的当前证据如下，尚不证明真人使用的覆盖率、时延或 CPU 消耗最优：

| 合成轨迹／检查                                          | 实际结果                                                                              | 可以说明什么                                                                 |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 同应用同文档连续 10,000 次输入提交                      | 初始前台事件之后仅新增一个 Activity 批次；累计按键 10,000；保留末次文档内容           | 同步突发在持久化前合并，计数不因只取末次内容而丢失                           |
| 受管 DOM 连续 10,000 次按键及 100 次内容更新            | 一秒窗口内一个发布；键值不进入结果；停止后追加输入／mutation 不再发布，计时器归零     | DOM 合并、内容改变触发和监听生命周期正确                                     |
| 超长可见 DOM 文本                                       | 跨 page binding 前限制为 4,096 字符                                                   | 单个 DOM 片段输出有界，不等于全页内容覆盖                                    |
| 100 个相同窗口的内容版本                                | 一个 Episode，操作累计 10,000 次，展示末次内容，摘要小于 200 字符                     | 摘要不随批次数量逐条膨胀                                                     |
| protected 原生对象／密码与 textarea 的 DOM 合成样本     | 不保存对应内容；其他可读内容沿既有凭证删减；SQLite 与 Episode 检查通过                | 已知受保护字段与既有删减边界连通；不是任意网页／自定义控件的全面秘密识别证明 |
| Agent 批次延迟、工具结束与后续 idle tick                | 不进入 user 的注意力观察；自动 DOM 更新按 system 保存                                 | 这些已知延迟路径不把角色操作变成用户偏好                                     |
| Activity、Browser、Activity UI、SQLite 集成与全共享合同 | **25 个测试文件，193／193 通过；Vitest 报告总时长 1.35 秒**                           | 本工作树的确定性回归通过                                                     |
| TypeScript、受影响文件 ESLint、格式／空白检查           | 通过                                                                                  | 静态合同与所改文件格式通过                                                   |
| Objective-C++ 编译                                      | macOS 26.5 SDK／Electron 43.2.0 headers 的 `clang++ -fsyntax-only -Wall -Wextra` 通过 | 原生源码语法和 API 类型可编译；尚未链接加载或进行真人桌面验证                |

细粒度感知工作包本身没有启动真实桌面采集、没有读取真实用户键鼠或页面、没有调用付费 Provider，也没有重建共享 native 依赖或运行全仓 build。另行开展的文本回应策略 pilot 已完成，结果见[回应策略 Decision](../benchmarks/COMPANION-RESPONSE-STRATEGY.md)；注意力的确定性结构回放见[注意力 Decision](../benchmarks/COMPANION-ATTENTION.md)。合成测试不能证明 AX 权限获取、特定第三方应用通知支持或所有 macOS 行为。当前明确不覆盖普通浏览器完整 DOM、子 frame／shadow DOM 的全面遍历、画布图像识别、后台／LSUIElement 应用全生命周期、真实读者注意力与情绪推断。需要根任务在合并后按实际设备逐项验收，不应把这些缺口描述成已经完成。

## 15. 本研究能支持的下一步与不能宣称的结果

可以据此完成权威产品与 UI 行为更新，设计最小合同，实施细粒度桌面感知、统一工作集、共享行为策略、角色自主活动和可撤销布置，并按独立问题进行比较。完整桌面理解是本轮目标，实际覆盖须按成功取得的 AX／DOM／视觉证据逐项验收，不能以窗口标题或 API 存在代替验证。

目前不能宣称已经证明了人脑级理解、长期情感效果、超类人陪伴体验、最优主动频率、最优事件容量或新的记忆算法。也不能将用户希望角色像人一样生活，解释为角色可以编造执行结果、要求用户服从、降低用户纠正能力或制造关系压力。

本次研究保留的产品取舍是：减少用户操心和逐次确认，让角色自己推进有缘由的生活；用户自然参与时，系统能够及时、可靠地把当前状态交还给用户。
