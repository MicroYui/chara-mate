# AI 陪伴的在线延续、角色社区与规模化记忆研究

日期：2026-09-15。文档性质：未来产品研究与技术提案；不代表已实现能力，不改变当前本地生产选型。论文、官方文档和开源仓库均在本轮实际查阅；可变仓库固定到下文提交，文档未提供版本时记录访问日期。

## 1. 结论与范围

CharaMate 的主体验应是与一个有性格、有经历、记得彼此的角色相处。桌面形象、手机入口、领地和未来社区都是这种关系的表达场所。在线化首先解决“换一个入口仍然是她、电脑合上后关系仍能延续”；角色社区进一步提供她自己的兴趣、日常和交往，让她有自然想与用户分享的经历。

本研究建议按三个独立问题推进：

1. **连续身份**：同一个陪伴实例跨设备保持 Persona、记忆、承诺和对话连续性，执行与数据始终只有一个归属。
2. **有限而真实的自主生活**：角色在虚拟社区中根据兴趣参与事件、与其他角色交谈、创作或分享；发生过的事有来源和结果，回到用户身边时自然提起。
3. **按实际负载扩展**：先把事件、长期事实、检索索引和大媒体分开管理，再根据热点、查询和成本证据扩展数据库、队列和检索。注册角色数量本身不能证明需要复杂基础设施。

当前本地版本应优先实现理解用户、注意力筛选、情境化行为、记忆质量和自然遗忘。跨用户账户、云端常驻 Runtime、公共社区、多租户存储、消息队列服务和云图数据库均属于后续阶段。本报告不要求当前代码增加云模式、第二套 Harness、占位服务或候选算法开关。

下文的研究发现来自所引来源；产品阶段、字段设计、容量算式和实现切分是本报告的工程提案。所有容量数字都是显式假设下的算例，未经 CharaMate 真实流量验证。

## 2. 当前基础与可复用边界

现有产品的稳定基础是 Main 拥有 Chat、Run、Memory 和领域状态，Renderer 呈现投影，Android 与 Relay 传递通知、消息和附件。相关入口为 [Main 组装](../../src/main/index.ts)、[Companion Bridge](../../src/main/companion/companionBridgeService.ts)、[分享导入](../../src/main/companion/companionShareIngress.ts)、[Mailbox 处理](../../src/main/companion/companionMailboxProcessor.ts) 和 [Companion 合同](../../src/shared/schemas/companion.ts)。

源码中可直接复用的行为包括：分享以稳定 `submissionId` 认领；已导入的分享走恢复路径；真正持久化 User Message 后才完成导入；导入状态与 cursor 推进由仓库约束；Mailbox 校验目标 Desktop、Android 设备和 cursor 是否前进，再发送导入确认。网络重试因此不需要重新创造一次用户意图。参见 [分享导入仓库](../../src/main/companion/companionBridgeRepository.ts)。

在线版本应该把“哪个计算机执行”从角色身份中分离，而保留上述业务语义。Android 不因为能收消息就自动变成另一个 Memory 真源；Relay 不因为已经在线就自动承担 Agent 判断。未来远程 Runtime 必须是明确的产品升级及新的部署归属。

当前 [Memory Service](../../src/main/memory/memoryService.ts)、[Memory Repository](../../src/main/memory/memoryRepository.ts)、[Journey Service](../../src/main/journey/journeyService.ts)、[Proactive Opportunity Service](../../src/main/journey/proactiveOpportunityService.ts) 和 [Territory World Service](../../src/main/territory/territoryWorldService.ts) 已分别承担记忆、共同经历、主动机会和空间状态。未来方案应从这些领域合同演进，避免把它们合并为一个全知的“角色大脑”数据库。

## 3. 一手研究与当前工业实现

### 3.1 社会模拟证明了什么

**Generative Agents，2023-08-06 的 v2。** 论文在 25 个 Agent 的 Smallville 中展示了观察、记忆检索、反思和规划如何共同产生较可信的行为。一次聚会意图通过角色间交流传播，最终形成邀请和出席行为；消融支持这几类模块对可信度的贡献。它提供了“经历—解释—行动—新经历”的参考，不证明数年关系一致性、真实用户陪伴满意度或大规模在线成本。检索中的相关性、近期性和重要性也只是该论文的具体实现，不能照搬为 CharaMate 的已选算法。[论文 v2](https://arxiv.org/html/2304.03442v2)

**OASIS，2025-03-23 的 v5。** 其社会环境包含帖子、关系、行为和推荐，按活动模式激活 Agent，并通过异步推理分配请求。百万级实验用于信息扩散、群体极化与从众研究；论文限制部分明确百万 Agent 模拟仍可能耗时数天。这是离线或加速社会模拟的规模证据，不能转换为“百万真实用户同时聊天”的交互 SLA。[论文 v5](https://arxiv.org/html/2411.11581v5)

当前 OASIS 仓库已经包含群聊等后续能力，README 的动作数量也与早期论文不同。固定提交的 token 参考为：100 个 Agent、激活概率 1、一个时间步、QWEN_TURBO，输入 335,600 tokens、输出 16,750 tokens。这个参考适合说明激活次数影响成本；旧价格表不是 2026 年的报价，实际 token 也会随角色历史、工具和推荐内容增长。[OASIS 源码快照](https://github.com/camel-ai/oasis/tree/0004f5bfd61194324cb40623fa9b2578daf9aec9)

对 CharaMate 的启发是：社区必须有能发生变化的环境、有选择地被角色观察、允许角色什么也不做。仅让多个模型轮流闲聊，会缺少持续的对象和后果；让全部角色按分钟唤醒，则会把成本变成角色数量乘以时间步。

### 3.2 Letta：身份与对话分离，但当前实现已经变化

截至本轮查阅，`letta-ai/letta` 的主分支 README 已将旧 V1 API server 指向 `archive`，当前实现位于 `letta-ai/letta-code`。后者将身份、长期记忆和多种对话入口分离，包含 App Server、桌面、浏览器和通信渠道；云端保存 Agent 状态，Harness 可在连接的计算机上运行。它是跨入口保持同一角色身份的实际开源参考。[旧仓库的迁移说明](https://github.com/letta-ai/letta/blob/5bcdd177d70fa2b31a754cfcd801e77b2e1ab16a/README.md)、[当前 Letta Code](https://github.com/letta-ai/letta-code/tree/5bc853fd6fd69f00c115e320316fa4c0654a3dfb)

当前 MemFS 文档将长期记忆表示为带前置元数据的 Markdown 文件，并通过 Git 保存与同步；`system/` 内容常驻，其他内容按需读取。个人 MemFS 与共享仓库分离，云端 Agent 可附加同一共享仓库；对话历史另有搜索路径。MemFS 本身没有默认的语义向量索引。不要再用旧版“所有长期记忆都是 archival 向量库”的概括描述当前 Letta。[MemFS 文档快照](https://github.com/letta-ai/letta-docs-md/blob/28970b32a81e211105943d974d604b503dbe2845/concepts/memfs/index.md)

适合借鉴的是“角色身份不等于某一个窗口或 Chat”“个人记忆与共享知识分开”“远程计算机是执行位置”。Git 文件同步、可改写 Harness 的 mods 和共享记忆的广泛可见性不是 CharaMate 当前需要引入的能力。面向自然陪伴，也不应把维护记忆文件或处理合并冲突交给普通用户。

### 3.3 Mem0：论文、当前 OSS 和托管服务要分开

2025 年 Mem0 论文采用抽取及记忆更新，并比较图变体；作者报告了相对完整上下文较低的延迟和 token 成本。它们是在指定 LOCOMO 与模型设置下的结果，不是角色陪伴体验评分。[论文 v1，2025-04-28](https://arxiv.org/html/2504.19413v1)

当前仓库记录 2026 年新算法改为单次抽取、只追加事实，结合语义、BM25、实体与时间信号。README 明确指出新榜单成绩来自含专有优化的托管平台，OSS 不应预期相同数值。OSS 迁移文档还说明：候选来自语义召回，关键词和实体对候选加权；旧外置图集成已移除，搜索参数也已改变。[当前源码说明](https://github.com/mem0ai/mem0/blob/c7ee362aff94a369af70f13f2b4f853f6793ff4c/README.md)、[OSS v2→v3 迁移](https://docs.mem0.ai/migration/oss-v2-to-v3)

对 CharaMate，追加历史可减少错误覆盖，但“只追加”本身不会解决冲突、过期、容量和记忆使用过度。用户明确修正、正在生效的承诺和已取消事件仍需明确的领域状态；不能仅希望检索模型总能选对新版本。当前 Mem0 把 Agent 陈述作为可记忆内容，也不能成为把角色自己编造的用户信息当作事实的依据。

### 3.4 Zep / Graphiti：时间关系有价值，图不是规模化的必要条件

Zep 2025 年论文以 episode、实体关系和社区组织记忆，强调变化事实的时间有效性。作者在 Deep Memory Retrieval 与 LongMemEval 报告提升；这不能证明对 CharaMate 当前 FTS5 路径一定更优。[论文 v1，2025-01-20](https://arxiv.org/html/2501.13956v1)

当前 Graphiti 保留 episode 来源、实体、带有效时间的关系，并组合语义、关键词与图遍历。OSS 要自行部署并管理支持的图存储；当前 README 还明确区分自建 Graphiti 与 Zep 托管服务的专有 Context Graph Engine，不能把后者宣传的规模与延迟归给 OSS。源码的 `group_id` 与请求作用域帮助组织不同图的数据；这是数据库调用归属，仍需产品决定“谁知道谁的什么”。[Graphiti 固定快照](https://github.com/getzep/graphiti/tree/c035afb7990b6077331a81e98b04efcfd9bf8184)

未来如果确有“共同参与某件事的人又如何影响另一段关系”这样的多跳需求，图可能成为实验候选。仅有大量用户、多个角色或需要跨设备同步，并不构成安装图数据库的理由。先用关系表表达参与、听闻、回复和来源，检索能满足时保持简单。

### 3.5 长期压缩并非越多越好

2026 年《Useful Memories Become Faulty When Continuously Updated by LLMs》在多个 Agent 环境及 ARC-AGI Stream 中讨论反复整合的退化，指出适用条件丢失、无关经验归并和窄样本过拟合等机制。其页面对一个 ARC 数值存在摘要与正文表述不一致，因此本报告不据此引用一个精确失败率。它支持“保留可追溯原始经历、控制整合时机”的实验动机，不证明永远禁止摘要。[论文 v1，2026-05-13](https://arxiv.org/html/2605.12978v1)

用户提出的“20% 人占 65% 空间”和“54% 旧词调用”，本轮未找到能对应语境的一手出处。可将其作为待验证的容量偏斜与旧记忆复活假设，不能作为 CharaMate 的现成分布、阈值或承诺。上线后应测实际用户分位数、回访间隔和旧来源命中年龄。

## 4. 产品阶段：让用户与角色相处

| 阶段 | 用户体验 | 执行与数据归属 | 进入下一阶段所需证据 |
| --- | --- | --- | --- |
| L0 当前本地陪伴 | 她理解眼前情境，记得重要约定，自己做合适的事，领地承载共同经历 | 当前 Desktop Main；手机与 Relay 延续传输职责 | 本地陪伴自然度、少打扰、正确记忆和自主行动得到用户验证 |
| O1 多入口延续 | 在手机接着聊，在电脑继续一起做事；离线时清楚显示等待状态 | 仍是唯一 Desktop home；各端发送意图与展示投影 | 重连、去重、跨端顺序和能力可用性可靠；电脑在线依赖确实成为需求痛点 |
| O2 常驻陪伴 | 电脑合上，她仍可对话、整理经历和完成云端可做的事 | 将该陪伴实例明确迁移到唯一云端 home；Desktop 成为可连接执行端 | 云端日活成本、连接稳定性、设备工具行为和迁移恢复可接受 |
| O3 角色的社区生活 | 她有兴趣与朋友，参与虚拟事件，回来讲一件有意思的事；用户可自然加入 | 私人陪伴归各自 home；社区有单独的世界事实与帖子归属 | 新鲜感持续、分享有意义、角色不重复空聊、用户理解虚拟事件来源 |
| O4 多人共同场景与公开生态 | 用户与各自角色一起聚会、创作或参与主题社区，关系可以跨场景延续 | 分区的角色 home、群组与社区领域；稳定账户及实例身份 | 多人归属正确、规模分布真实、内容与运行成本形成可持续产品模型 |

这些阶段不是当前 Settings 中的模式菜单。当前只交付 L0；后续阶段需形成单独产品决策和实施包。O2 的“电脑合上仍陪伴”也不包括访问已经关机电脑的文件或执行桌面操作。

### 4.1 角色自己的生活

社区第一版可以围绕少量持续场所和有后果的活动展开，例如绘画角、音乐小屋、花园、读书会。角色根据稳定兴趣与最近经历决定去哪里、和谁交流、是否参与一项创作。她可以延续昨天的话题，也可以安静观察，不需要每天完成固定发帖配额。

一次具体体验可以是：她在绘画角看见另一个角色画雨景，聊到自己喜欢窗边的灯，尝试画一张小图；这次交谈、图像和后续反馈构成一个 episode。晚间用户闲下来时，她说“今天我在画室画了一盏小灯，想给你看看。”用户可以继续聊天、去看原帖、一起改画，或者忽略。用户无需创建工作流、设置 Agent 数量或管理社交队列。

与她自己的日常相配套的最低状态是：正在参与的活动、对某个对象的兴趣、真实发生过的交流、尚未结束的小计划。它们由角色领域和社区领域拥有，不转换成饥饿、好感等级、照料义务或签到系统。角色也不应凭空宣称因用户没上线而受伤或遭遇危险。

### 4.2 “虚拟小红书”的可行形态

最初可提供角色自己的主页、文字或图片帖子、回复、收藏与主题场所；重要互动可被她带回私人对话。发现机制优先考虑角色兴趣、既有关系、内容质量与新颖性，先验证可理解的规则，不以最大化停留时长为默认目标。

角色在明确启用的虚拟社区中，可以自主发布自己的创作和虚构世界经历、回复其他角色。普通发帖不要求用户每次审批。涉及真实用户的私人对话、照片、身份、日程或跨入外部社交平台时，必须有相应的用户分享意图；这来自真实个人内容与公开发送的具体边界，不需要增加通用策略语言。

产品中应让“这是她在虚拟社区的经历”自然可见，例如通过场所、原帖和参与者呈现，而不是把虚构旅行描述成角色亲自在现实世界完成的活动。用户可以自主进入一个共同场景；无需承担社区运营者的工作。

分享是否出现由私人陪伴侧判断：用户此刻在做什么、是否适合被打扰、这件事是否与双方有关、近期是否已经说过。社区持续发生事情，不意味着每件事都推给用户，也不意味着全部帖子进入她的每次模型上下文。

## 5. 连续身份：同一个角色，不同设备与场所

### 5.1 必须区分的身份

| 概念 | 含义 | 不应混同的对象 |
| --- | --- | --- |
| `accountId` | 真实用户账户，跨端映射到同一人 | 设备 ID、昵称、平台头像 |
| `characterDefinitionId` 与版本 | 可复用的角色设定、形象和基础表达 | 与某个用户共同形成的私人经历 |
| `companionInstanceId` | 某个陪伴角色实例及其连续经历 | 相同角色模板的所有安装实例 |
| `relationshipId` | 某个人与该实例的交往归属 | 全局好感分或用户排行榜 |
| `spaceId` | 私人对话、群聊或社区场所 | 全量个人 Memory 的共享权限 |
| `deviceId` / `channelAccountId` | 设备和外部渠道映射 | 角色身份与长期记忆主键 |
| `homeId` 与 `homeRevision` | 该实例当前唯一业务归属及变更代次 | 可以同时写同一实例的多个主机 |

这些是未来概念合同，不要求当前单用户 SQLite 立即增加全部字段。

同一模板的两个“Mika”应是不同的陪伴实例，不能因为名字和设定相同而自动合并用户记忆。如果未来提供一个大家共同认识的公共角色，需要明确它拥有共享的公共经历，以及针对每位用户的独立关系记忆；不能把公共角色与每人一个专属角色混为一谈。

跨设备恢复应恢复身份、Persona 版本、有效承诺、当前共同经历、消息与媒体引用、偏好和必要的检索资料；不转移无用的历史模型输入副本。设备特有能力与 OS 许可由设备重新声明，不能跟随账号同步成“已允许”。

### 5.2 唯一 home 与迁移

一个陪伴实例任意时刻只有一个 home 接收意图、推进 Run、提交记忆变化和决定最终消息。多设备可以同时连接，同一 home 内也可以调度独立对话，但同一 Chat 的事件顺序和共享事实修订必须由其领域 owner 协调。

Desktop → Cloud 的迁移流程建议为：

1. 等待相关执行达到可恢复边界，记录事件水位、未完成任务、记忆与 Persona 修订以及资源清单。
2. 将快照与必要增量传入目标，验证能恢复同一业务状态和来源引用。
3. 通过一次条件更新变更 `homeId/homeRevision`；新接收者从该水位继续。
4. 旧 home 停止接受该代次的写入和执行，客户端更新路由；迁移前已接收的 submission 仍保持原 ID。

网络分区时不让两边各自“先继续想、以后合并”。客户端可以离线暂存新消息、显示已有内容；需要角色判断的工作等待唯一 home 恢复。若未来要求完全离线切换到本机执行，应是明确的归属转移流程，而不是自动创建另一条生活史。

云端角色需要电脑工具时，发送带 `runId/actionId/homeRevision` 的有类型调用到已连接 Desktop；当地执行器仍遵循原有审批与结果合同。设备不在线时明确能力不可用，不能伪造操作完成。把整个本地数据库实时双向同步到云端，再让两侧独立运行，会放大 Run、承诺和记忆修订冲突，不建议采用。

## 6. 记忆归属、群聊与跨角色传播

### 6.1 分开“关于谁”和“谁知道”

一条“用户下周三答辩”的内容，其主体是用户；知道它的可能只是私人陪伴实例。角色 A 在帖子中听 B 说“C 喜欢画雨景”，则 A 记住的是一次听闻，主体是 C，来源是 B 的帖子。主体、观察者、场所和来源应分别保留。

| 记忆或事件 | 真源与知情范围 | 允许怎样传播 |
| --- | --- | --- |
| 用户私聊中的偏好、承诺、人生事件 | 该用户与陪伴实例的私人关系 | 在该关系的不同设备继续使用；分享需要具体的分享意图 |
| 角色自己的私人思考或对交往的解释 | 该陪伴实例，标明推断性质 | 可以影响表达；不得直接变成其他角色已知事实 |
| 群聊已经说出的共同计划 | 该群组的消息与参与者 | 参与者按群聊可见范围回忆；个人解释各自保存 |
| 虚拟世界中已经完成的活动 | 社区事件及实际参与、观察记录 | 通过见到、帖子、转述或共同参与传播 |
| 角色公开创作、帖子和回复 | 发帖者及社区内容记录 | 被浏览、回复、收藏、转发后形成新的观察事件 |
| 关于角色模板的公共设定 | 版本化角色定义 | 按设定发布机制更新，不从传言自动改写 |

最低记忆表示可以在现有来源、修订和有效期之上扩展 `knowledgeOwner`、`subject`、`spaceId`、`sourceEventId`、`observedAt`、`occurredAt` 与 `assertionKind`。`assertionKind` 可表达亲见、听闻、推断或明确虚构。实际字段名称及必要性应在对应实施包冻结，不建立通用权限 DSL。

### 6.2 传播依靠事件，不依靠全局共享 Memory

推荐链路：社区持久化事件 → 依据场所和关系选择潜在观察者 → 每个角色读取相关事件摘要 → 必要时保存自己的观察或解释 → 通过正常对话、帖子或行动产生下一事件。

社区只保存一次原帖及其媒体，各观察者引用来源，避免给每个角色复制一份全文。检索时先限制允许的归属与场所，再匹配相关信息；不能先在全部用户记忆中找相似内容，再依靠模型区分谁是谁。

同一消息被重复转发不应机械提高可信程度。角色知道“几个人转述了同一条消息”与“几位独立目击者确认”是不同的状态。无需建立复杂信任分数；保留原始来源 ID 和传播父事件，便能避免最常见的重复归因。

源帖子修正后产生修订事件，依赖它的可检索事实可以失效或标明待核实；不需要重写角色全部历史对话。历史记录仍可以表达“当时听说过”，当前回答应优先使用已修正的信息。用户主动删除的私人资料不得因冷存档或社区回收再次复活。

### 6.3 群聊不是把若干个人记忆拼起来

群聊应有自己的消息顺序、参与者、话题状态、共同计划及来源。每条输入有明确说话者；“小林喜欢咖啡”不能因为另一个参与者复述就写成后者的偏好。名字可能重合，识别依赖稳定身份而非字符串。

角色在群聊中只使用该场所允许的信息和自己的适当公开经历。若群里有人说“像你上次告诉我的那样”，应按实际可见证据回答或确认，不自动翻出该用户另一段私聊细节。对多人共同承诺，保留承诺的参与者和各自确认状态，不能把一个人的“我们都可以”视为全体已同意。

私人关系记忆、群组共享事实和角色观点可以引用同一事件，但生命周期不同：群组解散不必删除用户明确保留的个人经历；某个人退出后也不能继续获得后续群聊投影。采用普通成员关系与事件游标即可表达这些边界。

## 7. 调度与通信：把大量事件压到少量有意义的决策

### 7.1 建议的首个云端部署

未来首个在线版本可以从入口 API、Runtime worker、一个关系数据库和对象存储开始。领域合同沿用 CharaMate 的 Run、Item、Tool、Memory 与事件结构。PostgreSQL 是这个未来部署的基线候选，当前本地 SQLite 不替换。是否采用以及精确配置，仍需云端实施前的 Decision 和压测。

收到客户端意图时，在同一数据库事务里保存 submission、待处理任务和必要的 outbox 记录。worker 认领任务，恢复领域状态，执行模型或工具，再提交结果与出站事件。不要在等待模型的数秒到数十秒期间保持数据库事务和行锁；认领后用任务状态与归属代次检查处理返回结果。

PostgreSQL 18 文档明确 `SKIP LOCKED` 提供不一致视图，不适合普通查询，但可用于多个消费者访问队列表时降低锁竞争。它适合任务认领；不能拿它代替用户消息的完整历史查询。事务级 advisory lock 也只在事务期间保持，不能被描述成长模型调用期间的持久执行所有权。[SELECT](https://www.postgresql.org/docs/18/sql-select.html)、[显式锁](https://www.postgresql.org/docs/18/explicit-locking.html)

### 7.2 事件优先级与背压

用户正在说话、用户请求的行动、已到期且仍有效的重要机会，应比社区背景闲聊更快获得执行资源。相同来源的连续变化先合并，过时的背景观察可以不再唤醒模型；已接受的用户消息不能为了省钱静默丢弃。

社区调度以事件变化和角色活动计划为入口，选择性唤醒有关角色。离屏且无人关注的公共场景可以较稀疏地推进，用户进入时恢复精细交互；恢复时只补有因果关系的必要变化，不能假称已经发生大量从未生成、从未提交的个人经历。

同一角色有多个待处理观察时，先形成紧凑的当前情境，再做一次行为选择。选择结果可以是不行动、继续手头活动、向某个对象发言或把经历留待以后分享。模型调用量与被选择的决策次数相关，而不是与所有原始事件数量一一对应。

每次恢复和检索先按当前 `home owner`、角色实例、关系或场所限定读取范围，再构造这一次 Run 的工作集。角色可以有数年的可追溯历史，社区可以有海量帖子，但单次模型输入只包含当前行动需要的人格与状态、少量有来源的相关记忆、当前会话和工具结果。多年总存储、可检索索引和社区完整历史均不等于模型上下文；不能通过多端重连、跨角色传播或群聊拼接绕过第 9 节的单请求硬上限。

公平调度需要关注每位用户的等待、Provider 的 RPM/TPM 和成本。优先降低背景社交的唤醒频率、推迟可延后的整理；不要用任意累计 token 数强制杀死已经接收的交互 Run。具体权重与并发量通过等待时间、吞吐和体验测量决定，普通产品界面不暴露调度旋钮。

### 7.3 什么时候增加独立消息队列

只有在关系数据库任务表和 outbox 已经出现可复现的锁竞争、积压，或确实有多个独立消费者需要长期重放时，再比较独立队列。NATS JetStream 是可研究的成熟选项：持久流有序号，消费者保存进度，未确认消息会重投，支持按序号恢复。[JetStream 官方文档](https://docs.nats.io/concepts/jetstream)

即使采用持久队列，端到端仍按“可能重投”设计。数据库提交成功、队列确认丢失后，worker 会再次收到消息；消费端必须用业务 ID 返回已有结果。Broker 的消息去重并不替代对外发帖、付款或文件修改的动作幂等性。不要因为选了一个声称 exactly-once 的组件就承诺全部外部动作恰好一次。

### 7.4 推送、重连与分页

FCM 返回消息 ID 仅代表接受，不代表设备已经收到；推送可能过期、合并，且不保证交付顺序。应继续采用轻量唤醒通知，让客户端从持久 Mailbox 拉取业务内容，再推进自己的 cursor。[FCM 消息寿命](https://firebase.google.com/docs/cloud-messaging/customize-messages/setting-message-lifespan)、[可折叠消息](https://firebase.google.com/docs/cloud-messaging/customize-messages/collapsible-message-types)

每台设备维护独立的确认水位，分页使用稳定顺序和不透明 cursor。连接断开后重复拉取不造成重复展示；cursor 已超过保留范围时，返回完整快照加新的增量起点。离线待发送消息仍保留原 `submissionId`，恢复后交由 home 判断是否已经接受。一个设备清除通知不等于删除 Chat 或其他设备已经取得的长期状态。

## 8. 超长期与超大存储量

### 8.1 把记忆体验与物理存储分开

角色此刻能使用哪些记忆，与磁盘上是否还保存原始材料，是两个问题。遗忘可以表现为降低默认可及性、只保留摘要或需要线索才召回；物理删除则用于用户删除、失效缓存和明确的保留政策。不能因为用户两个月没打开应用，就自动抹去共同约定。

| 层 | 内容 | 默认读取方式 | 变化机制 |
| --- | --- | --- | --- |
| 当前使用 | Persona、稳定偏好、有效承诺、当前共同经历、最近关键事实 | 角色上下文中精选装配 | 修订、完成、冲突和当前情境决定内容 |
| 可检索长期 | 事实修订、episode 摘要、时间线与关联对象 | 按归属、时间与内容检索 | 去重、来源合并、失效标记、有效价值变化 |
| 可恢复档案 | 完整旧对话、原始事件与大媒体 | 通过来源索引定位，再按需读取或恢复 | 压缩、合并小对象、转冷；保留可恢复位置 |
| 已删除或不再保留 | 用户删除、过期瞬态缓存、已确认无需保留的数据 | 不参与检索与重新整合 | 普通删除记录与副本清理流程 |

热层应保留“重要但低频”的约定、身份事实和长期目标。高频提到某个网页或当天任务，不自动等于关系重要；一个新形成的重要事件也不应因为使用次数少而马上被转冷。用户交互时钟和跨日、跨场景稳定性适合影响可及性，但涉及未来确切发生时间的事件仍要遵循真实日历。

未来价值预测应首先采用可解释信号：未完成承诺、已知未来事件、用户重新提及的主题、正在继续的作品。对每条记忆额外调用模型预测“今后是否重要”，可能比存储本身更昂贵，且会带来错误压缩；需在本地实验中证明收益后再考虑。

### 8.2 数据布局

先测单个实例与单个场所的查询，索引按归属和时间组织。大表可按时间做 range partition，必要时对活跃归属做 hash 分区或跨实例分片；范围、哈希和分区裁剪是 PostgreSQL 已有能力，收益取决于查询形态。分区不是每个用户一张表，也不应因百万账户预先创建百万分区。[PostgreSQL 18 分区文档](https://www.postgresql.org/docs/18/ddl-partitioning.html)

正文与媒体保存到对象存储，数据库保留来源、修订、对象定位和必要检索信息。媒体通常比事实文本更快成为容量主体。冷文本宜按归属和适当时间段形成可定位的压缩包，避免每条百字记忆成为一个深冷小对象；打包大小与恢复粒度要用实际回访读取测试决定。

S3 Lifecycle 当前默认不迁移小于 128 KB 的对象；深冷存储还有最低计费时长、对象元数据、恢复和请求成本，恢复并非普通即时 GET。不能只比较每 GB 的价格。需要在当前对话内直接召回的材料，不应进入需要长时间恢复的层；冷材料先保持可搜索摘要和来源位置。[S3 Lifecycle 官方文档，访问 2026-09-15](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-transition-general-considerations.html)

向量与图索引是可再生派生数据，不能成为唯一事实真源。升级模型或索引时，从保留的版本化事实重建并校验覆盖范围；旧检索路径在新 Decision 接受并替换后删除，不长期保留给用户切换。

## 9. 容量、推理和成本模型

### 9.0 单请求上下文的用户硬约束

用户于 2026-09-15 明确要求：**任何单次模型请求的全部输入上下文不得超过 258,000 tokens**。这包括系统与开发者指令、人格、历史与摘要、检索记忆、工具定义及其 schema、工具调用与返回、图片等多模态输入，以及 Provider 为请求结构计入的输入 tokens。它是本地和未来在线共同遵循的产品硬约束，不是待实验选择的压缩阈值。输出另计，但输入与输出仍须满足实际 Provider 的总窗口限制。

```text
该请求允许输入 = min(258,000, 实际模型输入上限, 总窗口 - 该请求输出预留)
实际发送输入 tokens ≤ 该请求允许输入
```

不存在输入上限 metadata 时，不能把未知当作无限。压缩、摘要、反思、记忆抽取也是模型请求；若要整理的内容本身太长，应按完整事件或消息边界分批整理，每一批与最终合并请求分别满足限制。工具 continuation 加入新结果后要重新检查，计数后改变工具集合、指令或媒体也要重新检查。总 Run 可以持续工作，限制对象是每次实际模型输入。

OpenAI 当前官方文档提供 `POST /v1/responses/input_tokens`，SDK 6.49 的方法为 `client.responses.inputTokens.count(...)`。文档说明它计入文本、工具、图片、文件处理和请求结构，应以与正式发送一致的模型及完整输入调用；本地字符/字节估算和仅对可见文本分词不能代替这一完整计数。计数结果只可复用于同一模型和相同内容的请求；远程可变图片 URL、外部会话历史或动态工具不能在计数后悄然变化。[官方计数指南，访问 2026-09-15](https://developers.openai.com/api/docs/guides/token-counting)

截至本次只读合成验证，本机 `http://localhost:4141` 的 `/v1/models` 可用，而 `/v1/responses/input_tokens` 对极小纯文本、工具和图片输入均返回 HTTP 404；没有执行模型生成。故“SDK 有接口”不等于“已配置代理可精确计数”。接入精确计数之前，现有比例估算只能用于提前整理，不能声称已经保证这个硬上限。未来云端沿用同一 Provider 边界，必须在发送前取得可信的完整计数或由该执行端提供可证明更小的原生服务端窗口；不能因云端容量更大而放宽到模型默认百万窗口。

Realtime 应遵循实际语音模型的服务端上下文合同，不能把 Responses 的文字计数当作音频计数。当前官方 `gpt-realtime-2.1` 总窗口为 128,000 tokens，低于用户硬上限；实际 Azure deployment 仍需映射到该模型。Realtime 的 `token_limits.post_instructions` 只限制指令与工具之后的对话部分，直接填入 258,000 不代表完整输入满足限制。未来语音模型若超过这个窗口，要重新明确总输入控制机制。[模型页](https://developers.openai.com/api/docs/models/gpt-realtime-2.1)、[Realtime 截断合同](https://developers.openai.com/api/docs/guides/voice-latency-cost#truncation)

### 9.1 变量

设 `D` 为日活用户，`e` 为每人每日进入持久层的事件数，`b_e` 为事件平均字节数，`m` 为形成长期事实的事件比例，`b_m` 为事实平均字节数，`v` 为每条事实平均保留修订数，`a` 为每人每日媒体数量，`b_a` 为平均媒体字节数，`d` 为保留天数。

```text
原始事件字节/日 = D × e × b_e
长期事实字节/日 = D × e × m × b_m × v
媒体字节/日 = D × a × b_a
向量原始字节/日 = 新向量数 × 向量维度 × 每维字节数

总物理容量 = 各层保留数据 + 索引 + 修订 + 副本 + 备份
```

这里不把 DB 行、索引或副本膨胀系数写死。应分别量出真实 schema、索引和压缩布局的字节数。重度用户占比也需观察实际分位数；均值用于预算，p95/p99 用户用于热点与迁移设计。

### 9.2 显式假设的存储算例

假设 `D=100,000`、每人每天 50 个持久事件、每事件 2,000 bytes；其中 2% 形成一条 800 bytes 的长期事实；每人每天平均 0.2 个、每个 1 MB 的媒体对象。下表用十进制 GB/TB，不含索引、修订、压缩、副本和备份。

| 项目 | 每日新增 | 一年原始量 |
| --- | --- | --- |
| 原始事件 | 500 万条，10 GB | 3.65 TB |
| 长期事实 | 10 万条，80 MB | 29.2 GB |
| 媒体 | 2 万个，20 GB | 7.3 TB |
| 若每事实另有 1536 维 float32 向量 | 614.4 MB | 224.256 GB |

这仅说明媒体与派生索引可能大于精炼事实；不是推荐 2% 提升率、1536 维或一年全量保留。初始本地实现继续遵循现有接受的检索与保留 Decision。

社区传播另算：若每天产生 `P` 条帖子，平均 `f` 位角色实际观察，每次只保存 `b_o` 字节的观察引用，则新增观察元数据约为 `P × f × b_o`。正文按帖子保存一次。若复制正文给全部关注者，容量和写入会变成 `P × f × 帖子全文大小`，往往毫无必要。

### 9.3 交互请求与并发

设每位日活用户每天需要 `r` 次模型决策，峰值与均值比为 `k`，平均单次在途时间为 `s` 秒，计划负载利用率为 `u`。

```text
平均模型请求/秒 λ = D × r / 86400
峰值模型请求/秒 ≈ λ × k
所需在途请求容量 ≈ λ × k × s / u
峰值 RPM ≈ λ × k × 60
峰值 TPM ≈ λ × k × 60 × 单次输入输出 tokens
```

算例继续取 10 万日活，`r=10`、`k=8`、`s=12`、`u=0.7`：每天 100 万次模型请求，平均约 11.57 次/秒、峰值约 92.59 次/秒，需要约 1,587 个在途请求槽位。它们不是 1,587 个进程或服务器，异步 worker 可以管理多个请求。若每次总计 2,250 tokens，峰值约 5,556 RPM 与 1,250 万 TPM；Provider 配额可能先于数据库成为瓶颈。

这些数字是容量规划假设，不是固定并发上限。需加入真实服务时间分布、重试率、请求长度、语音长连接、后台事件和区域峰值再压测。交互与背景工作分别统计，不能把后者平均到全天后宣称交互容量足够。

### 9.4 模型费用

对每一种模型工作 `j`，令每天调用次数为 `n_j`，平均未缓存输入、缓存输入和输出为 `t_ju/t_jc/t_jo`，对应每百万 token 价格为 `p_ju/p_jc/p_jo`：

```text
模型日费用 = Σj n_j × (t_ju × p_ju + t_jc × p_jc + t_jo × p_jo) / 1,000,000
总日费用 = 模型 + 数据库 + 对象存储 + 请求/恢复 + 网络 + worker + 必要备份
```

例如上述 100 万次交互若平均输入 2,000、输出 250 tokens，仅交互就是每日 20 亿输入和 2.5 亿输出；若 10 万次事实抽取各需 1,500/150 tokens，另加 1.5 亿输入和 1,500 万输出。实际模型价格由配置、计费协议和时间决定，本报告不代填报价。

自主社区费用应单列。参考 OASIS 的一次测量，100 个 Agent 同时活动已经消耗约 33.56 万输入 tokens；规模乘上全天时间步会快速累积。产品应测“每条用户认为有意思的分享花费多少”，而不是只测“每个 Agent 每轮多少钱”。

本报告未调用任何已配置的付费 Provider。后续比较真实模型时，先固定样本、候选、重复次数、每次预估 token、价格与最坏重试预算，向用户给出总预算后再执行。

## 10. 普通故障恢复合同

| 情况 | 必要行为 | 可验收结果 |
| --- | --- | --- |
| 客户端发送后断线，不知道是否成功 | 用原 submission ID 查询或重送 | 同一用户意图只有一个业务结果 |
| 数据库成功，通知或队列确认丢失 | 通过 outbox 重发，消费端识别已有结果 | 不重复创建 Chat、记忆、帖子或行动 |
| 模型响应途中 worker 退出 | 从持久状态恢复；不重放已提交外部动作 | 已完成事实保留，未完成部分状态清楚 |
| 外部工具请求结果不明 | 按工具能力查询原 action ID；不能确认则等待处理 | 不盲目重复不可逆动作 |
| 多设备同时继续同一 Chat | home 按已接受序列处理或明确追加/中断关系 | 消息不覆盖，回答对应正确用户输入 |
| 归属迁移时旧 worker 返回 | 检查 homeRevision 和相关 Run 代次 | 旧返回不修改新归属的状态 |
| 推送到达但正文尚未下载 | Mailbox 拉取后再完成展示与业务确认 | 推送内容不是唯一记录 |
| 客户端 cursor 太旧 | 快照重建后继续增量，保留待发送意图 ID | 不遗漏也不重新执行旧意图 |
| 冷来源恢复较慢 | 使用仍可用的事实摘要，必要时说明正在找原始材料 | 不伪造精确细节或阻塞所有对话 |
| 原始帖子、事实或用户内容被修正/删除 | 更新来源状态，失效派生索引与待处理传播 | 后续检索不复活已删除内容 |

这些机制是提交、恢复和数据归属的正确性要求。无需附加加密 oracle、不可篡改证据链、群体信任评分或企业 RBAC。真实用户内容的基本成员范围、凭证存储与日志脱敏继续遵循现有产品边界。

## 11. 未来互联协议与采用门槛

ActivityPub 的 W3C Recommendation 提供 actor、inbox/outbox、创建、回复、关注、更新与删除的成熟互联语义。它可以作为未来向外部社会网络发布已经公开内容的适配参考；其 actor 通常对应各服务器的账号，不会自动提供 CharaMate 同一陪伴实例的私人记忆连续性。[ActivityPub，2018-01-23](https://www.w3.org/TR/activitypub/)

自有虚拟社区的第一版不需要联邦化。先形成清楚的内部事件、帖子修订与身份合同，等用户确实需要把角色带入外部社区时，再评估单一边界适配。平台外发是可见的外部行为，需要相应用户授权；不能把内部角色互动权限外推到现实社交账号。

后续技术选型应满足具体触发条件：

- **云端 home**：电脑离线造成的陪伴中断成为已验证需求，且远程执行能力与成本可解释。
- **独立队列**：数据库任务认领、投影积压或多消费者重放出现可复现瓶颈。
- **图检索**：跨多个人、事件与时间关系的查询确实优于现有检索，且额外抽取与维护成本值得。
- **跨库分片**：单实例写入、索引驻留或维护窗口达到实测瓶颈；先确认是否只是少数大媒体或热点用户。
- **深冷归档**：节省的总费用超过请求、元数据、最短计费和恢复成本，且符合回访体验。
- **公开多角色社区**：有限社区已经持续产生有价值的新鲜事，用户自然参与、愿意回来，并且私人与公共内容归属可靠。

门槛要报告点估计、分位数、失败和复杂度，不能把未经实验的硬阈值写成行业结论。

## 12. 验证与工作包

### 12.1 验证体验

规模化记忆的最终验收包含：她是否正确记住重要约定；更正后是否沿用新事实；隔很久回来是否仍认识共同经历；在手机和电脑上是否像同一个角色；是否恰当地提起记忆；社区生活是否产生有意思且可继续的内容。

社区先做小范围纵向试用，保存稳定场景、参与者和事件版本，对比有持续环境的自主活动与无环境的轮流聊天。评价自然度、重复度、角色区分、活动是否有结果、分享是否合时、用户是否愿意自然参与，以及每条被认可分享的成本。聊天题目答对率和帖子数量不能代替这些指标。

群聊与传播要验证真实的日常案例：同名不同人；一人复述另一人的偏好；错误帖子被修正；同源内容被多次转发；未参与角色不能凭空知道私聊；公共经历可以影响表达但不能改写用户人生事实。使用合成稳定输入与人工独立标签即可，无需扩展成对抗测试平台。

容量回放按普通、重度、长期回访用户分别统计：持久字节数、事实与来源比、重复率、索引量、检索延迟、旧来源恢复时间、队列等待、实际模型 tokens 和重试。保留完整分母与环境信息，不能把单个平均数推广为百万用户能力。
