# AI 陪伴记忆研究：形成、使用、遗忘与长期连续性

调研日期：2026-09-15。范围：本地 CharaMate 的可实行方案，以及在线、多角色、多用户场景的后续方向。本文保留首轮研究与候选方案，不是生产选型 Decision；其中旧检索基线和实验建议不能当作当前默认。最新所选实现见[本地方案](ai-companion-local-implementation-2026-09-15.md)和对应 Decision。用户随后已授权商业重构真实评测不设总预算，固定 gpt-6-astra 和单请求完整输入不超过 258,000 Token；本文初期资料调研与公开数据计数本身没有调用付费模型。

2026-09-16 实施状态补记：下文交互时钟、成功使用信号与淡化规则是原研究候选，不能作为独立机制已经实现或本轮验收已经完成的证明；相关本地效果仍须按 Goal 的要求验证。Main v21 未保留独立互动日/engagement、未来需求预测或额外反馈投影；真实来源、普通反馈事实、按需检索及有来源的局部巩固沿唯一 Memory 路径实现，见 MEMORY-ADAPTIVE-CONSOLIDATION。R0/top8、U2 和“推断只进候选”的旧基础已由后续形成/检索契约替代；第 2–13 节的原假设、方案、未执行规模和当时结果保留原日期与分母。

## 1. 产品目标

用户需要的是一个逐渐理解自己、记得共同经历、知道何时回应和何时安静的角色。记忆的成果应表现为：用户时隔几个月说“上次那个面试”，角色能找回当时的事情，知道后来是否有变化，并按用户当时表达的需要回应；平常不会不断复述“我记得你喜欢……”，也不会因为用户一段时间没打开应用就忘掉重要约定。

“超类人”适合描述可检索的长时间跨度、可靠修订、准确保留用户明确表达的边界与跨场景连续性，不应描述为已经复现人脑、能准确读懂情绪或拥有人的情感。认知科学提供结构和假设，产品效果仍需要本项目验证。

现阶段优先提高三件事：

1. 存进去的是有证据、有时间、有归属的事情，尤其是用户如何经历它、希望怎样被回应，以及明确约定。
2. 在当前情境中找回合适证据，同时保留纠错、沉睡后重新想起和表达不确定的能力。
3. 把记忆自然用于回应和行动，而不是展示记忆库的容量或让用户不断管理条目。

研究基线 `fc81239` 暴露了一个观测口径问题：memory_usage 的 consumer 只有 context 和 tool。MemoryService.search 和 selectContext 在找到结果后就记录 usage；lastAccessedAt 来自这些记录，并在该基线参与 R0 的后续排序。因此它表示“被系统取出/暴露”，不表示用户重新提起，更不表示记忆在最终回答中使用正确。后续 [COMPANION-MEMORY-LIFECYCLE](../benchmarks/COMPANION-MEMORY-LIFECYCLE.md) 已选择并实现曝光中立排序，移除 lastAccessedAt 的排序影响，UI 改称“检索与上下文引用记录”；usage 继续作为检索/上下文观测保留。这里的旧排序描述不能当成此次集成后的现行行为。

还有一个数据限制：memory.record 当前明确要求不记录 unchanged memories，重复结果不等于一次新的用户确认。因此，历史 Revision 和 source 可以作为“已记录的形成/修订证据”，不能称为完整的用户重提轨迹。不能仅凭 sourceType=chat 就断言是用户明确陈述；候选的原始推断也可能来自 Chat。

### 3.1 公开数据计数与论文版本不能混用

本次直接读取 LoCoMo 官方 commit 3eb6f2c585f5e1699204e3c3bdf7adc5c28cb376 的 data/locomo10.json，并用 JSON 解析计数：10 conversations、1,986 QA，category 1–5 分别为 282、321、96、841、446；排除 category 5 后是 1,540。文件 SHA-256 为 79fa87e90f04081343b8c8debecb80a9a6842b76a7aa537dc9fdf651ea698ff4。这是公开输入的校验和与计数，不是模型评测结果。

因此应明确区分：LoCoMo 会议论文的对话规模描述、当前官方小规模公开文件、A-MEM v1 所述 7,512 QA，以及 Mem0 等论文排除一种题型后的评测集合。除非输入、问题类别、评判器和模型一致，不把公开排行榜的百分点差异解释为纯算法增益。

### 3.2 工业实现的版本漂移

Mem0 当前 README 宣称自动抽取为单次 ADD-only，不再让抽取过程覆盖旧记忆。本次进一步读取 [main.py 的固定版本](https://github.com/mem0ai/mem0/blob/c7ee362aff94a369af70f13f2b4f853f6793ff4c/mem0/memory/main.py)：自动 add 流程先查已有记忆，使用 additive extraction prompt，再批量建新记录及去重；公开 update API 仍存在，所以“ADD-only”不能解释成整个库不允许更新。search 文档还把 reference_date 标为 platform-only、OSS 不支持；不能将平台宣传中的每一项时间能力推定为开源实现均有。

Hindsight 当前 README 继续提供 retain/recall/reflect，存储说明包括 PostgreSQL + pgvector 或 Oracle；其 memory 类型描述已出现 mental models。Graphiti 当前 README 强调 episode 来源、双时间信息、事实失效保留历史，并列出 Neo4j/FalkorDB 等后端。本文使用这些固定版本理解机制，不引入其依赖或替换 CharaMate 的 Run/Memory 所有权。

### 3.3 两组容量/调用数字尚未溯源

对“20% 人占 65% 空间”“54% 旧词调用”，本次以中英文相关组合检索，没有找到可确认定义、分母、时间范围与采样方法的一手来源。这不证明数字一定错误；目前只能把它们当待验证的行业个例或产品假设，不能写成本项目观测。

后续应该自己量出：按用户/角色/介质分组的存储占比、不同年龄段记忆的真实用户查询命中、用户很久不互动后的找回率，以及多次提及是否来自同一次会话。日历年龄、交互年龄、被模型曝光年龄必须分开。

## 4. 把“形成 × 检索 × 使用”变成可测模型

用户提出的乘性直觉很有价值：第一段没有形成正确记忆，后面再强也无从找回；已经找回但没有用好，用户同样不会觉得被理解。但把多个减去 baseline 的分数直接相乘，可能出现负数或尺度不一致；对“使用力度”使用单调 sigmoid，还会暗含记忆用得越多越好。

在确实需要记忆的任务子集中，可以用条件概率作可解释分解：

$$
P(\text{成功的记忆帮助})
=P(F)\,P(R\mid F)\,P(U\mid R,F)
$$

F 表示需要的事实正确存在，R 表示所需证据被找回，U 表示证据被正确、适度地使用。这是事件链的概率分解，不假定三个阶段独立，也不是经过验证的陪伴体验定律。

诊断实验分别提供真实形成结果、完整正确记忆、或正确检索结果，比较哪一步导致损失。这里的“完整正确记忆”是普通人工标注参照，不需要额外密码学或证据系统。

完整体验还需要单独测量：回应是否贴合当下需要，是否把旧观点当现状，是否无端提起敏感往事，是否反复炫耀记忆，角色是否自然可亲，以及延迟和成本。评价时保留每一维，不急于压成一个“羁绊分”。

使用力度应当按情境验证。用户只说“今天好累”，合适的回应可能只是理解与陪伴；用户说“还记得我上次为什么不想面试吗”，才需要具体召回。可在相同事实下比较克制、适度、过量三种表达，用成对偏好测自然度和理解感，而不是奖励显式引用的数量。

| 前瞻记忆 | 未来的约定、触发线索、明确取消/完成 | commitment/event + occursAt/timeZone，复用机会调度与自动化边界 |
| 程序经验 | 哪种行动方法在什么前提下有效、用户怎样反馈 | procedure/agent_learning；可执行 Skill 仍由既有 Evolution/Skill 生命周期拥有 |
| 暂时情绪 | 用户当前表达的感受和此刻需要的互动方式 | 当前 Run/Chat 工作集；不能一次低落就成为长期人格结论 |
| 综合理解 | 跨事件的暂定解释，支持它和反对它的证据 | 推断仍是候选，不以反思结果覆盖明确事实；没有必要新增全局“心理画像分” |

一个有用的情景记忆可以写成自然语言：“准备周五面试时，用户明确说担心被临时追问，希望我先陪他练一遍，不要立刻给长清单；后来第一轮练习完成了。”情绪与需求只来自当事人表达或确认。角色自己的解释可以是当次回复中的试探，不必都持久化。

不要求每段对话都生成上述字段，也不把字段全部加入每轮上下文。先用现有 event/commitment 内容验证表达是否改善用户体验，再决定是否增加稳定的查询字段。多维是同一事实的不同检索视角，不是多份互相漂移的事实副本。

## 6. 主动、被动与反思的形成路径

主动形成继续由当前模型在理解语境后调用 memory.record：明确持久事实直接形成；精确改口创建同一 Memory 的 Revision；临时问题和无变化复述不强制生成新记录。

被动形成复用 Activity。观察到的只是行为事实，不能自动赋予情绪或关系含义。当前跨完整周稳定模式的候选规则先保留；若要替换它，需要单独证明新算法降低噪音又没有错失有价值经历。

反思的输入应是新完成的具体经历、用户反馈和可核对的旧证据，不是定时重读整个聊天库。最小候选可在 Journey 出现真实转折、用户主动回顾或既有 Evolution 触发时进行一次综合；它不拥有第二个持续运行的模型循环。没有新证据就不更新；失败保留原状，重复触发不得无限增加候选和 Revision。

应避免“摘要的摘要”逐步丢失原意。综合记忆需要指向原始来源，纠错仍能找到产生结论的那段用户表达。若模型反复读自己的总结，这些读取不能变成独立支持证据。

角色自主不等于悄悄把猜测升级成事实。可以自主理解、回应、选择安静、形成明确事实；需要长期采用的新推断保留现有候选边界。不要为每条记忆新增一次用户审批，也不要让普通用户配置衰减系数、查看排名或管理记忆层级。

## 7. 交互时钟、淡化和重新想起

### 7.1 先区分三种信号

1. **曝光**：进入 Context 或由工具返回。用于调试和避免重复提起，不增强长期重要性。
2. **真实用户证据**：明确形成、改口、用户确认，及将来能够可靠识别的真实重提。按来源事件去重，重放和同一来源的多次抽取只算一次。
3. **成功使用**：记忆支持了一次正确回应或行动，并存在可核对反馈。不能仅凭模型自报“我用了它”就认定成功。

第一版可以准确记录前两者的已知部分；第三者和任意自然语言重提识别需要语义标注与模型实验。旧 usage 不回填成真实用户证据。用户没有反驳，也不自动算正反馈。

跨日支持数量应采用去重后的实际用户来源日，而不是同一晚重复 100 次的词频。已明确修订的来源也不能都算作当前内容的支持：旧的“喜欢 A”和新的“不喜欢 A”支持的是不同 Revision。

### 7.2 交互时钟的定义

候选采用“真实用户互动推进的活动日序号”衡量可访问性年龄：有用户消息或有效语音 turn 的日期推进；Activity 采样、后台任务、主动气泡、工具续步、无用户输入的模型输出不推进。

必须同时保留日历时间。日历时间用于事件发生、事实有效期、跨年查询和提醒；交互年龄只用于自动回忆的优先级。两者不能互相替代。

Memory 域通过 typed 事件接收有效用户互动，不跨域扫描 Chat 表。事件带稳定来源 ID、实际时间和当时采用的时区；重放不重复推进。历史活动日不能因用户更换时区而被重新解释成更多互动，离线休眠本身也不推进交互年龄。

如果首版只能利用形成/修订来源，应该把指标称为“有记忆证据的互动日”，明确其覆盖不足；不能宣称它代表全部用户互动。

### 7.3 保护与淡化

自动 Context 的候选规则应先排除不合法证据，再处理排序/淡化：

- 当前稳定画像、用户 pinned 记录、未明确完成或撤销的承诺、未来相关事件、新记录及新 Revision 进入保护范围。
- 当前代码没有完整的 commitment 完成状态时，保守保护仍 active 的 commitment；不能从日期已过推断承诺已完成。
- importantMoment=false 可能表达不希望主动联系，并不表示这件事不重要；不能将它作为唯一重要性判断。
- 单会话、无后续支持的普通情节可以逐渐减少自动注入；已明确纠正的旧事实不以“熟悉”为理由恢复成当前事实。
- 新记录的保护窗口、衰减形状和阈值都属于本项目待测参数。不得直接复制 MemoryBank 的 S=1 或某篇论文的半衰期成为默认值。

本地首先比较可解释的规则，不训练“未来价值预测器”。可用特征包括：当前查询匹配、明确保护状态、距上次真实用户证据的交互年龄、不同来源日的支持、同一事件在不同情境被调用的证据、当前事实是否仍有效。所有特征都要能解释其来源。

### 7.4 “沉睡”是可访问性，不是数据删除

推荐让淡化成为自动 Context 选择阶段的派生属性，保留 Memory、Revision、来源和 FTS 文本。不要把低活跃记录自动改成 archived，否则当前 memory.search 的 active 过滤会使明确查询也找不回来。

明确查询仍走同一 R0 检索与历史过滤。提到旧项目、旧地点或明确过去时间时，应能取回相应事实；找回后是否变得更容易自动提起，取决于新用户证据，单次系统曝光不升级。一次旧故事被提起，也不意味着它的全部关联事项重新进入每轮上下文。

用户手动归档/删除继续保留现有语义，不能以“唤醒记忆”为由绕过。已被替代的旧事实只在明确历史问题中作为当时情况出现。

“可逆回收”在当前本地范围首先意味着重建自动 Context 的选择，不意味着先删除再想办法恢复。未来如确有介质冷存储需求，应先确认文件已可靠转移、来源链接可解析、恢复行为经过测试，再回收冗余热副本；它仍不是删除事实的许可。

## 8. 最小实现拆分与责任

这部分是可交付工作包建议，具体参数和候选胜出需要后续 Decision。共享合同与数据库变更由同一集成 owner 串行整合。

| 工作包 | 结果与归属 | 验证与边界 |
| --- | --- | --- |
| 用户证据与曝光分离 | MemoryService/Repository 记录去重证据信号，来源生成沿既有 memory.record 宿主边界；保留旧 usage 的曝光意义 | 重复工具调用、恢复、同日重复不虚增；用户改口记录到新 Revision；推断来源不能伪装明确陈述 |
| 交互时钟 | Main 在合法用户输入持久化后通知 Memory；Memory 域拥有活动日状态 | Text/Voice 同一语义；无声/background 不推进；时区变更、重启和晚到事件行为确定 |
| 自动 Context 选择 | 在现有 selectContext 中接入已选单一策略，R0 与 final top8 容量保持固定；显式检索不经自动淡化过滤 | 模型每轮不再重复整套检索；不新增用户设置或算法开关；保护与旧事找回成对验证 |
| 情景内容与自然使用 | 当前模型继续采用 event/commitment 记录表达过的情境、需要和结果；角色指令强调适度使用 | 使用真实预算内模型做形成质量与回应偏好 pilot；离线排序不能替代此项 |
| 存储可见性 | 使用已有领域文件/表元数据测大小与增长，区分文本、Revision、usage、图片、截图 | 先测容量贡献，不因理论“海量”引入独立向量库、图服务或周期模型压缩进程 |

若需要新表，优先只有一个由 Memory 域拥有的证据信号/活动日存储，并说明能否由现有记录可靠派生；不要同时保存同一可计算计数的多份真相。增长型曝光日志能否保留为汇总，属于独立存储取舍，不能在本次排序修改里悄悄删除现有使用历史。

正确性修复可以先落实：明确字段语义、不以曝光强化、来源去重、不绕过用户删除、保护尚未履行约定。衰减参数、未来价值打分、自动关联扩散和更丰富的形成策略属于选型问题，先实验再保留唯一生产实现。

## 9. 不调用付费模型的纵向配对实验

### 9.1 目的与输入

目标是检验“交互时钟 + 真实用户证据 + 保护 + 自动注入淡化”是否以更少的无关证据，保留当前任务需要的记忆和旧事重现能力。此实验不评价模型的情绪理解，也不声称获得真实未来需求分布。

建议第一轮使用 24 个独立手写人物/事件轨迹模板，每个派生 4 种时间表，得到 96 条轨迹；每条安排 6 个事先标注的查询点，共 576 个查询观测。这里是建议的预注册规模，尚未执行，不是项目测试通过数。独立单位主要是 24 个模板，不把 576 个相互依赖的查询当成 576 位用户。

时间表保持事实、事件顺序和用户措辞不变，只改变：连续使用、稀疏使用、长时间离开后返回、后台事件非常密集但用户互动少。改变日历时间时，相对发生关系和查询中的时间表达同步更新，避免制造错误的历史答案。

标注由故事脚本确定“什么事实正确、应返回哪个 Revision、哪些候选有帮助、哪些已经过时”，不得用候选打分公式反推标签。自然语言 query 不包含内部 ID；开发模板和保留模板按完整人物/故事隔离，避免仅改措辞的同一故事跨集合。保存随机种子、输入 hash、基线版本和逐项输出即可。

### 9.2 必须包含的情形

| 情形 | 主要检查 |
| --- | --- |
| 同一晚长时间重复普通话题 | 多次曝光或同会话重复不压过一次明确的重要约定 |
| 只说过一次的核心约定 | 没有高频也必须保留；未完成不因日历变久失效 |
| 新记录遇到旧记录大量噪音 | 新形成/新修订不被立即淡化 |
| 明确改口及之后再问过去 | 当前查询取新 Revision，明确历史查询取当时 Revision |
| 离开数月再次回来 | 仅日历流逝不导致承诺被忘；旧事实仍可找回 |
| 长期未提到的具体事件被突然重提 | 显式查询能找回，找回一次不导致随后所有无关对话反复提起 |
| 同一用户在不同活动日和情境确认同一事实 | 独立支持区别于一次长会话和模型自述 |
| 没有形成过的事实 | 返回空或不足，不因“很像”伪造证据 |
| 用户归档、删除、取消 | 不以淡化恢复机制绕过用户动作 |
| 后台自动化、Activity 和重启重放 | 不推进用户交互 clock，不强化记忆 |
| 时区切换和跨日语音 | clock 可复现，不重复计算同一合法来源 |
| 使用成功但没有明确用户反馈 | 不把模型自评当已证实强化 |

### 9.3 按一个变量分阶段比较

第一阶段只比较“把 context/tool 曝光作为最近访问”与“曝光不参与用户强化”，其他排序、内容和查询相同。

第二阶段在同一证据规则下比较不淡化与自动 Context 淡化，显式查询都保持 R0。第三阶段固定同一个淡化函数，只替换日历年龄和交互年龄。保护规则另做消融，用来说明哪些结果依赖保护，而不是把多个同时改变的因素归功于交互时钟。

所有候选复用同一 FTS 索引、同一输入、同一权限/当前性过滤、同一 final top8 与上下文预算。若要扩大召回候选池或引入重排，应单开检索实验，不混入遗忘比较。SQLite 的 BM25 是分数越小匹配越好，实现和指标必须统一方向；依据为 [FTS5 官方文档](https://www.sqlite.org/fts5.html)，查阅于 2026-09-15。

阈值只在开发集合确定，保留集合只用于一次确认。若优势只存在于为候选编写的等分词面样例，应报告没有证明一般中文情境收益。需要真实语义识别的重提标签，第一轮直接使用预先标注输入，不假装系统已经会识别它。

### 9.4 指标、报告和选型

- **证据覆盖**：返回的正确必需证据数 / 标注必需证据数；另报完整覆盖查询数 / 需要记忆的查询数。
- **自动噪音**：自动 Context 中无助当前任务的条数与 tokens / 所有自动注入条数与 tokens；不能仅靠少返回一切获得漂亮结果。
- **保护失误**：未完成约定、新 Revision、pinned/稳定画像分别报告遗漏数与各自分母。
- **旧事重现**：沉睡查询正确返回当前/历史 Revision 的次数 / 所有沉睡查询次数。
- **错误更新泄漏**：把旧说法作为当前事实的次数 / 发生改口的当前查询次数。
- **自强化**：只有模型曝光、没有新用户证据时，排名或强化统计变化的次数 / 对应干预次数。
- **代价**：SQL 查询耗时、自动 Context tokens、数据增长、实现模块/状态数；真实机器上分别报告首次与重复查询，不用合成吞吐替代真实延迟。

成对差异按轨迹模板聚合；区间采用按模板重采样或适合小样本的成对方法。报告点估计、区间、样本结构和反例，不以某个自定置信界限自动否决整体更好的简单方案。不能把算法直接保证的“不硬删”测试当作实际记忆质量提升。

这些离线实验最多证明：在指定输入上，策略尊重生命周期、减少某些已标注噪音，并保留指定找回能力。它们不能证明已经预测未来价值、形成深层情感理解或改善长期用户关系。更大规模的时间外真实标注、自然语言重提识别和用户偏好评价是后续证据。

实验 runner、候选配置和原始结果按根 AGENTS 生命周期置于可丢弃实验工作中。最终仓库留下中文 Decision、紧凑聚合与复现标识；获胜正确性案例改写为没有 Arm 身份的产品回归。若相当，保留更简单方案。

## 10. 容量：先算清数据，再决定压缩

物理容量、检索噪音与用户体验是三个不同问题。文本可能很小但反复注入很烦；截图可能很大但根本不进入长期记忆。减少自动注入 tokens 不会自动释放磁盘，归档一个记录也不必然减少 SQLite 文件大小。

2026-09-15 用户明确规定：单次模型请求输入上下文不得超过 258,000 Token，包含系统指令、历史、Memory、Tool Schema 与多模态输入估算。这是项目硬约束，不是论文推导的阈值。检索池、长期磁盘容量和模型输入工作集必须分开；即使长期保存数年的数据，也不能把全部 Memory 注入请求以填满窗口。每轮只选当前任务所需证据，并在完整请求装配后执行统一预算约束。

本地容量可用下面的账本估算，再用实际表和文件元数据校准：

$$
S_{\text{local}}
=S_{\text{chat}}+S_{\text{revisions}}+S_{\text{sources}}
+S_{\text{indexes}}+S_{\text{usage}}+S_{\text{assets}}+S_{\text{activity}}
$$

对于每一项记录日增长、保留周期、重复比例和重建可能性。不预设“20% 用户一定占 65%”，也不把数量最多的数据自动视为最有价值。

仅作容量算例：如果一天 50 次互动、每次持久文本平均 8 KiB，则一年约 142.6 MiB，尚未计算索引、Revision 和其他开销；如果一天 10 张图片、每张 300 KiB，则一年约 1.04 GiB。这里完全是显式假设，说明附件很可能主导容量，不能作为 CharaMate 当前测量。

因此本地优先顺序是：现有截图/事件保留策略是否按预期执行，附件是否已有可复用引用，重复记录和日志是否增长异常，再研究情节摘要和索引策略。不应因“超长期”就每天重新总结全部历史。重要约定、被纠正事实的历史和用户主动保留内容不靠自动硬删解决容量。

若有合法的冷存储需求，可把较老原始媒体与热检索文本分开，保留摘要、来源位置和准确的恢复状态；没有可靠恢复时就不能声称可逆。对单 SQLite 产品，增加数据库或服务前需证明现有方式不足。

## 11. 在线、多角色与跨平台后续形态

在线规模化保留同一记忆语义，但必须增加真实身份与关系作用域。这是未来产品工作，不在本地版本预先引入分布式存储。

推荐区分三类归属：用户确认的稳定事实、特定“用户—角色”关系中的共同经历、角色公开参与的世界事件。它们不应复制成每个角色各一份用户画像，也不应把一个角色知道的所有私事自动扩散到其他角色。群聊中，“A 说自己喜欢 X”和“B 说 A 喜欢 X”是不同来源；公共帖子也不自动成为事实。

跨平台连续性的产品形态是：用户在手机说过的事情，桌面角色能够在合适情境延续；不需要用户导入导出记忆文件。技术上沿用稳定身份、全局事件 ID、来源渠道、版本与有效时间。离线修改后重连按基准 Revision 合并无冲突变更；实质矛盾保留双方来源并在自然对话中澄清，不用“最后同步的设备覆盖一切”。

未来角色社区可让角色有可分享的新经历，但“角色在虚拟社区中经历的事”和“用户现实生活事实”要有明确来源。角色收到一条帖子，只能形成“某角色发布/表达了什么”，不能通过反复转述把传闻升级为事实。关联扩散需要先限定用户/关系/世界作用域，再评估关系检索，不做全库无限 fan-out。

规模估计采用实际工作负载：

$$
\text{写入需求}
=\text{活跃用户数}\times\text{单位时间事件数}\times\text{被保留比例}
$$

$$
\text{检索需求}
=\text{用户回合率}\times\text{每回合检索次数}
+\text{被允许的后台检索率}
$$

按用户或关系分区后，查询先限定作用域，保留热文本/索引和对象媒体的不同生命周期；对长尾重用户依据实际分位数与单用户写放大处理，不按平均用户估计峰值。向量、图和异步任务的引入都需要量出质量收益、召回规模、延迟与成本。在线工程可以采用服务数据库与对象存储，但不因此改变 MemoryRevision、来源和当前事实的领域合同。

多年记忆最重要的不是永远保留所有原文，而是能解释此刻为何相信某事、知道哪些已经改变、让重要经历在需要时重新出现，并让角色在新的情境中继续尊重用户表达过的意愿。

## 12. 本次可实施与仍需证据的边界

可以先落实：证据与曝光分离、去重来源、真实互动驱动的 clock、保护明确事实和未完成约定、显式查询不被自动淡化阻断、用户删除不被绕过，以及运行上述不调用模型的纵向实验。

需要预算内语义 pilot：自然表达下的形成准确性、真实重提识别、情景记忆是否保留了用户的意思，以及记忆使用是否自然、克制和有帮助。无关话题中的频繁提起必须作为负面结果。

需要更长期数据才能宣称：未来价值预测、跨月跨年情感连续性、不同用户的最优遗忘策略、跨角色扩散带来的社交收益、超多人容量和并发的工业效果。本轮不以外部最高分、认知术语或合成测试通过数代替这些结论。

## 13. 2026-09-15 离线实验补充

在本报告提出候选后，已用冻结的 12 个手写故事、4 种时间表执行 48 条轨迹，每条件 384 个查询。源数据 SHA-256 为 b27542fd897ff1ee4774c395d1b7938553741d391d4178c08bced7272c1ff19d。查询实际调用当前 MemoryService、MemoryRepository 与 SQLite FTS5；自然语言重提来源由事先标签给出，未调用模型。

曝光排序和用户证据投影均命中 240/336 条必需证据；交互年龄淡化减少了一半自动无关条目，同时让强相关旧事自动命中从 48/48 降到 36/48；日历年龄淡化降到 24/48。显式旧事查询仍为 48/48，但不能假定模型每次都会主动补查。后继独立登记的“仅移除曝光排序作用”条件，在同一 384 个查询中保持完全相同结果，并在真实 SQL 同分诊断中阻止纯曝光改变优先级。

因此本次最小选型建议是保留 R0，曝光不参与排序，不采用自动年龄淡化，也不为尚无质量增益的 clock/频次创建持久状态。交互时钟仍是比日历年龄更合理的研究候选，但当前结果没有证明它足以识别低频重要经历。上述候选规模与第 9 节原先建议的 96 轨迹不同，实际执行分母以本节及后续 Decision 为准。

语料有意包含许多短而无关的普通事件，用于检验过度形成后的处理；它不是当前 F2 自动形成的代表性质量评测，不能据此声称真实用户 Memory 库已经存在同等比例噪音。结果提示应优先保持形成质量、按当前语境使用证据，而不是依赖年龄删除修复噪音。

扩大的桌面软件、阅读、键鼠感知应先丰富 Activity 和 Episode 的来源粒度；每个按键、每次指针移动不构成一次独立用户记忆支持，也不应各触发一次长期形成或模型请求。
